# T-0-007: `packages/engine-client` LocalStore 포트·명령 실행기·멱등성·Worker 시뮬레이터

## 목표

클라이언트 엔진의 핵심을 만든다. ADR-002의 `LocalStore` 포트를 정의하고 메모리 구현과 "구현이 지켜야 할 계약 테스트"를 두며, 명령 실행기(`EngineClient`)가 domain `simulate`를 호출해 Career·Snapshot·명령 로그·idempotency 결과를 한 트랜잭션으로 저장하고 revision을 1 올린다. 같은 `commandId` 100회 병렬 실행이 결과 하나로 수렴하고, 손상된 Snapshot은 직전 정상 Snapshot + 명령 로그로 재구축된다. 시뮬레이션은 Web Worker에서 돌도록 메시지 프로토콜과 Worker 진입점을 만든다(ADR-003). Dexie 구현은 이 작업이 아니라 T-0-012(`packages/platform/web`)가 맡는다.

### 설계 결정(변경 금지. 의문이 있으면 질문)

1. 저장 구현은 platform이 맡는다(ADR-002 "구현은 `packages/platform`이 채널별로 제공"). engine-client에는 포트, 메모리 구현, 계약 테스트만 둔다.
2. Worker에서 도는 것은 domain `simulate`뿐이다. `LocalStore`는 메인 스레드에 남는다(toss 채널의 네이티브 Storage 브리지는 Worker에서 동작한다는 보장이 없다). 따라서 실행기는 **읽기 트랜잭션 → 시뮬레이션(비동기) → 쓰기 트랜잭션(재검증 후 저장)** 2단계다. Dexie 트랜잭션은 외부 Promise를 기다리면 자동 커밋되므로 시뮬레이션은 반드시 트랜잭션 밖에서 한다.
3. 엔진 명령의 이름과 payload는 domain `Command`와 같다. `RESOLVE_EVENT`는 outcomes를 payload에 그대로 들고 있으므로 명령 로그만으로 리플레이가 가능하다. 콘텐츠 팩의 EventDefinition을 payload로 바꾸는 일은 Phase 1 이벤트 엔진 작업이며 여기서 하지 않는다.
4. 시간과 ID는 주입한다(`now`, `newId`). 기본값은 `() => new Date().toISOString()`, `() => crypto.randomUUID()`. domain 순수성 규칙은 engine-client에 적용되지 않지만 `src/`에서 `node:` import·`window`·`document`·`indexedDB`·`localStorage`는 금지한다(브라우저·Node·Workers 공통 코드).
5. 도메인 오류는 `{ ok: false, error }`로 돌려주고 throw하지 않는다. 저장소 I/O 실패와 프로그래밍 오류는 throw한다(호출자가 ERROR 상태로 처리).
6. 로컬 저장소는 Career의 **모든** Snapshot을 보관한다(ADR-002 표). 정리(prune)는 이후 작업.

   ```ts
   import type { CareerSnapshot, CommandLogEntry, ErrorCode, NextAction, PutCareerBody } from '@offside/contracts';
   import type { Command, DomainSnapshot, Effect } from '@offside/domain';

   export type LocalCareerRecord = {
     id: string;
     ownerProfileId: string | null;    // 쿠키 차단·오프라인이면 null

   };

     careerId: string;
     revision: number;                 // 이 명령이 만든 revision
     resultHash: string;               // == snapshot.stateHash
     response: ExecuteSuccess;         // 최초 응답 그대로(replayed: false 상태로 저장)
     createdAt: string;
   };
   export type EngineCommand = Command & { commandId: string; expectedRevision: number };
   export type EngineError = { code: ErrorCode; message: string; details?: unknown };
   export type ExecuteSuccess = {
     ok: true;
     snapshot: CareerSnapshot;         // 저장된 형태(contracts)

     nextAction: NextAction;
     roll?: number;
     outcomeId?: string;
     appliedEffects: Effect[];
     replayed: boolean;                // idempotency 테이블의 응답이면 true
   };
   export type ExecuteResult = ExecuteSuccess | { ok: false; error: EngineError };
   ```

2. `src/ports/local-store.ts` — 포트. platform(T-0-012)은 이 타입만 import한다.

   ```ts
   export type StoreMode = 'readonly' | 'readwrite';
   export class LocalStoreConstraintError extends Error { readonly name = 'LocalStoreConstraintError'; }
   export interface LocalStoreTx {
     careers: {
       get(id: string): Promise<LocalCareerRecord | undefined>;
       put(record: LocalCareerRecord): Promise<void>;                  // upsert
       list(): Promise<LocalCareerRecord[]>;                           // updatedAt 내림차순, 같으면 id 오름차순
       delete(id: string): Promise<void>;
     };
     snapshots: {
       put(snapshot: CareerSnapshot): Promise<void>;                   // (careerId, revision) 기준 upsert
       get(careerId: string, revision: number): Promise<CareerSnapshot | undefined>;
       getLatest(careerId: string): Promise<CareerSnapshot | undefined>;
       listByCareer(careerId: string, range?: { fromRevision?: number; toRevision?: number }): Promise<CareerSnapshot[]>; // 닫힌 구간, revision 오름차순
       deleteByCareer(careerId: string): Promise<void>;
     };
     commandLog: {
       append(entry: CommandLogEntry): Promise<void>;                  // (careerId, revision) 중복이면 LocalStoreConstraintError
       listSince(careerId: string, afterRevision: number): Promise<CommandLogEntry[]>; // revision > afterRevision, 오름차순
       deleteByCareer(careerId: string): Promise<void>;
     };
     idempotency: {
       get(commandId: string): Promise<IdempotencyRecord | undefined>;
       put(record: IdempotencyRecord): Promise<void>;                  // upsert
       deleteByCareer(careerId: string): Promise<void>;
     };
     kv: {                                                             // DRAFT·설정 등
       get<T>(key: string): Promise<T | undefined>;
       put<T>(key: string, value: T): Promise<void>;
       delete(key: string): Promise<void>;
     };
   }
   export interface LocalStore {
     readonly kind: string;                                            // 'memory' | 'dexie' | 'toss-storage'
     transaction<T>(mode: StoreMode, run: (tx: LocalStoreTx) => Promise<T>): Promise<T>;
     close(): Promise<void>;
   }
   ```

   규칙: `readwrite`는 원자적이다. `run`이 throw하면 아무것도 남지 않는다. 같은 store의 `readwrite` 트랜잭션은 직렬로 실행된다. `run` 안에서 `tx` 밖의 비동기 작업(네트워크, Worker)을 기다리지 않는다(문서 주석으로 명시).

3. `src/store/memory.ts` — `MemoryLocalStore implements LocalStore`. `kind = 'memory'`. Map 기반. `readwrite`는 Promise 체인으로 직렬화하고, 시작 전에 `structuredClone`으로 전체 상태를 복사해 `run`이 throw하면 복원한다. 반환값과 저장값은 항상 복사본(외부 mutation이 저장소에 새지 않는다).

4. `src/testing/local-store-contract.ts` — `export function runLocalStoreContractTests(name: string, factory: () => LocalStore | Promise<LocalStore>): void`. `vitest`의 `describe/it/expect/afterEach`를 직접 import한다. `package.json`의 `exports`에 `"./testing": "./src/testing/local-store-contract.ts"`로 노출하고 `index.ts`에서는 re-export하지 않는다. 케이스: 각 테이블 CRUD와 반환 순서, `listByCareer` 구간, `listSince` 경계(`afterRevision` 자신 제외), `append` 중복 → `LocalStoreConstraintError`, `readwrite` 안 throw → 롤백(이전에 저장된 값 유지, 새 값 없음), 동시 `readwrite` 두 개가 직렬화된다(카운터 kv를 각각 +1 → 2), 반환값을 mutate해도 저장값이 바뀌지 않는다, `kv` 중첩 객체 왕복, `close()` 후 재호출 없음.

9. `src/engine.ts` — `createEngineClient(deps): EngineClient`

   ```ts
   export type EngineClientDeps = {
     store: LocalStore;
     simulator: Simulator;
     now?: () => string;
     newId?: () => string;
     ownerProfileId?: () => string | null;   // 기본 () => null
   };
   export type ExecuteRequest = { careerId: string; command: EngineCommand; createdServiceSeasonId?: string }; // CREATE_CAREER면 필수
   export type LoadResult =
     | { ok: true; career: LocalCareerRecord; snapshot: DomainSnapshot; recovered: { fromRevision: number; replayed: number } | null }
     | { ok: false; error: EngineError };
   export interface EngineClient {
     execute(request: ExecuteRequest): Promise<ExecuteResult>;
     loadCareer(careerId: string): Promise<LoadResult>;
     listCareers(): Promise<LocalCareerRecord[]>;
     deleteCareer(careerId: string): Promise<void>;          // careers·snapshots·commandLog·idempotency 모두 삭제
     buildSyncBody(careerId: string): Promise<PutCareerBody | null>; // 미동기화 명령이 없으면 null
     markSynced(careerId: string, revision: number): Promise<void>;  // lastSyncedRevision = max(현재, revision)
   }
   ```

   `execute` 알고리즘(그대로 구현):

   1. careerId별 실행 큐. 같은 careerId의 `execute`는 한 번에 하나만 돈다(Promise 체인 Map, 끝나면 정리). 다른 careerId는 병렬.
   2. **읽기 트랜잭션(readonly)**: `idempotency.get(commandId)` → 있으면 저장된 `response`에 `replayed: true`를 붙여 반환(payload가 달라도 최초 응답. 07 "같은 키 재요청은 최초 응답"). `careers.get`. `CREATE_CAREER`인데 career가 있으면 `VALIDATION_FAILED`; 그 외 명령인데 없으면 `CAREER_NOT_FOUND`; `status === 'ARCHIVED'`면 `CAREER_ARCHIVED`; `expectedRevision !== career.revision`이면 `CAREER_REVISION_CONFLICT`(details `{ serverRevision, expectedRevision }`; Worker 왕복 전에 거른다). `snapshots.getLatest` → `decodeSnapshot`. 실패하면 이 트랜잭션 안에서 이전 Snapshot들과 명령 로그를 읽어 두었다가 트랜잭션 밖에서 `replayCommandLog`로 복구한다(9-b 참고). 복구도 실패하면 `VERIFICATION_FAILED`.
   3. **시뮬레이션(트랜잭션 밖)**: `simulator.simulate({ snapshot, command, rulesetVersion, contentPackVersion })`. 버전은 career 기록(CREATE면 payload)에서. `ok: false`면 그대로 `EngineError`로 변환해 반환(코드 4종은 모두 `ErrorCode`에 있다). 아무것도 쓰지 않는다.
   4. **쓰기 트랜잭션(readwrite)**: 다시 `idempotency.get` → 있으면 그 응답 반환(다른 탭이 먼저 썼을 수 있다). 다시 `careers.get`으로 `revision === expectedRevision`(CREATE면 부재) 확인, 아니면 `CAREER_REVISION_CONFLICT`. 통과하면 순서대로 `snapshots.put(encodeSnapshot(...))`, `commandLog.append({ careerId, revision, commandId, commandType: command.type, payload: command.payload, resultHash: stateHash, createdAt })`, `careers.put({ ...revision, status: state.status, updatedAt, CREATE면 나머지 필드 초기화 })`, `idempotency.put({ ..., response: { ...success, replayed: false } })`.
   5. `ExecuteSuccess` 반환.

   `loadCareer`: 최신 Snapshot이 정상이면 그대로. 아니면 revision 내림차순으로 정상인 Snapshot을 찾고(없으면 `null`부터, 즉 `CREATE_CAREER` 로그 항목부터) 그 뒤 명령 로그를 `replayCommandLog`로 재생한다. 도달한 revision이 `career.revision`과 다르거나 재생이 실패하면 `VERIFICATION_FAILED`(details에 `atRevision`·`reason`). 성공하면 재구축한 최신 Snapshot을 `readwrite`로 덮어쓰고 `recovered`를 채운다.

   `buildSyncBody`: `baseRevision = lastSyncedRevision`, `snapshot`은 최신 Snapshot에서 `id`·`careerId`·`createdAt`을 뺀 것, `commands`는 `listSince(lastSyncedRevision)`에서 `careerId`·`createdAt`을 뺀 것, 세 버전 필드는 career 기록. 결과가 `PutCareerBodySchema.parse`를 통과해야 한다(테스트). 동기화 클라이언트(fetch·재시도 큐)는 이 작업이 아니다.
