# T-0-004: `packages/content` 이벤트 스키마·조건 DSL·`content:validate` CLI와 프로토타입 팩 0.1.0

## 목표

이벤트를 코드 분기가 아니라 검증되는 데이터로 만드는 첫 단계다. `packages/content`에 EventDefinition·조건 DSL·Effect·narrative token의 Zod 스키마와 화이트리스트를 두고, 04 "콘텐츠 검증" 규칙을 모두 구현한 `content:validate` CLI를 만든 뒤, 종이 프로토타입 이벤트 10개를 `packs/0.1.0`으로 기계적으로 옮긴다. 팩은 아직 플레이테스트 전이므로 `playtested: false`로 표시한다.

### 만들 것

1. `src/schema/condition.ts` — 조건 DSL.
   - 연산자 11개: `eq, neq, gt, gte, lt, lte, in, notIn, hasTag, all, any, not`. 형태는 04 예시와 같다: `{ "gte": ["career.age", 20] }`, `{ "in": ["career.currentRole", ["BENCH", "RESERVE"]] }`, `{ "hasTag": ["career.tags", "고집"] }`, `{ "all": [...] }`, `{ "any": [...] }`, `{ "not": {...} }`. 재귀 스키마는 `z.lazy`.
   - 필드 화이트리스트 `CONDITION_FIELDS`는 04 표를 **같은 순서**로 옮긴다: `career.age, career.stage, career.currentRole, career.pathDecision, career.tags, career.proSeasons, player.primaryPosition, player.positionGroup, player.archetypeId, player.baseOvr, player.attributes.<AttributeKey>, state.form, state.fitness, state.morale, context.tacticalFit, context.managerTrust, context.squadStatus, context.competitionRank, relationships.managerTrust, relationships.captain, relationships.rival, relationships.fans, relationships.agent, season.step, season.phase, season.simulationMode, season.tags, season.stats.<stat>, season.chapterHighlights, contract.monthsRemaining, contract.rolePromise, contract.wageBand, health.injuryEpisode, health.recurrenceRisk, rng.injuryRoll`. 각 필드에 값 타입(`int`, `string`, `enum`, `tags`)을 달아 `eq`에 문자열이 오는 숫자 필드처럼 타입이 어긋나면 검증 오류를 낸다. `hasTag`는 `tags` 필드에만, `gt/gte/lt/lte`는 `int` 필드에만 허용.
   - `season.stats.<stat>`의 stat은 `goals, assists, appearances, starts, minutes, rating, yellowCards, redCards`.
   - `evaluateCondition(condition, context: ConditionContext): boolean` — 순수 함수. `ConditionContext`는 화이트리스트 경로를 키로 하는 평탄한 `Record<string, number | string | string[]>`. 없는 필드는 `false`(throw 금지).
2. `src/schema/effect.ts` — 02·프로토타입 규칙.
   - `EffectSchema`는 domain `Effect` 타입과 동일 구조(`expectTypeOf`로 고정). `kind`별 허용 `target`: PERMANENT → `ATTRIBUTE_KEYS`, CURRENT → `form|fitness|morale`, CONTEXT → `tacticalFit|squadStatus|positionProficiency`, RELATION → `managerTrust|captain|rival|fans|agent`, DEFERRED → 위 넷 중 하나이며 `appliesAt.kind === 'NEXT_SEASON_STEP'` 필수. 그 외 조합은 오류(RELATION·CONTEXT가 attributes를 가리키면 "Base OVR 직접 변경 금지").
   - `stackingRule: 'REPLACE'`인 효과는 `expiresAt`이 `null`이어야 한다(도메인의 만료 되돌리기는 delta 감산이라 REPLACE와 맞지 않는다. T-0-002 리뷰 후속). 위반은 오류.
   - 프로토타입 기본값을 `EFFECT_DEFAULTS`로 둔다: `clamp` PERMANENT `0~99`, 나머지 `0~100`; `appliesAt` IMMEDIATE(DEFERRED는 `NEXT_SEASON_STEP: 1`); `expiresAt` CURRENT는 `STEPS_AFTER: 2`, 그 외 `null`; `stackingRule` `ONCE_PER_SOURCE`. "= 값" 표기는 `REPLACE`.
3. `src/schema/event.ts` — 04 `EventDefinition`.
   ```ts
   id: /^EVT-(MGR|CON|REL|INJ|MATCH|MEDIA|NAT|DEV)-\d{3}$/, version: int ≥ 1,
   phases: CareerPhase[] (1개 이상, 중복 없음), triggers: Condition, exclusionTags: string[],
   cooldown: { steps?: int ≥ 1; seasons?: int ≥ 1 } (둘 중 하나 이상. 없으면 검증 경고가 아니라 오류 — README "SHOULD"지만 04 검증의 "cooldown 없는 고빈도 이벤트 경고"를 weight ≥ 50에만 경고로 두고, 그 외는 통과),
   weight: int > 0, minAge?: int, maxAge?: int, safety: { minorSafe: boolean } (18세 미만 노출 가능 여부. README 안전 규칙),
   choices: 2~3개 { id: 'A'|'B'|'C', label: string, riskLabel: 'LOW'|'MEDIUM'|'HIGH', previewEffects: { label: string; target?: string; direction?: 'UP'|'DOWN' }[] (1개 이상), outcomes: 1개 이상 { id: string, kind: 'SUCCESS'|'NEUTRAL'|'FAIL'|'FIXED', weight: int > 0, title: string, cause?: string, effects: Effect[], addTags?: string[], removeTags?: string[], followUps?: { eventId: string; weightMultiplierBp?: int }[] } },
   narrative: { situation: string }
   ```
   - 선택지별 outcome `weight` 합이 정확히 100이 아니어도 되지만(04는 "> 0"), 프로토타입 변환분은 roll 구간 폭이므로 100이 된다. 팩 검증에서 합 ≠ 100이면 경고.
   - narrative 문자열(`situation`, `title`, `cause`, `label`)의 token은 `{name}`, `{name:이/가}`, `{club:을/를}`, `{manager}`, `{delta:formatted}` 형식만 허용. 사전은 `packs/<v>/narrative/tokens.json`(`name, club, manager, rival, captain, team, delta`), 조사 쌍은 `이/가, 을/를, 은/는, 과/와, 으로/로, 아/야`. 사전에 없는 token이나 잘못된 조사 쌍은 오류.
4. `src/schema/pack.ts` — `PackManifestSchema`: `{ contentPackVersion: semver, compatibleRulesetVersions: semver[] (1개 이상), clientMinVersion: semver, playtested: boolean, checksum: hex64, files: string[] (정렬) }`. `loadPack(dir)`는 Node 전용 CLI 모듈(`src/cli/`)에만 두고, 스키마 모듈은 Node API를 import하지 않는다(브라우저·Workers에서 `import { EventSchema } from '@offside/content'`가 가능해야 한다). `package.json` `exports`: `.`(스키마·evaluateCondition·타입), `./cli`(Node).
5. `src/cli/validate.ts` + `bin`: `pnpm --filter @offside/content validate [--pack <version>] [--write-checksum]`. T-0-001의 placeholder `validate.mjs`는 삭제한다. 04 "콘텐츠 검증"을 전부 구현한다.
   - 오류(exit 1): 스키마 위반, id·version 중복, outcome 없음, 가중치 합 ≤ 0, 존재하지 않는 Effect target·조건 필드·token, `followUps.eventId`가 팩에 없음, 후속 이벤트 순환(깊이 제한 필드가 없으므로 순환 자체를 금지: DFS로 검출), checksum 불일치(`--write-checksum`이 없을 때).
   - 경고(exit 0, stderr): cooldown 없는 weight ≥ 50 이벤트, 선택지 간 label 또는 effects 배열이 canonical JSON으로 동일, outcome weight 합 ≠ 100, `minorSafe: false`인데 `minAge` 미지정.
   - checksum: `files`에 나열된 파일을 정렬 순서로 읽어 각 파일을 canonical JSON(키 정렬·공백 없음)으로 직렬화해 이어 붙인 문자열의 SHA-256. Node `crypto`를 써도 된다(CLI 모듈이므로). `--write-checksum`은 manifest를 다시 쓴다.
   - 출력 마지막 줄: `content:validate OK (<pack> events=<n> warnings=<w>)`.
6. `packs/0.1.0/` — 프로토타입 이벤트 10개 변환. `docs/content/prototype/season-01-inside-forward.md`의 "프로토타입에서 코드로 옮길 때" 체크리스트 중 이 작업 몫만 한다:
   - ID 재부여: P01→`EVT-DEV-001`, P05→`EVT-DEV-002`, P02→`EVT-MGR-001`, P03→`EVT-REL-001`, P06→`EVT-REL-002`, P04→`EVT-INJ-001`, P07→`EVT-MEDIA-001`, P08→`EVT-CON-001`, P09→`EVT-CON-002`, P10→`EVT-CON-003`. `version: 1`.
   - `phases`: 모두 `['YOUTH']`(U18 시즌 이벤트). step·phase 제약은 문서의 트리거 JSON을 그대로 `triggers`에 둔다(이미 화이트리스트 필드로 정리되어 있다).
   - 각 표의 선택지 행 → `choices[].outcomes[]`, roll 구간 폭 → `weight`(합 100). 결과 문구 "성공: …" → `kind: 'SUCCESS'`, `title`은 콜론 뒤 문장. "(원인: …)" → `cause`, "(태그 `x`)" → `addTags: ['x']`. 줄여 쓴 Effect에 `EFFECT_DEFAULTS`로 메타데이터를 채우고 `sourceId`는 `<EVT-id>.<choiceId>.<outcomeId>`. 한글 대상명은 `target` 키로 옮긴다(`결정력`→`shooting`, `드리블`→`dribbling`, `크로스`→`crossing`, `체력`(PERMANENT)→`stamina`, `체력`(CURRENT)→`fitness`, `폼`→`form`, `사기`→`morale`, `전술적합도`→`tacticalFit`, `스쿼드상태`→`squadStatus`, `감독신뢰`→`managerTrust`, `숙련도 0.97`→`positionProficiency` `REPLACE 97`). 표에 없는 대상이 나오면 질문한다.
   - `cooldown`: 문서의 "cooldown 1시즌" → `{ seasons: 1 }`. `followUps`: "B 실패 시 EVT-P03의 가중치를 갈등 변형으로 고정" 같은 문장은 `followUps: [{ eventId: 'EVT-REL-001', weightMultiplierBp: 20000 }]`처럼 옮기고 애매하면 PR 본문에 적는다.
   - `safety.minorSafe: true`(README 안전 규칙 대상 없음 확인), `minAge`/`maxAge`는 문서에 나이 조건이 있을 때만.
   - `narrative/tokens.json`과 `manifest.json`(`compatibleRulesetVersions: ['0.1.0']`, `clientMinVersion: '0.1.0'`, `playtested: false`). `pnpm content:validate`가 오류 0으로 통과하고, 경고는 PR 본문에 나열한다.
7. `src/index.ts`에서 스키마·타입·`evaluateCondition`·`CONDITION_FIELDS`·`EFFECT_DEFAULTS`·`PACK_0_1_0 = '0.1.0'` export. `CONTENT_VERSION = '0.1.0'`.

### 테스트 (Vitest)

- 조건 DSL: 04 예시 JSON 파싱 성공. 화이트리스트 밖 필드 실패, `hasTag`에 int 필드 실패, `gte`에 string 실패, 중첩 `all/any/not` 평가 결과(진리표 4개), 없는 필드는 false.
- Effect: RELATION→attributes 실패, DEFERRED에 IMMEDIATE 실패, 기본값 채우기 결과가 프로토타입 표와 같다.
- 이벤트: 선택지 1개·4개 실패, `weight: 0` 실패, token `{club:와/과}` 실패(순서 틀림), `{unknown}` 실패.
- 팩 검증기(임시 디렉터리 fixture): 순환 followUps 검출, 중복 id 검출, checksum 불일치 검출, `--write-checksum` 후 통과.
- `packs/0.1.0`: 이벤트 10개 로드·검증 통과, 각 선택지 outcome weight 합 100, sourceId 유일, 모든 effect target이 domain 키 안에 있음.

## 제약

- 프로토타입 문서의 수치(delta, roll 구간, 문구)는 바꾸지 않는다. 밸런스 조정은 플레이테스트(U-005) 뒤 다른 작업이다.
- JSON 파일은 UTF-8, 2칸 들여쓰기, 키 순서는 스키마 정의 순서. 실명·실제 구단명 금지(프로토타입 문구 그대로면 통과).
- 버전은 안정 최신. 프리릴리스 금지. `zod` 외 새 의존성 금지.
- 커밋 메시지 `T-0-004: …`. 브랜치 `T-0-004-content-schema-pack`.
- 커밋 트레일러: `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`.
- 서브에이전트 리뷰를 띄우지 않는다. 예외는 하나뿐이다. Orca가 `gh pr create` 앞에 요구하는 게이트를 위해 `/review:pr`을 **한 번만** 실행한다(`/simplify`·병렬 fork 금지). 리뷰 결과 중 실제 버그·테스트 누락만 고치고 나머지는 PR 본문에 적는다. PR을 연 뒤에는 멈추고 피드백을 기다린다.
