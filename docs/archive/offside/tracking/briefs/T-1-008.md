# T-1-008: web 선수 만들기 SCR-002·003·004 + 복구 코드 발급 단계

## 목표
허브에서 만든 DRAFT 커리어를 세 화면(정보 입력 → 아키타입 선택 → 확인·KICKOFF)으로 채우고 `CONFIRM_PLAYER`로 확정한다. 확정 직후 복구 코드를 한 번 발급받는 단계를 거쳐 진로 선택 화면(SCR-007)으로 넘어간다. 확정을 반복해도 커리어는 한 번만 만들어진다.

- 읽어야 할 문서(순서대로): `docs/tracking/phase-1-plan.md` **D-1~D-7, D-14, D-16**, `docs/screens/01-career-start.md`(SCR-002~004), `docs/development/06-ui-ux-specification.md`, `docs/development/12-brand-guidelines.md`, `docs/development/13-visual-design-system.md`; 코드: `docs/tracking/briefs/T-1-007.md`(엔진·훅·라우트 골격·`screenForCareer`·`labels.ts`), `apps/web/src/engine/*`, `apps/web/src/shared/*`, `packages/domain/src/types.ts`·`player.ts`(DRAFT 필드·확정 규칙), `packages/content/rulesets/1.0.0/ruleset.json`(`positions`, `archetypes`, `backgrounds`, `nationalities`, `draftRules`), `packages/ui/src/index.ts`(Stepper·RadioGroup·ChoiceCard·CompareCards·PlayerHeader·Dialog·Toast), `apps/api/src/routes/profile.ts`(`GET /v1/profile`, `POST /v1/profile/recovery-code` 응답 형태), `apps/web/e2e/*`
- 정본 우선순위: phase-1-plan.md 결정 > docs/screens > 06 > 13

## 범위
- 만질 패키지·경로: `apps/web`만(`src/routes/career.$careerId.create.tsx`·`style.tsx`·`confirm.tsx`와 그 화면 모듈, `src/api/`, `src/shared/labels.ts` 확장, `e2e/`). 다른 패키지는 만지지 않는다.
- 만들 것:
  1. **SCR-002 선수 정보** `/career/$careerId/create`: 입력 5개 — 이름(`draftRules.nameMin~nameMax` 2~12자, 앞뒤 공백 제거), 국적(룰셋 `nationalities` 10개 select), 주발(LEFT/RIGHT/BOTH `RadioGroup`), 포지션(포지션군 4개 탭 또는 세그먼트 → 세부 포지션 `RadioGroup`, 룰셋 `positions` 설명 문구 표시), 배경(`backgrounds` 3개 `ChoiceCard`: name·blurb·시작 팀). `Stepper` 3단계(정보 → 스타일 → 확인). "다음"은 폼 상태를 검증한 뒤 `UPDATE_PLAYER_DRAFT { draft: { name, nationalityCode, preferredFoot, position, backgroundId, archetypeId } }` 한 번으로 저장한다(키 입력마다 명령을 보내지 않는다). 포지션이 바뀌었고 기존 `archetypeId`가 새 포지션의 아키타입이 아니면 같은 명령에 `archetypeId: null`을 함께 보낸다(SCR-003 인수 조건). 진입 시 기존 draft 값으로 폼을 채운다. 생년 입력은 Phase 1에서 뺀다(도메인 나이 17세 고정, D-7. 화면 문서는 오케스트레이터가 정정).
  2. **SCR-003 아키타입** `/career/$careerId/style`: draft 포지션의 아키타입 3개를 `CompareCards`(3열, 행: 핵심 능력 = `roleWeights` 상위 3개 능력 라벨, 약점 = `template`에서 가장 낮은 능력 2개, 예상 역할 = `summary`, 잠재력 범위는 **표시하지 않는다**)로 비교하고 `RadioGroup`으로 하나 고른다. 이전(SCR-002)·다음. "다음"은 `UPDATE_PLAYER_DRAFT { draft: { archetypeId } }`. 최종 OVR·실제 잠재력은 어디에도 보이지 않는다.
  3. **SCR-004 확인** `/career/$careerId/confirm`: `PlayerHeader`(이름·팀 = 배경 시작 팀·포지션·아키타입·등번호 "-")와 요약(주발·배경·예상 강점 = 핵심 능력 3개·룰셋 1.0.0·팩 0.1.0), "수정"(SCR-002로), `KICKOFF`(primary, `DisplayWord`가 아닌 버튼 문구). 누르면 COMMITTING 잠금 → `confirmPlayer` → 성공 시 복구 코드 단계로. 실패(ERROR)는 원인과 재시도. 이미 ACTIVE인 커리어로 진입하면 `screenForCareer`로 보낸다(확정 반복 방지).
  4. **복구 코드 발급 단계**(SCR-004의 일부, 경로 `/career/$careerId/confirm?step=recovery` 또는 같은 라우트의 내부 상태 — 새로고침해도 다시 보이도록 URL에 남긴다): `GET /v1/profile`로 프로필을 확인하고 `recoveryCodeIssuedAt`이 null이면 `POST /v1/profile/recovery-code`를 호출해 `OFS-XXXX-XXXX-XXXX`를 **한 번만** 크게 보여 준다(`--os-font-mono`, 복사 버튼 → `navigator.clipboard`, 실패 시 선택 가능한 텍스트). 문구: "이 코드가 없으면 다른 기기에서 복구할 수 없습니다." "설정에서 다시 발급할 수 있습니다." 동작: "저장했어요"(SCR-007로), "건너뛰기"(SCR-007로). 이미 발급된 프로필이면 이 단계를 건너뛴다. API가 없거나 실패하면(네트워크 오류·CORS·5xx) 발급 화면 대신 "지금은 발급할 수 없습니다. 설정에서 나중에 발급할 수 있습니다"를 보여 주고 계속 진행한다. 발급 여부는 커리어 상태에 영향을 주지 않는다.
  5. **API 클라이언트 최소본** `src/api/client.ts`: `apiFetch(path, init)` — base URL은 `import.meta.env.VITE_API_BASE_URL`(없으면 `http://localhost:8787`), `credentials: 'include'`, JSON 본문, 응답 봉투(`data`/`error`) 해석, 오류는 `{ code, message, retryable }`로 정규화, POST에는 `Idempotency-Key`(`crypto.randomUUID()`) 헤더. `getProfile()`, `issueRecoveryCode()` 두 함수만. contracts 스키마(T-1-006 머지 뒤 `ProfileSchema`·`IssueRecoveryCodeResponseSchema`)가 있으면 응답을 그것으로 검증하고, 없으면 최소 형태 검사. 동기화 클라이언트(T-1-011)가 이 모듈을 재사용한다.
  6. **가드**: 세 라우트 모두 `beforeLoad`/렌더 초기에 `screenForCareer(state)`와 비교해 단계가 앞서 있으면 해당 화면으로 `redirect`(예: archetypeId 없이 `/confirm` 진입 → `/style`). 뒤로 가기(브라우저)는 허용한다(06 내비게이션).
  7. **접근성·상태**: 모든 입력 키보드 완료 가능, 오류는 필드 옆 문장 + `aria-describedby`, 오류 후 입력·포커스 보존(SCR-002 인수 조건), COMMITTING 중 CTA 잠금, 폼은 `useScreenState`의 DRAFT 상태.
  8. **분석**: `screen_viewed`(SCR-002/003/004, careerPhase `'YOUTH'`), 확정은 액션 계층의 `command_*`로 이미 나간다.
  9. **E2E**(`apps/web/e2e/create.spec.ts`): 온보딩 KICKOFF → SCR-002 입력(이름·국적·주발·포지션 W·배경) → SCR-003에서 `inside-forward` 선택 → SCR-004 KICKOFF → 복구 코드 단계(`page.route`로 `/v1/profile`·`/v1/profile/recovery-code` 응답을 스텁: 발급 성공 1회, 실패 1회 시나리오) → SCR-007 경로(`/career/<id>/path`)에 도착. 유효성 오류(이름 1자) 시 포커스가 이름 필드에 남는다. 새로고침 후 draft 값이 유지된다. `a11y.spec.ts`에 세 화면 추가.
  10. **단위 테스트**: 폼 검증(이름 길이·공백), 포지션 변경 시 archetypeId 초기화 규칙, 아키타입 카드 행 계산(상위 3 능력·하위 2 능력), 가드 리다이렉트 표, 복구 코드 단계 분기(미발급·발급됨·API 실패), `apiFetch` 오류 정규화.
  11. **루트 레이아웃 접근성**(PR #23 리뷰에서 발견): `src/routes/__root.tsx`의 콘텐츠 래퍼를 `<main>` 랜드마크로 바꾸고, 자리표시 화면(`PlaceholderScreen`)에도 `h1`을 둔다. axe `landmark-one-main`·`page-has-heading-one` moderate 위반이 `/settings`·`/legal/*`에서 0건이 되어야 한다(`a11y.spec.ts`에 moderate 검사를 추가하지는 말고, PR 본문에 결과만).
- 만지지 말 것: `docs/`, `packages/*`, `apps/api`, SCR-007 이후 화면(T-1-009), 동기화(T-1-011), 설정 화면의 복구 코드 행(T-1-012).

## 제약
- 채널 리터럴 비교 금지, hex 색 리터럴 금지, `--os-*` 토큰만. 문구는 한국어·브랜드 어휘. `useScreenState` 6종만.
- 진짜 잠재력·최종 OVR을 화면·DOM·콘솔에 노출하지 않는다.
- 커밋 메시지는 `T-1-008: …`로 시작, 브랜치는 `T-1-008-…`.
- 서브에이전트 리뷰를 띄우지 않는다. gstack `/review`·`/codex`·adversarial 리뷰·`/simplify`·병렬 fork 전부 금지. 유일한 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드)다. 리뷰는 오케스트레이터가 한다.
- PR 직전 `git fetch origin && git merge origin/main`으로 최신 main을 합친다(T-1-009와 같은 시기에 진행되므로 `routes.ts`·`routeTree.gen.ts` 충돌은 라우트 생성기를 다시 돌려 해결). `pnpm-lock.yaml` 충돌은 손으로 고치지 말고 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile`로 재생성한 뒤 전체 체인을 다시 돌린다.
