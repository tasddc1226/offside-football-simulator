# T-4-003: 관계 로그·감독 교체·평판·슬럼프/라커룸/윤리/SNS 이벤트와 Phase 4 태그 (domain + content)

## 목표

T-4-001의 항등 `onSettlementRelations` 훅을 실제 관계·감독·평판 결산으로 채운다. 관계 Effect는 source/reasonTag 감사 로그와 축별 기억을 남기고, 최근 폼이 슬럼프 조건에 공급되며, 결산 성적에 따라 평판·감독 교체·주장단 상태가 결정론적으로 갱신된다. PROTOTYPE 이벤트 pool이 일반 EVENT 흐름에서 열리고, 단일 FAIL이 커리어를 막지 않는 검증과 Phase 4 태그 평가기 5종이 자동 증거로 고정된다.

## 1. 관계 로그·기억 태그(P4-1)

- `appendRelationshipLog`를 실제 RELATION Effect 적용 경로에 붙인다. 관계 5축에 성공적으로 적용된 각 effect마다 clamp 뒤 **실제 delta**가 0이 아닐 때 `{ target, delta, sourceId, reasonTag, seasonIndex: state.season?.index ?? state.seasonHistory.length, step }` 한 건을 남기고 최근 `relationshipRules.logMax`개만 보존한다.
- `reasonTag`가 non-null이면 해당 target의 `memoryTags[target]`에 추가한다. 같은 문자열은 기존 위치를 지우고 최신 끝으로 옮기며 최근 `memoryTagsMax`개만 유지한다. 값은 축 하나뿐이고 로그만 늘어나므로 같은 사람/축의 중복 Edge 구조를 만들지 않는다.
- popularity/media RELATION Effect는 `reputation` bag만 갱신하고 5축 relationshipLog에는 넣지 않는다. sourceId는 기존 applied/rejected 효과 결과와 EVENT_RESOLVED ref로 추적한다. 관계/평판 Effect는 attributes·profile.baseOvr를 바꾸지 않는 property test를 둔다.

## 2. 감독 수명주기와 선발 재평가(P4-2)

- additive 상태 계약:
  - `CareerState.nextManager: SeasonManager | null`(시즌 사이 다음 감독 예약, CREATE_CAREER null).
  - `CareerState.captaincy: 'NONE'|'VICE'|'CAPTAIN'`, `captaincySeasons: number`(기본 NONE/0).
  - `SeasonResult.managerId: string`, `captaincyAtEnd: CareerState['captaincy']`(그 시즌을 실제 지휘/마친 값). domain/contracts strict 스키마와 모든 fixture를 갱신하되 schemaVersion 1 유지.
- `onSettlementRelations`는 다음 순서를 지킨다: 평판 갱신 → 주장단 진전 → 감독 교체 판정. 원본 `SeasonResult.hash`가 이 필드를 포함하도록 result 조립 시 managerId/captaincyAtEnd을 넣고 hash를 다시 계산한다.
- 기대 순위 = 같은 리그 팀을 `squadStrength desc, id asc`로 정렬한 현 팀 순위. 부진 gap = `max(0, finalRank-expectedRank)`. 현 감독 tenure가 `minTenureSeasons` 이상이면 확률 `clamp(baseBp + gap*perRankGapBp, 0, maxBp)`로 **결정 RNG 1회** 판정한다. 미달이면 roll 0. 교체 시 새 id `${teamId}-mgr-${generation}`(해당 팀 MANAGER_CHANGED 타임라인 수+2), 이름은 managerRules.names에서 id 해시/코드포인트로 결정, 선호 archetype은 현 포지션에 맞는 정렬 후보를 순환해 `preferredArchetypeCount`개(기존 감독과 같은 집합이면 한 칸 이동), trustBase는 룰셋. `MANAGER_CHANGED(refId=newId)`와 `nextManager=newManager`; 유지면 현 manager의 tenure+1 복사본을 nextManager로 둔다.
- `START_SEASON`은 `nextManager ?? buildDefaultManager(...)`를 먼저 확정하고 nextManager를 null로 소비한다. 그 감독의 preferredArchetypeIds를 현 tactical style의 player position 선호 집합으로 사용해 tacticalFit을 재계산한다. 예약된 새 감독이면 managerTrust를 trustBase로 reset한 뒤 새 경쟁자/selection을 계산한다. 같은 manager 유지면 기존 trust를 유지한다. manager 변경 전후 tacticalFit·managerTrust·PLAYER selection rank가 실제로 재계산되는 golden/단위 테스트를 둔다.
- 주장단: 룰셋 값을 계획 확정치로 바로잡아 `captainAppointment { minCaptain:70, minSeasons:3 }`. PRO 시즌 수가 minSeasons 이상, 이번 `squadRoleAtEnd==='STARTER'`, captain 관계가 minCaptain 이상이면 NONE→VICE→CAPTAIN으로 한 단계 승격하고 `CAPTAIN_APPOINTED(refId='VICE'|'CAPTAIN')`. captaincy가 NONE이면 captaincySeasons=0, VICE/CAPTAIN인 시즌 결산마다 +1.

## 3. 평판·최근 폼

- 결산 popularity delta = `-decayCenti + (STARTER ? starterSeasonCenti : 0) + (평균 평점 tenths >=70 ? ratingAbove70Centi : 0) + (리그 1위 또는 컵 우승 ? titleCenti : 0)`, 0..clampMax. mediaCenti는 이벤트 Effect만 바꾸며 결산에서는 유지한다. 실제 delta를 별도 순수 함수로 테스트한다.
- `buildConditionContext`의 `season.stats.recentFormAvg`는 최근 경기 중 ratingTenths non-null 최대 5개의 정수 평균(`Math.round(sum/n)`), 없거나 시즌 밖이면 0. 저장하지 않는 파생값이다.
- 시장가치가 새 popularity를 읽는 기존 T-4-001 배선을 회귀 테스트하되 시장가치 자체를 상태에 저장하지 않는다.

## 4. presentation 이벤트 라우팅·팩

- T-3-001의 “presentation 전부 일반 후보 제외” 구현을 D-52 원문대로 정정한다. `selectEligibleEvents`가 일반 후보에서 제외하는 것은 전용 생성기가 있는 `INJURY`·`NATIONAL_TEAM`·`RUMOUR`뿐이다. `SLUMP`·`LOCKER_ROOM`·`ETHICS`·`MEDIA`는 일반 EVENT 슬롯에서 trigger/cooldown/followUp 규칙을 그대로 거쳐야 한다. 양쪽 필터 테스트를 둔다.
- 팩 0.2.0에 최소 4개 PROTOTYPE(`authoring:'PROTOTYPE'`) 이벤트를 추가한다: `EVT-SLUMP-010`(최근 5경기 평균 <60), `EVT-REL-010` LOCKER_ROOM(약속 위반 또는 낮은 managerTrust, 주장 중재 선택 포함), `EVT-ETH-010` ETHICS, `EVT-MEDIA-010` MEDIA/SNS. 실제 외부 전송·실명·조롱 문구는 없다. 각각 2~3 choice, previewEffects, sourceId/reasonTag, cooldown, `playtested:false` manifest/checksum을 갖는다.
- 슬럼프는 CURRENT/CONTEXT Effect만, 관계·윤리·미디어는 RELATION(관계 또는 popularity/media) 중심이며 PERMANENT attribute/Base OVR Effect를 금지한다. `promiseBreaches`/`약속_위반` 조건이 EVT-REL-010 입력으로 실제 통과하는 테스트를 둔다.
- P4-6 검증: presentation이 `SLUMP|LOCKER_ROOM|ETHICS|MEDIA`인 모든 FAIL outcome은 (a) followUp이 하나 이상이거나, (b) 음수 CURRENT/CONTEXT Effect가 모두 유한 `expiresAt`을 갖고 PERMANENT 음수 Effect가 없어야 한다. schema/pack validator로 강제한다. RELATION 손실 자체는 진행을 봉쇄하지 않으며 모든 choice 뒤 pending은 닫히고 ADVANCE 가능함을 domain 테스트로 고정한다.
- `RESOLVE_EVENT`가 ETH/MEDIA FAIL을 고르면 증가시키는 additive `CareerState.controversyFailures`(기본 0)를 추가한다. eventId prefix가 `EVT-ETH-` 또는 `EVT-MEDIA-`이고 chosen.kind FAIL일 때만 +1; 다른 event/outcome은 불변.

## 5. Phase 4 태그 평가기 5종

- 룰셋 `relationshipRules.tagThresholds`에 아래 숫자를 두고 domain/content strict schema로 검증한다: glass potential 85/major 3, manager trust 80/seasons 3, locker relation 75/seasons 3, comeback role STARTER, controversial failures 3.
- `TAG-GLASS-GENIUS`: profile.truePotential ≥85 + MAJOR episodes ≥3.
- `TAG-MANAGER-FAVOURITE`: 동일 `SeasonResult.managerId`로 managerTrust.after ≥80인 시즌 ≥3.
- `TAG-LOCKER-LEADER`: captaincy가 VICE/CAPTAIN, captaincySeasons ≥3, captain 관계 ≥75.
- `TAG-COMEBACK`: 직전 시즌 index에 발생한 MAJOR episode가 있고 이번 결산 squadRoleAtEnd STARTER.
- `TAG-CONTROVERSIAL`: controversyFailures ≥3.
- 평가기는 rng 0, 이미 부여된 tag/grant 중복 없음. 각 태그 참/거짓 한 쌍과 결산 훅 통합 테스트를 둔다.
