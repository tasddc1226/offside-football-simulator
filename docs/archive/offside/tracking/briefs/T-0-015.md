# T-0-015 — engine-client 동기화 클라이언트(체크포인트 PUT·재시도 큐·409 처리)

> 상태: todo → 워커 배정 시 in-progress. 브랜치 `T-0-015-client-sync-queue`. 선행: T-0-007(`buildSyncBody`·`markSynced`), T-0-008(`GET/PUT /v1/careers/{id}` 규칙) 머지.

## 목표

ADR-002 동기화 규칙과 01 "명령 처리 계약"의 6단계(확정 후 체크포인트 동기화)를 클라이언트 쪽에서 구현한다. 커리어 명령이 확정될 때마다 서버로 `PUT /v1/careers/{id}`를 보내고, 실패는 게임 진행을 막지 않으며(오프라인 무시·재시도), 409는 서버 Snapshot을 받아 "빨리감기 재전송" 또는 "충돌 신호"로 갈라 화면에 알린다. UI는 만들지 않는다. 화면(Phase 1)이 구독할 상태와 호출할 함수만 제공한다.

## 범위

만질 경로: `packages/engine-client/src/sync/**`(신설), `packages/engine-client/src/index.ts`(export 추가), `packages/engine-client/package.json`(exports 필요 시). 새 의존성 **없음**(`fetch`·타이머는 주입).

만지지 말 것: `apps/**`, `packages/platform/**`, `packages/contracts/**`, `packages/domain/**`, `packages/engine-client/src/`의 기존 파일(`engine.ts`·store·simulator·worker. 필요한 확장이 있으면 질문), `tooling/**`, `docs/**`.

## 설계 결정(변경 금지. 의문이 있으면 질문)

1. **의존성 주입.** `createSyncClient(deps)`:
   ```ts
   export type SyncTransportResponse = { status: number; headers: Headers; json(): Promise<unknown> };
   export type SyncDeps = {
     engine: Pick<EngineClient, 'buildSyncBody' | 'markSynced' | 'loadCareer'>;
     store: LocalStore;                                  // 서버 Snapshot 채택(결정 7)에 필요
     fetch: (url: string, init: RequestInit) => Promise<SyncTransportResponse>; // 세션 헤더는 platform이 감싼 fetch가 붙인다
     baseUrl: string;                                    // 예: '/v1' 또는 'https://api.offside.example/v1'
     now: () => string;                                  // ISO UTC
     newId: () => string;                                // Idempotency-Key·requestId
     timers?: { setTimeout; clearTimeout };              // 테스트용 fake timers
     policy?: Partial<SyncPolicy>;
     online?: () => boolean;                             // 기본 () => true. platform이 navigator.onLine을 넣는다
   };
   export type SyncPolicy = {
     debounceMs: number;                                 // 기본 1500. 연속 명령을 한 PUT으로 합친다
     immediateCheckpoints: readonly CheckpointType[];    // 기본 ['CAREER_CREATED','SEASON_SETTLED','CONTRACT_CONFIRMED','RETIREMENT']. 이 유형이면 debounce 없이 즉시
     retryBaseMs: number; retryMaxMs: number; retryMaxAttempts: number; // 기본 2000 / 60000 / 무제한(0). 지수 백오프 + 지터 ±20%
   };
   ```
   toss 채널은 platform이 `policy.debounceMs = 0`으로 넣는다(ADR-002 "모든 step 경계에서 동기화").
2. **공개 API.**
   ```ts
   export interface SyncClient {
     notifyCommitted(careerId: string, snapshot: DomainSnapshot): void;  // engine.execute 성공 뒤 앱이 호출. 큐에 넣고 정책대로 예약
     flush(careerId?: string): Promise<void>;                            // 예약 무시하고 지금 전송(탭 숨김·앱 종료 시 platform이 호출)
     getState(careerId: string): CareerSyncState;
     subscribe(listener: (careerId: string, state: CareerSyncState) => void): () => void;
     resolveConflict(careerId: string, choice: 'REMOTE'): Promise<void>; // 결정 7
     dispose(): void;
   }
   export type CareerSyncState =
     | { kind: 'IDLE'; lastSyncedRevision: number; lastSyncedAt: string | null }
     | { kind: 'SCHEDULED'; dueAt: number }
     | { kind: 'SYNCING'; attempt: number }
     | { kind: 'RETRYING'; attempt: number; nextAt: number; lastError: EngineError }
     | { kind: 'OFFLINE'; pendingSince: string }                          // online() false 또는 네트워크 오류. 온라인 복귀 시 재개
     | { kind: 'LOCAL_ONLY'; reason: 'NO_SESSION' | 'COOKIE_BLOCKED' }    // 401·403 CAREER_NOT_OWNED가 아닌 세션 부재. platform이 세션을 만들면 앱이 notifyCommitted를 다시 부른다
     | { kind: 'CONFLICT'; local: { revision: number; stateHash: string }; server: { revision: number; stateHash: string; snapshot: CareerSnapshot } }
     | { kind: 'FAILED'; error: EngineError };                            // 재시도해도 소용없는 4xx(VERSION_MISMATCH·VALIDATION_FAILED·CAREER_ARCHIVED). 게임은 계속, 설정 화면에 표시
   ```
3. **전송.** 먼저 `engine.loadCareer(careerId)`로 최신 Snapshot을 검증한다(손상이면 복구까지 수행. `ok: false`면 FAILED, `CAREER_NOT_FOUND`면 큐에서 제거). 그 다음 `engine.buildSyncBody(careerId)`가 `null`이면 IDLE. `buildSyncBody`·`markSynced`가 던지는 `Error`는 `EngineError { code: 'CAREER_NOT_FOUND' }`로 감싼다. 아니면 `PUT {baseUrl}/careers/{id}`에 헤더 `If-Match: <baseRevision>`, `Idempotency-Key`, `Content-Type: application/json`, `X-Request-Id`(contracts 상수 사용). 본문은 `PutCareerBodySchema.parse` 결과를 그대로. 성공(200)이면 `PutCareerResponseSchema.parse` 후 `engine.markSynced(careerId, revision)`. 전송 중 새 명령이 확정되면 끝난 뒤 곧바로 한 번 더 보낸다(큐는 careerId당 최대 1개 대기).
4. **Idempotency-Key.** 같은 본문(같은 `baseRevision`·같은 마지막 revision·같은 stateHash)의 재시도는 **같은 키**를 쓴다(서버 재생 경로). 본문이 바뀌면(새 명령 포함) 새 키. 키는 메모리에만 둔다(새 세션의 재시도는 결정 4의 "이미 반영됨 → 200" 서버 규칙이 받아준다).
5. **오류 분류.** 네트워크 예외·`online() === false`·5xx·`SERVICE_UNAVAILABLE`·`RATE_LIMITED`(contracts `RETRYABLE_BY_CODE` 기준) → RETRYING/OFFLINE(백오프). `401` 또는 `SESSION_EXPIRED` → LOCAL_ONLY(NO_SESSION). `409 CAREER_REVISION_CONFLICT` → 결정 6. 그 외 4xx → FAILED(재시도 없음). 오류 봉투는 `ErrorEnvelopeSchema.parse`, 파싱 실패면 `{ code: 'SERVICE_UNAVAILABLE' }`로 취급해 재시도.
6. **409 처리(ADR-002 규칙).** `GET {baseUrl}/careers/{id}`로 서버 Snapshot(`GetCareerResponseSchema`)을 받는다. 로컬 store에서 `snapshots.get(careerId, server.revision)`(T-0-007 store API 기준)을 찾아 **`stateHash`가 같으면 서버는 로컬 로그의 조상**이다 → `engine.markSynced(careerId, server.revision)` 뒤 즉시 재전송(빨리감기). 로컬에 그 revision Snapshot이 없거나 hash가 다르면 → `CONFLICT` 상태로 두고 자동 재시도를 멈춘다. 빨리감기는 한 사이클에 최대 1회(무한 루프 방지. 두 번째 409는 CONFLICT).
7. **충돌 해소(Phase 0 범위).** `resolveConflict(careerId, 'REMOTE')`: 서버 Snapshot을 채택한다. `decodeSnapshot`으로 검증(hash·rngState·careerId) → 실패면 `VERIFICATION_FAILED`로 FAILED. 성공이면 `readwrite` 트랜잭션 하나로 로컬 `careers.revision = server.revision`, `lastSyncedRevision = server.revision`, `snapshots.put(server)`, 로컬 명령 로그 중 `revision > server.revision`인 항목과 그 Snapshot·idempotency 삭제. 삭제 전에 버려지는 로컬 항목들을 `kv`에 `sync:discarded:{careerId}:{now}` 키로 JSON 보관(복구 가능성. 크기 상한 없음, Phase 1에서 정리 정책). `'LOCAL'`(이 기기 우선)은 **이 작업에서 구현하지 않는다**(서버 API에 강제 덮어쓰기가 없고, 커리어를 새 id로 포크해 재실행하는 방식이 후보. 결정 로그 참조). 타입은 `'REMOTE'`만 받는다.
8. **동시성.** careerId당 진행 중 전송은 1개. `flush()`는 진행 중 전송의 완료를 기다린 뒤 대기 중인 것을 보낸다. `dispose()`는 타이머를 모두 지우고 진행 중 fetch는 기다리지 않는다(결과는 무시).
9. **순수성.** `packages/engine-client/src/sync/**`에 `window`·`document`·`navigator`·`setTimeout` 전역 직접 참조 금지(주입만). 기존 순수성 스캔 테스트 범위에 자동 포함된다.

## 테스트(vitest, fake timers, 가짜 fetch)

- 명령 3개 연속 확정 → debounce 후 PUT 1회, 본문은 세 명령 모두, 200 뒤 `markSynced(3)`·IDLE.
- `immediateCheckpoints` 유형 → 타이머 없이 즉시 전송.
- 5xx 3회 뒤 200 → 같은 Idempotency-Key 3회, 백오프 간격이 2s·4s·8s(지터 범위 안), 마지막에 IDLE.
- 네트워크 예외 + `online() === false` → OFFLINE; `online()`이 true로 바뀌고 `notifyCommitted` 또는 `flush` → 재개.
- 전송 중 새 명령 확정 → 첫 PUT 완료 뒤 두 번째 PUT(baseRevision이 첫 응답 revision).
- 409 + 서버 Snapshot이 로컬 revision 5의 Snapshot과 hash 동일(로컬은 8) → `markSynced(5)` 뒤 재전송 본문이 revision 6~8, 200 → IDLE.
- 409 + 서버 hash가 다름 → CONFLICT, 재시도 없음(타이머 다 돌려도 fetch 호출 수 불변). `resolveConflict('REMOTE')` → 로컬 revision·Snapshot이 서버 값, 버린 항목이 kv에 있음, 이후 `buildSyncBody`는 `null`.
- 409가 빨리감기 뒤 또 409 → CONFLICT(루프 없음).
- 401 → LOCAL_ONLY; 422 VERSION_MISMATCH → FAILED, 재시도 없음.
- `dispose()` 뒤 타이머 발화 없음.
- Golden 통합: `createEngineClient(MemoryLocalStore)`로 `career01EngineCommands` 실행하며 각 명령 뒤 `notifyCommitted` → 가짜 서버(메모리, T-0-008 규칙 1·3·4를 흉내)와 주고받아 최종 `lastSyncedRevision === golden.revision`.
