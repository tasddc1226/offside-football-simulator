# T-1-006: contracts Phase 1 스키마 — 명령 payload 유니온, Player·Offer·Contract·Pending·Timeline·CareerState, 복구·삭제 요청/응답

## 목표
서버(api)와 클라이언트(web·engine-client)가 Phase 1 명령 payload 6종, `CareerState` 전체, 복구 코드·프로필 삭제 요청/응답을 같은 Zod 스키마로 검증한다. 스키마의 추론 타입은 domain 타입과 컴파일 타임에 동일하다(`expectTypeOf().toEqualTypeOf()`).

## 참조 명세
- 요구사항 ID: API-PRO-003~005, API-AUTH-004, API-CAR-005, 07 "로컬 명령 계약", 05 "Snapshot 계약"
- 읽어야 할 문서(순서대로): `docs/tracking/phase-1-plan.md` **D-6, D-7, D-9, D-10, D-12, D-13, D-14, D-15**(정본), `docs/development/07-api-contract.md`, `packages/domain/src/types.ts`·`simulate.ts`(`Command` 유니온), `packages/contracts/src/*`(기존 규칙: `strictObject`, `primitives.ts`, `index.test.ts`의 expectTypeOf 검사), `docs/tracking/briefs/T-1-004.md`(api가 지금 로컬 스키마로 검증하는 요청·응답 형태. 같은 형태를 contracts로 올린다), `docs/tracking/briefs/T-1-005.md` 5번(`ACCEPT_OFFER`)
- 정본 우선순위: phase-1-plan.md 결정 > 07 > 브리프

## 범위
- 만질 패키지·경로: `packages/contracts`만.
- 만들 것:
  1. `src/player.ts`: `PositionSchema`(D-1 8종), `PositionGroupSchema`, `PreferredFootSchema`, `PlayerDraftSchema`(6 필드 전부 nullable, `name`은 `string | null`), `PlayerProfileSchema`(domain `PlayerProfile` 전 필드. `truePotential`·`scoutedPotentialMin`·`scoutedPotentialMax`는 40~99 정수, `baseOvr`는 1~99 정수), `PlayerPublicSchema = PlayerProfileSchema.omit({ truePotential: true })`와 `type PlayerPublic`, 순수 함수 `toPlayerPublic(profile: PlayerProfile): PlayerPublic`. `PlayerProfileSchema`는 Snapshot `state` 내부 검증용이고 화면·API 응답은 `PlayerPublic`만 쓴다는 것을 주석에 적는다(D-6).
  2. `src/career-state.ts`: `SquadRoleSchema`, `LeagueTierSchema`(`'YOUTH' | 1 | 2 | 3`), `OfferSchema`, `ContractSchema`(`signatureType: z.literal('AUTO')`), `PendingSchema`(`null | { kind: 'EVENT', eventId, version } | { kind: 'OFFERS', offers }` 판별 유니온), `TimelineEntrySchema`(kind 4종), `EffectSchema`(domain `Effect`와 동일: `kind`·`sourceId`·`target`·`delta`·`clamp{min,max}`·`appliesAt`·`expiresAt`·`stackingRule`), `CareerStateSchema`(`strictObject`, domain `CareerState` 전 필드. `schemaVersion: z.literal(1)`, `attributes`는 `ATTRIBUTE_KEYS` 20개 키 전부 필수 정수(키 목록은 domain에서 `import`하지 말고 contracts에 복제 + 타입 검사 `satisfies readonly AttributeKey[]`), `rngState`는 기존 `RngStateSchema`, `tags`·`appliedSourceIds`·`resolvedEventIds`는 `string[]`). 기존 `SnapshotStateEnvelopeSchema`(느슨한 최상위 검사)는 그대로 두고 두 스키마의 용도 차이를 주석에 적는다.
  3. `src/commands.ts`: Phase 1 명령 6종 payload 스키마 — `CreateCareerPayloadSchema { careerId: ClientId, seed: string(min 1), simulationMode, rulesetVersion: Semver, contentPackVersion: Semver }`, `UpdatePlayerDraftPayloadSchema { draft: PlayerDraftSchema.partial() }`, `ConfirmPlayerPayloadSchema = z.strictObject({})`, `AdvancePayloadSchema { eligibleEvents: Array<{ eventId: string(min 1), version: int ≥ 1, weight: int ≥ 1 }> }` + superRefine으로 `eventId` 오름차순 검사(`<` 비교는 코드포인트 순과 같다는 주석), `ResolveEventPayloadSchema { eventId, definitionVersion: int ≥ 1, choiceId, outcomes: Array<{ id, weight: int ≥ 1, effects: EffectSchema[], addTags?: string[], removeTags?: string[] }>(min 1) }`, `AcceptOfferPayloadSchema { offerId: string(min 1) }`. `CommandRequestSchema`는 `z.discriminatedUnion('type', [...])`로 바꾸되 공통 필드 `commandId`·`expectedRevision`을 유지한다. Phase 2+ 명령 6종(`START_SEASON`, `SETTLE_SEASON`, `NEGOTIATE`, `REJECT_OFFER`, `LOAN_RETURN`, `RETIRE`)은 payload `z.record(z.string(), z.unknown())` 유지. `CommandLogEntrySchema`는 `payload` 타입을 record로 두되 superRefine에서 `commandType`에 맞는 payload 스키마를 `safeParse`해 실패하면 issue(경로 `['payload', ...]`). export: `COMMAND_PAYLOAD_SCHEMAS`(type → 스키마 맵), `type CommandPayloadByType`, `type Phase1CommandType`.
  4. `src/auth.ts`: `RECOVERY_CODE_ALPHABET = 'ABCDEFGHJKMNPQRSTVWXYZ23456789'`(30자, D-14), `normalizeRecoveryCode(input)`(대문자화 → 공백·하이픈 제거 → 앞의 `OFS` 제거), `formatRecoveryCode(normalized)`(12자 → `OFS-XXXX-XXXX-XXXX`), `RecoveryCodeInputSchema`(문자열을 정규화한 뒤 12자·알파벳 검사, `transform`으로 정규화 값 반환), `MergeChoiceSchema = z.enum(['MOVE_TO_LINKED', 'KEEP_LINKED_ONLY'])`, `IssueRecoveryCodeResponseSchema { code(표시형), issuedAt: IsoUtc }`, `RecoverProfileBodySchema { code: RecoveryCodeInputSchema, mergeChoice?: MergeChoice }`, `RecoverProfileResponseSchema { profileId, careerCount: int ≥ 0 }`, `RecoveryConflictDetailsSchema { currentCareerCount, targetCareerCount }`, `DeleteProfileStartResponseSchema { confirmToken(min 1), expiresAt: IsoUtc }`, `DeleteProfileConfirmBodySchema { confirmToken }`. `POST /auth/logout`과 `DELETE /careers/{id}`는 본문 없음·204라 스키마가 없다는 것을 주석으로 남긴다.
  5. `src/index.ts` export 갱신, `CONTRACTS_VERSION`을 `0.2.0`으로.
- 만지지 말 것: `docs/`, 다른 패키지(api의 로컬 스키마를 contracts로 바꾸는 일은 T-1-012·013), `ERROR_CODES`·HTTP 매핑·`RETRYABLE_BY_CODE`, `CHECKPOINT_TYPES`, `envelope.ts`, `CareerSnapshotSchema`.

## 완료 조건
- [ ] 타입 동일성 테스트(expectTypeOf): `Position`, `PositionGroup`, `PreferredFoot`, `SquadRole`, `PlayerDraft`, `PlayerProfile`, `Offer`, `Contract`, `Pending`, `TimelineEntry`, `Effect`, `CareerState`가 domain 타입과 같다. 명령 payload 5종은 `Extract<Command, { type: '…' }>['payload']`와 같다. `ACCEPT_OFFER`는 PR 직전 main을 합쳤을 때 domain `Command`에 있으면 같은 방식, 아직 없으면 D-9 리터럴 `{ offerId: string }`과 비교하고 PR 본문에 어느 쪽인지 적는다.
- [ ] payload 스키마마다 유효 1건·무효 1건 이상(예: `ADVANCE` 정렬 위반·weight 0, `RESOLVE_EVENT` outcomes 빈 배열, `CREATE_CAREER` 잘못된 semver). `CommandRequestSchema`가 알 수 없는 `type`을 거부하고 Phase 2+ 명령의 임의 payload는 통과시킨다. `CommandLogEntrySchema`가 `commandType`과 payload 불일치를 거부한다.
- [ ] `CareerStateSchema`: 확정 직후 상태 리터럴(20개 능력, `player.profile` 있음, `pending: null`, `contract: null`, timeline 1개)이 통과. 알 수 없는 키, 능력 키 누락, `schemaVersion: 2`, `pending`이 `{ kind: 'OFFERS' }`인데 `offers` 누락 각각 실패. 테스트 입력은 리터럴로 만든다(domain `simulate` 호출·fixtures 의존 추가 금지).
- [ ] 복구 코드: `normalizeRecoveryCode('ofs-abcd 2345-efgh')` → `'ABCD2345EFGH'`, `formatRecoveryCode` 왕복, `I L O U 0 1` 포함·길이 오류 거부.
- [ ] `pnpm lint && pnpm lint:deps && pnpm typecheck && pnpm test && pnpm build` 전체 통과. contracts를 소비하는 패키지(api·engine-client·web)의 typecheck·test도 깨지지 않는다. `CommandRequestSchema`가 유니온으로 바뀌어 기존 소비처가 깨지면 소비처를 고치지 말고 PR 본문에 적고 멈춘다.
- [ ] 문서: 코드 주석 외 문서 수정 없음.

## 제약
- contracts는 domain을 `import type`으로만 쓴다(ADR-005). 런타임 값 복제(포지션·능력 키 목록)는 타입 검사로 묶는다.
- 모든 객체 스키마는 `strictObject`. 날짜는 `IsoUtcSchema`, ID는 `ClientIdSchema`.
- 커밋 메시지는 `T-1-006: …`로 시작, 브랜치는 `T-1-006-…`.
- 서브에이전트 리뷰를 띄우지 않는다. Orca PR 게이트용 `/review:pr` 1회만 예외(`/simplify`·병렬 fork 금지).
- PR 직전 `git fetch origin && git merge origin/main`으로 최신 main을 합친다. `pnpm-lock.yaml` 충돌은 손으로 고치지 말고 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile`로 재생성한 뒤 전체 체인을 다시 돌린다.
