# 명예의 전당 읽기 지연 조사

T-11-718. 기존 결과·캐시·소급 처리·인원 갱신 정책을 유지하며 공개 목록의 D1 세션을 이어 쓴다.

## 조사 기준선

2026-11-13 10:36:36~11:55:27 KST, 운영 `ebea0f64` 이후 로그:

- 2초 이상 요청: `/v1/hof` 10건(최대 2,655ms), 컵 내 상태 1건(2,047ms), 채팅 입장권 1건(2,369ms).
- 같은 필터인지 확인할 수 없는 명예의 전당 요청 5개·3개가 각각 가까운 시각에 끝났다. 이 사실만으로 동일 요청의 중복 실행을 확정하지 않는다.
- 해당 구간의 요청 로그에서 API 5xx는 관측되지 않았다. SQL Insights는 적응형 집계이고 traces는 1% 표본이다.
  큰 명예의 전당 지연 묶음의 개별 SQL trace는 확보하지 못했다. 특정 SQL 또는 cron을 단일 원인으로 확정하지 않는다.
- 기본 요청 로그의 느림 기준은 2초, 공개 상태 집계는 1초다. 빠른 성공 로그는 표본이므로 로그 전체의 평균/p99를 실제 요청 분포로 쓰지 않는다.

## 확인한 구조와 변경

기존 목록 캐시 미스는 소급 처리 완료 메타데이터를 일반 DB(주 DB)에서 읽고,
목록 쿼리는 별도의 `first-primary` 세션을 새로 시작했다. 인원 엣지 캐시도 비어 있으면 저장된 인원을 일반 DB에서 읽었다.

변경 후:

1. 요청의 공개 읽기 세션을 `first-primary`로 만든다.
2. 소급 처리 상태 SELECT를 그 세션의 첫 쿼리로 실행해 주 DB 시점을 확보한다.
3. 처리가 끝난 상태에서는 목록과 저장된 인원을 같은 세션에서 읽는다.
4. 미완료 소급 처리의 조회·쓰기와 그 요청의 목록/인원 계산은 기존 주 DB 어댑터를 유지한다.

목록/인원 엣지 캐시가 비었고 저장된 인원이 신선한 경우 HOF 로더의 SQL은 여전히 3개다.
기존에는 세 읽기 모두 주 DB로 고정됐지만, 이제 첫 읽기만 주 DB 고정이고 이후 두 읽기는 세션 시점 이상인 복제본을 사용할 수 있다.
실제로 어떤 인스턴스가 선택되는지는 D1이 결정한다. SQL 수나 실행 CPU 감소를 뜻하지 않는다.
([D1 읽기 복제와 세션 일관성](https://developers.cloudflare.com/d1/best-practices/read-replication/))

인원의 조건부 UPDATE/INSERT 잠금·배경 재계산·TTL은 유지한다. 세션의 쓰기는 D1이 주 DB로 보낸다.
`D1_READ_SESSIONS_DISABLED=1`이면 기존 일반 DB로 돌아간다. 요청 간 세션/북마크/완료 플래그를 공유하지 않는다.
시즌 일정 middleware가 읽는 경우의 추가 쿼리는 이 HOF 로더 3개와 별개이며 이번 변경에서 유지한다.

## `job=hof-read` 진단

성공한 목록 요청이 middleware 진입부터 1초 이상 걸렸을 때만 한 줄을 남긴다. 요청별 `requestId`로 기존 요청 로그와 대조한다.

| 필드 | 범위 |
| --- | --- |
| `ms` | logger 시작부터 HOF data 준비까지. 응답 직렬화 완료까지의 전체 요청 시간과 약간 다름 |
| `beforeRouteMs` | HOF 핸들러 진입 전 시간. 시즌 일정 갱신 등 middleware 대기 포함 |
| `routeMs` | 핸들러 진입부터 data 준비까지 |
| `backfillMs` | 완료/커서 메타데이터와 필요할 때의 기존 소급 처리 |
| `listMs` | 목록·인원·검색 순위·표시 조립. 아래 `countMs`를 포함하므로 둘을 합산하지 않음 |
| `countMs` | 인원 캐시/저장값/최초 계산을 기다린 전경 시간. 배경 재계산 완료 시간은 포함하지 않음 |
| `edgeMs` | `routeMs - backfillMs - listMs`. 엣지 캐시와 나머지 처리 시간의 합이며 순수 Cache API 시간은 아님 |

`edgeHit`, `filling`, `readSessions`와 정규화된 정렬·시즌·포지션·페이지·크기를 기록한다.
검색어는 `search` 불리언만 기록한다. 이름·검색어 원문·계정·쿠키·SQL 바인드 값은 기록하지 않는다.

## 검증과 운영 판정

- 실제 로컬 D1과 어댑터 관찰로 메타데이터→목록→저장 인원의 순서·같은 세션 재사용·3개 SQL·요청 간 세션 분리를 확인한다.
- 세션 비활성화, 미완료 소급 처리의 주 DB 경로와 부분 결과 캐시 금지, 엣지 적중의 DB 호출 0회를 확인한다.
- 공유 인원의 동시 최초 계산·신선한 값·배경 갱신·잠금 만료를 일반 DB와 Sessions API 양쪽에서 검사한다.
- 로컬 SQL/모의 시간 검사는 실제 복제본 지역·운영 지연 개선율을 증명하지 않는다.
- 배포 후 같은 정렬/검색/캐시 미스 조건의 `hof-read`를 비교한다. 표본 수가 적으면 개선율을 확정하지 않는다.
  `beforeRouteMs`가 크면 middleware를, `countMs`가 크면 인원 저장/초기 계산을 따로 조사한다.
