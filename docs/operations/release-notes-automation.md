# 게임 내 릴리즈 노트 자동 게시

## 배포 흐름

`Production Release`의 deploy 모드에서 API·웹 검증, 앱 OTA 잡, 릴리즈 태그 잡이 모두
성공하면 `Publish in-game release notes`를 실행한다. preflight·staging·PR 검사는 게시하지 않는다.
기존 OTA 잡이 EXPO_TOKEN 부재로 건너뛰는 경우에도 스토어 출시를 추정하지 않으며,
앱 적용 여부는 PR에서 검토한 `.release-notes/*.json` 문구로 명시한다.

게시 실패는 해당 잡과 배포 실행의 실패로 드러난다. API·웹 배포를 되돌리지는 않는다.
원인을 해결하고 실패한 잡을 다시 실행한다. 다음 배포에서도 미게시 항목은 다시 시도한다.

## 작성과 보존

사용자에게 알릴 기능·수정은 PR에 공개 문구 JSON을 함께 넣는다. 내부 작업은 넣지 않는다.
LLM이나 외부 AI API가 CI에서 문구를 만들지 않아 별도 API 키·사용료가 없다.

한국 시간의 게시 날짜로 `YYMMDD 릴리즈노트`를 찾는다. 오늘 글이 있으면 본문 마지막 감사 인사
앞에 새 번호를 이어 붙이고, 없으면 만든다. 기존 제목·작성자·고정·버전·조회수·좋아요·댓글은 보존한다.
자동으로 새로 만든 글은 고정하지 않는다. 관리자는 기존 운영 도구로 수정·고정할 수 있다.

게시 ID는 `app_meta`의 `release-note:<id>` 키로 영구 기록한다. 이 키는 삭제하거나 재사용하지 않는다.
게시 문구의 해시도 저장한다. 이미 게시한 ID의 문구를 바꾸면 409로 중단하며 새 ID로 정정한다.
게임 데이터·세이브·DB 스키마는 변경하지 않는다. 게시 내용과 이력은 같은 D1 batch로 커밋한다.
관리자가 동시에 수정하면 CAS가 실패하고, 자동화는 본문을 덮어쓰지 않는다.
오늘 글을 삭제했거나 전체 본문이 5,000자를 넘으면 409로 중단한다. 수동 정리 후 재실행한다.

## 인증과 알림

게시 API는 `/v1/internal/release-notes` 하나다. GitHub의 RSA 서명을 검증하고 issuer·audience·
repository/owner의 숫자 ID·main ref·Production Release workflow·production subject·
배포 SHA·유효 시간을 검사한다. 로컬/스테이징·일반 관리자 쿠키·앱 세션은 허용하지 않는다.
장기 관리자 토큰이나 새 Worker secret은 필요하지 않다.

OIDC 정의는 [GitHub 공식 문서](https://docs.github.com/en/actions/reference/security/oidc)를 따른다.
기존 형식과 immutable ID 형식의 production subject를 허용하며 숫자 ID는 두 경우 모두 검증한다.

실제 게시 때만 `updated_at`을 갱신하고 게시판 엣지 캐시를 비운다. 재실행·미리보기는 알림을 만들지 않는다.
기존 웹·앱 소식 알림은 10분 간격 제한으로 새 글/수정을 확인한다. 처음 온 기기는 이전 글을
읽은 것으로 처리하며, 앱을 닫은 동안의 푸시 알림은 제공하지 않는다.

## 첫 적용

2026-10-03 운영 공지의 8~14번에 추가 초안 7개가 이미 수동 반영된 것을 확인했다.
이 초안은 `.release-notes/archive/2026-10-03-manual/`에 보관하며 첫 배포에서는 게시하지 않는다.
수동 게시 항목에는 자동 게시 이력이 없으므로 이 파일을 활성 폴더로 되돌리지 않는다.
이후 새 항목부터 자동으로 게시하며, 한 번 자동 게시된 항목은 ID로 중복을 막는다.

앱 푸시는 별도 후속 작업이다. 알림 권한·토큰 등록/해제·Expo/APNs/FCM 발송·사용자 수신 설정·
실기기 검증이 필요하며 이번 변경에는 포함하지 않는다.
