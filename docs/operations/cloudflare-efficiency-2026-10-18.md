# T-11-385 운영 반영과 관측 결과

추가 유료 구독 없이 Cloudflare 자원 활용과 실패 복구를 개선했다. DNSSEC는 활성화 요청 후 상위 DS 전파를 기다리는 중이며, 서명 검증까지 완료한 것으로 표시하지 않는다.

## 1차 배포 전후 각 10분

시각은 2026-10-18 KST다. API 정상 요청 로그는 코드에서 10% 표본을 남기며, 경고·오류는 전부 기록한다. Cloudflare Analytics는 적응형 추정값이다. 기간별 트래픽 구성이 달라질 수 있어 지연 변화 전체를 변경의 인과 효과로 해석하지 않는다.

웹 HTTP 요청이 약 19% 늘어난 동안 웹 Worker 실행 추정은 약 76% 줄었다. HTML·OG·설정·버전 파일은 Worker를 유지하고 해시 정적 파일만 우회한다. 운영 JS의 1년 immutable·noindex·nosniff, 버전 파일의 no-store, 공개 페이지 index, 알 수 없는 커리어의 실제 404를 확인했다. 로컬 Workers 추적에서도 정적 요청 2건은 Worker를 우회하고 동적 요청 3건만 실행했다.

HTTP 집계는 `offside-lab.com`, Worker 집계는 보조 workers.dev를 포함하는 script 단위다. 이 숫자는 청구서 계량값이나 확정 월 절감액이 아니다. 계정의 실제 구독 갱신일·청구액은 조회 권한 제한으로 확인하지 못했다.

## D1 정상 저장 비용

같은 이름·계속 익명인 null을 매번 부모 upsert에 SET해 HOF covering 인덱스 2개를 다시 쓰던 경로를 분리했다. 로컬 D1 `rows_written` 검증에서 부모 문장은 **6→4행**, 변경 없는 이름 UPDATE는 **0행**이었다. D1 왕복은 기존 한 batch로 유지한다. 실제 이름 변경 요청에는 조건부 UPDATE가 하나 더 생긴다. 이는 부모 문장 비용이며 전체 업로드·전체 D1·월 청구량 33% 절감을 의미하지 않는다.

8개 테스트에서 실제 쓰기량, 이름 변경·익명 전환, 운영 숨김·은퇴·옛 클라이언트, 동시 revision·중복 재시도, 후속 실패 시 전체 롤백을 검증했다. 이미 적용된 시즌 해시·revision 중복 방지를 유지했다. 한도 초과 업로드도 원자적으로 거절하며 카운터를 계속 재작성하지 않는다.

운영 Query Insights의 일반 시즌 부모 upsert(`pot` 갱신 변형 제외)를 같은 5분 창으로 비교했다. 16:40–16:45 KST는 추정 1,301회·7,806행으로 문장당 6행, 17:15–17:20은 453회·1,812행으로 문장당 4행이었다. 새 커리어·`pot` 갱신 변형은 비용이 달라 별도로 취급했다. 해당 부모 문장의 평균 SQL 실행 시간은 0.478→0.469ms였다. 조건부 이름 UPDATE를 포함한 전체 batch 지연을 의미하지는 않는다. 적응형 가중 추정이며 요청 수 자체를 절감률로 계산하지 않는다.

## 최종 배포 뒤 지연 관측과 다른 배포의 중첩

관측 중 별도 작업 [#800](https://github.com/tasddc1226/offside-football-simulator/pull/800)이 main에 머지됐고, [운영 배포](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39110695482)가 17:17 KST에 완료됐다. 따라서 이 10분 창은 `1380adc`와 `fe0abde`가 걸친 관측이며 #799만의 통제된 성능 비교가 아니다. 17:27 KST에 다시 조회한 웹 버전은 `fe0abde`다. #800에서도 이번 이름 upsert 변경은 유지된다.

다른 배포 시작 전인 17:08–17:13 KST도 HTTP 200 표본 397건·p95 774ms·p99 4,546ms, 관측된 5xx 0건이었다. 지연 상승을 #800 중첩만으로 설명할 수도 없다.

17:10–17:20 KST의 HTTP 200 표본 842건은 p95 784ms·p99 1,417ms로 배포 전 461/918ms보다 높았다. 이 창에서도 관측된 HTTP 5xx는 0건이다. 따라서 전체 API 지연 개선이나 성능 검증 완료로 표시하지 않는다.

동일 조건으로 커리어 ID·연도를 합쳐 시즌 업로드를 다시 집계하면 배포 전 210표본·p95 530ms·p99 751ms, 최종 배포 뒤 156표본·876/1,081ms다. 프로필·firsts·현재 컵·recap-status·club-strength 조회 묶음도 107표본·404/1,925ms에서 88표본·3,881/6,035ms로 상승했다. 변경한 시즌 저장 외 경로에도 긴 꼬리가 관측돼 원인을 코드 변경 또는 트래픽 구성 하나로 단정하지 않는다. 추가 17:20–17:25 KST 창도 HTTP 200 표본 455건·p95 792ms·p99 1,129ms였고 관측된 5xx는 0건이었다. 지연 상승이 이어져 성능 항목은 미완료다. 후속으로 같은 경로·부하의 전체 D1 batch와 배치/큐 경합을 확인하고, #799 영향이 확인되면 이전 코드로 롤백을 검토한다.

## 설정과 정기 점검

- DLQ 4개: 푸시 1일·결제 4일 → 모두 14일. 본 큐·소비자·재시도 설정은 유지했다. 최종 배포 뒤 점검에서도 적체는 각 0건이었다.
- 최소 TLS 1.0 → 1.2. 웹·API의 TLS 1.2 응답을 확인했다.
- Free 속도 제한 1개를 비밀번호 검사에서 복구 경로의 IP·데이터센터별 10초 100회로 변경했다. 미사용 WordPress·`.git`·`.env` 탐색 차단 규칙 1개를 추가했다. 정상 API·OAuth·결제 웹훅은 이 규칙의 대상이 아니다. 기존 workers.dev 보조 호스트는 OAuth 계약을 유지하며 앱의 계정별 제한이 적용된다.
- DNSSEC: Cloudflare Registrar의 자동 DS 등록·전파 대기. 공개 DS와 실제 주소의 AD 검증을 모두 확인해야 완료다.
- [17:17 KST 운영 점검](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39110885056): D1 4.05GiB·건강 이슈 없음, DLQ 각 0건·14일, R2 payload 약 9.010GB로 9GB 저장 정책 검토 경고가 표시됐다. 예약 시작 지연 때문에 같은 읽기 전용 workflow를 수동 실행했다. 실제 운영 자격 증명으로 새 점검 항목의 권한과 실행을 확인했다.
- 기존 시간별 `Production infrastructure health`에 DLQ 적체·보존 드리프트, R2 용량 참조, DNSSEC 전파 확인을 통합했다. 실패 조회를 0건으로 표시하지 않는다. 별도 로컬 MCP 모니터의 승인 도구 목록은 바꾸지 않았다.

R2 현재 payload의 9GB 경고는 10GB 참조의 90%이며 실제 월 GB-month 과금량이 아니다. D1 5GB 참조도 계정 전체 포함량과 청구 주기를 따로 확인해야 한다. 사용자 보관 기록과 월간 백업을 보호하기 위해 전체 R2 TTL·대량 삭제·스토리지 클래스 전환을 적용하지 않았다. 정상 로그 10%·트레이스 1%, 기존 예산·실시간 이슈 알림과 Argo 설정은 유지했다. Argo는 별도 과금 서비스이며 청구 근거 없이 임의 해지하지 않았다.

## 검증 범위와 복구

첫 PR은 필수 빠른 검사·API 3개·웹 E2E 3개 shard가 모두 통과했다. 둘째 PR은 백엔드만 바뀌어 빠른 검사·API 3개 shard가 통과했고 웹 E2E는 정책상 생략했다. 로컬 초기 동시 실행에서는 시간 제한과 빌드 디렉터리 재생성 경합이 발생해 해당 E2E 결과를 무효 처리했다. 빌드를 고정한 재실행은 301개 통과·10개 건너뜀·2개 실패였고, 남은 2개는 단독 재검증에서 통과했다. 게임 테스트는 456개 통과·1개 기존 건너뜀, 전체 lint·타입·서식·i18n·의존성·빌드와 번들 예산을 확인했다.

다음 일일 작업은 2026-10-19 04:00 KST 예정으로 아직 실행 전이다. 이번 변경에서 일일 처리·백업 로직이나 cron 시각은 바꾸지 않았다. 기존 시간별 점검이 완료 체크포인트를 확인하며, 다음 주기 성공과 백업 복원까지 검증한 것으로 표시하지 않는다.

단기 관측의 5xx 0건은 무오류 보장이 아니다. [설정별 롤백·DLQ 복구 절차](cloudflare-efficiency.md)를 따른다. 코드 롤백이 큐·존 설정이나 저장 데이터를 되돌리지는 않는다. 게임 데이터·기존 백업·실패 메시지를 임의 삭제하거나 일괄 재전송하지 않았다.

## D1 왕복 지연 후속: 지역 힌트

[PR #803](https://github.com/tasddc1226/offside-football-simulator/pull/803)은 API fetch의 배치를 Smart Placement에서 싱가포르 근접 지역 힌트 `aws:ap-southeast-1`로 바꿨다. [필수 CI](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39111713562)의 빠른 검사·API 3개 shard가 통과했고, [운영 workflow](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39112017069) 7개 잡이 모두 성공했다. 릴리즈는 `v2026.10.18.14`, 코드 `6b712c3`이다. DB 이전·AWS 자원 생성·새 구독·저장/인증/cron/queue 코드 변경은 없다. #800의 별도 작업도 유지했다.

배치 변경 전 17:20–17:30 KST HTTP 200 로그는 849표본·p95 787ms·p99 1,128ms, 관측된 5xx 0건이었다. 같은 창의 기존 1% 트레이스에서 APAC→SIN D1 span은 추정 344개·p95 175ms·p99 231ms, SQL 평균 0.589ms였다. 로그 표본과 트레이스 표본은 일대일 대응하지 않는다. HTTP root trace 103개(상한 200개 미도달)를 ID로 연결해 D1 child span만 다시 계산해도 추정 331개·p95 170ms·p99 231ms, SQL 평균 0.596ms였다. child span에 HTTP trigger가 직접 붙지 않아 빈 결과가 된 단순 필터를 0건으로 해석하지 않고 root trace ID 연결을 사용했다. Smart Placement `SUCCESS` 자체는 실제 왕복 감소의 증거가 아니었다.

Cloudflare 서비스 설정에서 대상 지역 힌트를 확인했다. 공개 조회 200·무효 Bearer 401·라이브 WebSocket 연결도 확인했다. 스모크 중 무세션 `/v1/profile` GET이 게스트 프로필을 만드는 동작을 미리 확인하지 못해 1건 생성했다. 이후에는 명시적인 무효 Bearer로 인증 거절만 확인했다. 기존 사용자 데이터를 수정하거나 테스트 기록 삭제를 실행하지 않았다.

API와 시즌 저장 지연은 낮아졌지만 주요 조회 p95는 높아졌고 D1 왕복 감소도 작았다. 전체 지연 문제를 해소했다고 표시하지 않는다. 한 창을 더 확인해 유지·복원 여부를 판단한다. 두 창 모두 HTTP root trace 상한 200개에 도달하지 않았다.

[17:47 KST 인프라 점검](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39112783276)도 통과했다. D1 4.05GiB·기존 건강 이슈 없음, DLQ 각 0건·14일, R2 payload 9.024GB로 저장 정책 검토 경고가 유지됐다. DNSSEC는 아직 parent DS·AD 검증 대기다. 이 점검은 API 지연 회귀 테스트나 다음 일일 작업 실행 증거를 대신하지 않는다.

추가 GraphQL에서 `coloCode`의 스키마 설명은 “스크립트가 실행된 데이터센터의 IATA 코드”임을 확인했다. 변경 전 상위 집계는 SIN 10,039건·ICN 110건·DXB 81건 등으로 이미 SIN 중심이었고, 변경 후도 SIN 10,734건 등이다. 이는 트레이스의 입구 `cloudflare.colo`와 다른 지표다. 지역 힌트가 실제 실행 위치를 실질적으로 바꿨다는 근거가 없으므로 `mode: smart`로 복원하기로 했다. 첫 창의 API p95 감소를 이 힌트의 효과로 설명하지 않는다. D1 쓰기 절감·정적 자산 우회·DLQ·WAF/TLS 변경과 #800은 유지한다.

두 번째 지역 힌트 창(17:48–17:58 KST)은 HTTP 200 추정 777표본·p95 398ms·p99 624ms로 회복했다. 시즌 업로드 123표본·553/627ms, 주요 조회 묶음 83표본·325/605ms였다. 연결한 HTTP root 102개(상한 미도달)의 D1 child span은 추정 315개·106/277ms, SQL 평균 0.409ms였다. 지역 힌트 이전에도 실제 실행 위치가 SIN이었기 때문에 이 회복의 원인을 지역 변경으로 단정하지 않는다.

이 창에는 17:56 KST `GET /v1/hof`의 **503 1건**이 있었다(5,180ms). 원본 cause는 인원 집계 SELECT의 `D1_ERROR: Network connection lost`였으며, 쓰기·업로드 실패나 SQL 문법 오류로 확인된 것은 아니다. 따라서 해당 창을 오류 0건으로 보고하지 않는다. [#805](https://github.com/tasddc1226/offside-football-simulator/pull/805)의 [필수 CI](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39113286128)가 통과했고 자동 배치 복원 코드 `a96acba`가 [운영 배포](https://github.com/tasddc1226/offside-football-simulator/actions/runs/39113570858), `v2026.10.18.15`로 반영됐다.

## 관측한 HOF 읽기 실패 복구

공개 목록의 페이지·인원·검색 순위 SELECT 각각에 기존 제한 재시도를 적용한다. 실패한 SELECT만 다시 실행하고 성공한 페이지나 소급 보정·캐시 loader·쓰기를 재실행하지 않는다. 정상 쿼리 수·인덱스·북마크 순서·검색 순위는 유지한다. 영구 연결 실패는 최대 3회 뒤 기존 오류로 종료하며 과부하·SQL 오류는 재시도하지 않는다.

실제 로컬 D1과 `first-primary` Sessions에서 SELECT 응답을 잃게 한 회귀 테스트는 수정 전 4개 실패를 재현했고 수정 뒤 7개가 통과했다. 기존 조회 비용·결과 테스트를 합쳐 17개가 통과했고 타입·린트·i18n도 확인했다. 이 테스트는 기반 D1 네트워크 문제가 제거됐다는 증거는 아니며, 운영에서 인위적인 오류를 주입하지 않는다. 짧은 ko/en/ja 릴리즈 노트는 웹·앱 공통 API 개선으로 작성했다. 필수 CI·운영 반영과 후속 관측을 확인한다.
