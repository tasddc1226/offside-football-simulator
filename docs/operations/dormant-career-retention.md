# 휴면 커리어 자동 보관 정책

## 적용 범위

운영 API의 기존 매일 KST 04:00 예약 작업에서 자동 실행한다. 별도 예약, 관리자 클릭, 월별 승인 절차는 없다.
운영 D1에 첫 시즌을 업로드한 커리어만 판단할 수 있다. `updated_at`은 서버 기록 갱신 시각이며 기기 플레이·접속 시각이 아니다.
새 커리어를 시작해 남은 선수, 오프라인 플레이, 시즌 도중 플레이와 실제 이탈을 구분하는 지표로 사용하지 않는다.

- 30일 이상 갱신 없음: 휴면 집계.
- 첫 실행 후 30일: 관찰만 진행한다. 시작 시각을 D1 `app_meta`에 저장하므로 재배포해도 유예 기간은 바뀌지 않는다.
- 90일 이상 갱신 없음 + 완료 시즌 1~3개: 보관 후보.
- 현재 서비스 시즌, 은퇴 선수, 칭호·명예의 벽, 카드·이적 내역·최초 기록·서버 기록·영구결번·구단주 결산의 대표 선수는 제외한다.
- 완료 시즌 0개·4개 이상은 제외한다.

**선수나 시즌 행을 삭제하지 않는다.** 소유권, 서비스 시즌, 성적·수상·나이·OVR·대회 기록은 계속 D1에 남긴다.
보관하는 것은 `career_seasons.events_json`, `signals_json`, `growth_json`뿐이다. 기기의 저장 형식은 바꾸지 않는다.
영구 삭제는 이번 정책에 포함하지 않는다. 보관 후 180일을 넘겼다는 이유로 선수나 유효한 보관 객체를 삭제하지 않는다.

## 자동 실행과 부하 제한

중복 예약 실행은 D1의 16분 임대로 막는다. 임대 중이면 `busy`로 기록하고 건너뛴다. 작업이 중단되면 임대가 만료된 뒤 다음 예약 실행에서 재개한다.

매주 집계한다. 최근 결과는 `app_meta`의 `cron:career-retention:last`에 시각과 함께 기록한다.
집계 값은 전체 미은퇴 수, 30일 휴면 수, 보호 조건을 통과한 후보 수, 이미 보관된 미은퇴 수다.

관찰 기간이 끝나면 첫 보관을 시작하고, 후보가 남아 있으면 하루 최대 50명씩 다음 날 계속 처리한다.
후보를 모두 처리한 뒤에는 다음 UTC 달의 1일까지 기다린다. 그 달에도 같은 방식으로 제한된 배치를 이어간다.
기존 `careers_status_updated_idx`와 시즌 PK를 사용하며 보호 대상과 R2 참조 확인용 인덱스도 함께 추가한다.
보관 자체는 선수당 최대 3개 시즌만 읽는다. 유저 화면 조회·폴링·새 네트워크 요청은 추가하지 않는다.

실행 결과는 기존 `job:daily` 로그와 `cron:daily:last`의 `careerRetention`에 남는다.
`mode`, 보관 수(`archived`), R2 압축 바이트(`bytes`), 동시 변경으로 제외한 수(`raced`), 참조 없는 객체 정리 수(`orphanObjects`)를 확인할 수 있다.
한 단계가 실패해도 다른 일일 정리·백업은 끝까지 실행하며, 전체 예약 작업은 오류로 종료해 실패가 숨겨지지 않는다.

## 보관과 재개

1. 상세 로그를 `BACKUP` R2의 `career-details/production/<careerId>/<uuid>.json.gz`로 올린다.
2. 업로드 성공 후 D1 batch에서 선수 소유자·상태·갱신 시각·보호 대상·시즌 개수·상세 원본을 다시 검사한다.
3. 읽었던 상태와 같을 때만 `careers.detail_archive_key`를 기록하고 상세 로그를 비운다. 불일치하면 보관을 취소한다.
4. 시즌 업로드와 은퇴 업로드는 기존 인증·소유권·본문·업로드 한도 검증 후 상세 기록을 복구한다.
5. 원래 커리어 ID·소유권·서비스 시즌을 유지한 채 기존 업로드 경로를 이어간다. 별도 생성/보상/은퇴 요청을 만들지 않는다.

오래 멈춘 선수의 재개 요청만 D1 갱신 시각을 먼저 기록해 예약 작업과 충돌을 막는다.
일반적인 최근 선수의 업로드는 기존 소유권 조회에서 보관 여부를 같이 읽으므로 추가 D1/R2 조회가 없다.
R2 장애·누락·잘못된 객체는 상세 원본을 버리거나 보관 포인터를 지우지 않고 요청을 실패시킨다. 기존 outbox의 재시도로 복구할 수 있다.
복구 batch가 성공하면 보관 포인터를 비운다. 이전 D1 백업이 그 객체를 참조할 수 있으므로 선수 기록이 남아 있는 동안 보관 객체를 유지한다.

## 참조 없는 객체와 계정 삭제

매일 `career-details/production/`의 객체를 최대 100개씩 커서로 점검한다.
올린 지 7일이 지난 객체 중 **해당 선수 기록이 삭제됐고 현재 보관 포인터에서도 참조하지 않는 객체만** 삭제한다.
선수를 다른 프로필로 합쳐도 같은 커리어를 참조하므로 유지한다. 계정 삭제로 커리어가 삭제되면 보관 객체는 이 순회에서 제거한다.
R2 생성 시점에서 7일의 유예를 두므로 진행 중인 보관 업로드를 지우지 않는다. 삭제된 계정의 객체가 없어지는 시점은 순회량에 따라 달라진다.

기존 백업 가지치기는 `d1/`만 대상으로 한다. `growth/`나 유효한 `career-details/` 객체에는 수명 기반 삭제를 적용하지 않는다.
선수 기록이 존재하는 동안 복구 이후에도 객체를 유지하므로 이전 D1 백업의 `detail_archive_key`도 계속 복구할 수 있다. 계정 삭제 이후 제거된 객체는 복구 대상이 아니다.

## 중단 및 배포

- `CAREER_RETENTION_DISABLED=1`: 새 집계·보관·객체 정리를 중단한다. 재개 시 상세 복구는 계속 동작한다.
- `BACKUP` 없음 또는 운영 환경이 아님: 예약 보관은 건너뛴다.
- 정리 오류가 발생하면 그 실행에서 다음 보관 대상으로 넘어가지 않고, 다음 예약 실행이 다시 시도한다.
- 마이그레이션을 먼저 적용하고 API를 배포한다. 최초 운영 실행은 무조건 30일 관찰이므로 배포 직후 상세 로그를 비우지 않는다.
- 배포/운영 마이그레이션은 이 PR 작성 작업에 포함되지 않는다.

## 검증 근거

로컬 Miniflare의 실제 D1/R2로 유예 기간, 보호 조건, 압축 원본, 성적 보존, 소유권 복구,
동시 업로드, R2 실패, 재실행, 참조 없는 객체 정리를 검증한다. 실제 웹/앱 시즌·은퇴 HTTP 경로도 회귀 검증한다.
운영 데이터 정리나 실기기 화면 검증을 수행한 것으로 해석하지 않는다.
