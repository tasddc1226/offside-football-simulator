# 인프라 용량 보호 (T-11-150)

## 조회

- 구단주 시즌 결산 선수단은 `careers_profile_status_legend_idx`를 지정한다. 마감 시각으로 전체 은퇴 커리어를 훑지 않고 해당 구단주의 선수만 읽는다. 시즌·숨김·마감 기준과 정렬은 그대로다.
- 공개 명예의 전당의 이름 검색 없는 인원 집계는 `careers_hof_count_idx` 커버링 인덱스로 처리한다. 큰 스냅샷 열이 있는 테이블 페이지를 읽지 않는다. 이름 검색은 기존 경로다.
- 명예의 전당 목록의 소급 보정이 끝난 경우에만 요청별 D1 Sessions API를 사용한다. 첫 목록 조회는 `first-primary`로 원본을 읽고, 이후 집계·검색 순위는 그 북마크 이상을 반영한 복제본을 사용할 수 있다. 실제 배치는 Cloudflare가 결정하며 항상 복제본으로 가는 것은 아니다.
- 인증·권한 확인·상태 변경·상세의 숨김 확인은 원본 DB를 계속 사용한다. 요청 사이에 북마크나 사용자 상태를 공유하지 않는다. 기존 엣지 캐시 정책과 응답 형태는 그대로다.
- 긴급 중지: `D1_READ_SESSIONS_DISABLED=1`.

## 이벤트 원본 보관

기존 5분 cron에서 시간당 한 번 실행한다. 업로드 후 7일 지난 `career_seasons.events_json`만 R2로 옮긴다. 이 열은 업로드 선택 로그이며 게임 재개·공개 기록·부정행위 재검사에서 조회하지 않는다. 진행 중·은퇴 커리어 모두 대상이지만 선수나 시즌 행은 삭제하지 않는다.

- 위치: `season-events/<env>/<UTC 날짜>/<고유 ID>.ndjson.gz`.
- 한 줄: `version: 1`, `careerId`, `year`, `createdAt`, `events` 원본.
- 요약·스냅샷·잠재력·`signals_json`·`growth_json`은 유지한다. 휴면 커리어의 30일 관찰/90일 보관 정책도 바꾸지 않는다.
- R2 멀티파트 완료 뒤 ID·연도·생성 시각·이벤트 값이 모두 같은 행만 `[]`로 비운다. 실패·동시 재전송은 새 값을 보존한다. 다시 올라온 과거 이벤트는 다음 실행 대상이다.
- SQL 안에서 페이지를 약 512KiB로 제한하고 최대 200행을 읽는다. 1행이 목표보다 크면 그 행만 처리한다. 큰 값이 많으면 후보 행 수도 줄여 반복 스캔을 제한한다.
- 시간당 최대 100페이지, 목표 약 50MiB; 60초 뒤 새 페이지를 시작하지 않는다. 남은 것은 다음 시간에 처리한다. 16분 임대로 중복 실행을 막고 성공 후 `cron:season-events:last`에 합계만 저장한다.
- 보관 파일은 매일 백업의 30일 정리 대상이 아니다. 백업과 함께 보존한다. 분석에서는 같은 선수·연도의 여러 업로드를 구분하고 중복 집계하지 않는다. 진행 중 재전송이 가능하므로 보관 파일 전체를 운영 DB에 덮어쓰지 않는다.
- 긴급 중지: `SEASON_EVENTS_ARCHIVE_DISABLED=1`. 이미 보관된 객체는 지우지 않는다.

## 백업

SQL/gzip 복구 형식과 보존 기간은 그대로다. D1 응답을 만들기 전에 SQL에서 실제 UTF-8/BLOB 크기로 페이지를 약 4MiB로 제한한다. 1행이 목표보다 크면 그 행만 읽는다. 작은 표는 최대 2,000행까지 늘리고 큰 표는 후보 수를 줄인다. SQL은 한 행씩 압축 스트림에 흘린다. R2 조각 업로드 실패는 읽기 스트림을 취소하고 멀티파트를 중단한다.

전체 백업은 기존처럼 여러 쿼리의 라이브 데이터 사본이며 트랜잭션 스냅샷은 아니다. 일관된 특정 시점 복구는 D1 Time Travel을 사용한다. 이벤트·성장·휴면 상세가 별도 R2로 이동한 후의 SQL 백업은 해당 보관 파일도 함께 보존해야 전체 원본 분석이 가능하다. 복구 방법은 [D1 백업](d1-backup.md)을 따른다.

## 자동 점검과 경보

매시 정각의 기존 cron이 `cron:infra-health:last`에 용량·증가 추세·최근 작업 상태를 기록하고 `job: infra-health` 로그를 남긴다. 운영 D1에서 허용되지 않는 `page_count`/`freelist_count` 대신 응답의 `meta.size_after`를 읽는다. 재사용 가능한 페이지도 포함된 물리 용량이며, 보관으로 즉시 파일 크기가 줄어드는 것은 아니다.

경보 조건:

- 보수적으로 잡은 10GB 예산의 70% 이상 사용.
- 최소 24시간, 최대 7일의 관측 증가율로 잔여 기간이 30일 이하. 배포 첫날의 짧은 간격으로 예측하지 않는다.
- 매일 작업 기록이 없거나 26시간 이상 오래됨, 매일 작업 실패, 완료된 백업 키 없음, 또는 R2 HEAD에서 완료된 백업 객체를 확인할 수 없음.
- 보관이 켜졌는데 성공한 이벤트 보관 결과가 없거나 2시간 이상 오래됨.

GitHub `Production infrastructure health`는 매시 17분에 main에서만 실행하고 기존 저장소 Secrets의 Cloudflare 자격 증명으로 이 상태 한 건을 SELECT한다. 보고서가 2시간 이상 오래되거나 경보가 있으면 Actions 작업이 실패한다. DB/API 실패도 정상으로 간주하지 않는다. 원본 응답·계정 데이터·토큰은 출력하지 않고 작업 요약에 용량과 경보 코드만 남긴다. 알림 수신은 GitHub Actions 알림 설정을 따른다. 별도 메일·푸시·Slack 발송은 추가하지 않는다.

배포 후 최초 정각 cron과 뒤따르는 Actions 실행을 확인해야 운영 연결 검증이 끝난다. 이후 한 번 이상의 성공한 새 백업과 보관 전후 증가율도 확인한다. 이 PR만으로 운영 부하 감소율이나 미래 트래픽 처리량을 보장하지 않는다.

## 검증

Miniflare의 실제 D1/R2로 인덱스 실행 계획·응답 유지·큰 한글/BLOB 백업과 빈 D1 복구·멀티파트 경계·업로드 실패와 동시 재전송·원본 인증 경로·임대/중지·시간당 상태 기록을 검증한다. 모니터링 스크립트는 성공/오래된 보고서/권한 오류를 별도 테스트한다. 원격 DB 쓰기나 수동 운영 보관은 구현 검증에 필요하지 않다.
