# App push delivery through Cloudflare Queues

All production Expo sends and receipt checks execute inside a Cloudflare Queue consumer.
HTTP requests and cron tasks publish delivery IDs, never Expo tokens or message content.

## Ownership and timing

- `PUSH_QUEUE` / `offside-push-production` handles news, personal events, reminders and manual tests.
- Each message contains at most 80 IDs, keeping scoped D1 claims below 100 SQL parameters.
- D1 delivery rows remain the transactional outbox and idempotency/result ledger. They cannot be
  removed safely: business writes and Cloudflare Queue publication have no shared transaction.
  The existing five-minute cron republishes committed due work after failed or interrupted publishing.
  Cron never sends to Expo, including during Queue outages.
- Ordinary personal events keep their existing five-minute publication cadence. News, career cohorts,
  cup final results and operator community events attempt publication immediately after commit.
- A consumer claims only its message's IDs. It preserves consent, session/token ownership, unread state,
  quiet hours, per-profile budgets, expiry, bounded retries and unknown-send handling.
- Accepted sends schedule delayed Queue receipt checks. Duplicate/future wakeups do not fork more jobs.
  A missed continuation is recovered by the cron publisher. Pending quiet-hour work is also republished
  by cron; it is not retried once a minute by the consumer.
- Existing cup/career/admin queue bindings and consumers are retained to drain messages published by the
  previous release. Producers prefer PUSH_QUEUE; legacy consumers still send only within Queue events.
- Manual tests return `accepted: true` after Queue publication (not after Expo acceptance). Their
  original device/profile cooldown and daily budget are reserved before enqueueing. A failed/ambiguous
  Queue publish returns 503 and cancels the pending row, with no direct-send fallback. The Queue job
  contains only the delivery ID and requested locale. Receipt confirmation is not device receipt proof.

## Deployment prerequisites

This change does not provision resources or deploy by itself. Before deploying the new Worker:

1. Create `offside-push-production` and `offside-push-production-dlq` in the same account.
2. Set both Queue retention periods to 1,209,600 seconds (14 days), and verify the DLQ has no consumer.
3. Apply migration `0111_empty_kabuki.sql` (notification source-key lookup index), then deploy the checked-in production Wrangler config: batch size 1, concurrency 1, retries 3,
   dead-letter queue `offside-push-production-dlq`. Other existing queues keep their settings.
4. Verify the binding and health workflow's new DLQ inventory before enabling normal traffic.
5. Observe Queue age/backlog/DLQ plus push_results accepted/confirmed/failed/unknown, split by kind.
   Run an explicitly authorized own-device test and verify both its receipt and actual device arrival.

Rollback: redeploy the prior Worker; retain the queues and D1 records. Its existing cron can recover
normal delivery rows, but the old code does not send newly queued pending manual tests. Cancel those
pending manual tests before rollback or let them expire; never replay `sending`/`unknown` rows.
Do not purge queues or remove legacy bindings until all in-flight messages are accounted for.

## Validation

Integration tests use local D1 and stub Expo responses, including Queue duplicate delivery, consent/token
changes, quiet hours, 429 backoff, ambiguous transport, interrupted leases, receipt checks, manual-test
localization and fail-closed publishing. A separate workerd/Miniflare test exercises a real Queue binding.
No production messages or real-device pushes are generated by these tests.
