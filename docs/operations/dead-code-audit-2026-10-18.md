## 실제 정리와 보존 근거

- `apps/web/src/ui/team/TeamPicker.svelte`, `apps/mobile/src/screens/owner/TeamPicker.tsx`: import·문자열 로드·라우트 등록이 없다. 현재 `Team`은 `TeamLineup`의 라커룸에서 편성한다. 공유 `pickSorts`도 두 구형 파일만 사용했다. production 분석에서는 기존 후보 계산 `pickCandidates`와 `pct`, 관련 타입도 이 구형 모달의 테스트만 참조함을 추가 확인해 전용 테스트와 함께 제거했다. 실제 라커룸의 후보 계산·정렬·편성은 유지했다.
- `apps/mobile/src/screens/owner/RecapCard.tsx`: `HonorChip` 포함 외부 소비자가 없다. 현재 구단주 기록은 `OwnerArchive`/`SeasonRecap`에서 제공한다. 이 파일만 쓰던 `recapCardView`와 그 전용 테스트 1개도 제거했다. 실제 결산·배지·읽음 상태·공유 로직은 유지했다.
- `getCareerOwner`, `storedSeasonOvr`: 전체 저장소에 호출이 없다. 현재 라우트가 쓰는 `careerHeadQuery`, `seasonOvrQuery`는 다른 조회와 batch로 실행한다. 삭제는 운영 쿼리 횟수나 소유권 검사를 바꾸지 않으며, 낡은 주석만 실제 헤더 조회에 맞췄다.
- 나머지 미사용 정의: `draftRetireAt`, `founderLabel`, `titleGradeNote`, `WRITE_KEYS`, `PLAYER_NUDGE_MS`, `AVATAR_H`, `PRICE`, `baseMastery`, `ACH_CATEGORY_NAME`, 앱 UI `Divider`. 백업은 기존 코드대로 `ft_save`·`ft_hof`만 쓰고, 감독 숙련은 실제 `masteryXp`에서 계산한다. 상수를 삭제하며 허용 키나 감독 결과를 바꾸지 않았다.
- 사용되지 않는 재수출: 웹 helpers의 `pushEvLog`/`seasonLabel`, creditRoll의 `ROLL_SPEED`, shareCard의 크기 상수, app-core의 `TITLE_GRADES`/`TEAM_PRESET_MAX`, mobile UI barrel의 미사용 alias. 실제 원본 구현과 직접 import 소비자는 유지했다. API `app`의 쓰이지 않는 default alias도 제거했다.
- 팀 초안은 `packages/app-core/src/teamDraft.ts`의 순수 저장소 어댑터로 합쳤다. 웹은 `sessionStorage`, 앱은 기존 MMKV `kv`를 그대로 사용한다. `ft_team_draft_v1:` 키, JSON 구조, 이름 입력 중 빈 문자열, 서버 schema 검증, 저장 실패 시 deep-copy 메모리 fallback, 팀 전적을 제외한 충돌 기준을 보존했다. 생성 시 저장소 I/O가 없고 브라우저 전역 접근도 콜백 안에 있어 SSR에서 안전하다.
- 하드코딩 문구 기준선은 제거·이동된 코드에 맞춰 내렸다. 새 사용자 문구나 release note는 없다(`release-notes: none`).

## 삭제하지 않은 기능과 우선순위

활성 기능의 이용률 자료 없이 '불필요한 기능'이라고 판정해 제거하지 않았다. 팀 라커룸과 구형 선택 모달처럼 **동일 기능의 대체 경로가 이미 있고 호출이 끊긴 구현**을 실제 제거 대상으로 삼았다.

1. **구형 일일 실행 경로(P1)**: `cron/daily.ts:runDaily`, `cron/backup.ts:backupToR2`는 production 분석에서 테스트 전용으로 남는다. 현재 cron은 단계별 `runDailyTick`/백업 tick을 사용하지만 일부 회귀 테스트와 운영 문서는 옛 경로를 기준으로 한다. 먼저 현재 tick 경로로 테스트를 이관하고 수동 복구 계약을 확인한 뒤 제거해야 한다. 테스트를 함께 지워서 깨끗하게 보이게 만들지 않는다.
2. **Push receipt 처리 공통화(P1)**: `push/dispatch.ts`와 `push/personal.ts`의 receipt 조회·만료·DeviceNotRegistered 처리 구간이 실제로 겹친다. 공지/개인 알림의 lease·재시도·보존 기한·최종 DB 반영은 다르다. 다음 작업에서는 순수 receipt 결과 해석/transport만 공통화하고 만료·429/5xx·누락 receipt·해제된 기기·동시 실행 회귀를 먼저 고정한다. 알림 기능 자체를 합치거나 삭제할 근거는 없다.
3. **댓글·랭킹·공유 UI 부품(P2)**: 게시판/팀 댓글의 CommentAct, 두 랭킹 화면의 정렬·로드 상태, RecapShare/TeamShare의 capture 수명 관리가 반복된다. UI 부품/순수 컨트롤러 단위 통합 후보이며 각 화면의 권한·페이지네이션·스크린리더·capture 해제 시점은 유지해야 한다. 기능 중복과 구현 중복을 구별한다.
4. **Radar/TrainRadar·미니게임(P2)**: 그림 요소는 반복되지만 읽기 전용 능력치와 훈련 터치, 접근성, 좌표계/애니메이션이 다르다. 작은 SVG 공통 부품은 가능하나 하나의 화면으로 대체하지 않는다.
5. **Agents 역할별 도구 루프(P2)**: 공통 진행/실패 처리 추출 후보. 역할별 도구 허용·일정·출력 계약을 유지한 테스트가 필요하다. 같은 텍스트 구조만으로 에이전트 기능을 줄이지 않는다.
6. **Push 번역 연결(P2, 별도 기능 수정)**: `api/i18n/en/communityPush.ts`, `ja/communityPush.ts`는 미참조지만 현재 community push가 ko를 직접 import한다. 번역 쌍은 보존했다. 수신자 언어 전달·fallback을 설계해 연결할 문제이며, 미사용 번역 삭제로 해결하지 않는다.
7. **네이티브 의존성(P3)**: Expo config의 `expo-build-properties`, 폰트 패키지/네이티브 모듈을 위한 `expo-font`·`expo-system-ui`는 JS import만으로 사용 여부를 판정할 수 없다. mobile `sharp`, `@offside/tsconfig`도 직접 사용 근거가 약하지만 toolchain·native fingerprint 확인 후 별도 의존성 정리로 처리한다. 이번 작업에서는 manifest/lockfile/native 설정을 수정하지 않았다.
8. **옛 계약/백필(P3)**: 기존 품질 점검 문서에 남은 `linked.toss`, `toss_anon_key_hash`, 일회성 백필은 저장 데이터·구버전 클라이언트·운영 완료 표시 확인이 필요하다. 이번 소스 감사에서 제거 안전성을 입증하지 않았고, 해당 항목이 지금도 미처리인지는 별도 운영 조회가 필요하다.

웹/앱의 nav·인증·avatar는 플랫폼 차이를 담당한다. 서버 시뮬레이션과 클라이언트 재생, D1 migration/서로 다른 응답 schema, 독립 실행 실험 스크립트도 비슷하다는 이유로 통합하지 않았다. 특히 계약 타입·번역 키·오래된 save migration은 실행 중인 기능이나 저장 포맷과 연결될 수 있다.
