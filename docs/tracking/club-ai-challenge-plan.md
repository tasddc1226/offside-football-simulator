# T-11-222: 은퇴 카드로 즐기는 AI 구단 챌린지

상태: 기획 제안 · 문서-only draft PR. 구현·DB 변경·판매·배포 승인이 아니다.
작성: 2026-10-12. 적용 시즌: 미정. 시즌 1 중 시범 도입 가능성을 검토하되 검증 전 개막일을 약속하지 않는다.

## 문제와 유저 니즈

사용자의 “콘텐츠가 적다”는 피드백은 분석 출발점이다. 콘텐츠 수 부족이 이탈 원인이라는 결론이나 기존 콘텐츠 이용률 저조의 증거는 없다. 이미 업적, 친선전, 컵, 팀 프리셋, 승부 예측이 있다. 먼저 발견 여부와 실제 사용을 나누어 측정한다.

검증할 가설은 은퇴 뒤 카드와 팀을 얻었지만 시즌 도중 스스로 정할 소규모 목표가 부족하다는 것이다. 육성 결과를 다시 써 보고, 높은 OVR 선수와 자리에 맞는 선수를 비교하고, 다음에 키울 역할을 찾는 경험을 제안한다. 접속 시간을 늘리기 위한 일일 숙제가 목표가 아니다.

주 대상은 은퇴 카드를 얻어 팀 편성을 시작한 구단주와 이미 팀이 있지만 공식 경쟁 외의 목표를 원하는 유저다. 입문은 직접 키운 은퇴 카드 1명을 실제 선발에 넣고 나머지를 유스로 채워 가능하게 한다. 아직 은퇴하지 않은 유저에게는 현재 상태를 설명한다. 육성 진행을 강제로 중단시키는 팝업이나 반복 알림은 두지 않는다.

## 첫 버전의 경험

시즌 중 원하는 때 AI 상대 약 3팀에 각각 도전한다. 연속 3승이 아니라 상대별 독립 승리로 완료를 기록한다. 순서와 이전 상대 승리 여부로 잠그지 않는다. 정규 경기 승리만 클리어다. 무승부는 미클리어로 표시하고 승부차기·연장전은 추가하지 않는다. 3팀 모두 이기면 전체 완료 기념을 남긴다.

구단주 → 내 팀의 “구단 챌린지” → 상대 목록 → 상대 강점·편성 조건·내 완료 상태 → 챌린지 전용 편성 → 자리별 실력·시너지 확인 → 경기 시작 → 문자 중계·결과 → 편성 비교 또는 재도전 순서다. 화면 문구는 예시이며 구현 때 공통 ko/en/ja 사전과 `copy-style.md`를 따른다.

편성은 공식 랭킹·컵 선발과 완전히 분리한다. 공식 팀을 복사하거나 기존 5개 프리셋을 읽어 초안으로 가져올 수 있지만 저장·불러오기로 공식 팀 PUT을 호출하지 않는다. 전용 편성의 저장 여부와 미저장 표시를 명확히 한다. 상대 강점, 기본 승리 조건, 선택 조건은 시작 전에 모두 공개한다. 한 번의 패배에 “잘못된 선수”라고 단정하지 않고 난수의 영향과 실제 편성 차이를 함께 보여 준다.

모바일은 상대·조건·시작 버튼이 한 화면에서 읽히는 단순 구조로 설계한다. 선수 선택은 기존 카드 표시와 편성 도구를 재사용한다. 320px/390px, 터치 영역 44pt, 하단 메뉴에 저장 버튼이 가리지 않는지 구현 단계에서 검증한다. 이번 PR에는 화면 구현과 시각 검증이 없다.

이 이름과 난이도·OVR은 저작 초안이다. 상대가 특정 전술에 무조건 지거나 내 카드에 맞춰 몰래 강해지는 보정은 없다. 선택 조건은 보상·입장·다음 상대 해금에 영향을 주지 않는 도전 표시다. 조건을 못 맞춰도 기본 승리는 유효하다.

엔진이 지원하는 전술은 포메이션·자유 배치의 자리/좌표·자리별 실력·공격/중원/수비/GK 줄 힘·기존 시너지로 제한한다. 압박, 수비 라인 높이, 점유율 지시, 맨마킹, AI의 경기 중 전술 변경은 구현돼 있다고 쓰지 않는다. AI는 공개한 고정 합성 라인업을 입력하며 새 능력치나 유형을 만들지 않는다. 3팀 공통으로 `simulateMatch(..., season, { neutral: true })`를 제안해 기존 홈 이점을 제거한다.

## 편성 자격과 공정성

로그인한 현재 서비스 시즌의 구단주가 서버에서 소유한 은퇴 카드만 넣는다. 최소 1명은 본인이 직접 육성한 은퇴 카드여야 하며 실제 11명 선발 중 한 자리에 있어야 한다. 구매한 카드만으로 입문 조건을 충족할 수 없다. 나머지 자리에는 현재 소유한 구매 카드도 허용한다. 중복 카드 ID, 비은퇴·숨김·미래 시즌 카드는 거절한다. 과거 모든 시즌의 카드 합계는 공식 팀과 같이 3명까지다. 프리시즌 카드 1명으로도 입문 가능하다. 남은 자리는 고정 유스로 채우고 유스가 시너지를 만들지 않는 현행 규칙을 유지한다.

카드 실력은 현행 `slotRating` 및 과거 카드 fallback을 따른다. 높은 OVR이 유리할 수 있지만 적합 자리와 시너지의 실제 이점이 의미 있는지 구현 전에 비교 검증한다. 기존 리롤·강화·스카우트 등 유료 아이템으로 얻은 카드 차이는 그대로 반영하므로 완전 동일 전력 경쟁이라고 홍보하지 않는다. 공개 랭킹·PvP 보상은 없고 입문 상대는 무구매 카드 1명+유스 표본으로 검증한다. 유료 재시도·확률 배수·챌린지 전용 강화·능력치 파밍·월구독 필수 조건은 없다.

컵 경기 1시간 잠금 중에도 챌린지 전용 편성과 경기는 허용한다. 이 편성은 컵 명단을 바꾸지 않고 카드를 소모하거나 강화하지 않는다. 카드의 기존 거래/방출/컵 잠금은 그대로 지킨다. 출품 중 카드는 첫 버전에서는 신규 챌린지 선발에 넣지 않는다. 사용자 보호용 카드 잠금은 사용 금지가 아니므로 현행 편성 가능한 카드이면 챌린지에도 허용하되 거래·방출을 풀지 않는다.

## 경기·난수·재도전·보상

첫 버전은 서버 단일 경기 계산을 재사용한다. 경기 시작은 의도적인 버튼 입력이다. 재요청·타임아웃·동시 탭은 같은 멱등 키로 같은 attempt/seed/result를 받는다. 명시적인 새 시도만 새 서버 난수를 받는다. 클라이언트가 경기 ID·시드·승패·보상을 지정하지 못한다. 승인 직후 결과를 계산·저장하므로 중계 종료나 앱 종료로 나쁜 결과를 폐기할 수 없다. 중계 다시 보기는 저장 결과 재생이며 새 시도가 아니다.

새 시도에는 서버 생성 무작위 attempt ID를 시드 입력으로 고정하고 시작 때 전체 라인업·시즌·엔진 버전을 동결한다. 원본 `simulateMatch`의 결정성은 같은 ID와 전체 입력을 쓸 때만 성립한다. 시드를 미리 노출하지 않고 완료 후에도 클라이언트 예측 API를 제공하지 않는다. 같은 편성 반복도 허용하지만 승리를 얻을 때까지 난수만 돌리는 행동이 콘텐츠 중심이 되지 않도록 완료 후 추가 경제 보상 없이 편성 변경·줄 힘·시너지 비교를 유도한다. 난수 운으로도 승리 가능하다는 점을 숨기지 않는다.

하루 숙제나 소진 재화 없이 자유 재도전한다. 비용 방어용 초기 가정은 구단주당 새 시도 10초 간격, 활성 attempt 1개, 분당 최대 6회다. 이는 공개 일일 도전 횟수가 아니라 과다 요청 제한이며 한도·안내는 부하 검증 뒤 확정한다. 동일 멱등 키는 rate limit 때문에 결과 복구를 막지 않는다. 결과와 조건 판정은 한 번만 계산하고 완료 요청은 읽기만 한다.

첫 클리어 기념은 상대별 완료 표시와 3팀 완료 기념 기록으로 한정한다. 거래 가능한 재화, 아이템, 공식 업적점수·레이팅·컵 칭호는 지급하지 않는다. 보상/완료 고유키는 `(ownerId, challengeSetId, opponentId 또는 all)`로 한다. 계정 전환·기기 교체·재도전·시즌 전환·같은 set의 content version 수정으로 재지급하지 않는다. 전혀 다른 후속 set의 기념은 별도 승인 사항이다. 선택 조건 달성 기록은 같은 조건 ID로 upsert하며 경제 보상은 없다.

## 서버 권위와 API·데이터 개념

다음은 구현 계약 초안이며 이 PR은 엔드포인트·테이블·마이그레이션을 추가하지 않는다.

| API 개념                                | 역할                                                                              |
| --------------------------------------- | --------------------------------------------------------------------------------- |
| `GET /v1/club-challenges/catalog`       | 공개 상대·조건·버전 목록. 인증 불필요, `edgeCached`, 저작 변경 시 `purgeEdge`     |
| `GET /v1/club-challenges/me?season=...` | 내 완료·초안·최근 attempt를 한 번에. 세션 필요, 개인 응답, 화면 열 때 `cachedGet` |
| `PUT /v1/club-challenges/lineup`        | 공식 팀 PUT과 분리. revision 비교로 동시 편집 충돌을 반환                         |
| `POST /v1/club-challenges/attempts`     | 멱등 키와 opponent/version/revision을 받고 서버 자격·스냅샷·시드·결과 확정        |
| `GET /v1/club-challenges/attempts/:id`  | 본인 저장 경기와 완료/기념 상태 복구. 결과 제출 POST는 두지 않음                  |

개념 데이터는 `ChallengeSet/Version`(공개 상대 합성 입력·조건·engine version), `ChallengeLineup`(구단주/시즌/revision), `Attempt`(멱등 키·시즌·버전·전체 snapshot·result·상태), `Completion/RewardLedger`(고유키)로 분리한다. 최신 카드 ID만 저장하면 이후 거래·삭제·규칙 변경으로 재계산이 달라지므로 11자리 능력·roles/fallback·유형·주발·국적·raised·좌표·유스·적용 시너지·neutral·상대 전체 입력을 불변 스냅샷에 담는다. 공개/비공개 선수명 원문과 계정 메일은 담지 않고 표시 시 안전한 이름 정책을 적용한다.

시작 때 소유·은퇴·시즌·와일드카드 수·직접 육성 선발·출품 상태와 초안 revision을 원자적으로 검증한 뒤 snapshot/attempt를 만든다. 거래와 시작이 경합하면 DB 조건부 쓰기 또는 원자적 batch의 직렬화 기준으로 먼저 성공한 작업을 따른다. 읽고 계산한 뒤 무조건 INSERT하는 TOCTOU 방식은 허용하지 않는다. 같은 키의 동시 시작은 유일 제약으로 1건만 생성하고 payload가 다르면 409다.

경기 뒤 거래·방출은 기존 제약대로 가능하며 완료 결과는 snapshot으로 유지한다. 다음 시도는 현재 소유를 재검증하고 사라진 카드는 초안에서 비운 뒤 사용자 확인을 받는다. challenge lineup에 넣었다는 이유로 새 영구 거래 잠금을 만들지 않는다. 기존 공식 팀·컵의 방출/거래 제약은 우선한다.

결과·완료·기념 원장은 원자적으로 확정하는 것이 목표다. 부분 실패를 피할 수 없다면 attempt의 pending/settled 상태와 동일 키의 복구 작업으로 결과를 재사용해 빠진 원장만 채운다. Queue 재전달이나 서버 재시작으로 재보상하지 않는다. 소유·스냅샷·멱등성 계약을 거래·방출 담당 코드와 검토할 수 없으면 구현 착수를 보류한다.

## 저장 호환·시즌·버전·장애

챌린지는 서버 개인 기록으로 분리하고 기존 `GameState`·은퇴 카드 능력·공식 팀 저장 포맷을 바꾸지 않는다. 구형 앱은 추가 기능을 표시하지 않아도 기존 저장을 계속 읽는다. 편성 로컬 초안은 계정·서비스 시즌·set·version별 캐시로 격리하고 복구 코드나 localStorage 삭제로 서버 완료를 초기화하지 않는다. 저장 포맷을 실제 바꾸는 후속 구현은 `packages/game/src`의 대응 마이그레이션이 필수다.

신규 시도의 시즌은 서버 승인 시각으로 결정한다. 시즌 마감 전 승인된 경기는 옛 시즌과 스냅샷으로 끝내고 중계 중 경계를 넘어도 그대로 조회한다. 마감 이후 옛 시즌 신규 시작/초안 저장은 `SEASON_CLOSED`로 거절하며 새 시즌 초안으로 복사 후 자격을 다시 검증한다. 미래 카드 금지·과거 카드 3명은 새 시즌 기준으로 다시 센다. 동일 set 완료 기념은 시즌이 바뀌어도 유지한다. 공식 시즌 결산·랭킹에는 들어가지 않는다.

set/version과 engine version을 attempt에 고정한다. 공개된 진행 버전을 조용히 재밸런싱하지 않는다. 결함 수정은 새 version으로 신규 시도만 전환하고 기존 결과·기념은 보존한다. 버전 교체 중 오래된 화면의 신규 시작은 갱신 안내와 409를 반환한다. 치명적 오류는 신규 시작만 중단하고 기존 결과 조회·보상 복구는 유지한다. 기존 버전 결과를 현재 엔진으로 재계산하지 않는다.

오프라인에서는 캐시된 상대·초안·결과만 읽고 경기 시작/공식 보상 판정을 하지 않는다. 연결 복구 때 서버 초안 revision과 진행 attempt를 확인한다. 응답 유실은 같은 키로 복구하며 새로운 키를 자동 생성하지 않는다. 다른 계정 attempt 조회는 거절한다. 429는 기다릴 시각을, 409는 버전·소유·초안 충돌 이유를, 장애는 재접속 복구 가능 상태를 안내한다. 로그인 만료 뒤 재로그인해도 동일 attempt를 복구한다.

목록 N+1·폴링·화면 재진입마다 refetch는 금지한다. 공개 카탈로그를 공유 캐시하고 내 상태/카드 자격은 묶어 읽는다. 카드 조회는 ID 묶음 1회, 최근 경기 목록은 페이지·개수 제한, 새 조회 조건은 인덱스와 실행계획을 검토한다. 개인 기록은 bounded retention으로 최근 상세만 보존하는 정책을 확정하고 완료·보상 원장은 유지한다. 기존 거래 제한을 회피할 수 있는 권한 혼합이나 원문 개인정보 계측은 금지한다.

## 계측과 성공·중단 기준

아래 임계치는 실측 결과가 아닌 시범 승인용 가정이다. 기존 콘텐츠 발견 개선과 함께 비교하며 초기 2주 또는 자격 유저 200명 도달 시 평가한다. 모수가 작으면 효과 결론을 유보한다.

| 이벤트                                       | 질문과 최소 필드                                                                      |
| -------------------------------------------- | ------------------------------------------------------------------------------------- |
| `club_challenge_view`                        | 자격 유저가 발견했나. entry, season, set/version                                      |
| `club_challenge_opponent_view`               | 강점·조건을 읽었나. opponent ID                                                       |
| `club_challenge_lineup_save`                 | 편성을 비교했나. revision, real-card/youth/past-card 수, 역할 적합도 구간, synergy ID |
| `club_challenge_attempt_start/settled`       | 끝까지 진행했나. attempt ID, engine version, 결과, 처리시간, 카드 수 구간             |
| `club_challenge_retry`                       | 운만 돌리는가. 같은 편성 hash 여부, 재시도 간격, 회차 구간                            |
| `club_challenge_first_clear/reward_recorded` | 기념이 중복 없이 남나. 고유 완료 ID                                                   |
| `club_challenge_error`                       | 복구 가능한가. 오류 코드, 중복 복구 여부. payload·토큰·이름 없음                      |

경제·완료 이벤트는 서버 원장 ID로 dedupe하고 클라이언트 view는 분석 동의 정책을 따른다. 원문 카드명·메일·복구 코드·계정 비밀·자유 입력은 전송하지 않는다. 직접 육성/구매 카드 여부는 집계 구간으로 보고 개인 구매 이력 원문을 옮기지 않는다.

진행 기준 가정은 자격 유저 중 25% 이상 1회 시작, 시작 유저 70% 이상 결과 확인, 직접 육성 1명+유스 입문 집단에서 3회 안에 최소 1승 비율 60% 이상이다. 편성을 바꾼 재도전 비율과 기존 육성·친선전 감소 여부를 함께 본다. 최고 OVR 조합만 택하는 행동이 지배적이면 역할 비교의 효용을 재검토한다. 7일 재방문은 보조 지표이며 챌린지로 인한 인과 효과로 단정하지 않는다.

신규 시작 즉시 중단 기준은 중복 기념 지급 1건, 소유/컵 잠금 우회 1건, 결과 변조 1건이다. p95 경기 확정 2초 초과 또는 실패율 1% 초과가 30분 지속되면 신규 시작을 제한한다. D1 read/write와 CPU/attempt를 기준선과 비교해 서비스의 다른 요청에 영향을 주면 확대를 중단한다. 수치와 관찰 창은 인프라 담당 검토 후 확정한다. 입문 실패·같은 편성 난수 반복이 높으면 난이도·안내를 수정하며 새 유료 해결책을 만들지 않는다.

## 대안과 단계별 범위

| 대안                              | 장점                                              | 비용/한계와 결정                                                                                             |
| --------------------------------- | ------------------------------------------------- | ------------------------------------------------------------------------------------------------------------ |
| 기존 콘텐츠 발견 개선             | 새 경기 모드 없이 업적·친선·프리셋·예측을 찾게 함 | 원인이 발견 문제라면 먼저 해야 한다. 동선과 계측 개선을 비교 기준으로 유지                                   |
| 팀의 부족한 역할 → 다음 육성 목표 | 선수 육성 핵심 루프와 직접 연결                   | 카드 현황 분석만으로도 가능. 이번 결과에 실제 자리 실력·시너지를 보여 주고 자동 육성 추천/확정 최적해는 후속 |
| 친구 미니 리그                    | 지인과 반복 경쟁                                  | 초대·일정·탈퇴·공정성·승부 조작·알림 운영이 커진다. 첫 범위에서 제외                                         |
| 소규모 AI 챌린지                  | 자율 접근, 일정/타인 대기 없이 카드 재사용        | 새 API·완료 원장·상대 저작 필요. 3팀과 기념 기록으로 제한                                                    |

0단계: 기존 콘텐츠 이용/발견 기준선을 수집하고 본 기획의 규칙·거래 원자성·서버 비용·적용 시즌을 검토한다. 이번 문서 PR은 여기까지다.

1단계: 합성 상대 3팀, 독립 승리, 전용 편성, 서버 snapshot/멱등성, 첫 완료 기념, 무구매 입문 경로를 구현한다. 구현 PR에서 단위·통합 검증, 동시 탭/거래 경합/시즌 경계/복구 테스트와 웹·앱 모바일 검증을 한다. 밸런스 검증은 그때 승인된 범위에서 수행한다.

2단계: 소규모 시범 공개와 계측으로 진행/중단을 결정한다. 상대 추가, 조건 기록 확대, 부족 역할 안내는 관찰 뒤 별도 범위로 제안한다. 감독 커리어, 시즌 리그, PvP 랭킹, 친구 리그, 전술 엔진 확대는 포함하지 않는다.

## 미결정 사항과 구현 전 게이트

- 적용 서비스 시즌과 공개일, 시범 대상·모수·기간. 시즌 중 밸런스 변경 금지 원칙과 분리된 AI 저작 난이도 승인.
- 3팀의 최종 합성 능력·배치·이름과 무구매 입문 승리 확률. 표는 난이도 보장 데이터가 아니다.
- 선택 조건의 최종 ID와 공개 설명, 기념 기록 표시 위치. 공식 업적점수와 섞지 않는 계약.
- 새 시도 과다 요청 제한의 실제 수치, 최근 경기 보존 개수/기간, 개인정보 삭제 시 익명 기록 처리.
- 소유 검증과 거래 원자성, 상태 전이/원장 유일 제약/인덱스, 콘텐츠·엔진 버전 보존 방식.
- 과거 카드 missing roles·type·foot·raised의 fallback 검증, 구형 앱 호환, 실제 ko/en/ja 문구.
- 실제 출시 직전 웹/API/스토어/설치 앱 배포 SHA·버전 재확인. 미배포 #649·#609와의 의존은 없음.

기획 승인과 구현 승인·운영 배포 승인은 별개다. 이 문서는 비공개 이용자 메일·개인정보·세션 로그를 사용하거나 복제하지 않았다.
