## 문제·유저 니즈와 기존 콘텐츠의 차이

가설은 시즌 전체 업적보다 짧고 오늘 한 경기보다 긴 선택 목표가 팀에 연속성을 줄 수 있다는 것이다. 모드가 하나 더 생겨 기존 경기를 반복해야 하는 숙제를 만들지 않는다. [구단주 과제·칭호](../owner-quests-and-titles-plan.md), [시즌 결산](../owner-season-recap-plan.md), [명예관](../owner-profile-honors-plan.md)과 목표·표시 보상이 겹친다. 현행 업적은 시즌별 점수·등급에 연결되므로 별도 점수 체계를 복제하지 않고 **선택한 기간의 이야기·증거 목록**을 더하는 안이다.

#656의 NPC 경기와 달리 신규 경기 모드를 만들지 않는다. 기존 리그·컵·친선전 결과를 읽기만 한다. 프로젝트 선택이 RP 매칭·컵 참가 조건·공식 명단에 개입해서는 안 된다.

## 핵심 루프와 화면 흐름

내 구단 → 프로젝트 후보(인정 경기·기한·현재 자격·기념 전시물) → 하나 선택 → 진행 띠/이번 경기 기여 → 기존 리그·컵·친선전 플레이 → 기록 확정 후 기여 반영 → 완료 역사 페이지 또는 기한 종료 기록. 진행 상세에는 “확정/동기화 대기/이 자료로 확인 불가”가 나뉜다. 강제 팝업·매일 접속·실패 알림은 두지 않는다.

**제안값:** 한 번에 1개, 기간 2~3주. 예시 A는 “직접 키운 선수 6명 이상 선발로 인정 경기 10회”, 예시 B는 “선택 선수의 새 팀 경기 득점 20골”이다. 수치·기간·인정 경기 종류는 검증 전 후보다. 특정 선수의 원래 선수 커리어 통산 골에 팀 경기 골을 합치지 않는다. 팀 경기 통산을 택하면 별도 명칭·원장으로 표시한다. 현역 선수 커리어 통산 기록 목표는 신뢰할 수 있는 업로드 증분이 필요한 후속 후보로 둔다.

## MVP·후속 범위

MVP는 직접 육성 선발 기용 한 유형, 시작 이후 확정된 리그·컵·친선전의 중복 없는 기여, 진행/종료 요약, 구단 역사 전시물이다. 세 경기 종류를 모두 필수로 요구하지 않아 컵 탈락·리그 미참가 이용자도 가능한 목표를 제공한다. 각 경기 종류의 저장된 명단에서 raised/선수 참조를 입증할 수 있는지 먼저 확인한다. 입증 불가능한 종류는 일단 제외하고 이를 사전에 표시한다.

후속은 특정 선수 별도 통산, 포지션 육성 프로젝트, 구단 역사 타임라인·전시물 배치다. 현재 경기 상세는 경기 종류별로 달라 프로젝트용 정규화 이벤트 어댑터가 필요하다. 모든 기존 경기를 이미 한 스트림으로 받을 수 있다고 가정하지 않는다. 매칭/RP 경기의 프로젝트 기여는 첫 MVP에서 제외하고 RP 파밍 유인을 피한다.

## 규칙·실패·중단·재시도 경계

- 선택 시 목표 버전·기간·인정 mode·소유/육성 정의를 고정한다. 시작 이전 경기 소급은 하지 않는다. 경기 수락 시점이 프로젝트 기간 안이고 서버에서 정상 확정된 경기만 인정하는 안을 제안한다. 마감 직전 시작 경기의 정산 유예는 별도 고정한다.
- 승리뿐 아니라 정상 완료 참가도 셀 수 있다. 자동 리그의 실제 출전/확정 명단만 인정하고 신청·빈 팀·몰수 경기는 세지 않는다. 무승부도 참가 조건에는 포함한다. 원래 결과를 프로젝트가 수정하지 않는다.
- 같은 선수란 이름이 아닌 careerId다. 직접 육성은 careers.profileId와 프로젝트 소유자 일치이며 구매 카드는 육성 인원으로 세지 않는다. 나중에 판매해도 이미 인정된 기여는 유지하고 다음 경기에는 당시 소유·실제 출전을 검증한다.
- 친구와 반복 경기로 쉬운 기여를 쌓는 것을 줄이기 위해 친선전은 같은 상대 하루 1경기만 인정하는 초안을 제안한다. 현행 친선 입장 횟수를 바꾸는 규칙이 아니라 프로젝트 집계 상한이다. 다계정 공모를 완전히 식별할 수 있다는 주장은 하지 않는다.
- 중도 포기는 역사에 중단으로 남고 기념 보상은 없다. 다른 목표로 바꾸면 기존 프로젝트는 포기 확정이며 진행도를 이전하지 않는다. 재선택은 새 projectId·새 기간, 같은 테마 보상은 중복 지급하지 않는다. 보류 중 시간은 서버 달력 기준으로 흐르되 매일 접속 조건은 없다.
- 실패는 기한 내 미달이다. 일부 기여 기록은 보존하고 다음에 강제로 초기 목표를 올리지 않는다. 이벤트 누락 복구 기간에는 “확인 중”으로 두고 실패를 확정하지 않는다.

## 모드별 데이터·이벤트 제안

`ProjectDefinition(id, version, objective, allowedModes, reward)`, `ClubProject(profileId, startsAt, endsAt, cutoffPolicy, status)`, `ProjectContribution(projectId, sourceMode, sourceMatchId, metric, amount, evidenceVersion)`, `ProjectHistory`를 둔다. 유일키는 `(projectId, sourceMode, sourceMatchId, metric)`이며 결과 정정은 기존 기여의 취소/대체 이력으로 처리한다. 단순 누적 UPDATE만 남기면 재전달·정정 때 복구가 안 된다.

경기 확정 트랜잭션 뒤 전달 가능한 이벤트를 쓰거나 원장 cursor 기반 제한된 catch-up을 제안한다. 새 사용자 화면마다 전 경기 스캔·매 경기 모든 프로젝트 스캔은 피한다. `(profileId, status)`, `(projectId, sourceMode, sourceMatchId)` 인덱스와 큐 중복 처리·백필 경계를 구현 설계에서 정한다. 기존 경기 확정 실패를 프로젝트 부가 집계 실패 때문에 유발하지 않는다.

API는 `/v1/club-projects/catalog`, `/me`, `/select`, `/:id/history`, `/:id/abandon` 제안이다. 이벤트 `project_selected`, `project_contribution_accepted`, `project_contribution_reversed`, `project_ended(reason)`를 사용한다. 보상 고유키는 `(profileId, projectThemeId, milestoneId)`로 원장에 남긴다. 팀 역사에는 프로젝트 기간·조건·기여 선수 익명 참조·완료/중단만 남기고 원 커리어 기록과 구분한다.

## 데이터·서버 경계와 공통 오류 계약 제안

이 절과 아래 엔티티·API·이벤트 이름은 **신규 설계 제안**이다. 현재 존재하는 API처럼 호출하지 않는다. 서버가 정의 버전·참가 자격·전체 경기 입력·시드·성공 판정·표시 보상을 확정한다. 선수 커리어는 로컬 기원이라는 현행 한계가 있어 서버 저장 카드만으로 원 육성의 진위를 완전히 증명할 수 없다. 그래서 MVP는 비거래·비성능 보상이며 의심 신호만으로 자동 제재하지 않는다.

새 경기 생성 요청은 `(profileId, idempotencyKey)` 유일키와 payload hash를 갖는다. 같은 키·같은 입력은 같은 결과를 반환하고 다른 입력은 409다. 시작 시 소유권·거래 상태·정의 버전·편성 revision을 조건부 쓰기와 함께 검증한다. 읽은 뒤 무조건 저장하는 방식으로 거래 경합을 처리하지 않는다. 경기 ID·시드는 서버가 만들고 결과를 먼저 저장하므로 앱 종료·재전송으로 패배를 버리거나 다시 굴리지 못한다. 서버 검증 실패는 시도를 소비하지 않는다. 이미 수락된 시도는 요청이 끊겨도 조회로 복구한다. 원자적 확정에 실패하면 pending 상태와 동일 키 복구로 한 번만 마감하며 결과를 다시 계산하지 않는다.

전체 입력 스냅샷에는 11자리·좌표·실력/roles와 fallback·유형·주발·국적·raised·유스·감독 효과·시너지·모드 보정·상대 입력·규칙/엔진 버전을 포함한다. 기존 `matchDetailOf`의 줄 요약만으로 재현된다고 가정하지 않는다. 입력 hash만 저장해 원본이 사라지는 설계도 피한다. 옛 엔진을 실행할 수 없으면 저장 결과만 보여 주고 새 버전 재계산으로 순위를 섞지 않는다. 경기 중 압박·맨마킹·전술 교체는 현행 기능이 아니므로 MVP 성공 조건으로 쓰지 않는다.

일반 서버 과다 요청 제한, 본인 결과 조회 권한, 동시 편집 revision 검사는 필요하다. 정확한 요청 한도·보관 기간은 부하와 개인정보 검토 후 결정한다. 재시도 제한이 같은 키의 결과 복구를 막아서는 안 된다. 로그·계측에는 선수명·메일·채팅·세이브·팀 스냅샷 원문을 넣지 않고 콘텐츠 ID·버전·익명화된 집계 식별자·상태·오류 코드만 남긴다. 공개 이름은 현행 공개 동의·숨김·삭제 정책을 따른다.

목록은 열 때만 로드하고 웹 `cachedGet`을 사용한다. 공개 정의·집계는 세션 조회 없는 `edgeCached`, 변경 시 `purgeEdge`; 개인 진행은 개인 응답으로 분리한다. 목록마다 선수 상세를 N번 받지 않는다. 새 필터·정렬은 limit과 인덱스를 함께 설계한다. 반복 폴링·클라이언트 전체 이력 스캔을 MVP 전제로 두지 않는다.

## 경제·보상·공정성의 기본 제안

MVP 보상은 완료 기록·비거래 전시물·꾸미기다. 능력치·잠재력·카드 강화·구단 자금·리롤/강화/스카우트권·RP·기존 업적점수는 지급하지 않는다. 확률 보상, 재화 입장료, 유료 재도전, 구독으로 조건 완화·기여 배수는 제안 범위에 없다. 이 원칙을 바꾸려면 경제 영향과 기존 보상 중복을 별도로 승인받는다. 보상은 아래 고유키와 서버 원장으로 한 번만 지급하고 표시 재생은 지급이 아니다. 익명 프로필의 복구 한계를 안내하고 타 프로필 자동 병합을 전제하지 않는다. MVP 서버 기록 쓰기는 로그인 구단주를 제안하되 읽기 공개 범위는 동의 기준을 따른다.

## 저장·서비스 시즌·구버전 호환

새 모드 서버 엔티티와 전용 draft를 사용한다. 기존 `GameState`·저장 RNG·`care`·`boost`·원 은퇴 수치·카드 소유권·공식 팀 선발·컵/리그 고정 명단·friendlyJson을 덮어쓰지 않는다. 후속 구현에서 로컬 저장을 추가하면 선택 필드/별도 namespace와 `packages/game/src/save.ts`의 이전 저장 마이그레이션을 검증한다. 기존 저장을 읽지 못할 때 새 저장으로 교체하지 않는다.

신규 API는 분리하고 구형 앱의 strict 응답 스키마에 새 필드를 억지로 끼우지 않는다. 미지원 앱은 신규 모드 진입만 숨기고 기존 게임은 유지한다. 시즌 경계는 서버 시각과 서버 일정으로 판정한다. 정의 변경은 이미 수락된 입력·목표·보상 버전을 고정하고 진행 중 난도를 조용히 바꾸지 않는다. 긴급 중단은 신규 시작만 먼저 막고 기존 결과 조회·미지급 복구는 열어 둔다. 계정 삭제 시 개인 귀속 기록을 삭제/비식별 처리하는 기존 정책을 따르며 영구 전시는 개인정보 영구 보존을 뜻하지 않는다.

## 모바일 화면 수용 원칙

기존 OFFSIDE 토큰·타이포·카드와 경기 리포트를 유지하고 새 전역 디자인 체계는 만들지 않는다. 한 화면의 주 행동은 조건 확인 후 시작/이어하기 하나로 둔다. 조건 미달 이유와 대체 선수를 시작 전에 읽을 수 있게 하고 색만으로 통과를 구분하지 않는다. 320/390px에서 가로 넘침·하단 메뉴/안전 영역에 가린 버튼·가려진 키보드 포커스가 없어야 한다. 터치 목표 44px/pt 이상을 제안하고 스크린리더 라벨·글자 확대·움직임 줄이기를 검증한다. 웹 키보드로 편성 대체 조작이 가능해야 하며 드래그만 강요하지 않는다.

서버 대기는 기존 LoadState 뼈대, 빈 기록은 조건 설명, 오류는 재시도와 복구 상태를 보인다. 패배와 시스템 오류를 구분한다. UI 예시 문구는 구현 단계에 `copy-style.md`와 ko/en/ja 사전으로 확정한다. 이번 문서 작업에서 화면 구현·브라우저·기기·게임 플레이 검증은 실행하지 않는다.

## 적용 시즌과 단계 제안

여러 주가 필요한 목표이므로 시즌 종료까지 남은 기간이 충분한 시점에만 선택을 연다. 첫 시범은 시즌 2 중반 이후, 충분한 기간이 없으면 시즌 3 후보로 미룬다. MVP는 시즌을 넘는 진행을 받지 않고 종료 후 전시물만 유지한다. 향후 시즌 횡단 목표는 별도 버전과 인정 규칙이 필요하다.

## 대안과 선택 이유

현행 업적에 목표 핀만 더하면 구현은 작지만 기간별 구단 역사를 검증하지 못한다. 별도 신규 경기 모드는 병행 목표라는 취지와 다르다. 기존 업적 UI를 재사용하는 선택 프로젝트를 추천하며 증거 가용성이 낮으면 먼저 목표 핀만 시범 도입한다.

## 성공 지표: 가설과 실제 관측 구분

**실제 관측:** 사용자 요청, 위 코드 구조와 PR 상태뿐이다. 이 모드의 이용률·만족도·잔존율·개선 폭은 아직 관측하지 않았다. 기존 문서의 과거 운영 수치를 신규 모드 효과의 근거로 전용하지 않는다.

**검증 가설과 측정 설계:** 후보 노출 대비 선택률, 선택 뒤 첫 인정 경기까지 도달률, 기여가 발생한 서로 다른 날 수, 기한 완료/중단/집계 대기 비율, 직접 육성 선수의 유효 출전 다양성을 본다. 신규 게임 이용이 늘었는지 기존 경기만 보상이동했는지 구분하고 친선 상대 집중도·리그 참여 감소도 함께 확인한다.

제안 관찰창은 시범 2주이고 표본이 적으면 연장한다. 참여자만의 잔존율을 전체와 단순 비교해 인과 효과라고 쓰지 않는다. 출시 전 참여 노출·자격·동의·비교군/단계적 공개 계획과 판정 문턱을 정한다. 원정/과제/재시작 세션 중복을 제거하고 오류 중단과 자발적 중단을 나눈다. 구매·플레이 시간을 늘리는 것을 단독 성공 기준으로 삼지 않는다. 수치 목표·확정 효과는 아직 없다.

## QA·수용 조건 (후속 구현 시, 현재 미실행)

- 선택 전 경기·시작 시각이 범위 밖인 경기·몰수는 집계되지 않고 정상 무승부는 참가 목표에 포함된다.
- 같은 matchId 재전달과 결과 정정이 누적치를 중복·음수로 만들지 않는다.
- 구입 카드를 직접 육성으로 세지 않고 카드 판매 뒤 과거 기여를 지우지 않는다.
- 친선 동일 상대 일일 상한이 프로젝트에만 적용되고 친선 플레이 권한·횟수는 바뀌지 않는다.
- 특정 선수의 선수 커리어 통산과 프로젝트 팀 경기 지표가 섞이지 않는다. 마감 후 catch-up은 정의된 기한까지만 가능하다.

- 같은 키 재전송·동시 탭·두 기기·응답 유실에서도 결과/보상이 한 번이다. 타인 결과 수정·임의 성공 제출은 거절된다.
- 판매/방출/감독 전향과 시작 경합, 카드 중복·숨김·누락 roles·옛 상세 누락을 검증한다. 실패 시 공식 팀을 바꾸지 않는다.
- 시즌 마감 직전/정각/직후, 정의 교체, 구버전 앱, 진행 중 중단·계정 복구·삭제를 검증한다.
- 기존 커리어 세이브·골든 결과·RP·디비전·리그 순위·컵 명단·친선 기록/횟수·아이템 원장이 모드 외에 변하지 않는다.
- 공개 GET의 세션 불필요, 반복 진입 캐시, N+1 없음, 집계/목록 한도와 인덱스, 개인정보 없는 계측을 확인한다.

## 미결정 사항과 구현 진입 조건

2~3주 기간, 인정 경기별 실제 증거 가용성, 정상 참가와 몰수 구분, 친선 공모 억제 수준, 마감 정산 유예, 테마 보상 재획득 주기, 특정 선수 통산을 어느 원장으로 정의할지, 사용자 중단 이력 공개 여부.

조건별 입증 가능한 데이터, 원자적 결과/보상 확정, 장애 복구, 경제 보상 제외, 웹·앱 동시 규칙 제공을 검토한 후 별도 구현 승인을 요청한다. 기획 PR 병합만으로 구현이나 운영 변경을 시작하지 않는다.
