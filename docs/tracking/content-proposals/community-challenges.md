## 문제·유저 니즈와 기존 콘텐츠의 차이

가설은 자기 팀을 다른 사람이 다른 제한으로 풀어 보는 즐거움과 편성 아이디어 공유에 수요가 있을 수 있다는 것이다. 기존 친선전은 현재 팀과 일대일 경기이고 RP는 자동 매칭 경쟁이다. 도전장은 **공개 시점 팀 스냅샷과 검증 가능한 프리셋**을 고정해 언제든 공략한다. 현재 팀 변경·카드 매각이 공개 도전장의 난도를 몰래 바꾸지 못한다.

#656의 NPC/전용 편성/서버 성공 기록과 겹치지만 제작자·공개 수명·콘텐츠 검증/신고·통계 조작 방어가 추가된다. [팀 프리셋 공통 코드](https://github.com/tasddc1226/offside-football-simulator/blob/8615586b81e5e7f727528e78365f684c4898ad66/packages/app-core/src/teamPresets.ts)는 개인 편성 저장 참고이고 공유 가능한 도전장 엔티티가 이미 있다는 근거는 아니다. 감독 퍼즐과 조건식 개념은 공유할 수 있으나 별도 PR의 미구현 검사기에 의존하지 않고 이 문서만으로 요구사항을 정의한다.

## 핵심 루프와 화면 흐름

제작: 내 팀 → “도전장 만들기” → 공개 스냅샷 확인 → 출전 조건/성공 조건 프리셋 → 검증·시험 결과 → 공개 범위/삭제 안내 → 공유 링크.

공략: 링크/목록 → 버전·상대·조건·표본 수·성공률 → 전용 편성(임대 대안 포함) → 조건 확인 → 서버 경기 → 기록/조건 리포트 → 재도전 또는 공략 편성 공유. 제작자 보유 카드명과 도전자 비공개 이름을 무단 공개하지 않는다. 미지원 버전·삭제된 도전장은 이유와 목록으로 돌아가기를 제공한다.

## MVP·후속 범위

MVP는 초대 링크 공개, 계정당 활성 도전장 소수(제안 3개), 허용된 프리셋만, 불변 팀 snapshot, 서버 시도·성공률·개인 기록, 신고/비공개/종료다. 자유 텍스트 제목은 초기 자동 조합명으로 대체하는 안을 우선 제안한다. 발견 피드·댓글·추천 경쟁은 후속으로 둬 공개 UGC 운영 부담을 제한한다.

출전 프리셋은 선발 자리 실력 상한·포지션 그룹 최소/최대·국적 수 제한, 성공은 90분 승리·득점 이상·실점 이하의 명시적 AND 조합만 제안한다. 임의 코드·스크립트·자연어 판정·클라이언트 성공 신고는 허용하지 않는다. 점유율·패스 등 없는 정본 수치는 지원하지 않는다. 제작자 검증은 합법적 공략 입력의 존재 확인이며 성공 가능성을 수학적으로 보증하지 않는다.

후속은 검토된 탐색 목록·선정전·공략 조합 비교다. 제작 보상·다운로드 보상·좋아요 보상·성공 수에 비례한 재화·상금은 MVP에 없다. “공모”를 콘텐츠 공모전으로 해석하더라도 선정전 보상은 별도 승인 대상이며, 계정 간 담합 공모도 아래처럼 방어한다.

## 규칙·실패·중단·재시도 경계

- 제작 시 서버 현재 소유와 출전 자격을 검증하고 11자리·감독·효과·전체 규칙을 복제한다. 정식 컵/리그 고정 명단은 수정하지 않는다. 현재 소유 이후 판매는 기존 공개 도전장의 snapshot에 영향을 주지 않으며 신규 생성은 재검증한다.
- 제작자가 카드·조건·이름을 바꾸면 새 version이고 구버전 시도·성공률은 따로 남는다. 오류 수정이라고 구버전 기록을 새 버전에 합치지 않는다. 제작자 자기 도전은 test 범주로 통계/명예에서 제외한다.
- 첫 유효 시도 성공률은 `(다른 로그인 프로필의 최초 정산 성공 수)/(그 프로필의 최초 정산 시도 수)`다. 전체 시도 성공률은 별도 수치이며 두 값을 섞지 않는다. 재생·시작 전 거절·시스템 오류는 분모에서 빼고 정상 패배·수락 후 이탈은 정산 결과로 포함한다. 표본 수와 집계 시각을 함께 표시하고 작은 표본은 순위화하지 않는다. 최소 표시 표본은 미정이다.
- 출전 미달은 시작 전 실패, 무승부는 승리 프리셋에서 미달이다. 수락 시드·조건·snapshot은 고정되고 앱 종료로 시도/분모를 삭제하지 못한다. 새 시도는 자유 재도전하되 경제 보상은 없다.
- 제작자 비공개/삭제는 새 시작을 막고 이미 수락한 본인 결과는 가능한 범위에서 복구한다. 선수 숨김·개인정보 삭제 요구 시 snapshot의 공개 식별자를 제거한다. 링크만 아는 공개도 유출될 수 있음을 발행 전에 안내한다.
- 명예는 본인 완료 표시·전시 배지 중심이다. 제작/성공 횟수로 무한 꾸미기 자산을 주지 않는다. 지나치게 쉬운 도전장·교대 승리·다계정 서로 성공시켜도 거래 가능한 이익이 없다. 중복 snapshot/조건 hash로 복제 목록을 묶고 요청 상한·신고/숨김을 둔다. IP/기기 추정만으로 동일인 판정·영구 제재를 하지 않는다.

## 모드별 데이터·이벤트 제안

`CommunityChallenge(challengeId, creatorId, visibility, status)`, `ChallengeVersion(version, sourceSnapshot, entryPredicate, successPredicate, engineVersion, contentHash, publishedAt)`, `CommunityAttempt(profileId, test, snapshot, result)`, `FirstOutcome(challengeVersionId, profileId)`, `ChallengeStats`, `Report`를 제안한다. 최초 결과는 서버 정산 순서로 한 건만 확정하고 동시 두 시도의 먼저 수락된 attempt를 기준으로 할지 구현 전에 정한다. 추천안은 최초 수락 attempt 기준으로 두고 정산 지연으로 바뀌지 않게 한다.

API 개념 `/v1/community-challenges`(POST), `/:id/versions`(POST), `/:id`(GET/공개 종료), `/:id/attempts`(POST), `/attempts/:id`, `/:id/report`다. 수정 가능한 범위와 작성자 권한 검사를 모든 쓰기에 둔다. 공개 링크 ID는 추측 어려운 식별자를 쓰되 개인 기록 인가는 별도로 검증한다. 서버 검사기의 enum·범위·조건 개수/조합 제한을 계약으로 둔다.

이벤트 `challenge_draft_validated`, `challenge_published`, `community_attempt_settled`, `community_first_outcome`, `challenge_reported`, `challenge_hidden`을 제안한다. 통계 재집계는 attempt와 최초 결과 원장으로 복원한다. 공개 원본 snapshot과 계측용 통계를 분리하며 실제 선수명·개인별 전적 목록을 분석 로그에 담지 않는다. 기념 고유키 `(profileId, challengeId, milestoneId)`로 버전 수정·복제·재시도 파밍을 막고, 글로벌 배지는 별도 고정된 모음 목표로만 검토한다.

## 데이터·서버 경계와 공통 오류 계약 제안

이 절과 아래 엔티티·API·이벤트 이름은 **신규 설계 제안**이다. 현재 존재하는 API처럼 호출하지 않는다. 서버가 정의 버전·참가 자격·전체 경기 입력·시드·성공 판정·표시 보상을 확정한다. 선수 커리어는 로컬 기원이라는 현행 한계가 있어 서버 저장 카드만으로 원 육성의 진위를 완전히 증명할 수 없다. 그래서 MVP는 비거래·비성능 보상이며 의심 신호만으로 자동 제재하지 않는다.

새 경기 생성 요청은 `(profileId, idempotencyKey)` 유일키와 payload hash를 갖는다. 같은 키·같은 입력은 같은 결과를 반환하고 다른 입력은 409다. 시작 시 소유권·거래 상태·정의 버전·편성 revision을 조건부 쓰기와 함께 검증한다. 읽은 뒤 무조건 저장하는 방식으로 거래 경합을 처리하지 않는다. 경기 ID·시드는 서버가 만들고 결과를 먼저 저장하므로 앱 종료·재전송으로 패배를 버리거나 다시 굴리지 못한다. 서버 검증 실패는 시도를 소비하지 않는다. 이미 수락된 시도는 요청이 끊겨도 조회로 복구한다. 원자적 확정에 실패하면 pending 상태와 동일 키 복구로 한 번만 마감하며 결과를 다시 계산하지 않는다.

전체 입력 스냅샷에는 11자리·좌표·실력/roles와 fallback·유형·주발·국적·raised·유스·감독 효과·시너지·모드 보정·상대 입력·규칙/엔진 버전을 포함한다. 기존 `matchDetailOf`의 줄 요약만으로 재현된다고 가정하지 않는다. 입력 hash만 저장해 원본이 사라지는 설계도 피한다. 옛 엔진을 실행할 수 없으면 저장 결과만 보여 주고 새 버전 재계산으로 순위를 섞지 않는다. 경기 중 압박·맨마킹·전술 교체는 현행 기능이 아니므로 MVP 성공 조건으로 쓰지 않는다.

일반 서버 과다 요청 제한, 본인 결과 조회 권한, 동시 편집 revision 검사는 필요하다. 정확한 요청 한도·보관 기간은 부하와 개인정보 검토 후 결정한다. 재시도 제한이 같은 키의 결과 복구를 막아서는 안 된다. 로그·계측에는 선수명·메일·채팅·세이브·팀 스냅샷 원문을 넣지 않고 콘텐츠 ID·버전·익명화된 집계 식별자·상태·오류 코드만 남긴다. 공개 이름은 현행 공개 동의·숨김·삭제 정책을 따른다.

목록은 열 때만 로드하고 웹 `cachedGet`을 사용한다. 공개 정의·집계는 세션 조회 없는 `edgeCached`, 변경 시 `purgeEdge`; 개인 진행은 개인 응답으로 분리한다. 목록마다 선수 상세를 N번 받지 않는다. 새 필터·정렬은 limit과 인덱스를 함께 설계한다. 반복 폴링·클라이언트 전체 이력 스캔을 MVP 전제로 두지 않는다.

## 경제·보상·공정성의 기본 제안

MVP 보상은 완료 기록·비거래 전시물·꾸미기다. 능력치·잠재력·카드 강화·구단 자금·리롤/강화/스카우트권·RP·기존 업적점수는 지급하지 않는다. 확률 보상, 재화 입장료, 유료 재도전, 구독으로 조건 완화·기여 배수는 제안 범위에 없다. 이 원칙을 바꾸려면 경제 영향과 기존 보상 중복을 별도로 승인받는다. 보상은 아래 고유키와 서버 원장으로 한 번만 지급하고 표시 재생은 지급이 아니다. 익명 프로필의 복구 한계를 안내하고 타 프로필 자동 병합을 전제하지 않는다. MVP 서버 기록 쓰기는 로그인 구단주를 제안하되 읽기 공개 범위는 동의 기준을 따른다.

## 저장·서비스 시즌·구버전 호환

새 모드 서버 엔티티와 전용 draft를 사용한다. 기존 `GameState`·저장 RNG·`care`·`boost`·원 은퇴 수치·카드 소유권·공식 팀 선발·컵/리그 고정 명단·friendlyJson을 덮어쓰지 않는다. 후속 구현에서 로컬 저장을 추가하면 선택 필드/별도 namespace와 `packages/game/src/save.ts`의 이전 저장 마이그레이션을 검증한다. 기존 저장을 읽지 못할 때 새 저장으로 교체하지 않는다.

신규 API는 분리하고 구형 앱의 strict 응답 스키마에 새 필드를 억지로 끼우지 않는다. 미지원 앱은 신규 모드 진입만 숨기고 기존 게임은 유지한다. 시즌 경계는 서버 시각과 서버 일정으로 판정한다. 정의 변경은 이미 수락된 입력·목표·보상 버전을 고정하고 진행 중 난도를 조용히 바꾸지 않는다. 긴급 중단은 신규 시작만 먼저 막고 기존 결과 조회·미지급 복구는 열어 둔다. 계정 삭제 시 개인 귀속 기록을 삭제/비식별 처리하는 기존 정책을 따르며 영구 전시는 개인정보 영구 보존을 뜻하지 않는다.

## 모바일 화면 수용 원칙

기존 OFFSIDE 토큰·타이포·카드와 경기 리포트를 유지하고 새 전역 디자인 체계는 만들지 않는다. 한 화면의 주 행동은 조건 확인 후 시작/이어하기 하나로 둔다. 조건 미달 이유와 대체 선수를 시작 전에 읽을 수 있게 하고 색만으로 통과를 구분하지 않는다. 320/390px에서 가로 넘침·하단 메뉴/안전 영역에 가린 버튼·가려진 키보드 포커스가 없어야 한다. 터치 목표 44px/pt 이상을 제안하고 스크린리더 라벨·글자 확대·움직임 줄이기를 검증한다. 웹 키보드로 편성 대체 조작이 가능해야 하며 드래그만 강요하지 않는다.

서버 대기는 기존 LoadState 뼈대, 빈 기록은 조건 설명, 오류는 재시도와 복구 상태를 보인다. 패배와 시스템 오류를 구분한다. UI 예시 문구는 구현 단계에 `copy-style.md`와 ko/en/ja 사전으로 확정한다. 이번 문서 작업에서 화면 구현·브라우저·기기·게임 플레이 검증은 실행하지 않는다.

## 적용 시즌과 단계 제안

작성·검증·신고 운영과 통계 무결성 부담이 가장 크므로 시즌 3 이후 초대 링크 시범 후보로 둔다. 구단주 시즌과 원 snapshot 시즌을 따로 저장한다. MVP는 현재 서비스 시즌에서만 새로 시작할 수 있게 하고 시즌 경계 종료/결과 조회 기간을 게시 전에 고정한다. 이후 영구 퍼즐 보관은 구버전 엔진 지원 정책이 있어야 한다.

## 대안과 선택 이유

현재 친선 공유는 가장 작지만 불변 상대·제한 조건·성공률이 없다. 운영자 제작 퍼즐만 제공하면 운영 위험은 작지만 제작 수요를 검증하지 못한다. 링크 전용 제한 프리셋을 먼저 추천하고 공개 피드는 신고·중복·통계 기준이 충족된 뒤 검토한다.

## 성공 지표: 가설과 실제 관측 구분

**실제 관측:** 사용자 요청, 위 코드 구조와 PR 상태뿐이다. 이 모드의 이용률·만족도·잔존율·개선 폭은 아직 관측하지 않았다. 기존 문서의 과거 운영 수치를 신규 모드 효과의 근거로 전용하지 않는다.

**검증 가설과 측정 설계:** 유효 초안 대비 공개율, 공개 도전장 중 제작자 외 첫 공략 도달률, 조건 위반/신고/숨김 비율, 유효 공략자 기준 성공률 분포와 재도전 편성 변화, 중복 콘텐츠 비중을 본다. 제작자 자기 도전·동일인 의심 신호·작은 표본은 별도로 표시하고 성공률을 난도의 확정치로 쓰지 않는다. 탐색 피드 전에는 링크 전달 기반의 선택 편향을 명시한다.

제안 관찰창은 시범 2주이고 표본이 적으면 연장한다. 참여자만의 잔존율을 전체와 단순 비교해 인과 효과라고 쓰지 않는다. 출시 전 참여 노출·자격·동의·비교군/단계적 공개 계획과 판정 문턱을 정한다. 원정/과제/재시작 세션 중복을 제거하고 오류 중단과 자발적 중단을 나눈다. 구매·플레이 시간을 늘리는 것을 단독 성공 기준으로 삼지 않는다. 수치 목표·확정 효과는 아직 없다.

## QA·수용 조건 (후속 구현 시, 현재 미실행)

- 공개 후 원 팀 변경/판매/이름 변경이 고정 경기 입력을 바꾸지 않는다. 공개 이름 철회는 별도 반영된다.
- 제작자 시험·시작 전 거절·중계 재생은 성공률 분모에서 제외되고 정상 실패·수락 후 종료는 결과대로 포함된다.
- 두 기기 최초 시도 경합과 정산 순서 역전에도 최초 결과 선정 기준이 바뀌지 않는다.
- 조건 수정은 새 version 통계이며 옛 성공을 새 조건 달성으로 표시하지 않는다.
- 쉬운 복제 도전장·교대 성공·같은 버전 반복으로 재화/꾸미기를 무한 획득하지 않는다.
- 신고·공개 종료·계정 삭제·구버전 엔진 미지원에서도 이미 수락한 결과의 조회와 개인정보 정책을 지킨다.

- 같은 키 재전송·동시 탭·두 기기·응답 유실에서도 결과/보상이 한 번이다. 타인 결과 수정·임의 성공 제출은 거절된다.
- 판매/방출/감독 전향과 시작 경합, 카드 중복·숨김·누락 roles·옛 상세 누락을 검증한다. 실패 시 공식 팀을 바꾸지 않는다.
- 시즌 마감 직전/정각/직후, 정의 교체, 구버전 앱, 진행 중 중단·계정 복구·삭제를 검증한다.
- 기존 커리어 세이브·골든 결과·RP·디비전·리그 순위·컵 명단·친선 기록/횟수·아이템 원장이 모드 외에 변하지 않는다.
- 공개 GET의 세션 불필요, 반복 진입 캐시, N+1 없음, 집계/목록 한도와 인덱스, 개인정보 없는 계측을 확인한다.

## 미결정 사항과 구현 진입 조건

활성 3개 상한·공개 수명, 최소 통계 표본, 최초 수락 시도 정의, 임대 풀 제공 범위, 자유 제목/신고 운영 인력, 불가능 조건 검증 강도, 중복 hash 범위, 전시 배지 단위와 공개 철회 후 기록, 엔진 구버전 지원 기간.
