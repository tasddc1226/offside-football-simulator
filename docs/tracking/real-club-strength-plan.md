## 1. 목표와 단계

목표는 게임 속 NPC 구단의 전력이 현실 성적을 닮게 하는 것이다. 처음 안은 "매일 순위표를 자동 수집해 일별 전력 팩 발행"이었으나, 1인 운영 부담과 출처 권리가 불확실한 점, 그리고 **현재 게임이 구단별 전력을 상대 경기에 쓰지 않는다는 점**을 근거로 단계안으로 바꾼다. 전력 값을 현실에 맞춰도 상대가 연결되어 있지 않으면 체감이 없다.

| 단계 | 내용                                                         | 상태                       |
| ---- | ------------------------------------------------------------ | -------------------------- |
| 1    | 상대 구단 연결 (T-11-134): 시즌 상대·경기 승률·순위표 연결   | 구현 중                    |
| 2    | 한 리그(K1 추천) 현실 순위표 → 월 1회 운영자 전력표(JSON)    | 기획, 출처 확인 후 착수    |
| 3    | 반응이 좋으면 출처 계약·리그 확대·갱신 주기 단축·일별 자동화 | 후보, 2단계 결과 보고 결정 |

대상은 선수 커리어의 현실 구단 모델 `Club.str`이다. 구단주 유저 팀의 카드·배치 기반 `packages/contracts/src/owner-team.ts:teamOvr`, `apps/api/src/team/sim.ts:lineupOvr`, PVP 레이팅·매칭·선수 OVR은 변경하지 않는다. 현실 경기 결과의 자동 게시, 실시간 능력치 변경, 실제 일정 전체 재현, 대표팀·컵·친선 성과, 현실 승강의 기존 커리어 소급 적용은 이번 범위 밖이다.

### 1단계: 상대 구단 연결 (T-11-134, 구현 중)

현재 `packages/game/src/engine.ts:newSeason`의 `season.rivals`는 `L.avg + gauss()*L.spread`로 만든 숫자 19개로 실제 NPC 구단과 무관하고(`engine.ts:194`), `packages/game/src/match.ts:rollResult`는 내 구단 str와 리그 평균 차이만 본다(`match.ts:132`). 1단계는 다음을 바꾼다.

- 시즌 상대를 리그의 실제 구단으로 정한다. 전력은 구단 `str` 기반이며 시즌 폼 편차를 더한다.
- 리그 경기마다 상대 구단을 정하고, 승률에 상대 전력을 반영한다.
- 순위표의 팀 이름·전적을 해당 구단과 직접 연결한다.
- 평균 밸런스(우승·주전·성장 분포)는 기존과 맞추고 `tooling/fulltime-sim`으로 비교 검증한다.
- 옛 저장은 다음 시즌부터 적용한다(시즌 중 `rivals` 보존). RNG 소비 수·순서를 보존한다.

1단계가 끝나면 `CLUBS.str`를 바꾸는 순간 상대 난도와 순위표에 바로 반영되므로 2단계는 전력 값만 갈아 끼우면 된다.

### 2단계: 한 리그 월 1회 전력표

- 한 리그(K1 추천)부터 현실 순위표로 전력표를 만든다. 순위 번호만 쓰면 소화 경기 차이에 흔들리므로 경기당 승점·득실차를 쓴다(4절).
- 매일 자동 서버 파이프라인은 두지 않는다. 월 1회 정도 운영자가 스크립트로 전력표(JSON)를 만들어 코드로 배포한다(웹 배포 + OTA).
- 기존 커리어는 다음 가상 시즌 시작 때 채택한다(BAL 채택과 같은 원칙).
- 출처 권리는 착수 전 사용자가 약관을 확인한다(법적 판단이 아님).

### 3단계: 확대 검토

반응이 좋으면 출처 계약, 리그 확대, 갱신 주기 단축을 검토한다. 일별 자동 발행·manifest·롤백·오류 경보는 이때 설계한다(5절 후보). 현실 승강에 맞춘 리그 구성 갱신(PL 2026-27 차이 등)은 별도 검토 항목으로 남긴다.

## 2. 모든 게임 구단이 현실 팀과 1:1인가?

### 가장 작은 매핑 관리

기존 게임 ID·배열 순서는 그대로 두고 작은 CSV/JSON 대응표 `gameClubId, sourceCompetition, sourceSeason, sourceTeamKey, officialName, aliases, reviewedAt, status`만 유지한다. 출처 stable ID가 있으면 sourceTeamKey로 사용하고 없으면 검토한 이름 키와 별칭을 명시한다. 순위나 fuzzy 이름 유사도로 자동 확정하지 않는다. 같은 도시·2군·상무는 구분한다.

현재 리그에서 미대응/강등/해체된 게임 구단은 기존 직접 정의 전력 또는 마지막 허가된 정상 전력을 유지하고 이유를 남긴다. 승격·신생 현실 구단은 자동 게임 콘텐츠 추가 없이 대기 목록으로 둔다. 사용자가 모든 현실 참가 팀을 게임에 맞추고 싶다면 새 팀 추가·기존 ID 보존·옛 저장 소속 처리를 별도 범위로 결정한다. 개명은 동일 팀인지 확인 후 별칭만 추가, 합병/재창단은 새 정체성 검토가 필요하다. 시즌이 바뀔 때 대응표와 제외 목록만 다시 검토하는 정도로 시작한다.

**현재 `CLUBS.str`만 덮는 것으로는 NPC 상대 경기 전력이 현실 값으로 바뀌지 않는다.** 그래서 상대 연결(1단계)을 먼저 하고 전력 값 교체(2단계)를 뒤에 둔다. 2단계 구현 전에는 내 구단·시장·컵·승강 전력을 같은 버전으로 읽는 공통 `clubStrengthOf(id, careerContext)` 조회가 필요하며, 열린 시장은 재생성하지 않는다.

현재 엔진 기준은 [추적 정본](README.md)과 [풀타임 전환 ADR](../adr/ADR-013-fulltime-replacement.md)이다. 관련 기존 기획은 [K2 승격](k2-promotion-plan.md), [시즌 2 밸런스](season2-balance-plan.md), [서비스 시즌/카드](season-card-market-plan.md)이다.

## 4. 전력 계산식 (2단계, 기존 안 재사용)

입력 최소 필드: 출처/대회/현실 시즌/그룹, 팀 키, 경기 수 `P`, 승점 `Pts`, 득실차 `GD`, 조회 UTC 시각. 순위 번호는 표시/검증용이다. 경기 수가 다르므로 `PPG=Pts/P`, `GDPG=GD/P`를 쓰고 P=0은 계산하지 않는다.

```text
PPG_i = Pts_i / P_i; GDPG_i = GD_i / P_i
avgPPG = sum(Pts) / sum(P); avgGDPG = sum(GD) / sum(P)
target_i = leagueAvg + 6*(PPG_i-avgPPG) + 2*clip(GDPG_i-avgGDPG, -2, 2)
w_i = P_i / (P_i + 10)
raw_i = (1-w_i)*baseline_i + w_i*target_i
new_i = boundedChange(round(raw_i), previous_i)
```

- `baseline_i`는 현실 시즌 시작 때 고정한 기존 직접 정의값이다. 매번 previous로 바꾸면 같은 자료가 반복 누적되므로 피한다.
- 리그 평균은 매핑된 게임 팀 일부가 아니라 선택한 공식 전체 순위표로 계산한다(상무·미매핑 팀이 평균을 왜곡하지 않게).
- P<3은 기존값 유지, 이후에도 w로 완충한다. 월 1회 갱신이므로 일일 한도 대신 **갱신 1회당 한도**(제안 ±3점, 시즌 baseline 대비 ±6점)를 둔다. 리그 평균·분산의 이상 변화는 발행 보류. 6·2·10·3은 후보 계수이며 검증 후 결정한다.
- 예: 리그 평균 전력 63, 평균 PPG 1.4, 팀 P=10/Pts=20/GD=8, 평균 GDPG=0이면 target=68.2. baseline=65와 w=0.5를 혼합한 raw=66.6을 반올림해 67.
- 리그별 기존 평균/자금력/등급은 유지하고 성과는 해당 리그 안에서만 보정한다. K1 PPG 2.0과 PL PPG 2.0은 같은 절대 실력이 아니다. J1 특별대회·MLS 컨퍼런스·K1 split·승점 삭감은 출처별로 사용할 표를 정한다.
- 순위표만으로 상대 강도·홈 이점·최근 폼은 알 수 없다. 시즌 누적 성과 모델이며 "최근 폼 모델"이라 부르지 않는다.
- 새 현실 시즌에서 P/Pts/GD가 리셋되면 새 baseline을 고정한다. 정정·시즌 전환은 확인 후 새 후보를 계산하고, 무경기 기간은 마지막 값을 유지한다. 컵·친선·대표팀·유소년은 입력 제외.

## 5. 운영·오류·버전

**2단계 운영:** 운영자가 월 1회 정도 허가된 순위표 스냅샷으로 로컬 스크립트를 실행해 전력표 JSON을 만든다. 스크립트는 대회/시즌/그룹 일치, 필수 팀 누락, ID 중복/미매핑, P·Pts·GD 자료형·합계, 가능하면 Pts=3W+D 대조, 극단 변경을 검증하고 이전 값과의 diff(팀/이전/입력/혼합/최종값/제외 이유)를 출력한다. 운영자가 diff를 확인해 코드(전력표 JSON)로 커밋하며 웹 배포와 OTA로 나간다. 서버 파이프라인·클라이언트의 외부 조회·키 노출은 없다. 누락은 0점으로 채우거나 이름 유사도로 덮지 않고 해당 리그 갱신을 보류한다. 진행 중 경기의 live 표는 피하고 확정 누적표를 쓴다.

**3단계 후보(지금은 만들지 않음):** 서버에서 하루 1회 순위표 수집·검증·자동 발행, inputHash 멱등 처리, manifest(`strengthVersion, mappingVersion, formulaVersion, source, competitionSeason, cutoffUtc, inputHash, clubStrengths, exclusions, publishedAt`), 직전 정상 팩으로의 원자적 롤백, 발행/보류 로그, 단일 페이지 실패·429·스키마 변경·권리 만료 경보. 월 1회 운영에서 정정률과 운영 부담을 본 뒤 필요하면 도입한다.

## 6. 기존 커리어 채택 (2단계)

기본안은 **다음 가상 시즌 시작에 채택**이다(BAL 채택과 같은 원칙). 시즌 중 `rivals`·열린 시장·기록은 유지하고 병역/이적도 같은 채택 버전을 쓴다. 새 커리어는 시작 때 최신 전력표를 고정한다. 다음 접속/경기 구간 채택은 시즌 중 난도가 변하므로 택하지 않는다.

기존 저장의 내 구단 str·rivals·pending 제안·mil.prevClub·leagueMoves·과거 기록을 로드만으로 최신값에 덮지 않는다. 새 optional 필드와 `save.ts:migrateSave`로 전력표 버전을 관리하고 save v 변경으로 기존 저장을 버리지 않는다. 과거 기록은 당시 전력 버전을 유지한다. 팩 누락/손상/오프라인이면 마지막 유효값으로 진행하고 외부 I/O가 게임 RNG를 소비하지 않게 한다. 전력표가 코드에 포함되므로 같은 코드 버전이면 재현된다.

현실 시즌, 게임 `s.year`의 가상 시즌, 서비스 시즌 ID는 별개다. `apps/api/src/db/repos/careers.ts:firstUploadSeasonAt`은 최초 업로드 서버 시각으로 서비스 시즌을 정하므로 이전 전력표로 만든 커리어가 다음 서비스 시즌 순위에 들어올 수 있다. 순위 공정성을 위한 적용 버전 기록·cohort 표시 정책은 2단계 구현 전에 정한다.

## 8. 검증·출시·남은 결정

1. **1단계 (T-11-134):** 같은 seed로 우승·주전·성장·이적·컵·승강·병역·은퇴 점수 분포를 `tooling/fulltime-sim`으로 기존과 비교. 옛 저장 시즌 중 로드 회귀, RNG 소비 순서 보존 확인.
2. **2단계 준비:** 대응표(위 매핑)와 약관 확인 → 합성/허가 순위표로 P=0·소수 경기·정정·리셋·누락·복수 그룹·중복 검증 → 기존 전력 대비 PPG/GDPG 혼합 후보 비교(과거 시점 표만 사용해 누수 방지) → 한 리그만 도입, 전력표 JSON 배포와 다음 시즌 채택. 적용 안내·ko/en·릴리스 노트는 구현 PR에서 준비한다.
3. **3단계 판단:** 2단계 반응·운영 부담·정정률을 보고 리그 확대, 출처 계약, 주기 단축, 일별 자동화, 현실 승강 반영 여부를 결정.

수용 기준(2단계): 대응·허가 확인 100%, 빈 응답·중복 전력 오염 0, 같은 입력 재계산 동일값, 미매핑/누락 팀 격리, 옛 저장/열린 시장/병역 복원 회귀 실패 0, 밸런스 변화(주요 성취율 상대 ±5%)는 표본과 함께 경보 후보로 검토(허용치 미확정).

남은 사용자 결정: 2단계 첫 리그(K1 추천)와 출처·예산·약관 확인, 미대응 구단(상무·강등·승격팀) 처리, 계수·최소 경기·갱신당 변화 한도, 갱신 주기(월 1회 기준), 순위 cohort/공정성 정책, 3단계 착수 여부.
