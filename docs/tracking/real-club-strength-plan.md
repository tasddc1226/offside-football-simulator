## 1. 목표와 권장 최소 버전

사용자가 원하는 흐름은 **매일 현실 리그 순위표 조회 → 팀별 경기 수·승점·득실차 검증 → 경기당 성과로 전력 계산 → 정상 데이터의 일별 전력 팩 발행**이다. 승인된 출처의 순위표 스냅샷 하나로 시작하며 개별 경기 이력이나 Elo 엔진은 MVP 필수가 아니다. 순위 번호만 쓰면 같은 성적이어도 팀 수·소화 경기 차이에 따라 전력이 흔들리므로 승점/경기와 득실차/경기를 사용한다.

1인 운영에는 초기 구단 대응표를 한 번 검토한 뒤, 정상 데이터는 자동 일별 발행하고 누락·급변·매핑 변경·이용 권리 만료 등 예외만 운영자가 확인하는 방식을 권장한다. 주간 수동 승인이나 서비스 시즌 경계에서만 발행하는 것을 필수 조건으로 두지 않는다. 게임이 기존 커리어에 언제 채택할지는 수집/발행과 별도 결정이다.

대상은 선수 커리어의 현실 구단 모델 `Club.str`이다. 구단주 유저 팀의 카드·배치 기반 `packages/contracts/src/owner-team.ts:teamOvr`, `apps/api/src/team/sim.ts:lineupOvr`, PVP 레이팅·매칭·선수 OVR은 변경하지 않는다. 현실 경기 결과의 자동 게시, 실시간 능력치 변경, 실제 일정 전체 재현, 대표팀·컵·친선 성과, 현실 승강의 기존 커리어 소급 적용도 MVP 밖이다.

## 2. 모든 게임 구단이 현실 팀과 1:1인가?

### 가장 작은 매핑 관리

기존 게임 ID·배열 순서는 그대로 두고 작은 CSV/JSON 대응표 `gameClubId, sourceCompetition, sourceSeason, sourceTeamKey, officialName, aliases, reviewedAt, status`만 유지한다. 출처 stable ID가 있으면 sourceTeamKey로 사용하고 없으면 검토한 이름 키와 별칭을 명시한다. 순위나 fuzzy 이름 유사도로 자동 확정하지 않는다. 같은 도시·2군·상무는 구분한다.

현재 리그에서 미대응/강등/해체된 게임 구단은 기존 직접 정의 전력 또는 마지막 허가된 정상 전력을 유지하고 이유를 남긴다. 승격·신생 현실 구단은 자동 게임 콘텐츠 추가 없이 대기 목록으로 둔다. 사용자가 모든 현실 참가 팀을 게임에 맞추고 싶다면 새 팀 추가·기존 ID 보존·옛 저장 소속 처리를 별도 범위로 결정한다. 개명은 동일 팀인지 확인 후 별칭만 추가, 합병/재창단은 새 정체성 검토가 필요하다. 시즌이 바뀔 때 대응표와 제외 목록만 다시 검토하는 정도로 시작한다.

## 4. 일별 순위표 입력과 간단한 평가식

입력 최소 필드: 출처/대회/현실 시즌/그룹, 팀 키, 경기 수 `P`, 승점 `Pts`, 득실차 `GD`, 조회 UTC 시각. 있으면 승/무/패·득점/실점으로 교차검증한다. 순위 번호는 표시/검증용이다. 경기 수가 다르므로 `PPG=Pts/P`, `GDPG=GD/P`를 사용하고 P=0은 계산하지 않는다.

예시 제안:

```text
PPG_i = Pts_i / P_i; GDPG_i = GD_i / P_i
avgPPG = sum(Pts) / sum(P); avgGDPG = sum(GD) / sum(P)
target_i = leagueAvg + 6*(PPG_i-avgPPG) + 2*clip(GDPG_i-avgGDPG, -2, 2)
w_i = P_i / (P_i + 10)
raw_i = (1-w_i)*baseline_i + w_i*target_i
new_i = boundedChange(round(raw_i), previous_i)
```

`baseline_i`는 해당 현실 시즌 시작 때 고정한 기존 직접 정의값 또는 이전 허가된 정상값이다. 매일 baseline을 previous로 바꾸면 새 경기 없이도 같은 자료가 반복 누적되어 전력이 이동하므로 피한다. 리그 평균은 매핑된 게임 팀 일부가 아니라 선택한 공식 전체 순위표로 계산해 상무·현실 승격팀의 미매핑이 평균을 왜곡하지 않게 한다. 변하지 않은 순위표는 checksum으로 no-op 처리한다. 최소 경기 기준 예: P<3은 기존값 유지, 3경기 이후에도 w로 완충한다. 6·2·10·3은 후보 계수이며 검증 후 결정한다.

예: 리그 평균 전력 63, 리그 평균 PPG 1.4, 팀 P=10/Pts=20/GD=8, 평균 GDPG=0이면 target=68.2. baseline=65와 w=0.5를 혼합한 raw=66.6을 반올림하면 67이며 일일 한도가 1점이면 previous=65에서 66까지만 제안한다. 같은 스냅샷 다음날에는 재발행하지 않는다. 한도 때문에 남은 차이를 자동으로 매일 소진할지는 별도 정책이며 MVP는 새 데이터가 있을 때만 재계산을 권장한다.

리그별 기존 평균/자금력/등급은 유지하고 성과는 해당 리그 안에서만 보정한다. K1 PPG 2.0과 PL PPG 2.0이 같은 절대 실력은 아니다. J1 특별대회·MLS 컨퍼런스·K1 split·승점 삭감처럼 순위 체계가 다른 경우 어떤 공식 표/기간과 성과 승점을 사용할지 출처별로 정한다. 행정 삭감이 실력 저하로 반영되지 않게 확인하거나 예외 유지한다. 그룹별 비교는 표본/상대 차이를 남기며 억지로 한 표로 합치지 않는다.

한도 제안: 하루 ±1점, 시즌 baseline 대비 ±6점, 리그 평균/분산의 이상 변화는 발행 보류. 정확한 최대 변화폭과 반올림·리그 평균 보존 여부는 미확정. 순위표만으로 상대 강도/홈 이점·독립적인 최근 폼은 알 수 없으므로 “최근 폼 모델”이라고 과장하지 않는다. MVP는 시즌 누적 성과 기반이며 작은 표본은 장기 prior와 혼합한다. 최근 폼이 필요하면 후속으로 합법적으로 저장한 일별 누적값 차분을 검토하되 정정·시즌 전환을 구분해야 한다.

새 현실 시즌/대회 ID에서 P/Pts/GD가 리셋되면 새 baseline을 고정하고 P=0의 전력을 0으로 만들지 않는다. 경기 수 감소·승점/득실 정정은 값이 이상하다고 단순 거절하지 않고 시즌 전환/공식 정정 여부 확인 후 새 후보를 계산한다. 비시즌·무경기일은 마지막 정상값 유지. 컵·친선·대표팀·유소년 순위는 MVP 입력 제외한다.

## 5. 일별 운영·오류·버전

권장 운영은 서버에서 하루 1회 허가된 순위표를 일괄 수집하고 검증 통과 시 자동 전력 팩 발행이다. 클라이언트마다 외부 원문을 조회하거나 실시간 폴링하지 않는다. 게임은 자기 적용 정책에 따라 작은 파생 팩만 받는다. 모든 현실 결과를 게임 뉴스로 게시하지 않는다.

검증 항목: 대회/시즌/그룹 일치, 필수 팀 누락, ID 중복/미매핑, P/승점/득실 자료형·합계, 가능하면 승무패와 Pts=3W+D 대조(해당 대회 규칙에 맞춤), 비정상 시각, 극단 변경, 급변 한도, 이전 스냅샷과 차이. 단일 페이지 실패/빈 응답/인증 만료/429/스키마 변경/권리 만료는 발행하지 않고 경보한다. 리트라이는 제한·backoff와 일일 quota 안에서 수행한다. inputHash는 조회 시각·응답 행 순서를 제외하고 대회·시즌·그룹·팀별 P/Pts/GD의 정규화 값으로 계산한다. 같은 inputHash의 재시도/재발행은 previous를 다시 갱신하지 않는다. 동일 입력 재시도는 멱등적이며 정정된 표는 새 버전으로 계산한다. 개별 경기 종료·중복·중단 판정은 순위표 제공처가 반영한 누적값을 사용하므로 fixture 수집 상태기계는 MVP 밖이다. 진행 중 경기의 live 표를 피하고 확정 누적표/조회 cutoff를 사용한다. 종료 직후 표 정정·지연 가능성을 기록하고 다음 일별 조회에서 바로잡는다.

누락을 0점으로 채우거나 이름 유사도로 덮지 않는다. 정상 팀만 발행하면 누락으로 리그 평균이 흔들릴 수 있으므로 MVP는 해당 리그 팩 발행 보류를 권장한다. 다른 리그 팩을 유지할지는 독립 리그별 팩 구조로 검토한다. 이상 변화는 diff에서 팀/이전/입력/혼합/최종값·제외 이유를 보여주고 운영자가 확인한다. 정상 일별 발행까지 매번 사람이 승인할 필요는 없다.

작은 manifest에 `strengthVersion, mappingVersion, formulaVersion, source, competitionSeason, cutoffUtc, inputHash, clubStrengths, exclusions, publishedAt`을 둔다. 계산/매핑 버전은 명시하며 이미 발행된 버전 내용은 덮어쓰지 않는다. 로그에 발행/보류/수동 승인·반려/롤백 이유와 이전 버전을 남긴다. 직전 정상 팩으로 pointer를 원자적으로 돌리는 롤백을 준비한다. 장애 때 마지막 정상값을 유지하되 계약상 보관·구독 종료 후 이용이 허용된 범위에 한한다. 키는 서버 비밀값이다.

## 6. 기존 커리어에는 언제 적용할 것인가?

**매일 수집·계산·발행**과 **저장된 커리어 채택 시점**은 별도다. 아래는 사용자 결정 대상이며 서비스 시즌 경계만을 강제하지 않는다.

| 선택                                             | 효과와 구현 전에 확인할 점                                                                                                                                    |
| ------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 새 커리어만 최신 팩 사용, 시작 때 전체 고정      | 저장/재현이 가장 단순하지만 기존 커리어에는 일별 변화가 안 들어옴. 서로 다른 팩의 순위 비교·표시 필요.                                                        |
| 기존 커리어도 다음 가상 시즌 시작에 최신 팩 채택 | 일별 현실 변화가 다음 게임 시즌에 반영됨. 시즌 중 rivals·열린 시장·기록은 유지, 병역/이적도 같은 채택 버전 사용. 초기 추천 후보이나 사용자 결정 전 확정 아님. |
| 다음 접속/경기 구간에서 채택                     | 체감 갱신이 빠르지만 주전/계약/경기 난도가 시즌 중 변함. 같은 시드의 다른 일자 결과·진행 중 표·offline 차이를 설명할 정책 필요.                               |

기존 저장의 내 구단 str·rivals·pending 제안·mil.prevClub·leagueMoves·과거 기록을 로드만으로 최신값에 덮지 않는다. 새 optional 필드와 `save.ts:migrateSave`로 팩/채택 버전을 관리하고 save v 변경 때문에 기존 저장을 버리지 않는다. 과거 기록은 당시 전력 버전을 유지한다. 구단 소속은 현실 소속과 가상 `leagueMoves`를 구별한다. 옛 커리어에 baseline을 부여할 때 저장된 소속 str는 원래 값을 보존하는 별도 override가 필요할 수 있다.

전체 팩을 로컬 저장할지 version ID+오프라인 캐시를 둘지는 구현 선택이다. 팩 누락/손상/오프라인이면 마지막 유효값으로 진행한다. 같은 코드·BAL·전력 버전·seed·선택이 같을 때 재현 가능하게 외부 I/O가 게임 RNG를 소비하지 않도록 한다. 롤백이 이미 진행한 커리어를 자동 소급 변경하지 않게 채택 정책에 맞춰 처리한다.

현실 시즌, 게임 `s.year`의 가상 시즌, 서비스 시즌 ID는 별개다. `apps/api/src/db/repos/careers.ts:firstUploadSeasonAt`은 최초 업로드 서버 시각으로 서비스 시즌을 정하므로 이전 현실 팩으로 offline 생성한 커리어가 다음 서비스 시즌 순위에 들어올 수 있다. 일별 팩을 쓰는 순위 공정성을 위해 적용 버전 기록·cohort 표시/분리·허용 정책을 구현 전에 결정한다. 기존 BAL의 시즌 중 고정 원칙과 일별 str의 관계도 사용자 선택 후 명세한다.

## 8. 검증·출시·결정 필요 사항

1. **대응표/권리 확인:** 첫 리그와 현재 시즌 표를 선택, 기존 별칭↔공식 팀 검토, 미대응 팀 유지 정책 확정. 모든 리그를 한 번에 붙이지 않음.
2. **shadow 계산:** 합성 또는 허가된 순위표로 P=0/소수 경기/정정/리셋/누락/복수 그룹/중복/쿼터 실패를 확인. 과거 시점 표만으로 이후 성과를 검증해 데이터 누수 방지. 기존 전력·순위만 사용 모델과 PPG/GDPG 혼합 후보 비교. 개별 경기 Elo 백테스트는 필수 아님.
3. **게임 연결 별도 PR:** 공통 전력 조회·rivals 반영 범위·선택한 커리어 채택·기존 저장 회귀·오프라인·roll back을 검증. 같은 seed로 우승·이적·주전·컵·승강·병역·은퇴 점수 분포와 극단 구단 영향을 baseline과 비교. 현재 문서 작업에서 Simulator/Xcode는 실행하지 않음.
4. **제한 도입:** 권리와 검증이 끝난 한 리그의 정상 일별 자동 발행, 예외 수동 확인, 마지막 정상값 fallback. 적용 정책 안내·ko/en·가이드·릴리스 노트는 구현 PR에서 준비. 날짜 미확정. 운영 부담/정정률을 보고 리그를 추가.

수용 gate: 적용 대상 매핑/허가 확인 100%, 중복·빈 응답 전력 오염 0, 같은 입력 재계산 동일값, 미매핑/리그 누락·급변 예외 격리, 정상 무경기일 no-op, 정정/리셋 구별, 롤백 성공, 옛 저장/열린 시장/병역 복원 회귀 실패 0. 밸런스 변화 예: 주요 성취율 상대 ±5%를 경보 후보로 두되 표본과 신뢰구간을 함께 검토한다. 허용치/N은 확정하지 않는다.

사용자 결정: 첫 리그와 출처/예산, 현재 시즌 미대응 구단 처리와 향후 참가팀 콘텐츠 갱신, 상무 처리, 계수·최소 경기·변화 한도, 기존 커리어 채택 시점, 순위 cohort/공정성 정책. 사용자 의도인 매일 순위표 기반 갱신은 유지하며 이 선택들을 임의 확정하지 않는다.

## 9. 작업 근거·검증 기록

- 독립 clone에서 문서 3개만 변경, 원래 작업 공간과 병렬 작업 보존. 루트 `AGENTS.md`·`CLAUDE.md` 확인, main에 `.agents/skills` 없음.
- 조사 시 열린 PR: [#539 시즌 결산](https://github.com/tasddc1226/offside-football-simulator/pull/539), [#529 앱 스토어](https://github.com/tasddc1226/offside-football-simulator/pull/529), [#495 Android 출시](https://github.com/tasddc1226/offside-football-simulator/pull/495). 직접 같은 전력 갱신 PR은 찾지 못했으며 향후 구현 시 재확인.
- 기존 draft [#544](https://github.com/tasddc1226/offside-football-simulator/pull/544)를 사용자 최신 의도에 맞춰 수정. 개별 경기 Elo·주간 승인·서비스 시즌 경계만 발행하는 기존 권장안은 MVP 필수에서 제거.
- 독립 재검토: 중요한 코드/수식 오류 없음. 전체 공식 표 기준 평균과 시각/순서 제외 inputHash·재시도 no-op 보완을 반영했다.
- 문서 서식·상대 링크·`git diff --check`·public hygiene·독립 검토와 [CI 운영](../operations/ci-and-staging.md)의 두 PR 잡을 확인한다. 문서-only CI는 게임 실행/e2e/배포를 생략하므로 기능 검증을 완료했다고 주장하지 않는다.
