# T-11-132: 실세계 경기 결과 기반 NPC 구단 전력 갱신 기획

> 상태: 제안 · 사용자 정책 결정 및 데이터 이용 권리 확인 전 · 구현 없음
> 코드 기준: 원격 main `59d6b3220981e3e1676a455535872c3c25630e4a`, 확인일 2026-10-07 KST
> 범위: 기획 문서와 draft PR. 기능 구현, 데이터 계정 생성·계약·결제, 머지, 운영 배포는 포함하지 않는다.
> 아래 수식·계수·주기·수용 임계값은 검증을 위한 제안이며 확정된 게임 규칙이 아니다.

## 1. 목적·범위·비목표

현재 배열 순서로 고정된 NPC 현실 구단의 전력을 최근 실제 리그 성과로 설명 가능하게 갱신한다. 한 경기의 이변을 바로 능력치로 바꾸기보다 장기 실력과 최근 폼을 나누어 검토하고, 승인된 불변 전력 팩을 일정한 게임 경계에서 사용한다. 현실 결과를 게임 경기 결과로 복사하는 기능이 아니다.

대상은 선수 커리어의 `Club.str`이다. 구단주 유저 팀의 카드·배치 기반 `packages/contracts/src/owner-team.ts:teamOvr`, `apps/api/src/team/sim.ts:lineupOvr`, PVP 레이팅과 매칭은 별도 체계이며 변경 대상이 아니다. 선수 OVR·잠재력·국가 전력·리그 자금력·팀 이름·엠블럼도 자동 갱신하지 않는다. 모든 실제 경기 결과의 자동 게시, 즉시 전력 변경, 실제 일정 전체 재현, 현실 승강의 기존 커리어 소급 적용은 비목표다.

## 4. 지속 가능한 ID 매핑

현재 league-index는 게임 내부 기존 저장 참조일 뿐 현실 클럽의 안정적 식별자가 아니다. 별도 canonical key를 신규 레지스트리에 부여하고 기존 gameClubId에 명시 연결하는 이행을 한다. 게임 ID를 이름·순위·제공처 ID로 재생성하지 않는다. 기존 `pl-0` 등은 영구 유지하며 명시적 매핑 레지스트리에 `gameClubId, canonicalClubKey, provider, providerTeamId, validFrom, validTo, aliases, sourceEvidence, reviewedAt, status`를 둔다. 매핑 버전은 전력 버전과 별개로 기록한다. 현재 별칭이 어느 실제 구단을 가리키는지는 사용자 확인 전 추측으로 확정하지 않는다.

- 명칭·도시·스폰서 변경: 별칭 이력과 표시 정책만 변경, 동일 법적/스포츠 정체성인지 검토한다.
- 현실 승강: 기간별 실제 소속 이력만 바꾼다. 기존 커리어의 `leagueMoves`·팀 수·과거 기록을 덮지 않는다. 게임 기본 참가 목록 갱신은 별도 시즌 콘텐츠 변경이다.
- 신생·합병·해체·재창단: 자동 이름 매칭 금지. 동일성 검토 후 새 canonical key와 충돌 없는 신규 게임 ID를 승인한다. 기존 인덱스는 재사용·삭제하지 않고 tombstone으로 보존한다.
- 제공처 교체: canonical key는 유지하고 provider ID를 추가한다. 동일 경기의 양쪽 ID 연결도 검토해 중복 반영을 막는다.
- 상무·B팀·U23·동명이인·중립 구단: 특수 항목으로 검토 대기. 미매핑은 격리하며 유사 문자열로 임의 연결하지 않는다.

MVP는 현재 승인된 게임 참가 목록·ID만 대상으로 한다. 새로운 팀·실제 승강을 자동 게임 콘텐츠 추가로 묶지 않는다.

## 5. 경기 정규화·정정

최소 입력은 provider fixture ID, canonical 양 팀 ID, competition/season ID, UTC kickoff/finished/observed 시각, 상태, 90분 스코어, 홈/원정/중립, source revision, payload hash다. 제공처 상태를 내부 `scheduled/live/provisional/final/corrected/postponed/suspended/cancelled/void`로 명시 매핑한다.

`final` 확인 후 유예(예: 24~48시간, 제안)를 지난 정규 리그 경기만 후보에 넣는다. 중단·지연·취소·몰수·행정 판정은 자동 반영하지 않고 검토한다. 재개 경기는 같은 fixture와 최종 스코어 한 번만 계산하며, 재경기는 별도 ID여도 원 경기 무효 관계를 보존한다. 연장·승부차기와 90분 결과는 혼동하지 않는다. 리그 플레이오프는 정규 리그와 별도 분류하고 MVP 제외를 권장한다.

동일 provider/fixture의 upsert는 멱등적이다. 다른 제공처·재발급 ID는 양 팀·대회·시각 후보로 중복 경보 후 수동 확정한다. 정정은 원본 이벤트를 지우지 않고 supersedes 관계를 남기며 변경 경기 이후 평가를 시간순 재계산한다. 이미 배포된 팩은 수정하지 않고 새 버전 후보로 만든다. 지연 입력은 해당 경기 종료 시각 기준으로 폼을 산정하고 승인 cutoff 이후 유입은 다음 후보로 이월한다. 주간 최근 창 재조회와 월간 시즌 합계 대조(제안)로 과거 정정을 탐지한다. 합계 불일치·누락은 해당 리그 발행을 막는다.

## 6. 설명 가능한 장기 실력·최근 폼·게임 수치

한 리그 안 상대 대비 장기 Elo와 최근 기대 대비 성과를 분리한다. 선수 명성·매출·팬 투표·베팅 가격은 MVP 입력에 넣지 않는다. 리그 간 절대 Elo 비교는 하지 않는다.

예시(모든 계수는 제안):

```text
E_home = 1 / (1 + 10^((R_away - R_home - H) / 400))
S = win:1, draw:0.5, loss:0
R_home' = R_home + K*(S-E_home); R_away' = R_away - K*(S-E_home)
H = 50 (중립 0), K = 16 (장기 실력, 득실 보너스 없음)
F_i = weightedMean(S_i-E_i, 최근 8경기, 반감기 4경기)
confidence = n_eff / (n_eff + 8)
z_i = clip((R_i - leagueMeanR)/max(leagueSdR, 100), -2, 2)
confidenceLong = n_long_eff / (n_long_eff + 20)
longStr_i = (1-confidenceLong)*baselineStr_i + confidenceLong*(leagueAvg + 4*z_i)
targetStr_i = round(longStr_i + 2*confidence*clip(F_i, -0.5, 0.5))
candidateStr_i = clip(targetStr_i, previousStr_i-1, previousStr_i+1)
```

Elo는 상대와 홈 이점을 반영한 느린 실력, F는 최근 기대 이상/이하 성과다. n_long_eff는 허가된 과거 자료를 포함한 장기 유효 경기 수이며 부족하면 직접 작성 baselineStr 쪽으로 축소한다. 2점 폼 계수라도 F가 ±0.5로 제한되므로 폼 기여는 최대 ±1점이다. 득실 보너스는 대승·잘못된 스코어 영향과 설명 비용 때문에 MVP 제외 권장. 첫 장기 R은 이전 시즌 자료가 허가되고 충분하면 학습하고, 그렇지 않으면 중립 사전값을 사용한다. 기존 str에서 R을 역산하는 선택은 기존 서열 편향을 남기므로 별도 비교한다.

예시 K1 평균 63, z=1, baselineStr=65, confidenceLong=0.8, F=0.25, confidence=0.5이면 longStr=66.6, target은 round(66.85)=67이다. 이전 65라면 이번 발행은 66까지이고 1점 제한으로 남은 차이를 숨기지 않는다. 한 점 str 변화는 현재 경기식의 기본 승률 약 2.4%p·이적 자격 변화로 이어질 수 있으므로 “작은 변화”도 밸런스 확인이 필요하다.

리그 평균·spread·tier·wealth는 MVP에서 기존 값을 유지한다. 국내 결과만으로 K1과 PL의 절대 격차를 새로 추정할 수 없다. 장기 z 정규화로 리그 내부 우열만 반영하고, 기존 평균과 분포가 크게 달라지면 발행을 막는다. 리그 간 비교는 추후 허가된 대륙대회 자료와 별도 모델 검증이 필요하다.

표본 부족·시즌 초반은 신뢰도를 낮춰 기존값/사전값 쪽으로 축소하고 예: 5경기 미만은 자동 후보 제외한다. 비시즌에는 새 결과가 없다는 이유로 약팀화하지 않고 마지막 정상값을 유지한다. 시즌 전환 시 R은 유지·평균 회귀를 후보 비교하고 F는 시간 감쇠하되 신뢰도도 낮춘다. 승격 신생팀은 새 리그의 중립 사전값과 기존 게임값을 검토하며 하위리그 Elo를 그대로 이식하지 않는다. 컵·친선·대표팀·유소년은 수집/평가 MVP 제외, 게임 내 컵 자체를 제거하는 뜻은 아니다.

## 7. 수집과 발행의 분리·운영 방어

수집 예: 하루 1회 서버 측 일괄, 지난 7일 정정 재조회. 후보 계산 예: 주 1회. 게임 발행은 운영자 검토 후 서비스 시즌 경계에 1회로 권장한다. 실시간 폴링이나 클라이언트별 외부 API 호출은 하지 않는다. 데이터 신선도와 게임 규칙 안정성은 서로 다른 주기다. 주기·쿼터·관리 시간이 맞지 않으면 월간 수동 입력도 검토하되 권리 확인은 동일하다.

수집 → 검증/격리 → 후보 계산 → 이전 팩 diff → 승인 → 불변 팩 발행 순서로 분리한다. 1인 운영에서는 후보 생성과 발행 명령을 분리하고 승인 기록·체크리스트로 실수를 줄인다. 자동 승인·무인 게시를 전제하지 않는다.

방어 항목: ID·시각·상태·스코어의 스키마 검증, 미래 종료 시각·음수/극단 점수·동일 팀 대진 거절, fixture/시즌 합계 대조, 매핑 충돌·반복 정정·출처 교체 경보, 한 발행 ±1점·누적 예: 30일 ±3점 제한, 팩 평균/분산 변화 한도, 리그 전체 결측률 임계값. 비정상 스코어는 결과까지 임의 수정하지 않고 격리한다. provider 한 곳을 MVP 기본으로 쓰되 의심 결과는 공식 증적의 합법적 확인 후 수동 판단한다. 키는 서버 비밀값, 클라이언트·문서·로그에 남기지 않는다.

리트라이는 지수 backoff·쿼터 상한, 429/인증 만료/스키마 변경 시 수집 중단 경보. 수집 장애·매핑 오류·빈 데이터는 0점으로 변환하지 않는다. 계약상 보관·종료 후 이용이 허가된 마지막 정상 팩과 직접 작성 번들 baseline을 유지하고 운영 화면에 cutoff와 지연을 표시한다. 발행 중 부분 실패는 active pointer 변경을 원자적으로 수행해 혼합 버전을 막는다.

## 8. 데이터 버전·저장 호환·공정성

불변 manifest 제안: `strengthVersion, mappingVersion, formulaVersion, sourceRevision/hash, cutoffUtc, competitionSeasonIds, clubStrengths, coverage, excludedFixtures, reviewId, publishedAt, checksum`. 원본과 파생물이 계약 보존 조건을 만족하는지 별도 점검한다. 게임 클라이언트는 승인된 작은 팩만 받으며 동일 버전 내용을 덮어쓰지 않는다.

**MVP 권장:** 서비스 시즌에 사용할 팩을 개막 전에 고정하고 새 커리어 생성 때 전체 구단 전력 팩을 저장해 커리어 종료까지 유지한다. 새 현실 결과는 다음 발행 후보를 준비할 뿐 가상 2027·2050년에 진행할 때 최신 현실 값을 자동 채택하지 않는다. 현실 연도·리그 시즌, 서비스 시즌 ID, 가상 `s.year`는 별도 필드이며 1:1 대응하지 않는다. 서비스 시즌 도중 새 커리어에 다른 팩을 주는 정책은 순위 공정성 때문에 MVP 제외 권장이다. 구체 적용 경계는 사용자 결정 전 미확정이다. 특히 `apps/api/src/db/repos/careers.ts`의 `firstUploadSeasonAt`은 최초 업로드 서버 시각으로 서비스 시즌을 정한다. 시즌 A에 오프라인 생성한 A 팩 커리어가 시즌 B에 처음 업로드되면 B 순위에 A 팩이 섞일 수 있다. 팩을 소급 변경하지 않고 순위 eligibility/cohort를 분리할지, 서버 승인 생성 메타데이터를 사용할지 사용자 결정이 필요하며 이 경계 해결을 출시 gate로 둔다.

기존 BAL은 가상 시즌 경계 갱신을 지원하지만 전력은 전체 커리어 고정안을 추천한다. 시즌마다 채택하는 확장안을 선택하면 신규/기존 유저 차이·오프라인 플레이·열린 시장·병역 복원·순위 cohort를 추가 설계하고 시즌 진행 중에는 절대 교체하지 않는다.

옛 저장에는 `legacy-static-v1` 전체 baseline을 명시 부여하는 마이그레이션을 준비한다. 단, 현재 소속의 저장 str는 과거 앱 버전·승격·병역으로 baseline과 다를 수 있으므로 그대로 보존한다. 진행 중 rivals·기록·pending 시장·mil.prevClub을 재생성하지 않는다. baseline과 소속 override를 함께 저장하고 이후 조회가 동일하게 해석되도록 설계한다. 서버 최신값을 로드 시 강제로 넣지 않는다. 로컬 전체 팩 저장은 가장 단순한 후보이나 용량·업로드 계약 영향은 구현 전 확인한다. 팩 ID만 저장한다면 영구 조회/오프라인 캐시/삭제 금지 계약이 필요하다. 구독 종료 시 참조 금지와 같은 약관은 기존 커리어의 불변 보존 요구와 충돌하므로 제공처 선정 전 해결한다. 유지 허가가 없으면 그 제공처 팩을 출시하지 않는다. 이미 배포한 데이터의 권리 철회는 별도 중단·삭제·사용자 복구 정책을 법적 조건에 맞춰 준비한다.

구단 str 변경이 난수 소비를 바꾸지 않도록 외부 데이터 로딩·매핑·hash는 게임 RNG를 사용하지 않는다. 같은 seed, 게임 코드/밸런스 버전, 전력 팩, 저장 상태, 선택으로 같은 결과를 재현한다. 서로 다른 팩까지 같은 결과라고 주장하지 않는다. 서버 커리어 기록에도 적용 버전·서비스 시즌을 남겨 추적하고 기존 업로드 스키마의 unknown field 제거 여부를 확인한다. 순위 비교의 cohort 표기/분리와 시즌 중 긴급 수정 예외는 사용자 승인 대상이다. 전력 팩이 같아도 기존 BAL·클라이언트 버전이 다르면 완전 재현 조건이 부족하다.

롤백은 직전 승인 팩으로 새 발행의 active pointer를 돌린다. 이미 시작한 커리어 스냅샷은 유지한다. 잘못된 팩 커리어를 강제 수정하는 것은 복구가 아니라 별도 공정성 정책 결정이며 자동 실행하지 않는다.

## 9. 수동 검토·감사·백테스트·수용 기준

diff는 구단 ID/별칭/실제 ID, 이전/장기/폼/최종 str, 반영 경기 수·제외 이유, 최고 변화 팀, 평균·분산, 승강 후보·주전 판정·이적 자격 경계 영향을 보여준다. 운영자는 원자료 cutoff·권리 상태·매핑 변경·정정 목록을 확인하고 이유를 적어 승인한다. 작성자·승인자(1인 운영이면 동일인임을 명시), 시각, checksum, 이전 팩, 변경 이유, rollback 이유를 append-only 감사 기록으로 남긴다. 원본 증적 보존은 계약 범위 안에서 한다.

구현 단계의 검증 계획:

- 시간 분할 백테스트: 과거 경기까지만 학습하고 이후 결과를 예측해 데이터 누수를 막는다. 기존 고정 전력·리그 동일 전력 baseline과 Elo/폼 후보를 Brier score·draw calibration·팀별 편향으로 비교한다. 최소 한 시즌과 시즌 초반 구간을 권장하되 역사 데이터 권리·확보 비용은 미확정이다.
- 밸런스: 동일 시드 집합으로 리그 우승·상위 진출·이적/재계약·주전·컵/발롱도르·승강/병역 복원·은퇴 점수 분포를 baseline과 비교한다. 최종 표 이름 연결과 MLS 20팀 제한도 확인한다. 향후 구현 PR에서 기존 테스트와 `tooling/fulltime-sim`을 실행한다. 이번 문서 PR은 Simulator·Xcode를 실행하지 않는다.
- 데이터 테스트: 중복/재시도 멱등, 정정 재계산, 중단/연기/재경기/무효, DST/UTC, 시즌 경계, 매핑/별칭/제공처 교체, 신규·폐지 ID, 인증·쿼터 실패, 손상 팩/오프라인 fallback.
- 저장 회귀: 기존 fixture 세이브와 승격 직후·열린 시장·상무 복무·전역·개명·오프라인 저장을 유지하며 신규 팩 도입 전후 동일 행동/난수 순서를 확인한다. RNG 외부 I/O 분리를 검사한다.

출시 gate 제안: 허가 근거 확인 100%, 적용 구단 매핑 검토 100%, final 완료 경기만·중복 기여 0, 미매핑/치명적 불일치 시 발행 0, checksum·롤백 리허설 성공, 기존 save 회귀 실패 0, 같은 팩 동일 seed 재현 실패 0. 예측 품질은 baseline보다 개선 또는 합의한 허용오차 내여야 한다. 밸런스 주요 성취율 상대 변화 예: ±5%를 검토 경보로 쓰되 작은 표본에 기계적으로 적용하지 않고 신뢰구간과 팀별 극단을 함께 판단한다. 최종 허용치·검증 N·사용자 경험 목표는 구현 전에 확정한다.

## 10. 단계별 출시와 1인 운영 MVP

1. **기획/권리 gate(현재):** 사용자 정책과 제공처 허가·요금·매핑 의도를 확정한다. 불확실하면 기존 전력 유지.
2. **오프라인 shadow:** 권리가 확인된 단일 리그 완료 경기만 CSV/API 일괄 입력, 평가와 diff 생성. 게임 영향 없음. 수주 운영 시간·정정 빈도·quota 비용을 측정한다.
3. **게임 통합 후보:** 공통 전력 조회·상대 분포 모델·불변 커리어 스냅샷·옛 저장 호환을 별도 구현 PR에서 검증한다. 예측 개선만으로 게임 밸런스 출시 승인하지 않는다.
4. **다음 서비스 시즌 제한 도입:** 수동 승인 팩, 신규 커리어만, 마지막 정상값 fallback. 발행 전 공지·ko/en 안내·공개 가이드·릴리스 노트 및 cohort 정책 준비. 날짜 미확정.
5. **확장:** 운영 부담/권리/백테스트 기준이 충족되면 리그를 하나씩 추가한다. 무인 발행·컵 모델·현실 승강 콘텐츠·가상 시즌별 채택은 별도 결정.

권장 최소 구현은 “허가된 한 리그 → 하루 일괄 수집 → 주간 후보 diff → 개막 전 수동 팩 승인 → 서비스 시즌/커리어 고정”이다. 전용 실시간 인프라·관리자 웹 UI 대신 초기 CSV·검증 명령·버전 파일·검토 PR 흐름을 사용할 수 있다. 반복 수집과 게임 배포를 분리하며 전력 값 공개 방식은 계약 조건을 따른다.
