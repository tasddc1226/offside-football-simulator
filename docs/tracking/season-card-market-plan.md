## 1. 목적과 결정 수준

직접 키운 선수의 커리어가 은퇴로 끝나지 않고 구단 구성과 유저 간 교류로 이어지게 한다.
서비스 시즌마다 새로운 선수를 육성할 동기를 주면서 기존 기록과 선수에 대한 애착은 보존한다.

사용자가 제시한 방향:

- 실제 플레이하는 유저를 구단주로 정의하고, 구단주가 여러 팀을 꾸리는 방향으로 확장한다.
- 유저 간 선수 트레이드·사고팔기를 검토한다.
- 현실의 특정 기간을 서비스 시즌으로 정의하고 명예의 전당을 시즌별로 분리한다.
- 은퇴 당시의 선수를 거래하는 설정의 어색함을 해결한다.

아래의 카드 발급 방식·참가 조건·마감 처리·단계별 순서는 대화에서 제안한 기본안이다.
문서 추가는 이 내용을 검토 가능한 형태로 보존하는 작업이며, 세부 정책 확정이나 기능 구현·배포를 뜻하지 않는다.
기존 ADR을 대체하지 않는다. 구현 시 아키텍처 변경은 별도 ADR로 결정한다.

| 영역 | 확인 근거 | 확장 시 차이 |

게임 진행은 브라우저에서 실행되고 서버에는 요약이 적재된다. 서버에 저장됐다는 이유만으로 기록이 검증됐다고 보지 않는다.
과거 아카이브의 서비스 시즌·이적시장 설계를 현행 구현으로 간주하지 않는다.

## 3. 세 가지 시간·기록 개념

| 개념 | 정의 | 예시 |
|---|---|---|
| 커리어 시즌 | 선수 인생 속 한 해 | 2034년, 25세, 리그 28골 |
| 서비스 시즌 | 현실의 시작·종료 시각으로 정한 경쟁 기간 | 오프사이드 S1 |
| 커리어 카드(가칭) | 특정 커리어의 한 해를 고정한 선수 자산 | S1 출신 선수의 2034년 모습 |

서비스 시즌의 실제 길이·개막일은 미정이다. 커리어 연도와 서비스 시즌 ID를 혼용하지 않는다.

## 4. 핵심 경험: 은퇴 후 남기고 싶은 한 해

선수 생성 → 은퇴까지 육성 → 커리어 기록 등록 → 한 해 선택 → 카드 발급 → 구단 편성 → 교환·거래.

은퇴는 기록을 확정하는 조건이다. 카드의 나이와 능력치는 은퇴 시점이 아니라 선택한 연도를 따른다.
예를 들어 빠른 윙어였던 24세, 득점왕이었던 28세, 패스가 좋아진 33세 중 하나를 선택한다.
전성기를 시스템이 추천할 수는 있지만 높은 OVR만으로 자동 확정하지 않는 안을 우선한다.

초기 발급 제안:

- 커리어 하나당 거래 가능한 카드 한 장. 발급 후 연도 변경·중복 재발급은 허용하지 않는다.
- 능력치·포지션·특성은 동일한 시점의 기록으로 고정한다. 항목별 최고 수치를 합치지 않는다.
- 연도 내 어느 시점(시즌 종료 등)을 저장할지와 카드에 포함할 특성은 구현 전에 확정한다.
- 카드의 경기 성능과 평생 업적을 구분한다. 레전드 스코어를 카드 능력치로 그대로 치환하지 않는다.
- 원 육성자와 커리어 기록은 보존하고 현재 카드 소유자·이적 이력을 별도로 관리한다.
- 거래되는 것은 구단 편성에 사용하는 카드 소유권이다. 원래 세이브나 육성자의 명예의 전당 기록을 양도하지 않는다.
- 다른 구단주가 영입해도 카드를 복제하지 않는다. 한 카드는 한 소유자에게만 귀속한다.

현재 연도별 기록만으로 과거의 전체 능력치를 정확히 복원할 수 없다.
발급 대상 연도의 스냅샷 저장을 먼저 설계해야 하며, 기존 선수의 누락 정보를 추정해 거래 카드로 만들지 않는다.
기존 커리어의 발급 자격·소급 지원 여부는 별도 결정한다.

## 5. 서비스 시즌과 명예의 전당

초기 제안은 해당 서비스 시즌에 새로 생성한 선수를 경쟁 참가 대상으로 삼는 것이다.
시즌 개막 전에 키운 강한 선수를 마감 직전에 등록하는 방식은 막아야 한다.

| 상황 | 제안 처리 |
|---|---|
| 해당 시즌 생성·마감 전 은퇴 | 자격과 기록 확인 후 시즌 순위에 반영 |
| 마감 때 현역 | 강제 은퇴·세이브 초기화 없이 계속 플레이 |
| 마감 후 은퇴 | 전체 기록에는 남기되 종료된 시즌 순위에 추가 반영하지 않음 |
| 이전 시즌 출신 카드 | 소유·거래 유지. 출신 시즌 표시는 유지 |
| 시즌 종료 | 순위 확정본과 과거 시즌 조회 제공 |

전체 명예의 전당과 시즌 명예의 전당을 병행한다. 이전 시즌 현역이 다음 시즌 경쟁자로 자동 편입되지는 않는다.
마감 후 완주한 카드도 최초 참가 시즌 출신으로 남긴다는 안이며, 이 카드의 시즌 대회 참가 자격은 별도로 정해야 한다.

마감 공정성은 출시 전 결정이 필요하다. 로컬 생성·은퇴 시각만으로 참가를 인정할 수 없다.
서버 참가 등록 시각, 제출 마감, 오프라인 플레이·업로드 지연 유예, 장애 시 예외 처리를 함께 설계한다.
경계 시각은 서버 기준으로 판정하고 사용자 화면에는 KST 마감 시각을 명시한다.
동점 순위·부정 기록 제외·확정 후 정정 이력도 필요하다.

시즌 중 밸런스 패치로 같은 시즌의 육성 조건이 달라질 수 있다.
경쟁 적용 버전과 변경 공지 원칙을 별도 결정하며, 본 문서에서 기존 밸런스 적용 정책을 변경하지 않는다.

## 6. 구단 구성과 거래 수요

먼저 카드로 팀을 만들고 실제로 활용할 수 있어야 한다.
포지션·역할·팀 조합이 결과에 영향을 주어 좋은 수비수·골키퍼도 찾을 이유를 만든다.
유저별 여러 팀은 확장 목표이며 초기 팀 수·선발/후보 수·동일 카드의 여러 팀 중복 편성 여부는 미정이다.

구단 콘텐츠 후보는 간단한 팀 경기, 포지션별 과제, 팀 구성 목표다.
모든 기능을 동시에 만들기보다 내 카드로 팀을 꾸리는 재미를 먼저 검증한다.

장기적으로는 다음 두 경쟁을 검토한다:

- 시즌 대회: 해당 서비스 시즌 출신 선수 중심. 새 육성의 동기.
- 전체 대회: 여러 시즌 선수를 조합. 기존 카드의 지속적 활용.

초기 유저가 적을 때는 대회를 나눠 참여자를 분산하지 않는다.
명예의 전당 시즌제를 먼저 적용하고 구단 대회 분리는 참여 규모와 매칭 상황을 보고 결정한다.
매 시즌 더 강한 카드를 내거나 기존 카드를 삭제하는 방식으로 신규 수요를 만들지 않는다.

## 7. 유저 이적시장

현재 커리어 안의 NPC 구단 이적과 유저 간 카드 거래는 서로 다른 기능이다.

| 단계 | 범위 | 먼저 확인할 점 |
|---|---|---|
| 1: 직접 교환 | 1:1 카드 제안·수락·취소·내역 | 상대 카드 비교, 양측 소유권, 중복 제안 처리 |
| 2: 정가 거래 | 게임 내 재화로 등록·구매·취소, 포지션·시즌 필터 | 재화 수급, 가격 형성, 수수료와 소모처 |
| 3: 확장 | 경매·구매 요청·추가 거래 방식 | 유동성과 운영 비용이 충분한지 |

초기에는 현금 거래·현금화 없이 게임 내 교환과 재화만을 검토한다.
가격 상한·수수료율·거래 제한·재화 지급량은 확정하지 않는다.
초보의 재화 획득, 반복 육성에 따른 공급 증가, 다계정·자전 거래를 함께 검토해야 한다.

카드에는 원 육성자와 현재 소유자, 선택 연도·출신 서비스 시즌, 실제 거래 이력을 보여줄 수 있다.
표시되는 개인 정보는 공개 동의 범위로 제한하며 육성자의 평판이 강제적인 공개 신상으로 이어지지 않게 한다.

## 8. 시장 개방 전 필수 조건

- 기록 진위: 클라이언트가 보낸 능력치를 그대로 거래 자산으로 승인하지 않는다.
  서버 검증 범위·비용·검증 불가능한 기존 기록 처리 방식을 먼저 결정한다.
  관찰용 자동 플레이 신호만으로 유효함 또는 부정행위를 확정하지 않는다.
- 유일성: 커리어당 카드 한 장 발급을 서버에서 보장한다. 재시도·복수 기기에도 중복 발급되지 않아야 한다.
- 소유권: 거래 수락 시 소유자·등록 상태를 다시 확인하고 양측 자산·재화를 함께 이전한다.
  동시 구매, 중복 수락, 재전송, 취소 경쟁으로 복제·소실·이중 지출이 없어야 한다.
- 경기와 거래: 등록 중 편성·출전 허용 여부와 진행 중 경기의 참조 시점을 정한다.
- 기록 보존: 카드 양도와 원 커리어 기록을 분리한다. 계정 삭제 시 타인이 소유한 카드·육성자 표시 처리도 정한다.
- 저장 호환: 새 스냅샷 필드를 추가할 때 기존 세이브 마이그레이션을 제공한다.
- 서버 비용: 목록 페이지네이션·필터 인덱스·공개 캐시·쓰기 후 무효화를 설계한다.
  화면을 열 때만 읽고 카드마다 상세를 호출하는 N+1이나 짧은 폴링을 피한다.

서버 검증을 위해 모든 게임 진행을 즉시 서버로 옮긴다는 결정은 아니다.
검증 설계를 별도 비교한 뒤, 검증 가능한 기록부터 제한적으로 시장을 여는 안을 검토한다.

## 9. 권장 진행 순서와 완료 기준

| 순서 | 산출물 | 완료 기준 |
|---|---|---|
| A. 정책 확정 | 시즌 참가·마감·기존 기록·카드 발급 정책 | 아래 미결 항목 중 출시 경계 조건 결정 |
| B. 시즌 명예의 전당 | 참가 등록·시즌 필터·확정 순위 | 경계·지연 제출·현역 지속·과거 기록 보존 검증 |
| C. 카드 기록 기반 | 연도 스냅샷·검증·유일 발급 | 같은 해의 능력치 사용, 중복 발급 방지, 이전 세이브 호환 |
| D. 구단 편성 | 보유 카드·포지션 배치·간단한 활용 | 포지션별 카드가 필요해지는 플레이 경험 확인 |
| E. 직접 교환 | 제안·수락·취소·이력 | 동시 처리·재시도에도 소유권 일관성 유지 |
| F. 재화 시장 | 정가 거래·검색·재화 원장 | 재화 흐름과 거래 수요 확인 후 제한 공개 |

A~F는 기획 단계의 순서다. 실행 일정·작업 티켓·API·테이블 스키마는 아직 확정하지 않는다.

## 10. 구현 전 결정할 질문

1. 서비스 시즌은 얼마나 길게 운영하며, 첫 개막과 마감은 언제인가?
2. 서버 참가 등록과 오프라인 플레이는 어떻게 양립하고 지연 제출은 어디까지 허용하는가?
3. 기존 커리어·기존 은퇴 선수는 전체 명예의 전당에만 남길지, 카드 전환 경로를 제공할지?
4. 카드에 선택 가능한 연도와 저장 시점은 무엇이며, 은퇴 전 미리보기·선택 확인을 어떻게 제공할지?
5. 커리어당 한 장·발급 후 변경 불가를 최종 채택할지?
6. 같은 카드의 여러 팀 편성, 거래 중 출전, 늦게 완주한 이전 시즌 카드의 대회 자격은 어떻게 정할지?
7. 검증 가능한 기록의 기준과 부정 기록 처리·이의 제기·계정 삭제 정책은 무엇인지?
8. 시즌 내 밸런스 변경과 서로 다른 시즌 카드의 경기 성능은 어떻게 비교할지?
9. 초기 팀 규모·경기 방식·재화 수급과 소모처는 무엇인지?

이 질문을 확정하기 전에도 기획 검토는 진행할 수 있지만, 미정 정책을 현재 서비스의 약속으로 안내하지 않는다.
