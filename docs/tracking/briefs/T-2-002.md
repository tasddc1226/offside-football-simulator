## 목표

## 도메인 계약(D-26·D-34)

### 파생 값(순수 함수, `packages/domain/src/selection.ts` 신설)

```ts
computeTacticalFit(attributes, archetypeId, position, style, rules): number  // 0~100 정수
  styleScore  = Σ_k roleWeights[position][k] × attributes[k]  (k는 ATTRIBUTE_KEYS 순서, 없는 키 0)
  archetype   = preferredArchetypeIds[position]에 archetypeId 포함 ? 100 : 0
  fit         = round(styleScore × tacticalFitWeights.style + archetype × tacticalFitWeights.archetype)

familiarityOf(proficiency, rules): 1.0 | 0.97 | 0.92   // proficiencyThresholds로 등급 판정 → positionFamiliarity

computeExpectedPerformance({ baseOvr, tacticalFit, form, fitness, morale, familiarity }, rules): number
  = round1((baseOvr×0.70 + tacticalFit×0.12 + form×0.08 + fitness×0.06 + morale×0.04) × familiarity)
  // round1 = Math.round(x × 10) / 10. 더하는 순서는 performanceWeights 키 순서로 고정.

computeSquadStatus({ rolePromise, captaincy, lastRating }, rules): number  // 0~100 정수
  = clamp(squadStatusByRole[rolePromise] + captainBonus[captaincy] + ratingAdj, 0, 100)
  ratingAdj = lastRating === null ? 0 : clamp(round((lastRating − ratingNeutral) × ratingScale), −ratingAdjMax, +ratingAdjMax)
  // Phase 2는 captaincy 'NONE' 고정(Phase 4가 연다), lastRating은 T-2-003이 채우기 전까지 null.

computeSelectionScore({ tacticalFit, managerTrust, expectedPerformance, squadStatus }, rules): number
  = round1(tacticalFit×0.40 + managerTrust×0.25 + expectedPerformance×0.25 + squadStatus×0.10)

rankSelection(candidates, slots, benchSlots, rules): SelectionRanking
  // 정렬 키: score 내림차순 → baseOvr 내림차순 → id 오름차순(안정). 부상·징계·대표팀 제외는 T-2-003·Phase 4가 `excluded: reason`으로 넣는다(필드만 둔다).
  // rank ≤ slots → 'START', ≤ slots+benchSlots → 'SUB', 나머지 'OUT'.
  // reason: 선수(id 'PLAYER')와 경계 후보(선수가 START면 첫 SUB, 아니면 마지막 START)를 비교해 가중 차이 |w_c × (a_c − b_c)|가 가장 큰 구성 요소 c와 그 부호 있는 차이.

deriveTacticalRoom(state, ruleset): TacticalRoomView | null   // 시즌 없으면 null. 화면(T-2-007)이 그대로 쓴다.
  { styleId, styleName, formation, playerPosition, playerRole: SquadRole, tacticalFit, managerTrust, expectedPerformance, familiarity, ranking: SelectionRanking }
```

```ts
type SelectionCandidate = { id: 'PLAYER' | string; name: string; baseOvr: number; tacticalFit: number; managerTrust: number; expectedPerformance: number; squadStatus: number; score: number; excluded: null | 'INJURY' | 'SUSPENSION' | 'NATIONAL_TEAM' };
type SelectionRanking = { position: Position; slots: number; benchSlots: number; candidates: Array<SelectionCandidate & { rank: number; appearance: 'START' | 'SUB' | 'OUT' }>; playerReason: { component: 'TACTICAL_FIT' | 'MANAGER_TRUST' | 'EXPECTED_PERFORMANCE' | 'SQUAD_STATUS'; delta: number } | null };
type Competitor = { id: string; name: string; position: Position; archetypeId: string; attributes: Record<AttributeKey, number>; baseOvr: number; form: number; fitness: number; morale: number; tacticalFit: number; managerTrust: number; squadStatus: number; rolePromise: SquadRole };
```

- `context.tacticalFit`은 시즌이 있을 때 `computeTacticalFit`의 실제 값이다(계약 전에는 제안의 `tacticalFitEstimate`가 그대로 남는다). `context.squadStatus`는 `computeSquadStatus`로 다시 계산한다(입력이 바뀔 때마다 — 이 작업에서는 START_SEASON·역할 결정 시). `context.positionProficiency`는 "현재 `primaryPosition`의 숙련도 0~100"으로 뜻을 고정한다(배경 초기값 95·100 유지).
- `FootballSeason`에 `squad: { competitors: Competitor[] }`, `selection: SelectionRanking`(선수 포지션의 최신 순위), `styleId: string`을 추가한다. `season.squadRole`은 `selection`의 선수 appearance로 갱신한다: START → STARTER, SUB이고 rank = slots+1 → ROTATION, 그 외 SUB → BENCH, OUT → RESERVE.
- 경쟁자는 `START_SEASON`에서 룰셋 `positions` 순서로 포지션마다 `perPosition`명 생성한다(선수 포지션이 바뀌어도 다시 추첨하지 않는다). 생성 규칙: 팀 `squadStrength` 기준 Base OVR이 `squadStrength ± ovrSpread` 안에 들도록 아키타입 템플릿을 정수 배율로 맞춘 뒤 jitter(정수·고정소수점, `Math.round` 1회). `rolePromise`는 생성 순서대로 STARTER, ROTATION(포지션 정원이 2 이상이면 둘 다 STARTER). form·fitness·morale은 룰셋 `seasonBoundaryReset` 값(roll 없음). `tacticalFit`·`squadStatus`는 위 순수 함수. 이름은 `competitorNames`에서 **중복 없이** 뽑는다.

### 감독 역할 제안(step 1 필수 슬롯, RULE-TIME-001)

T-2-001이 자동 통과시키던 `ROLE` 슬롯을 실제 결정으로 바꾼다. roll을 소비하지 않는다.

```ts
Pending += { kind: 'ROLE_PROPOSAL'; step: number; proposal: RoleProposal }
type RoleProposal =
  | { type: 'KEEP'; position: Position; squadRole: SquadRole }
  | { type: 'POSITION_CHANGE'; from: Position; to: Position; squadRoleAfter: SquadRole; tacticalFitAfter: number; proficiencyAfter: number }
  | { type: 'ROLE_CHANGE'; position: Position; from: SquadRole; to: SquadRole };
명령 RESOLVE_ROLE { decision: 'ACCEPT' | 'DECLINE' }   // CMD-SIM-004(D-34). '조건부 훈련'은 T-2-005가 붙인다.
```

- 제안 산출(결정론, roll 없음): 선수의 현재 포지션 순위(`rankSelection`)로 `projectedRole`을 구한다. (a) 감독 선호 아키타입 포지션 후보 중 `positionAdjacency[primaryPosition]`에 속하고, 그 포지션에서 계산한 `computeTacticalFit`이 현재보다 `≥ 15` 높으며, 그 포지션의 projectedRole이 현재보다 좋으면 `POSITION_CHANGE`. (b) 아니면 projectedRole ≠ `contract.rolePromise`이면 `ROLE_CHANGE`(from = rolePromise, to = projectedRole). (c) 아니면 `KEEP`.
- ACCEPT: POSITION_CHANGE → `profile.primaryPosition = to`, `context.positionProficiency = proficiencyOnChange`(인접 80·그 외 60), `context.tacticalFit` 재계산, `selection` 재산출, `managerTrust += acceptTrustDelta`. ROLE_CHANGE → `season.squadRole = to`, `contract.rolePromise`는 **바꾸지 않는다**(계약은 Phase 3), `context.squadStatus` 재계산, `managerTrust += acceptTrustDelta`. KEEP → `managerTrust += keepConfirmTrustDelta`.
- DECLINE: 상태 변화 없이 `managerTrust += declineTrustDelta`(clamp 0~100). `preferredPosition`은 어떤 경우에도 불변(RULE-PLY-001).
- 결정 뒤 `pending = null`, 타임라인 `ROLE_RESOLVED`(refId = proposal.type), checkpoint `STEP_BOUNDARY`(기존 규칙). 재생 시 같은 명령 로그가 같은 상태를 낸다.
- 실패: `VALIDATION_FAILED { reason: 'NO_ROLE_PROPOSAL' }`(pending이 ROLE_PROPOSAL이 아닐 때), `NOT_ACTIVE`.

## T-2-001 산출물(PR #36)과의 접점

- `packages/domain/src/season.ts`: `selectOpenSlot`이 `ROLE` 슬롯을 `{ kind: 'ROLE', step }` pending으로 열고, `isAutoPassablePending`이 ROLE을 자동 통과시키며, `simulate.ts`의 `nextActionForPending`이 ROLE에 'ADVANCE'를 준다. 이 작업은 ROLE을 자동 통과 목록에서 빼고 `ROLE_PROPOSAL` pending(제안 포함)으로 열어 nextAction 'DECISION'을 준다. CHAPTER·CONTRACT·INJURY·NATIONAL_TEAM 자동 통과는 그대로 둔다.
- `START_SEASON` payload는 `{ simulationMode, serviceSeasonId }`다(PR #36 편차, 유지). `startSeason`이 `buildInitialCompetitions`로 `LEAGUE`·`CUP` 자리표시자 2건을 만든다 — 이 작업이 룰셋 `leagues[]`·`cups[]`로 대체한다(`competitionId`는 룰셋 id).
- `LeagueCalendar.cupRounds`의 round enum은 `'R1' | 'SEMI' | 'FINAL'`(domain `ruleset.ts`, content 스키마 `CupRoundSchema`) — `'R2'`를 추가하고 기본 캘린더에 `{ round: 'R2', step: 7 }`을 넣는다.
- 룰셋에 `seasonBoundaryReset { form: 50, fitness: 80, morale: 60 }`이 있다(경쟁자 초기 form·fitness·morale에 재사용).
- walk가 step을 넘길 때 `expireEffectsThroughWalk`가 AT_STEP 효과를 만료시킨다. 역할 결정의 managerTrust 변화는 Effect가 아니라 직접 갱신(즉시 확정)으로 두되, `appliedSourceIds`처럼 재생 시 중복 적용되지 않게 명령 revision에 묶는다.
- golden `career-02-season.json`은 `{ rulesetVersion, contentPackVersion, startSeason: {FAST, CHAPTER}, commands: {FAST, CHAPTER} }` 구조다. 각 모드 명령 로그의 `START_SEASON` 바로 뒤에 `RESOLVE_ROLE`을 넣는다.

## 제약

- RNG 소비 순서를 문서화하고 테스트로 고정한다(RULE-RNG-001). 새 roll은 경쟁자 생성뿐이다.
- `Date`·`Math.random` 사용 금지(domain). 정수·고정소수점, 반올림은 각 함수에서 한 번. 정렬은 안정 키.
- Base OVR·`attributes`는 이 작업에서 바뀌지 않는다(포지션 전환도 능력치를 즉시 바꾸지 않는다 — SCR-012 인수 조건).
- 모든 오류 문구·주석·룰셋 문구는 한국어. 커밋 메시지는 `T-2-002: …`로 시작, 브랜치는 `T-2-002-…`.
- 서브에이전트 리뷰를 띄우지 않는다. gstack `/review`·`/codex`·adversarial 리뷰·`/simplify`·병렬 fork 전부 금지. 유일한 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드)다. 리뷰는 오케스트레이터가 한다.
- PR 직전 `git fetch origin && git merge origin/main`으로 최신 main을 합친다. `pnpm-lock.yaml` 충돌은 손으로 고치지 말고 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile`로 재생성한 뒤 전체 체인을 다시 돌린다.
- 명세를 고치지 않는다. D-26·D-34와 충돌하는 지점이 있으면 그 항목만 PR 본문에 적고 나머지를 끝낸다.
