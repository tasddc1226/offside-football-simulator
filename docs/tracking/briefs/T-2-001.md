# T-2-001: 시즌 구조 — FootballSeason·12 step 캘린더·START_SEASON/SETTLE_SEASON·ADVANCE 재정의·checkpoint·결정 예산

## 목표

Phase 2의 첫 도메인 작업. 커리어에 "축구 시즌"이라는 시간 구조를 넣는다. 룰셋이 정의한 12 step 캘린더 위에서 `START_SEASON`으로 시즌을 열고, `ADVANCE`가 "다음 결정이 열리는 step 또는 결산까지" 진행하며, `SETTLE_SEASON`으로 시즌을 닫는다. 경기 결과·선발·통계는 이 작업이 아니다(T-2-002·T-2-003). 이 작업은 **구조와 상태 기계, 결정론, checkpoint 규칙**을 만든다.

## 데이터 계약(D-24, 02 DATA-SEA-001을 domain 타입으로)

```ts
type FootballSeason = {
  index: number;                 // 커리어 안의 시즌 순번(1부터)
  serviceSeasonId: string;       // 커리어 생성 시 createdServiceSeasonId
  simulationMode: 'FAST' | 'CHAPTER';
  calendarId: string;            // 룰셋 leagueCalendar.id
  currentStep: number;           // 1..12, 단조 증가
  phase: SeasonPhase;            // steps[currentStep-1].phase의 캐시
  steps: SeasonStep[];           // 길이 12
  teamId: string;
  squadRole: SquadRole;
  competitions: CompetitionRecord[];
  matches: MatchRecord[];        // T-2-003이 채운다. 이 작업에서는 항상 []
  ageReferenceStep: 1;           // 11 "나이·시즌 경계": 나이는 step 1 기준
};
type SeasonStep = { index: number; phase: SeasonPhase; windowOpen: boolean; decisionSlots: DecisionSlot[]; summary: StepSummary | null };
type DecisionSlot = { kind: 'EVENT' | 'CHAPTER' | 'CONTRACT' | 'ROLE' | 'INJURY' | 'NATIONAL_TEAM' | 'SETTLEMENT'; required: boolean; importance?: 'MAJOR' | 'MINOR'; refId?: string };
type StepSummary = { passedAtRevision: number; decisionsOpened: number; matchesPlayed: number };  // matchesPlayed는 이 작업에서 0
type CompetitionRecord = { competitionId: string; kind: 'LEAGUE' | 'CUP'; played: number; won: number; drawn: number; lost: number; goalsFor: number; goalsAgainst: number; position: number | null; cupRound: string | null };
type MatchRecord = { /* 이 작업은 타입만 정의(id·step·competitionId·opponentTeamId·home·result) — 값은 T-2-003 */ };
type SeasonSummary = { index: number; simulationMode: SimulationMode; teamId: string; competitions: CompetitionRecord[]; settledAtRevision: number };
```

- `CareerState`에 `season: FootballSeason | null`과 `seasonHistory: SeasonSummary[]`를 추가한다. 기존 `currentStep`·`seasonPhase`·`simulationMode`는 유지하되 시즌이 있을 때는 `season`의 캐시다(Phase 1 화면 호환 — 화면 코드는 바꾸지 않는다).
- `TimelineEntry.kind`에 `SEASON_STARTED`·`STEP_PASSED`를 추가한다(`SEASON_SETTLED`는 이미 있다). 문장은 넣지 않는다(D-12).
- `CheckpointType`에 `STEP_BOUNDARY`를 추가한다(11 "데이터 반영").
- `schemaVersion: 1` 유지(출시 전). 새 필드는 기존 fixture에서 `season: null`, `seasonHistory: []`로 채운다.

## 룰셋 계약(D-33)

`packages/content/rulesets/1.0.0/ruleset.json`(스키마 `packages/content/src/schema/ruleset.ts`, domain 타입 `packages/domain/src/ruleset.ts`)에 `leagueCalendar`를 추가한다. 기본 캘린더는 RULE-TIME-001 표 그대로다.

```ts
leagueCalendar: {
  id: 'default-12',
  steps: Array<{ index: 1..12; phase: SeasonPhase; windowOpen: boolean; slots: Array<{ kind: DecisionSlot['kind']; required: boolean; importance?: 'MAJOR' | 'MINOR' }> }>;
  transferWindowStep: 7;
  cupRounds: Array<{ round: 'R1' | 'SEMI' | 'FINAL'; step: number }>;   // 5, 9, 11
}
```

- 슬롯 표: step 1 필수 1(ROLE), 2 선택 0~1(EVENT), 3 챕터 0~1(CHAPTER MAJOR 후보), 4 EVENT, 5 EVENT, 6 CHAPTER MINOR, 7 필수 0~1(CONTRACT, windowOpen), 8 EVENT(NATIONAL_TEAM 창), 9 EVENT, 10 CHAPTER, 11 CHAPTER MAJOR, 12 필수 1(SETTLEMENT).
- 룰셋 검증(zod superRefine): step 12개·index 연속·phase 순서(PRESEASON → LEAGUE → SETTLEMENT, 되돌아가지 않음)·step 12는 SETTLEMENT 필수 슬롯 1개.
- 룰셋 버전은 `1.0.0` 유지, manifest checksum 갱신(기존 절차). `packages/domain/src/__fixtures__/ruleset-proto.json`과 `packages/fixtures/src/career-01/ruleset-proto.json`에도 같은 `leagueCalendar`를 넣는다.
- 리그 팀 수·컵 라운드 수·경쟁자 분포(D-33의 나머지)는 T-2-002가 룰셋에 넣는다. 이 작업은 캘린더만.

## 명령·진행 규칙(D-25)

- `START_SEASON { simulationMode }`(CMD-SIM-001): `status === 'ACTIVE'`, `contract !== null`, `season === null`, `pending === null`일 때만. 시즌을 만들고 `currentStep = 1`, step 1의 슬롯을 연다(`pending`에 결정으로 노출 — 아래). `simulationMode`는 시즌 동안 고정. 실패 코드: `VALIDATION_FAILED { reason: 'SEASON_ALREADY_ACTIVE' | 'NO_CONTRACT' | 'PENDING_DECISION' | 'NOT_ACTIVE' }`.
- `ADVANCE`(CMD-SIM-002, 기존 명령 재정의): 시즌이 없으면 **지금 동작 그대로**(Phase 1 이벤트·제안 흐름, golden 불변). 시즌이 있으면 현재 step부터 다음 결정이 열리는 step 또는 step 12까지 진행한다: 지나가는 step마다 `summary`를 채우고 `STEP_PASSED` 타임라인을 남긴다. 결정이 열린 step에서 멈추고 `pending`을 채운다. 같은 step에 결정이 둘 이상이면 CONTRACT·INJURY·ROLE → EVENT → CHAPTER 순으로 하나씩(RULE-TIME-002). step 12에 도달하면 SETTLEMENT 슬롯을 `pending`으로 연다.
- 모드 필터(RULE-TIME-003): FAST는 `required` 슬롯·CONTRACT·INJURY·ROLE·MAJOR CHAPTER만 연다. CHAPTER는 전부. FAST에서 건너뛴 EVENT/MINOR CHAPTER는 노출되지 않은 것으로 기록하고 **roll을 소비하지 않는다**.
- 결정 예산(RULE-TIME-004): 시즌 시작 시 룰셋 슬롯에서 모드별 상한(CHAPTER 10·FAST 6, 챕터 4)을 넘는 선택 슬롯을 **결정론적으로**(step 오름차순 뒤쪽부터, 같은 step이면 importance MINOR 먼저) 잘라낸다. 잘린 슬롯은 `season.steps[].decisionSlots`에서 `skippedByBudget: true`로 남긴다(다음 시즌 후보는 Phase 2 후반 몫).
- EVENT 슬롯의 실제 이벤트 선택은 지금처럼 `ADVANCE.payload.eligibleEvents`(content가 고른 후보, 가중 roll)로 한다 — 슬롯은 "이 step에 이벤트 결정이 열린다"만 뜻한다. `eligibleEvents`가 비어 있으면 그 슬롯은 건너뛴다(roll 없음). CHAPTER 슬롯은 이 작업에서 `pending: { kind: 'CHAPTER', step, importance }`로 열되 실제 판단 내용은 T-2-004 몫이므로 `RESOLVE_CHAPTER` 같은 새 명령은 만들지 않고, `ADVANCE`가 CHAPTER pending을 "자동 통과"로 닫는다(플레이스홀더, 주석으로 명시). CONTRACT·ROLE·INJURY·NATIONAL_TEAM 슬롯도 같은 방식으로 자동 통과한다.
- `SETTLE_SEASON`(CMD-SIM-003): `season.currentStep === 12`이고 SETTLEMENT pending이 열려 있을 때만. `seasonHistory`에 `SeasonSummary`를 push, `season = null`, `age += 1`(11 "나이·시즌 경계"), `state.form/fitness/morale`를 룰셋 상수로 회귀(D-29 — 상수가 없으면 룰셋에 `seasonBoundaryReset { form, fitness, morale }` 추가), `SEASON_SETTLED` 타임라인, `pending = null`. 성장식·능력 변화는 T-2-005 몫이라 여기서는 능력치를 바꾸지 않는다. 실패 코드 `VALIDATION_FAILED { reason: 'SEASON_NOT_SETTLEABLE' }`.
- checkpoint: 결정이 열린 step과 step 12에 멈출 때의 Snapshot은 `STEP_BOUNDARY`(결정이 없는 통과 step은 Snapshot을 남기지 않는다 — ADVANCE 한 번이 한 revision).
- 재생 결정론: 같은 seed·명령 로그에서 시즌 진행이 byte-identical. step 경계에서 저장한 Snapshot으로 재개해 끝까지 간 결산 hash == 연속 실행 hash(11 "테스트").

## 제약

- RNG 소비 순서를 문서화하고 테스트로 고정한다(RULE-RNG-001). 새 roll은 EVENT 슬롯의 이벤트 선택(기존)뿐이다 — 이 작업은 다른 roll을 추가하지 않는다.
- `Date`·`Math.random` 사용 금지(domain). 정수·고정소수점만.
- 모든 오류 문구·주석은 한국어. 커밋 메시지는 `T-2-001: …`로 시작, 브랜치는 `T-2-001-…`.
- 서브에이전트 리뷰를 띄우지 않는다. gstack `/review`·`/codex`·adversarial 리뷰·`/simplify`·병렬 fork 전부 금지. 유일한 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드)다. 리뷰는 오케스트레이터가 한다.
- PR 직전 `git fetch origin && git merge origin/main`으로 최신 main을 합친다. `pnpm-lock.yaml` 충돌은 손으로 고치지 말고 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile`로 재생성한 뒤 전체 체인을 다시 돌린다.
- 명세를 고치지 않는다. D-24·D-25와 충돌하는 지점이 있으면 그 항목만 PR 본문에 적고 나머지를 끝낸다.
