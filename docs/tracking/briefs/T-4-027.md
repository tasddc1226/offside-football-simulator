# T-4-027: Phase 3+4 확장 팩 격리 staging — 0.3.0 실플레이 QA

## 목표

일반 staging LINE TEST(`svc_line_test`, 콘텐츠 팩 0.1.0)을 유지하면서, Phase 3+4 확장 콘텐츠 팩 0.3.0을 실제 브라우저에서 검증할 별도 웹/API Worker를 만든다. expanded 환경은 명시적인 수동 배포만 허용하고 production·PR preview·기본 빌드의 신규 커리어 버전은 0.1.0으로 유지한다.

0.3.0 manifest는 ruleset 1.0.0과 호환되고 정적 번들에 포함돼 있지만 `playtested: false`다. 이 환경은 그 상태를 해제하는 실플레이 QA 전용이며 출시 환경이 아니다.

## 불변 조건

- `ACTIVE_CONTENT_PACK_VERSION`은 0.1.0이다. `vite build --mode expanded`만 0.3.0을 선택한다.
- 기존 `ci.yml`의 main → 일반 staging 자동 배포와 PR preview 배포는 수정하지 않는다.
- 일반 staging의 Worker, origin, `ACTIVE_SERVICE_SEASON_ID=svc_line_test`, 0.1.0 seed를 수정하지 않는다.
- 새 Worker는 staging D1을 공유하되 서비스 시즌과 origin은 expanded 전용 값만 사용한다.
- 신규 커리어는 선택한 서비스 시즌의 ruleset/content pack과 정확히 일치해야 한다. 기존 커리어 후속 PUT·replay는 현재 포인터와 비교하지 않고 생성 당시 버전에 계속 고정한다.
- expanded QA 커리어와 서비스 시즌 행은 production 데이터와 섞지 않는다.

## 리소스

| 구분            | 값                                                                             |
| --------------- | ------------------------------------------------------------------------------ |
| 웹 Worker       | `offside-web-expanded` / `https://offside-web-expanded.tasddc1569.workers.dev` |
| API Worker      | `offside-api-expanded` / `https://offside-api-expanded.tasddc1569.workers.dev` |
| D1              | 기존 `offside-staging` (`37688e3f-b905-4240-abdb-e23e778dfad9`)                |
| 서비스 시즌     | `svc_phase34_qa`, PRESEASON, `is_test=1`, ruleset 1.0.0, pack 0.3.0            |
| API 허용 origin | expanded 웹 origin 한 개만 허용                                                |
| 배포            | `.github/workflows/deploy-expanded-staging.yml` 수동 `workflow_dispatch`       |

Workers 두 개만 새로 만들고 기존 계정의 staging D1을 공유한다. 별도 유료 데이터 자원이나 production binding은 만들지 않는다.

## 구현

1. `apps/web/src/engine/versions.ts`
   - 순수 선택 함수가 expanded mode만 0.3.0으로 고른다.
   - DEV localStorage 오버라이드는 기존대로 DEV에서만 허용한다.
   - production·preview·staging·toss mode는 override 값이 있어도 0.1.0이다.
   - `contentForCareer(state)`와 engine-client의 기존 버전 pinning은 그대로 사용한다.
2. `apps/api/wrangler.jsonc`, `apps/web/wrangler.jsonc`
   - `expanded` env와 별도 Worker 이름을 추가한다.
   - API의 D1 binding만 일반 staging과 같고, `ALLOWED_ORIGINS`, `WEB_APP_URL`, Google callback, 서비스 시즌 포인터는 expanded URL/ID로 제한한다.
3. `apps/api/seeds/bootstrap-expanded.sql`
   - `svc_phase34_qa` 한 행만 멱등 upsert한다. 일반 non-production bootstrap과 분리되어 수동 workflow 밖에서는 실행되지 않는다.
4. `apps/api/src/sync/apply-sync.ts`
   - 새 커리어 생성 시 서비스 시즌 행의 versions와 PUT body versions를 비교한다.
   - 기존 커리어 분기에는 이 검사를 추가하지 않아 포인터 변경이 replay나 후속 동기화를 막지 않는다.
5. `.github/workflows/deploy-expanded-staging.yml`
   - main ref와 `DEPLOY_EXPANDED_QA` 확인 문구를 모두 요구한다.
   - 로컬 검증·expanded 웹 build를 원격 쓰기보다 먼저 수행한다.
   - 일반 staging job과 같은 `cloudflare-staging` concurrency group으로 공유 D1 migration/seed를 직렬화한다.
   - 배포 뒤 health, 서비스 시즌 id/versions/isTest, 허용·비허용 CORS origin, 웹 root를 확인한다.

## 로컬 검증

```bash
pnpm install --frozen-lockfile
pnpm --filter @offside/content exec vitest run packs/0.3.0/pack.test.ts src/packs/load-content-pack.test.ts
pnpm --filter @offside/web exec vitest run src/engine/versions.test.ts src/engine/engine.test.ts
pnpm --filter @offside/api exec vitest run src/routes/careers.test.ts --testNamePattern '서비스 시즌 manifest'
pnpm --filter @offside/content typecheck
pnpm --filter @offside/web typecheck
pnpm --filter @offside/api typecheck
VITE_API_BASE_URL=https://offside-api-expanded.tasddc1569.workers.dev pnpm --filter @offside/web build:expanded
pnpm --filter @offside/api exec wrangler deploy --env expanded --dry-run
pnpm --filter @offside/web exec wrangler deploy --env expanded --dry-run
```

`db:migrate:expanded`, `db:seed:expanded`, `deploy:expanded`는 원격 상태를 바꾸므로 로컬 검증에서는 실행하지 않는다.

## 배포와 사후 확인

이 workflow가 main에 반영된 뒤에만 실행한다. 첫 실행 시 `expanded-staging` GitHub Environment가
생성되고 repository-level Cloudflare secrets를 사용한다. 별도 승인 보호 규칙이 필요하면 dispatch 전에 설정한다.

```bash
gh workflow run deploy-expanded-staging.yml --ref main -f confirmation=DEPLOY_EXPANDED_QA
```

workflow가 성공하면 다음을 확인한다.

1. `GET https://offside-api-expanded.tasddc1569.workers.dev/v1/service-seasons/current`가 `svc_phase34_qa`, ruleset 1.0.0, pack 0.3.0, `isTest: true`를 반환한다.
2. expanded 웹의 설정/선수 확정 화면에서 활성 팩 0.3.0을 확인하고 새 QA 커리어를 만든다.
3. 저장된 새 커리어의 `created_service_season_id=svc_phase34_qa`, `content_pack_version=0.3.0`을 staging D1에서 확인한다.
4. 기존 0.1.0 커리어를 열어 이벤트 진행·새로고침·동기화 후에도 0.1.0인지 확인한다.
5. expanded profile 리허설로 FAST·CHAPTER를 각각 한 시즌 완주한다. 이 경로는 실 API를 스텁하지
   않고, 0.3.0에서 실제로 만난 범용·부상·관계 이벤트 화면 제목을 attachment에 남긴다.

```bash
E2E_STAGING_PROFILE=expanded \
E2E_STAGING_SEASON_NAME='PHASE 3+4 QA' \
E2E_STAGING_URL=https://offside-web-expanded.tasddc1569.workers.dev \
E2E_STAGING_API_URL=https://offside-api-expanded.tasddc1569.workers.dev \
pnpm --filter @offside/web e2e:staging
```

실 staging E2E는 커리어·프로필·분석 이벤트를 실제 D1에 쓰므로 자동 workflow에는 넣지 않고 담당자가
한 번만 실행한다. 복구 코드 원문은 로그·attachment에 남기지 않는다.

## 중단·롤백

- 신규 QA 생성을 즉시 멈출 때는 `svc_phase34_qa.status`를 LOCKED로 바꾼다. 다음 수동 배포는 seed가 PRESEASON으로 되돌리므로 재개 의사가 있을 때만 dispatch한다.
- expanded Worker에 문제가 있어도 일반 staging과 production Worker/포인터는 바뀌지 않는다. 링크 배포를 중단하고 Worker 이전 버전으로 rollback하거나 QA Worker만 제거한다.
- QA 종료 후에도 0.3.0 팩 코드와 `svc_phase34_qa` 커리어 행은 유지한다. 팩을 제거하면 저장된 0.3.0 커리어를 다시 열 수 없다.
- 기존 커리어는 생성 당시 버전에 고정되므로 expanded 포인터를 변경하거나 Worker를 중단해도 0.1.0 데이터 자체를 변환하지 않는다.

## 권한·제약

- GitHub Actions에는 기존 `CLOUDFLARE_API_TOKEN`, `CLOUDFLARE_ACCOUNT_ID`가 필요하다. 최소 범위는 Workers Scripts 편집과 staging D1 편집이다.
- 사후 확인 담당자는 staging D1 읽기 권한만 있으면 된다. production D1/Worker 권한은 이 절차에 필요하지 않다.
- 새 API Worker에는 Google secret이 자동 복사되지 않는다. 이번 QA는 익명 프로필·복구 코드 기준이며 Google 연결을 시험하려면 expanded Worker에 별도로 secret을 넣는 승인 작업이 필요하다.
- 서비스 시즌 응답은 HTTP 60초, 웹 query는 최대 5분 캐시될 수 있다. 새 배포 확인은 새 브라우저 context에서 수행한다.
- 서버 복구 응답이 `createdServiceSeasonId`를 포함하지 않아 현재 포인터로 로컬 record를 복원하는 기존 한계는 이 작업 범위 밖이다. 저장된 content pack version과 서버 career 행은 바뀌지 않는다.
