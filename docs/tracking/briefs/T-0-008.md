# T-0-008: `apps/api` 커리어 동기화 — `GET /careers`, `GET /careers/{id}`, `PUT /careers/{id}`(If-Match·409·422), 100회 병렬 멱등 테스트

## 목표

ADR-002의 동기화 API를 만든다. 클라이언트가 checkpoint마다 보내는 Snapshot + 명령 로그를 낙관적 잠금(`If-Match` = `baseRevision`)으로 받아 D1에 원자적으로 저장하고, revision이 어긋나면 `409 CAREER_REVISION_CONFLICT`와 서버 revision을 돌려준다. 같은 요청 100개가 동시에 와도 서버에는 결과가 하나다(phase-00 완료 조건). 서버는 시뮬레이션·리플레이를 하지 않는다(ADR-003, 검증은 API-VER-001 후속). 클라이언트 쪽 동기화 큐는 T-0-015다.

### 설계 결정(변경 금지. 의문이 있으면 질문)

1. **`If-Match`와 `baseRevision`은 같아야 한다.** 다르면 `400 VALIDATION_FAILED`, details `{ reason: 'IF_MATCH_MISMATCH' }`. `If-Match`가 없으면 같은 코드에 `{ reason: 'IF_MATCH_REQUIRED' }`.
2. **첫 동기화**: career 행이 없으면 `baseRevision`은 0이어야 하고(아니면 `404 CAREER_NOT_FOUND`), `createdServiceSeasonId`가 `service_seasons`에 있어야 한다(없으면 `400 VALIDATION_FAILED`, `{ reason: 'SERVICE_SEASON_UNKNOWN' }`). 세 버전 필드를 그대로 고정하고 소유자는 세션 프로필이다.
3. **이후 동기화**: 소유자가 다르면 `403 CAREER_NOT_OWNED`; `status = 'ARCHIVED'`면 `409 CAREER_ARCHIVED`; 버전 2종이 저장값과 다르면 `422 VERSION_MISMATCH`; `serverRevision !== baseRevision`이면 아래 4의 예외가 아닌 한 `409 CAREER_REVISION_CONFLICT`, details `RevisionConflictDetailsSchema` = `{ serverRevision, serverSnapshotUrl: '/v1/careers/{id}' }`.
4. **이미 반영된 요청은 성공으로 본다(멱등).** `serverRevision !== baseRevision`이지만 요청 `snapshot.revision <= serverRevision`이고 서버에 같은 `(revision, stateHash)` Snapshot이 남아 있으면 `200`에 현재 `serverRevision`을 돌려준다(쓰기 없음). 이 규칙 덕에 같은 PUT 100개가 동시에 와도 1개가 쓰고 99개가 200을 받는다. 남아 있지 않으면(5개 보존 창 밖) 409다.
5. **서버 측 무결성 검사(리플레이 아님)**: `stateHash === sha256Hex(state)`(WebCrypto), `SnapshotStateEnvelopeSchema.parse(JSON.parse(state))`, `state.careerId === {id}`, `state.rngState`가 `snapshot.rngState`와 깊은 동일, `state.rulesetVersion`·`contentPackVersion`이 본문과 동일, commands가 있으면 마지막 `resultHash === snapshot.stateHash`. 하나라도 어긋나면 `400 VALIDATION_FAILED`, details `{ reason: 'STATE_HASH_MISMATCH' | 'STATE_INVALID' | 'CAREER_ID_MISMATCH' | 'RNG_STATE_MISMATCH' | 'VERSION_FIELD_MISMATCH' | 'RESULT_HASH_MISMATCH' }`. `state` 길이가 256KB(`SNAPSHOT_STATE_RECOMMENDED_BYTES`)를 넘으면 거부하지 않고 로그에 `warn`(1MB 본문 상한은 T-0-006 bodyGuard).
6. **쓰기는 batch 하나**: `[UPDATE careers SET revision = :to, status = :status, last_synced_at, updated_at WHERE id = :id AND revision = :from]` + `INSERT snapshots` + `INSERT command_log × n`. 첫 동기화는 `INSERT careers`가 UPDATE 자리에 온다. batch가 제약 위반(동시 쓰기)으로 실패하면 서버 revision을 다시 읽어 4를 적용하고, 아니면 409. batch 뒤 `pruneSnapshots(keep 5)`를 별도로 실행한다(실패해도 200. 로그만).
7. **`status`는 state에서 읽는다.** 파싱한 state의 `status`가 `DRAFT|ACTIVE|RETIRED|ARCHIVED` 중 하나면 careers 행에 반영하고, 아니면 `STATE_INVALID`.
8. **응답 `meta.careerRevision`**을 모든 커리어 라우트에 채운다. `PUT` 성공 응답은 `PutCareerResponseSchema`(`verificationStatus`는 저장값, 기본 `PENDING`).
9. **모든 커리어 라우트는 세션 필수**(`requireProfile`). `PUT`은 T-0-006의 Origin·JSON·Idempotency-Key 규칙을 그대로 탄다.

### 만들 것

1. `src/routes/careers.ts`
   - `GET /v1/careers?limit&cursor`: `listCareersByOwner` → `CareerSummaryListSchema`(`lastSyncedAt` = `last_synced_at`). `limit` 기본 20, 최대 50(초과는 50으로 자름).
   - `GET /v1/careers/:id?since=<revision>`: 소유자 확인 → 최신 Snapshot(`CareerSnapshotSchema` 전체 필드, `id`는 `${careerId}:${revision}`) + `listCommandsSince(since ?? 0)` → `GetCareerResponseSchema`. 없으면 404, 남의 것이면 403.
   - `PUT /v1/careers/:id`: 위 결정 1~9. 본문은 `PutCareerBodySchema.parse`(T-0-006 bodyGuard가 넘긴 rawBody 사용).
2. `src/sync/verify-snapshot.ts`: 결정 5의 순수 검사 함수 `verifyIncomingSnapshot(body, careerId): Promise<{ ok: true; status; parsed } | { ok: false; reason }>`.
3. `src/sync/apply-sync.ts`: 결정 2·3·4·6·7의 흐름을 `applySync(db, { profileId, careerId, body, now })` 하나로. 라우트는 얇게.
4. `src/app.ts`에 라우트 등록.

### 테스트 (Vitest + 로컬 D1, T-0-006의 세션 헬퍼 사용)

- 픽스처: `@offside/fixtures`의 `career01`을 **직접 실행하지 않는다**(api는 engine-client를 import할 수 없다). 대신 테스트 파일 안에 canonical JSON 문자열 state 2~3개와 그 SHA-256을 만들어 쓰는 헬퍼 `makeSnapshot({ careerId, revision, status })`를 둔다(state는 최소 형태 `{ schemaVersion: 1, careerId, status, rngState: { s: [1,2,3,4], draws: 0 }, rulesetVersion, contentPackVersion }`).
- 첫 동기화: `If-Match: 0`, `baseRevision 0`, commands 1개(revision 1), snapshot revision 1 → 200, careers 행 생성(소유자 = 세션 프로필, 버전 고정), snapshots 1, command_log 1. 응답이 `successEnvelope(PutCareerResponseSchema)` 통과, `meta.careerRevision === 1`.
- 이어서 `If-Match: 1`, commands 2~3, snapshot 3 → 200, revision 3. `GET /careers/{id}?since=1` → snapshot revision 3 + commands 2·3. `GET /careers` → 1건, `lastSyncedAt` 있음.
- 잘못된 revision: `If-Match: 1`(서버 3) → 409 `CAREER_REVISION_CONFLICT`, details `{ serverRevision: 3, serverSnapshotUrl: '/v1/careers/{id}' }`, 아무것도 쓰이지 않음.
- `If-Match` 없음 → 400 `IF_MATCH_REQUIRED`; `If-Match`와 `baseRevision` 불일치 → 400 `IF_MATCH_MISMATCH`.
- 버전 드리프트: 두 번째 PUT의 `rulesetVersion`이 다르면 422 `VERSION_MISMATCH`.
- 소유권: 다른 프로필 세션으로 PUT/GET → 403 `CAREER_NOT_OWNED`; 없는 id GET → 404.
- 무결성: `stateHash` 한 글자 변조 → 400 `STATE_HASH_MISMATCH`; `rngState.draws` 변조 → 400 `RNG_STATE_MISMATCH`; 마지막 command `resultHash` 불일치 → 400 `RESULT_HASH_MISMATCH`; state의 `careerId` 다름 → 400 `CAREER_ID_MISMATCH`; `createdServiceSeasonId` 미존재 → 400 `SERVICE_SEASON_UNKNOWN`.
- **100회 병렬 멱등**: 같은 PUT(같은 `Idempotency-Key`, 같은 본문)을 `Promise.all`로 100개 → 전부 200, `revision` 동일, careers.revision은 한 번만 증가, snapshots·command_log 행은 1세트. (일부는 idempotency 재생, 일부는 결정 4의 "이미 반영됨" 경로일 수 있다. 두 경로 모두 200이어야 한다.)
- **100회 병렬 경쟁**: 같은 `baseRevision`에 서로 다른 내용(다른 stateHash, 다른 Idempotency-Key) 100개 → 정확히 1개 200, 나머지 409, DB에는 1세트.
- ARCHIVED 커리어(직접 `status` 갱신) → 409 `CAREER_ARCHIVED`.
- 보존: revision 1~8을 순서대로 동기화하면 snapshots에 4~8만 남고 command_log는 8개 전부.
- 재업로드: `baseRevision 3`, commands 빈 배열, snapshot revision 3(서버와 같은 hash) → 200, 쓰기 없음. 같은 revision인데 hash 다름 → 409.
- 모든 라우트 세션 없음 → 401 `PROFILE_REQUIRED`.

- 서버는 `packages/domain`의 `simulate`를 호출하지 않는다(리플레이는 API-VER-001 후속). `sha256Hex`는 WebCrypto.

- 커밋 메시지 `T-0-008: …`. 브랜치 `T-0-008-api-career-sync`.
- 커밋 트레일러: `Co-Authored-By: Claude Sonnet 5 <noreply@anthropic.com>`.
