# T-3-004: Phase 3 계약·이적 상태 strict 검증과 동기화 회귀 (contracts + api + engine-client)

## 목표

T-3-003(PR #54, main `e1ae3de`)이 완성한 제안·협상·이적·임대 상태를 모든 저장/동기화 경계에서 엄격히 검증한다. 끝나면 `career-10-transfer`·`career-11-loan`의 모든 중간 Snapshot과 네 명령 payload가 contracts를 통과하고, Node↔workerd·API PUT 3경로·engine-client replay/fork/import·브라우저 Worker가 같은 최종 hash를 내며, 임대/clubHistory가 포함된 Snapshot 크기가 예산 안이라는 자동 증거가 있다. 기능·UI는 추가하지 않는다.

## 1. payload·상태 strict 계약

- `COMMAND_PAYLOAD_SCHEMAS`/`CommandRequestSchema`/`CommandLogEntrySchema`가 아래를 strict하게 받는 양·음성 테스트를 둔다. 알려지지 않은 키, 잘못된 enum, 빈 offerId, 잘못된 null은 거부해야 한다.
  - `NEGOTIATE { offerId, ask: WAGE|ROLE|LENGTH }`
  - `ACCEPT_OFFER { offerId }`
  - `REJECT_OFFER { offerId: string|null }`
  - `LOAN_RETURN { decision: RETURN|PERMANENT }`
- domain의 `Command`/`Pending`/`Offer`/`Contract`/`ClubStint`/`CareerState`와 contracts inferred type이 `expectTypeOf`로 1:1인지 고정한다.
- `career-10-transfer`·`career-11-loan` 명령 로그를 처음부터 재생하고 **매 명령 뒤** `CareerStateSchema.parse` → canonical 재직렬화 → `stateHash` 재계산을 수행한다. 다음 중간 상태를 명시적으로 단언한다: COUNTERED/WITHDRAWN offer, TRANSFER/FREE_AGENT 원자 전환, LOAN의 `parentContract.suspended`, LOAN_RETURN 뒤 열린 stint 1개, 자동 FA 복원 뒤 원소속 context.
- `packages/fixtures/src`의 실제 `*.golden.json` 집합과 `KNOWN_GOLDEN_FILES`가 정확히 같아야 한다. 목록을 조용히 누락해 통과시키지 않는다.

## 2. Snapshot·PUT 크기

- 기존 `snapshot-size.test.ts` 표에 career-10·11을 추가하고 다음 시점을 각각 잰다: 제안 3개 이상 시장, 협상 직후, 이적 직후, 임대 중(parentContract 포함), 3시즌 최종 상태.
- 상태 canonical JSON은 `SNAPSHOT_STATE_RECOMMENDED_BYTES` 256KB 미만, Snapshot+해당 fixture 명령 로그 PUT 본문은 `REQUEST_BODY_MAX_BYTES` 1MB 미만을 테스트 상한으로 고정한다.
- PR 본문에 바이트 표와 기존 Phase 2 최대 15.3KB 대비 증분/예산 비율을 적는다. 128KB를 넘으면 구현을 압축하지 말고 가장 큰 필드별 바이트 근거와 후속 설계만 보고한다.

## 3. API·workerd 동기화 3경로

- `cross-runtime-hash`와 worker probe에 career-10·11을 추가한다. Node와 Miniflare/workerd 모두 fixture를 처음부터 재생해 revision·stateHash·`rngState.draws`·`verifySnapshot` 결과가 golden과 정확히 같아야 한다.
- `season-sync.test.ts` 패턴으로 transfer와 loan fixture 각각을 다음 세 경로로 PUT한다: (a) 한 번에 전체 로그, (b) checkpoint/시장 결정 경계별 분할 PUT(`baseRevision`·If-Match 연쇄), (c) 성공 응답 유실 뒤 같은 Idempotency-Key·같은 body 재시도. 세 경로의 최종 revision/hash/verificationStatus와 열린 permanent stint 수가 같다.
- 잘못된 `parentContract`, 겹치는 열린 stint 2개, LOAN인데 parentContract null인 조작 Snapshot은 contracts 또는 서버 무결성 경계에서 거부되어야 한다. 현재 정본이 그 교차 불변식을 검증하지 않는다면 검증 함수를 가장 좁은 경계에 추가하되 domain 상태를 변형하지 않는다.
- DB 스키마·migration은 바꾸지 않는다. `db:check`가 그대로 통과해야 한다.

## 4. engine-client·브라우저 Worker

- career-10·11에 대해 replay, fork-by-replay, server import가 같은 final hash를 내고 명령 로그 순서·checkpoint가 보존되는 테스트를 추가한다. fork는 새 careerId 외 상태 의미가 같고, 중복 ACCEPT/LOAN_RETURN 재시도가 계약·stint를 한 번만 만든다는 기존 revision/멱등 규칙을 검증한다.
- LocalStore 계약에 `CONTRACT_CONFIRMED`, `SEASON_SETTLED`, `STEP_BOUNDARY`에서 transfer/loan Snapshot 저장·복원 항목을 추가한다. 구현 변경은 회귀가 드러낸 일반화 누락만 허용한다.
- 브라우저 Web Worker hash-probe에 career-10·11 전체 replay를 추가한다. 각각 5,000ms 미만, hash/revision/draws golden 일치. Node와 브라우저 실측 ms를 PR 본문에 적는다.

## 테스트·인수 조건

- 위 양·음성/중간 상태/3경로/replay·fork·import/크기 테스트가 모두 자동화돼 있다.
- `pnpm install --frozen-lockfile && pnpm lint && pnpm lint:deps && pnpm typecheck && pnpm test && pnpm build && pnpm --filter @offside/web check:bundle && E2E_PORT=5195 pnpm --filter @offside/web e2e && pnpm --filter @offside/api db:check` 통과.
- 실 API e2e가 로컬 샌드박스에서 포트 권한으로 불가능하면 정확한 명령·오류를 적고, 가능한 unit/Miniflare 체인과 GitHub CI를 끝까지 완료한다. 실패를 성공으로 보고하지 않는다.
- PR 본문: P3-3/P3-4 연결, fixture별 runtime 표, PUT 3경로 표, 크기·시간 표, 변경 파일, 범위 밖 결함. 브랜치 `T-3-004-contract-sync-validation`, 커밋 `T-3-004: ...`.
