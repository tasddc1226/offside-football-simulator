# T-0-006: `apps/api` HTTP 계층 — requestId·구조화 로그·오류 봉투·CORS/Origin, 세션 미들웨어(쿠키+Bearer), 익명 프로필 발급, `GET /profile`·`PATCH /profile/settings`, Idempotency-Key

## 목표

T-0-005의 데이터 계층 위에 서버의 공통 HTTP 규칙을 만든다. 모든 응답에 `requestId`가 있고, 오류는 contracts 봉투로만 나가며, 로그는 구조화 JSON 한 줄이고 비밀값을 담지 않는다. 세션 미들웨어는 `Authorization: Bearer`를 먼저 보고 없으면 쿠키를 본다(ADR-002·ADR-009: 두 채널 같은 세션 테이블). `GET /profile`은 세션이 없으면 익명 프로필과 세션을 만들어 `HttpOnly; Secure; SameSite=Lax; Max-Age=1년` 쿠키를 발급한다. 상태 변경 요청은 `Idempotency-Key`와 허용된 `Origin`을 요구한다. Google 로그인·복구 코드·앱인토스 세션 발급·rate limit(KV)은 이 작업이 아니다.

### 설계 결정(변경 금지. 의문이 있으면 질문)

1. **세션 토큰은 무작위 256비트(base64url)이고 서버는 SHA-256 해시만 저장한다.** 쿠키 값도 Bearer 값도 같은 토큰 형식이다. 서명 쿠키·JWT를 쓰지 않는다. 쿠키 이름 `offside_session`, 속성 `HttpOnly; Secure; SameSite=Lax; Path=/; Max-Age=31536000`. 만료는 생성 시각 + 365일 고정(슬라이딩 갱신은 후속 작업).
2. **프로필 자동 발급은 `GET /profile`에서만** 한다(07 API-PRO-001). 다른 보호 라우트는 세션이 없으면 `401 PROFILE_REQUIRED`를 돌려주고 만들지 않는다.
3. **Bearer가 헤더에 있으면 쿠키를 보지 않는다.** Bearer가 무효면 쿠키로 폴백하지 않고 `401 PROFILE_REQUIRED`다(toss 채널은 재발급 경로가 따로 있다).
4. **상태 변경 메서드(POST·PUT·PATCH·DELETE)의 규칙**: `Origin`이 허용 목록에 있어야 한다(없거나 다르면 `403 ORIGIN_NOT_ALLOWED`); `Content-Type`은 `application/json`이어야 한다(아니면 `400 VALIDATION_FAILED`, details `{ reason: 'JSON_BODY_REQUIRED' }`); 본문 1MB 초과는 `400 VALIDATION_FAILED`, details `{ reason: 'BODY_TOO_LARGE' }`; `Idempotency-Key`(`^[A-Za-z0-9_-]{8,128}$`)가 없으면 `400 VALIDATION_FAILED`, details `{ reason: 'IDEMPOTENCY_KEY_REQUIRED' }`. GET·HEAD·OPTIONS는 Origin을 요구하지 않는다.
5. **Idempotency 재생 규칙**: 세션 프로필 + 키로 조회. 저장된 응답이 있고 `request_hash`(메서드+경로+본문의 SHA-256)가 같으면 저장된 상태·본문을 그대로 돌려주고 `Idempotent-Replayed: true` 헤더를 붙인다. 해시가 다르면 `400 VALIDATION_FAILED`, details `{ reason: 'IDEMPOTENCY_KEY_REUSED' }`. 저장 대상은 2xx와 409 응답이며 TTL 24시간. 5xx·429는 저장하지 않는다. 세션이 없는 요청은 idempotency를 거치지 않는다(먼저 401).
6. **오류는 contracts가 정본이다.** `AppError { code: ErrorCode; message?; details? }`를 throw하면 오류 핸들러가 `HTTP_STATUS_BY_CODE`·`RETRYABLE_BY_CODE`로 봉투를 만든다. 예상하지 못한 예외는 `503 SERVICE_UNAVAILABLE`(retryable true)로 나가고 스택은 로그에만 남긴다. 알 수 없는 경로는 상태 404에 코드 `VALIDATION_FAILED`, message "알 수 없는 경로"(표에 404 범용 코드가 없다. 전송 계층 예외로 PR 본문에 적는다).
7. **로그는 요청당 JSON 한 줄** (`console.log(JSON.stringify(...))`): `{ level, ts, requestId, method, path, status, durationMs, profileId?, errorCode?, error? }`. `profileId`는 그대로 적어도 된다(서버 발급 불투명 ID). 헤더·쿠키·토큰·본문·이메일·선수명은 절대 넣지 않는다. 오류 로그의 `error`는 `{ name, message, stack }`이며 message에 요청 본문을 섞지 않는다.
8. **환경 변수**(`wrangler.jsonc` `vars`, 테스트는 `app.request(path, init, env)`로 주입): `ENVIRONMENT` (`local`\|`preview`\|`staging`\|`production`), `ALLOWED_ORIGINS`(쉼표 구분. local 기본 `http://localhost:5173,http://127.0.0.1:5173`). 앱인토스 origin 4종은 T-0-010이 환경별로 넣는다. 비밀값 없음.

### 만들 것

1. `src/env.ts`: `Bindings = { DB: D1Database; ENVIRONMENT: string; ALLOWED_ORIGINS: string }`, `Variables = { requestId: string; db: DrizzleDb; session?: SessionContext; startedAt: number }`, `parseAllowedOrigins(env)`.
2. `src/errors.ts`: `AppError`, `toErrorEnvelope(err, requestId)`, `errorHandler`(Hono `app.onError`), `notFoundHandler`. Zod 실패는 `VALIDATION_FAILED` + details `{ issues: [{ path, message }] }`(값은 넣지 않는다).
3. 미들웨어 `src/middleware/*.ts`, 적용 순서: `requestId` → `logger` → `cors` → `originGuard` → `bodyGuard`(Content-Type·크기) → `session` → 라우트별 `requireProfile` → `idempotency`.
   - `requestId.ts`: `req_` + UUID 생성(들어온 `X-Request-Id`는 신뢰하지 않고 무시). 응답 헤더 `X-Request-Id`. `c.set('requestId')`.
   - `logger.ts`: 결정 7. 시간은 `Date.now()` 차이.
   - `cors.ts`: `hono/cors`. `origin`은 허용 목록 함수, `allowHeaders = CORS_ALLOWED_HEADERS`, `exposeHeaders = CORS_EXPOSED_HEADERS`(contracts), `credentials: true`, `allowMethods GET,POST,PUT,PATCH,DELETE,OPTIONS`, `maxAge 600`.
   - `originGuard.ts`, `bodyGuard.ts`: 결정 4. 크기는 `Content-Length`가 있으면 먼저 보고, 없으면 본문을 읽어 바이트 수로 판단한다(읽은 본문은 `c.set('rawBody')`로 라우트에 넘겨 두 번 읽지 않는다).
   - `session.ts`: 결정 1·3. 토큰 → `sha256Hex` → `findActiveSession`. 성공하면 `c.set('session', { id, profileId, channel })`. 실패해도 여기서는 401을 내지 않는다(라우트가 결정).
   - `requireProfile.ts`: 세션 없으면 `PROFILE_REQUIRED`.
   - `idempotency.ts`: 결정 5. T-0-005 `idempotency` 저장소 사용.
4. `src/auth/session.ts`: `issueSession(db, { profileId, channel, now })` → `{ token, session }`, `sessionCookie(token, env)`(문자열 생성), `readSessionToken(c)`(Bearer 우선).
5. 라우트 `src/routes/profile.ts`
   - `GET /v1/profile`: 세션 있으면 프로필 조회(없어진 프로필이면 세션 폐기 후 새로 발급), `last_seen_at`이 1시간 이상 전이면 갱신. 세션 없으면(쿠키 없음·무효·만료) `createProfile` + `issueSession(channel 'web')` + `Set-Cookie`. Bearer가 무효인 경우만 401(결정 3). 응답 `ProfileSchema`: `linked.google = !!google_sub`, `linked.toss = !!toss_anon_key_hash`, `recoveryCodeIssuedAt`.
   - `PATCH /v1/profile/settings`: `requireProfile` → `idempotency` → 본문 `PatchProfileSettingsBodySchema.parse` → `updateSettings` → `ProfileSchema` 응답.
6. `src/app.ts`: `createApp()`가 위 미들웨어와 라우트(`/v1/health`, `/v1/profile`, `/v1/profile/settings`)를 조립. `src/index.ts`는 `export default { fetch: app.fetch }`. 기존 `app` named export와 health 테스트는 유지.
7. `wrangler.jsonc`에 `vars`(결정 8). 비밀값 없음.

### 테스트 (Vitest + T-0-005 로컬 D1)

- `GET /v1/profile` 쿠키 없음 → 200, `Set-Cookie`에 `offside_session=`, `HttpOnly`, `Secure`, `SameSite=Lax`, `Path=/`, `Max-Age=31536000` 전부 포함, 본문이 `ProfileSchema` 통과, DB에 profiles 1·sessions 1.
- 같은 쿠키로 재요청 → 같은 `id`, `Set-Cookie` 없음, 행 수 증가 없음. 위조 쿠키(임의 문자열) → 새 프로필 발급(200 + 새 쿠키). 만료 세션(직접 `expires_at` 과거로 삽입) → 새 프로필 발급.
- Bearer: `issueSession(channel 'toss')`로 만든 토큰 → 200, 같은 프로필; 무효 Bearer + 유효 쿠키 동시 → 401 `PROFILE_REQUIRED`(폴백 없음); 유효 Bearer + 다른 프로필 쿠키 → Bearer의 프로필.
- `PATCH /v1/profile/settings`: 세션 없음 → 401; `Idempotency-Key` 없음 → 400 details.reason `IDEMPOTENCY_KEY_REQUIRED`; 정상 → 200 갱신·DB 반영; 같은 키·같은 본문 재요청 → 동일 본문 + `Idempotent-Replayed: true`, `updated`가 한 번만 일어남(spy 또는 `last_seen_at`/settings 비교); 같은 키·다른 본문 → 400 `IDEMPOTENCY_KEY_REUSED`; `textScale: 110` → 400 `VALIDATION_FAILED` details.issues에 path `["textScale"]`; `Content-Type: text/plain` → 400 `JSON_BODY_REQUIRED`; 1MB + 1바이트 본문 → 400 `BODY_TOO_LARGE`.
- Origin: PATCH에 `Origin` 없음 → 403 `ORIGIN_NOT_ALLOWED`; 허용되지 않은 origin → 403; 허용 origin → 통과; GET은 Origin 없어도 200. OPTIONS 프리플라이트(허용 origin, `Access-Control-Request-Headers: content-type, idempotency-key`) → `Access-Control-Allow-Headers`에 `Content-Type`·`Idempotency-Key`·`If-Match`·`Authorization`, `Access-Control-Expose-Headers`에 `X-Request-Id`, `Access-Control-Allow-Credentials: true`. 허용되지 않은 origin의 프리플라이트에는 `Access-Control-Allow-Origin`이 없다.
- 오류 봉투: 알 수 없는 경로 → 404 + `ErrorEnvelopeSchema` 통과; 라우트에서 `throw new Error('boom')`(테스트 전용 라우트를 `createApp({ testRoutes: true })`로 추가) → 503 `SERVICE_UNAVAILABLE`, `retryable: true`, 본문에 "boom"·스택 없음; 모든 오류 응답의 `meta.requestId`가 `X-Request-Id` 헤더와 같고 `req_`로 시작.
- 로그: `console.log`를 spy → 요청마다 정확히 한 줄, `JSON.parse` 가능, 키 `requestId`·`method`·`path`·`status`·`durationMs` 존재; 쿠키·토큰 원문·`Authorization` 값·이메일 문자열이 어떤 로그 줄에도 없다(테스트가 실제 토큰 값을 잡아서 검색). 503 케이스 로그에는 `error.stack`이 있다.
- 성공 응답이 `successEnvelope(ProfileSchema)`를 통과한다.
