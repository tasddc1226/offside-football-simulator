# T-3-001: 계약·제안 v2 타입 슬라이스 — Offer/Contract v2·clubHistory·제안 상태기계·타임라인/pending 예약·조건 DSL `contract.*`·CMD-CON payload 스키마 (domain + contracts + content 스키마)

## 목표

Phase 3(계약·임대·이적, 트랙 A)과 Phase 4(부상·관계·평판, 트랙 B)를 나란히 돌리기 위한 **타입 슬라이스**. 이 작업은 로직을 거의 만들지 않는다 — 두 트랙이 같은 파일(`types.ts`·`simulate.ts`·contracts `career-state.ts`·`commands.ts`·content `condition.ts`)을 동시에 만지지 않도록, 타입·스키마·화이트리스트·타임라인 kind·pending 형태를 **한 번에** 예약한다(D-53). 시장 생성(T-3-002)·명령 처리(T-3-003)·화면(T-3-005)은 이 위에 새 파일로 붙는다. 끝나면 (1) `Offer`·`Contract`가 v2 필드를 갖고 Phase 1 첫 계약 경로가 그 기본값을 채우며, (2) `clubHistory[]`가 현 소속을 기록하고, (3) `NEGOTIATE`·`REJECT_OFFER`·`LOAN_RETURN` payload가 strict 스키마로 검증되며(도메인은 T-3-003 전까지 명시적 오류로 거부), (4) 골든이 새 필드·hash만 바뀌고 `rngState.draws`는 그대로다.

## 데이터 계약(D-44·D-45·D-46을 domain 타입으로)

```ts
export type OfferKind = 'RENEWAL' | 'TRANSFER' | 'LOAN' | 'FREE_AGENT';
export type NegotiationAsk = 'WAGE' | 'ROLE' | 'LENGTH';
export type NegotiationState = 'OPEN' | 'COUNTERED' | 'WITHDRAWN';

export type Offer = {
  id: string;
  kind: OfferKind;                               // Phase 1 첫 계약은 'FREE_AGENT'
  teamId: string;
  teamName: string;
  fromTeamId: string | null;                     // RENEWAL이면 현 구단 id, 그 외 null
  leagueTier: 'YOUTH' | 1 | 2 | 3;
  lengthSeasons: number;
  wageMinorPerWeek: number;
  signingBonusMinor: number;
  transferFeeMinor: number | null;               // TRANSFER만(표시용), 그 외 null
  rolePromise: SquadRole;                        // 유지 — D-44의 appearancePromise.squadRole은 이 필드로 갈음한다
  appearancePromise: { minutesShareBp: number }; // Phase 1: contractRules.promiseMinutesShareBp[rolePromise]
  positionPlan: Position;                        // Phase 1: profile.primaryPosition
  shirtNumber: number;
  tacticalFitEstimate: number;
  competitorSummary: { rank: number; ovrGap: number } | null;   // T-3-002가 채운다, Phase 1은 null
  validUntilRevision: number | null;             // null = 만료 없음(Phase 1 제안·안전 잔류 제안)
  negotiable: { wage: boolean; role: boolean; length: boolean }; // Phase 1: 전부 false
  negotiationState: NegotiationState;            // 생성 시 'OPEN'
  negotiatedAsk: NegotiationAsk | null;          // NEGOTIATE 뒤 T-3-003이 기록, 생성 시 null
  loan: { parentTeamId: string; seasons: 1; wageShareBp: number; buyOptionMinor: number | null } | null;
};

export type ContractKind = 'PERMANENT' | 'LOAN';
export type Contract = {
  /* 기존 필드 전부 유지 */ id; offerId; teamId; teamName; leagueTier; lengthSeasons; wageMinorPerWeek; signingBonusMinor; rolePromise; shirtNumber; signatureType: 'AUTO'; signedAtRevision;
  kind: ContractKind;                            // Phase 1: 'PERMANENT'
  appearancePromise: { minutesShareBp: number };
  positionPlan: Position;
  suspended: boolean;                            // 임대 중 원소속 계약이면 true(D-46). Phase 1: false
  loan: Offer['loan'];                           // kind LOAN일 때만 non-null
  promiseBreaches: number;                       // D-47(T-3-003이 증가), 생성 시 0
  signedSeasonIndex: number;                     // 서명 시점의 seasonHistory.length + 1 (= 다음에 시작할 시즌)
};

export type ClubStintEndReason = 'EXPIRED' | 'TRANSFERRED' | 'LOANED' | 'RETURNED' | 'RENEWED';
export type ClubStint = {
  teamId: string;
  teamName: string;
  leagueTier: Contract['leagueTier'];
  kind: ContractKind;
  fromSeasonIndex: number;                       // 이 소속으로 처음 시작하는 시즌 index
  toSeasonIndex: number | null;                  // 아직 소속이면 null
  endReason: ClubStintEndReason | null;
  contractId: string;
};
// CareerState += clubHistory: ClubStint[]  — 현 소속 항목(toSeasonIndex null)을 포함한다.
// Phase 1 acceptOffer가 첫 항목을 push한다. 마감·이어붙이기는 T-3-003(D-45) 몫.

export type MarketSummary = {
  openedAtRevision: number;
  seasonIndex: number;                           // 시장이 열린 시점의 seasonHistory.length (첫 계약은 0)
  reason: 'FIRST_CONTRACT' | 'EXPIRED' | 'INTEREST' | 'LOAN_END' | 'PRE_NEGOTIATION';
  safeOfferId: string | null;                    // 안전 잔류 제안 id(D-44), 첫 계약은 null
};
```

- `Pending` 변경(형태만 예약, 생성기는 뒤 작업):
  - `{ kind: 'OFFERS'; offers: Offer[]; market: MarketSummary }` — Phase 1 `generateOffers` 경로가 `market: { reason: 'FIRST_CONTRACT', safeOfferId: null, … }`를 채운다.
  - `{ kind: 'CONTRACT'; step: number; offers: Offer[]; market: MarketSummary }` — step 7 재계약 사전 협상(D-43 (a)). 지금은 아무도 만들지 않으므로 `isAutoPassablePending`·`slotPriority`가 지금처럼 통과시키되, `offers.length > 0`이면 통과시키지 않는다(테스트로 고정). D-53 표의 `FootballSeason.market`은 두지 않는다 — 시장 요약은 pending 안에만 있다.
  - `{ kind: 'LOAN_RETURN'; options: Array<'RETURN' | 'PERMANENT'>; buyOptionMinor: number | null }` 신규.
  - 트랙 B 예약: `{ kind: 'INJURY'; step: number; episodeId: string; eventId: string; version: number }`, `{ kind: 'NATIONAL_TEAM'; step: number; eventId: string; version: number }`(D-49·D-51·D-52). 지금은 생성기가 없으므로 값 없이 형태만 바꾸고 `isAutoPassablePending`은 그대로.
- `TimelineEntry.kind` += D-53 표 전부(한 커밋): 트랙 A `CONTRACT_RENEWED`·`TRANSFERRED`·`LOANED`·`LOAN_RETURNED`·`OFFER_REJECTED`·`OFFER_EXPIRED`·`NEGOTIATED`, 트랙 B `INJURED`·`REHAB_CHOSEN`·`RECOVERED`·`INJURY_RECURRED`·`MANAGER_CHANGED`·`NATIONAL_TEAM_CALLED`·`NATIONAL_TEAM_DECLINED`·`CAPTAIN_APPOINTED`. 문장은 넣지 않는다(D-12). 이 작업에서 실제로 기록하는 건 없다.
- `SeasonResult` += `stepSummaries: Array<{ step: number; phase: SeasonPhase; matchesPlayed: number; decisionsOpened: number; passedAtRevision: number }>`(PR #45 후속: 결산 뒤 `season`이 null이 되면서 다이어리 step 요약이 사라지는 문제). `settleSeason`이 `season.steps[].summary`에서 채운다 — 이 작업의 유일한 로직 변경이며 결산 hash는 바뀐다(골든 표에 기록).
- `Command` 유니온(domain `simulate.ts`) += `{ type: 'NEGOTIATE'; payload: { offerId: string; ask: NegotiationAsk } }`, `{ type: 'REJECT_OFFER'; payload: { offerId: string | null } }`(null = 전부 거절 → 잔류), `{ type: 'LOAN_RETURN'; payload: { decision: 'RETURN' | 'PERMANENT' } }`. 처리기는 **T-3-003 전까지** 기존 오류 코드(가장 맞는 것, 없으면 `VALIDATION_FAILED`)로 "T-3-003에서 구현" 메시지를 돌려준다 — throw 금지, 테스트로 고정.
- `schemaVersion: 1` 유지(D-53). 새 필드는 전부 기본값이 있는 additive 필드이며, 재생(fixture 명령 재실행)으로 채워진다 — 마이그레이션 코드는 쓰지 않는다. 저장 상태는 정수만(D-36).

## 제안 상태기계(D-44, 타입과 순수 함수만)

- 저장 상태에는 `Offer.negotiationState`(`OPEN`/`COUNTERED`/`WITHDRAWN`)와 `validUntilRevision`만 둔다. `GENERATED`·`OFFERED`·`ACCEPTED`·`REJECTED`·`EXPIRED`는 pending 목록 안에 있는지·타임라인으로 표현한다(phase-03 상태기계를 저장 필드로 중복하지 않는다).
- `packages/domain/src/negotiation.ts`(신규, 순수 함수·rng 없음): `isOfferExpired(offer, revision)`, `canNegotiate(offer)`(OPEN이고 `negotiable`에 참이 하나 이상), `expireOffers(offers, revision) → { kept, expired }`(안전 잔류 제안은 `validUntilRevision === null`이라 절대 만료되지 않음). T-3-003이 이 함수들을 명령 처리기에서 부른다. 이 작업에서는 아무 처리기도 부르지 않는다.

## 조건 DSL 화이트리스트(content 스키마 + 런타임 컨텍스트, 두 트랙 몫을 한 번에)

`packages/content/src/schema/condition.ts` 경로 목록과 `runtime/condition-context.ts` 값 공급을 같이 늘린다. 값이 아직 모델링되지 않은 경로는 기존 `NOT_MODELED_*` 관례로 채우고 주석에 소유 작업을 적는다.

## 테스트와 인수 조건

- 타입: `Offer`·`Contract` v2가 Phase 1 첫 계약 경로(career-01 골든)에서 기본값으로 채워지고, `clubHistory`가 정확히 1건(`toSeasonIndex: null`, `fromSeasonIndex === 1`, `kind: 'PERMANENT'`)이다. `signedSeasonIndex === 1`.
- 상태기계 함수: `isOfferExpired` 경계(`validUntilRevision === revision`은 유효, `< revision`은 만료 — 하나로 정해 테스트로 고정), `expireOffers`가 `validUntilRevision: null`을 절대 만료시키지 않음, `canNegotiate`가 COUNTERED/WITHDRAWN·`negotiable` 전부 false에서 false.
- 명령: `NEGOTIATE`·`REJECT_OFFER`·`LOAN_RETURN`이 contracts에서 strict 검증되고(잘못된 `ask`·빈 `offerId` 거부), domain에서는 throw 없이 실패 결과를 돌려준다.
- pending: `CONTRACT` pending이 `offers: []`이면 자동 통과, 1건 이상이면 정지(`isAutoPassablePending`) — 합성 상태로 테스트.
- DSL: 새 경로 12개가 스키마에서 통과하고, 런타임 컨텍스트가 표의 값을 낸다(`contract.seasonsRemaining`은 career-06-settled처럼 시즌을 한 번 지난 fixture로 `lengthSeasons − 1` 확인). 모르는 경로는 지금처럼 거부.
- 이벤트 선택기: `presentation`이 있는 합성 정의가 EVENT 후보에서 빠진다.
- 결산: `SeasonResult.stepSummaries.length === 12`이고 `season.steps[].summary`와 같은 값(career-06-settled).
- 재생 불변: 골든 9종 전후 표에서 `rngState.draws` 동일, hash·신규 필드만 변경. `pnpm test`의 기존 테스트(T-2-011 결정론·집계·B > A 포함)가 그대로 통과.
- 전체 체인: `pnpm install --frozen-lockfile && pnpm lint && pnpm lint:deps && pnpm typecheck && pnpm test && pnpm build && pnpm --filter @offside/web check:bundle && E2E_PORT=5188 pnpm --filter @offside/web e2e` 통과(e2e는 화면을 안 바꾸므로 회귀 확인용).

## 제약

- `Date`·`Math.random` 금지, 정수 저장(D-36), 새 rng 소비 없음(draws 불변이 인수 조건).
- Base OVR·attributes·truePotential 불변. 시장가치를 상태에 저장하지 않는다(ADR-010). `relationships`·`context`·`state`에 쓰지 않는다(트랙 B·T-3-003 몫).
- 문구·주석 한국어. 커밋 `T-3-001: …`, 브랜치 `T-3-001-…`. 커밋은 슬라이스별로 나눈다(타입·offers 기본값 / pending·타임라인 / DSL·이벤트 / contracts·payload / 골든).
- 서브에이전트를 띄우지 않는다 — 리뷰용이든 조사용이든 전부(gstack `/review`·`/codex`·adversarial·`/simplify`·병렬 fork·Agent/Explore 조사 에이전트 금지). 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드).
- e2e 전에 `lsof -nP -iTCP:5188 -sTCP:LISTEN`이 비어 있어야 한다.
