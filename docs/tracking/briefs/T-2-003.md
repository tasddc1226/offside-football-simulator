# T-2-003: 포지션별 경기 통계 generator — 일정·상대 수준·출전 시간·통계·평점·카드·부상 이탈·집계

## 목표

Phase 2 Wave 2 도메인 작업. T-2-001의 시즌 구조와 T-2-002의 선발 판정 위에서 **경기를 실제로 계산**한다. 시즌 시작 시 리그·컵 일정을 만들고, `ADVANCE`가 step을 지날 때 그 step의 경기를 순서대로 돌려 팀 결과·선수 출전(선발·교체·결장)·출전 시간·포지션군 통계·평점·카드·부상 이탈을 정수·고정소수점으로 생성하고 시즌 누계와 대회 기록을 갱신한다. 챕터(사용자 판단)는 T-2-004, 성장·결산 Effect는 T-2-005다. FAST와 CHAPTER는 **같은 generator**를 쓴다.

## 데이터 계약(D-35)

```ts
type MatchRecord = {                     // T-2-001이 타입만 둔 것을 확정
  id: string;                            // `${seasonIndex}-${step}-${order}` 형태, 정렬 키
  step: number; order: number;           // step 안 경기 순서(0부터)
  competitionId: string; kind: 'LEAGUE' | 'CUP'; round: string | null;   // 컵이면 'R1'|'R2'|'SEMI'|'FINAL'
  opponent: { id: string; name: string; strength: number };              // 이름 없는 상대는 `${leagueId}-opp-${n}`, 이름은 룰셋 `opponentNameTemplate`로 조합
  home: boolean;
  result: { goalsFor: number; goalsAgainst: number; outcome: 'WIN' | 'DRAW' | 'LOSS' };
  appearance: 'START' | 'SUB' | 'OUT';
  outReason: null | 'NOT_SELECTED' | 'UNUSED_SUB' | 'INJURY' | 'SUSPENSION';
  minutes: number;                       // 0~90 정수
  involvement: number;                   // 0~100 정수(역할별 관여량)
  stats: PositionStats;                  // 아래
  ratingTenths: number | null;           // 평점×10 정수 40~100(표시는 /10 → 4.0~10.0). 저장값은 정수만 허용(canonicalize 불변식, T-2-002에서 확정), 0분이면 null
  cards: { yellow: 0 | 1 | 2; red: boolean };
  injuredOff: boolean;
  chapterId: string | null;              // T-2-004가 채운다. 이 작업은 항상 null
};
type PositionStats =
  | { group: 'FW'; goals; assists; xgCenti; shots; offsides }                       // 전환율은 파생(goals/shots)
  | { group: 'MF'; assists; chancesCreated; progressivePasses; passesAttempted; passesCompleted; ballRecoveries }
  | { group: 'DF'; tackles; interceptions; aerialsWon; goalsConcededInvolved; cleanSheet: boolean }
  | { group: 'GK'; saves; psxgMinusGoalsCenti; cleanSheet: boolean; crossesClaimed; buildUpPasses };
type SeasonPlayerStats = { group; appearances: { total; started; sub; zeroMinute; out }; minutes; ratingSumTenths; ratedMatches; yellow; red; injuries; totals: PositionStats /* boolean은 count */ };
type Availability = null | { kind: 'INJURY' | 'SUSPENSION'; matchesRemaining: number; sinceMatchId: string };
```

- `FootballSeason`에 `schedule: Array<{ step; order; competitionId; kind; round; opponentId; home }>`(시즌 시작 시 확정), `matches: MatchRecord[]`(지난 경기만, 일정 순), `playerStats: SeasonPlayerStats`, `availability: Availability`, `lastRatingTenths: number | null`을 추가한다. `StepSummary.matchesPlayed`를 실제 값으로 채우고 `StepSummary`에 `results: Array<{ matchId; outcome; goalsFor; goalsAgainst; appearance; ratingTenths }>`을 더한다(연대기용 요약, 문장 없음).
- `CompetitionRecord`는 경기마다 갱신한다. 리그 `position`은 다른 팀의 경기를 돌리지 않고 결정론적 기대 승점으로 매긴다: 각 상대 팀의 누적 기대 승점 = Σ(그 팀 strength 기반 라운드당 기대 승점, 정수 ×100) — 우리 팀 실제 승점과 비교해 순위(동률은 strength 내림차순 → id). 컵은 이기면 다음 라운드 일정이 활성, 지면 `cupRound = 'OUT_R1'` 같은 탈락 표기와 이후 컵 경기 제거(일정은 `schedule`에 남기고 `skipped: 'ELIMINATED'`).
- 일정(roll 없음): 리그는 `leagues[].teamCount`로 원형 라운드로빈 2회전(홈·원정 교대), 라운드 r(0부터)을 step `3 + floor(r × 9 / roundsTotal)`에 배치(step 3~11). 상대는 같은 `leagueId`의 룰셋 팀 + 이름 없는 팀(`strength = league.strength + 균등 분산 오프셋`, 오프셋은 index로 결정 — roll 없음). 컵은 R1 step 5·R2 7·SEMI 9·FINAL 11, 상대 strength는 라운드가 오를수록 `cupStrengthByRound` 기준값(roll 없음). 같은 step에서 리그 경기가 먼저, 컵이 뒤.

## 경기 계산 규칙(D-27·D-35)

경기 하나의 RNG 소비 순서(테스트가 draw 카운트로 고정한다):

1. **팀 결과**: `diff = teamStrength − opponent.strength (+ homeBonus)` → 룰셋 `resultTable`(diff 구간 → 승·무·패 정수 확률) → `roll100` 1회 → 결과. 득점은 `scoreTable[outcome]`에서 `rollInt` 2회(우리 골·상대 골, 결과와 모순되지 않게 표에서 고른다).
2. **선발**: `rankSelection`(T-2-002, roll 없음). `availability`가 있으면 후보에서 제외(`excluded`), 경기마다 `matchesRemaining − 1`. 경쟁자의 form은 룰셋 `competitorFormDrift`로 결정론적으로 흔든다(roll 없음, 경기 index 기반) — 순위가 영원히 고정되지 않게.
3. **출전 시간**: START → `rollInt`로 교체 아웃 여부·분(룰셋 `minutesTable.start`), SUB → 투입 분(`minutesTable.sub`, 0분 투입 안 됨도 포함 → `UNUSED_SUB`), OUT → 0분·roll 없음.
4. **관여량**: `involvement = clamp(round(expectedPerformance × k + roll))`, roll 1회(`rollRange`), 상대 strength로 정규화.
5. **통계 항목**: 포지션군 표의 항목을 **고정 키 순서**로 각 1회 roll(포아송 근사는 정수 표 조회 + `rollInt`). 제약: FW `goals ≤ result.goalsFor`, `assists ≤ goalsFor − goals`; MF `assists ≤ goalsFor`, `passesCompleted ≤ passesAttempted`; DF·GK `cleanSheet = goalsAgainst === 0 && minutes ≥ 룰셋 기준`; `goalsConcededInvolved ≤ goalsAgainst`. 0분이면 roll 없이 전부 0.
6. **카드**: `roll100` 1회 → none/yellow/red(룰셋 `disciplineTable`, 포지션군별). 경고 누적 `yellowSuspensionAt`(5)에 닿거나 퇴장이면 `availability = SUSPENSION`(red는 `rollInt`로 1~2경기).
7. **부상 이탈**: 출전했으면 `roll100` 1회(룰셋 `injury.perMatchPercent`, 체력 낮으면 +) → `injuredOff = true`, `availability = INJURY`, 이탈 경기 수 `rollRange(min,max)`. 능력치·재활은 만지지 않는다(Phase 4).
8. **평점**(roll 없음): `ratingTenths = clamp(60 + Σ 항목별 가중치(포지션군별, 룰셋 `ratingWeights`, ×10 정수) + 결과 보정 − 카드 보정, 40, 100)` — 전 과정 정수 산술. `season.lastRatingTenths` 갱신 뒤 `context.squadStatus = computeSquadStatus({ rolePromise: contract.rolePromise, captaincy: 'NONE', lastRating: lastRatingTenths / 10 }, selectionRules, contractRules.squadStatusByRole)`(T-2-002, 룰셋 ratingNeutral 6.5·ratingScale 8·±20). 0분이면 `ratingTenths = null`, `lastRatingTenths` 유지.

- `ADVANCE`가 step을 지날 때: **그 step의 경기를 일정 순서대로 먼저** 돌리고 나서 결정 슬롯을 연다(T-2-001의 EVENT roll보다 앞). 결정이 열려 멈춘 step도 경기는 이미 끝난 상태다(챕터가 경기 하나를 결정으로 빼내는 것은 T-2-004가 이 지점에 끼운다 — 그 훅 자리를 함수 경계로 남긴다).
- 팀 strength: 우리 팀은 `squadStrength`(T-2-002), 상대는 위 규칙. `leagueStrength`는 상대 strength 산출에만 쓰고 Expected Performance에 다시 곱하지 않는다(03 "중복 적용 금지").
- **저장되는 모든 수는 정수**(`canonicalize`가 safe integer만 허용 — T-2-002가 이 이유로 브리프의 소수 반올림을 정수 반올림으로 바꿨다). 부동소수는 함수 안의 중간값으로만 쓰고 저장 전에 `Math.round` 한 번, 더하는 순서 고정. 평점·xG·PSxG처럼 소수가 필요한 값은 `…Tenths`·`…Centi` 정수로 든다.

## T-2-002 산출물(PR #37)과의 접점

T-2-002가 머지된 `origin/main`에서 시작한다. 아래 이름은 실제 코드 기준이며 바꾸지 않는다(추가만 허용).

- `packages/domain/src/selection.ts` 공개 API: `findTacticalStyle`, `computeTacticalFit`, `familiarityOf(proficiency, rules)`, `computeExpectedPerformance`, `computeSquadStatus`, `computeSelectionScore`, `rankSelection`, `squadRoleFromSelection`, `rankPositionForPlayer(input: RankPositionForPlayerInput)`, `computeRoleProposal`, `deriveTacticalRoom`(T-2-007 뷰 — 만지지 않는다). 모든 결과값은 `roundToInt`로 정수.
- `packages/domain/src/competitors.ts`: `generateCompetitors(ruleset, team, rngState)` — START_SEASON에서 이미 호출됨. 이 작업은 경쟁자를 다시 생성하지 않는다.
- 시즌 상태(`FootballSeason`): `styleId`, `squad.competitors: Competitor[]`(포지션 8 × 2, `form`·`fitness`·`morale`·`tacticalFit`·`managerTrust`·`squadStatus`·`rolePromise` 전부 정수), `selection: SelectionRanking`(`candidates[].excluded: null | 'INJURY' | 'SUSPENSION' | 'NATIONAL_TEAM'`, `rank`, `appearance`), `squadRole`.
- **경기마다 선발**: `rankPositionForPlayer({ ruleset, styleId: season.styleId, position: profile.primaryPosition, playerName, baseOvr, tacticalFit: context.tacticalFit, managerTrust, form, fitness, morale, familiarity: familiarityOf(context.positionProficiency, selectionRules), squadStatus: context.squadStatus, competitors: season.squad.competitors })`. 결과를 `season.selection`에 저장하고 **`season.squadRole = squadRoleFromSelection(season.selection)` 불변식**을 경기마다 유지한다(T-2-002 리뷰에서 RESOLVE_ROLE 네 분기에 같은 불변식을 넣었다).
- `availability`가 있으면 PLAYER 후보를 `excluded`로 넣어야 한다. `RankPositionForPlayerInput`에 `excluded?: SelectionCandidate['excluded']`를 **추가**(기본 null)해 `rankSelection`에 전달한다 — 기존 호출부의 동작은 바뀌지 않게. `Availability.kind`와 `excluded` 값은 같은 문자열('INJURY' | 'SUSPENSION')을 쓴다. 경쟁자의 부상·정지는 이 작업 범위 밖(모델 없음).
- `competitorFormDrift`(룰셋, 이 작업이 추가)는 `Competitor.form`(정수)만 경기 index 기반으로 결정론적으로 바꾼다. 다른 경쟁자 필드는 시즌 내 불변.
- `FootballSeason`·`StepSummary`에 필드를 추가하면 `packages/contracts/src/career-state.ts`의 대응 스키마(`FootballSeasonSchema` 등, strictObject)에도 **같은 PR에서** 추가한다. T-2-006이 golden 순회로 검증하므로 누락되면 그쪽이 깨진다. 스키마 추가는 "최소 수정 예외"에 포함된다.
- `season.lastRatingTenths`·`context.squadStatus` 갱신은 위 8번 규칙. `context.tacticalFit`·`positionProficiency`는 이 작업에서 바뀌지 않는다.

## 테스트와 인수 조건

- [ ] 일정: `teamCount` 12 → 리그 22경기, step 3~11에 2~3경기, 홈·원정 11:11, 같은 상대와 홈·원정 1회씩. 컵 4라운드가 5·7·9·11에 있고 탈락 뒤 컵 경기가 돌지 않는다. 일정 생성은 roll을 소비하지 않는다.
- [ ] 경기 RNG 순서(1~8)가 draw 카운트 테스트로 고정된다. OUT·0분 경기는 팀 결과 roll만 소비한다.
- [ ] 제약 전부: 골 ≤ 팀 골, 패스 성공 ≤ 시도, 클린시트 조건, 0분이면 통계 0·평점 null, `minutes` 0~90, `ratingTenths` 40~100 정수. 시즌 종료 상태 전체가 safe integer만 담는다(`canonicalize` 통과).
- [ ] 0분·교체 출전·퇴장·부상 이탈이 각각 `appearances`·`outReason`·`availability`에 올바르게 집계되는 fixture 4개(강제 seed 탐색은 테스트 헬퍼로 seed를 찾아 고정한다).
- [ ] 정지·부상 중에는 `rankSelection`에서 `excluded`이고 `matchesRemaining`이 경기마다 줄어 0에서 해제된다.
- [ ] 같은 seed 1,000회 반복 실행의 시즌 hash가 전부 같다. 서로 다른 seed 1,000개 시즌이 예외 없이 끝나고 위 제약을 지킨다.
- [ ] FAST와 CHAPTER의 `matches`가 같은 seed에서 동일하다(분포 동일성의 Phase 2 형태).
- [ ] 포지션군 4종(같은 Expected Performance 입력)의 1,000경기 `ratingTenths` 중앙값 차이가 3 이내다(balance-targets "포지션별 기여", 0.3점).
- [ ] 리그 순위가 1~teamCount 안이고 승점이 많을수록 순위가 좋다(단조성 테스트).
- [ ] step 경계 Snapshot 재개 hash == 연속 실행 hash(경기가 낀 시나리오).
- [ ] `pnpm lint && pnpm lint:deps && pnpm typecheck && pnpm test && pnpm build && pnpm --filter @offside/web check:bundle && pnpm --filter @offside/web e2e` 전체 통과. 시즌 하나(FAST)의 domain 계산 시간을 Node에서 측정해 PR 본문에 적는다(T-2-006의 Worker 측정 기준값).

## 제약

- `Date`·`Math.random` 금지, 정렬은 안정 키, 반올림은 함수마다 한 번.
- Base OVR·`attributes`·`truePotential`은 바뀌지 않는다. 폼·체력·사기도 이 작업에서는 바꾸지 않는다(T-2-005) — 단, 룰셋 `competitorFormDrift`는 경쟁자에게만.
- 문구·주석 한국어. 커밋 `T-2-003: …`, 브랜치 `T-2-003-…`.
- 서브에이전트 리뷰 금지(gstack `/review`·`/codex`·adversarial·`/simplify`·병렬 fork). 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드).
- PR 직전 `git fetch origin && git merge origin/main`. `pnpm-lock.yaml` 충돌은 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile` 뒤 전체 체인 재실행.
- 명세를 고치지 않는다. D-27·D-35와 충돌하면 그 항목만 PR 본문에 적고 나머지를 끝낸다.

## 진행 보고

- 체크포인트마다 `orca worktree set --worktree active --comment "..."` 갱신.
- 막히면 질문을 PR 본문 또는 터미널에 남기고 멈춘다.
- 끝나면 PR을 열고 본문에 요구사항 ID, RNG 소비 순서, golden 전후 표, 계산 시간, 테스트 방법, 범위 밖 발견 사항을 적는다.
