# T-4-024: 실사용자 플레이 시간 측정 준비 — `season_settled`에 초 단위 경과 추가 (D-62 출시 QA 잔여)

## 목표

Phase 3·4 완료 조건 "FAST 한 시즌 4~6분·CHAPTER 8~12분"은 자동화 시간으로 대체할 수 없어(D-62) 실사용자 측정이 남았다. 현재 `season_settled` 분석 이벤트는 `elapsedSecBucket`(`<60/<180/<360/<720/<1800/>=1800`)만 보내 4~6분·8~12분 판정에 해상도가 부족하다. 시즌 시작(`seasonStartedAt`)부터 결산까지의 경과를 **초 단위 정수**로 함께 보내고, 측정 쿼리·프로토콜은 오케스트레이터가 문서(`docs/qa/play-time-measurement.md`, `line-test-plan.md` §5)로 붙인다.

## 참조·선행

- 정본: [D-62·D-65](../phase-3-4-plan.md), [phase34-acceptance.md](../../qa/phase34-acceptance.md) "사용자 게이트"·`session-length.spec.ts` 메모, [line-test-plan.md](../line-test-plan.md) §5 측정 쿼리, [T-2-012](T-2-012.md) D-55 이벤트 표.
- 코드: `apps/web/src/engine/funnel.ts`(`recordSeasonSettled`·`elapsedSecBucket`·`FunnelRecord.seasonStartedAt`), `apps/web/src/platform/index.ts`(analytics 큐 → `POST /v1/analytics/events`), API `apps/api/src/routes/analytics.ts`·`packages/contracts`의 이벤트 스키마(props 제한 여부 확인), D1 `analytics_events`(`props_json`·`client_ts`).

## 1. 작업

- `recordSeasonSettled`가 `elapsedSec: Math.min(Math.round((Date.now() - baseline) / 1000), 7200)`을 기존 props에 추가해 보낸다(bucket은 유지, 상한 2시간). `SeasonSettledProps` 타입·기존 단위 테스트 기대값을 그대로 맞춘다.
- `step_passed`에도 시즌 시작 기준 `elapsedSec`(같은 baseline, 같은 상한)을 추가한다 — step별 이탈·소요 분석용. baseline이 없으면(복구 커리어 등) 필드를 생략한다.
- API/contracts가 props 키를 화이트리스트로 검증한다면 두 키를 허용 목록에 추가한다(스키마 파일만). 화이트리스트가 없으면 건드리지 않는다.
- 이벤트 이름·기존 props·큐 동작은 바꾸지 않는다. 룰셋·도메인 변경 없음.
