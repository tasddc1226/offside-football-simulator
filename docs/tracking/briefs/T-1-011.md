# T-1-011: 동기화 클라이언트 배선·저장 상태 표시·충돌 화면·"이 기기 진행 유지"(fork-by-replay)

## 목표
커리어 명령이 확정될 때마다 서버에 저장되고, 사용자는 저장 상태를 어디서나 본다. 다른 기기와 어긋나면 "다른 기기 진행 가져오기 / 이 기기 진행 유지"를 고른다. 오프라인·세션 없음·쿠키 차단에서도 게임은 멈추지 않는다.

## 범위
- 만질 경로: `apps/web/src/**`, `apps/web/e2e/**`, `packages/engine-client/src/fork.ts`(신설)·`fork.test.ts`(신설)·`src/index.ts`(export 한 줄). 그 외 패키지 금지. `packages/engine-client/src/sync/**`·`engine.ts`·`store/**`는 고치지 않는다. 필요한 확장이 있으면 PR 본문에 적고 멈춘다.
- 만들 것:
  1. **포크(engine-client)** `packages/engine-client/src/fork.ts`:
     ```ts
     export type ForkResult =
       | { ok: true; newCareerId: string; revision: number }
       | { ok: false; error: EngineError };
     export async function forkCareerByReplay(
       deps: { engine: EngineClient; store: LocalStore; newId: () => string },
       careerId: string,
     ): Promise<ForkResult>;
     ```
     동작: `readonly` 트랜잭션에서 `careers.get(careerId)`와 `commandLog.listSince(careerId, 0)`를 읽는다. 레코드가 없으면 `CAREER_NOT_FOUND`. 로그가 revision 1부터 빈틈없이 이어지지 않거나 첫 항목이 `CREATE_CAREER`가 아니면 `{ ok: false, error: { code: 'VERIFICATION_FAILED', details: { reason: 'FORK_LOG_INCOMPLETE', atRevision } } }`. 통과하면 `newCareerId = deps.newId()`로 로그를 순서대로 `engine.execute`에 넣는다. `CREATE_CAREER`는 payload의 `careerId`를 `newCareerId`로 바꾸고 나머지 payload는 그대로. `commandId`는 항목마다 `deps.newId()`, `expectedRevision`은 `entry.revision - 1`, `createdServiceSeasonId`는 원본 레코드 값. 하나라도 `ok: false`이면 `engine.deleteCareer(newCareerId)`로 새 커리어를 지우고 그 오류를 돌려준다. 원본은 어떤 경우에도 건드리지 않는다. 트랜잭션 안에서 `execute`를 부르지 않는다(`execute`는 자체 트랜잭션을 연다). 결정론이라 결과 state는 `careerId`만 다르다.
     테스트 `fork.test.ts`(`MemoryLocalStore` + `inlineSimulator` + `@offside/fixtures`의 `career01EngineCommands`·룰셋): 골든 끝까지 실행한 뒤 포크 → 새 커리어 revision 동일, 두 최신 state에서 `careerId`를 뺀 나머지 deep-equal, 원본 레코드·Snapshot 불변, 새 레코드 `lastSyncedRevision === 0`; 로그 중간 항목을 지운 뒤 포크 → `FORK_LOG_INCOMPLETE`; 중간 실패(가짜 simulator가 n번째에서 실패) → 새 커리어가 남지 않는다.
  2. **fetch 어댑터** `apps/web/src/api/sync-fetch.ts`: `createSyncClient`의 `fetch`로 넘길 함수. `credentials: 'include'`, JSON 헤더는 sync 클라이언트가 넣는다. base URL 상수는 T-1-008의 `src/api/client.ts`가 export한 것을 쓴다(없으면 같은 규칙 `VITE_API_BASE_URL` → `http://localhost:8787`으로 그 파일에 추가).
  3. **동기화 부트스트랩** `src/engine/sync.ts`: `getSyncClient(): Promise<SyncClient>` 지연 싱글턴. deps: `engine`(`getAppEngine()`의 EngineClient), `store`(같은 LocalStore), `fetch`(2번), `baseUrl = `${API_BASE_URL}/v1``, `now: () => new Date().toISOString()`, `newId: () => crypto.randomUUID()`, `online: () => navigator.onLine`, policy 기본값. 브라우저 이벤트 연결: `online` → `flush()`; `visibilitychange`(hidden)·`pagehide` → `flush()`(await 하지 않는다). 시작 시 `listCareers()`를 돌며 `revision > lastSyncedRevision`인 커리어는 최신 Snapshot으로 `notifyCommitted`(이전 세션의 미전송분 재개). `dispose`는 부르지 않는다(앱 수명과 같다).
  4. **세션 확보** `src/api/profile.ts`: 앱 부트스트랩에서 한 번 `getProfile()`(T-1-008이 만든 함수 재사용. `GET /v1/profile`이 익명 프로필 쿠키를 발급한다). 성공하면 LocalStore `kv 'profile:id'`에 `id`를 저장하고 TanStack Query `['profile']`에 캐시. 실패해도 앱은 뜬다. `EngineClientDeps.ownerProfileId`는 넣지 않는다(D-19).
  5. **액션 연결** `src/engine/career-actions.ts`의 `execute` 래퍼: `engine.execute`가 `ok: true`이고 `replayed: false`일 때만 `sync.notifyCommitted(careerId, snapshot)`. `deleteCareer`: 로컬 삭제는 항상 수행하고 `DELETE /v1/careers/{id}`를 호출한다. 재시도 가능한 실패(네트워크·5xx·`RATE_LIMITED`)면 kv `sync:pending-delete`(careerId 배열)에 두고 앱 시작·`online` 때 재시도. `CAREER_NOT_FOUND`·`CAREER_NOT_OWNED`·401은 성공으로 본다(목록에서 지운다).
  6. **상태 훅·배지** `src/engine/use-sync.ts`: `useSyncState(careerId)`(`subscribe` + `useSyncExternalStore`), `useSyncSummary()`(모든 로컬 커리어 중 가장 급한 상태 하나. 우선순위 CONFLICT > FAILED > LOCAL_ONLY > OFFLINE > RETRYING > SYNCING·SCHEDULED > IDLE). `src/shared/SyncBadge.tsx`: 상태 → 문구·아이콘·색. 문구 표(그대로 쓴다): IDLE "저장됨"(+ `lastSyncedAt` 상대 시각 "방금"·"n분 전"·"n시간 전", `<time dateTime>`; `lastSyncedAt`이 null이면 "아직 저장 안 됨"), SCHEDULED·SYNCING "저장 중", RETRYING "저장 다시 시도 중", OFFLINE "오프라인 · 이 기기에만 저장됨", LOCAL_ONLY "로컬 전용", CONFLICT "다른 기기와 어긋남", FAILED "서버 저장 실패". 색은 13의 semantic 토큰만, 문구 필수(색만으로 구분 금지). `aria-live="polite"` 갱신은 CONFLICT·FAILED로 바뀔 때 한 번만. 배치: 허브 카드(SCR-001) 안, 커리어 레이아웃 헤더(`/career/$careerId` 상위 라우트). 브랜드 어휘 금지(저장·복구는 평이한 한국어, 12 문서).
  7. **설정 SCR-030 동기화 행** `/settings`: T-1-007이 둔 "동기화 상태" 행을 채운다. 요약 배지 + 마지막 저장 시각 + "지금 동기화" 버튼(`flush()`, 진행 중 잠금) + LOCAL_ONLY이면 안내문 "이 브라우저에서는 서버 저장을 할 수 없습니다. 쿠키가 차단됐거나 세션이 없습니다. 복구 코드 없이 브라우저 데이터를 지우면 되돌릴 수 없습니다."와 "다시 연결" 버튼(`getProfile()` 재시도 → 성공 시 미전송 커리어 전부 `notifyCommitted`). FAILED이면 코드별 문구: `VERSION_MISMATCH` "앱을 새로고침해 최신 버전을 받으세요", `CAREER_ARCHIVED` "보관된 커리어는 더 저장하지 않습니다", 그 외 "서버가 저장을 거부했습니다(코드)".
  8. **충돌 대화상자** `src/shared/SyncConflictDialog.tsx`(ui `Dialog` + `CompareCards`): 커리어 레이아웃에 마운트하고 현재 커리어의 상태가 `CONFLICT`가 되면 연다. 제목 "다른 기기에서 이 커리어가 더 진행됐습니다". 비교 카드 둘: "이 기기"(로컬 revision, 나이, 단계 문구, 마지막 타임라인 항목 종류 한국어) / "다른 기기"(서버 Snapshot의 `state`를 contracts `CareerStateSchema.safeParse`로 읽어 같은 값. 파싱 실패면 revision만). 버튼 셋:
     - "다른 기기 진행 가져오기": `resolveConflict(id, 'REMOTE')` → 쿼리 무효화 → `screenForCareer`로 이동 → 토스트 "다른 기기의 진행을 가져왔습니다".
     - "이 기기 진행 유지": `forkCareerByReplay` → 성공이면 `resolveConflict(원본, 'REMOTE')` → 새 커리어 최신 Snapshot으로 `notifyCommitted(newId)` → 새 커리어의 `screenForCareer`로 이동 → 토스트 "이 기기의 진행을 새 커리어로 복사했습니다. 원래 커리어는 다른 기기의 진행을 따릅니다". 실패면 대화상자 안에 원인 문장(`FORK_LOG_INCOMPLETE`는 "이 기기에 명령 기록이 다 남아 있지 않아 복사할 수 없습니다")과 "다시 시도".
     - "나중에": 닫는다. 배지는 CONFLICT로 남고 로컬 명령은 계속된다. 다음에 커리어 화면에 들어오면 다시 연다.
     포커스 트랩·복귀, 키보드로 완료 가능, 실행 중 버튼 전부 잠금(COMMITTING).
  9. **분석**: `sync_state_changed { kind }`, `sync_conflict_resolved { choice: 'REMOTE' | 'LOCAL' | 'LATER' }`. 이름·서사·코드 값 금지.
  10. **E2E** `apps/web/e2e/sync.spec.ts`(`page.route`로 `/v1/**` 스텁. 서버 Snapshot은 `@offside/fixtures` golden의 중간 revision Snapshot을 그대로 써서 `decodeSnapshot`이 통과하게 한다): (a) 커리어 생성 → `PUT` 200 → 카드 배지 "저장됨"; (b) `PUT` 409 + `GET`이 낮은 revision·다른 hash Snapshot → 대화상자 → "다른 기기 진행 가져오기" → 배지 "저장됨", 화면이 서버 상태의 단계; (c) 같은 상황에서 "이 기기 진행 유지" → 허브에 카드 2장, 새 카드 쪽으로 `baseRevision: 0`인 `PUT` 발생; (d) `context.setOffline(true)` → 배지 "오프라인 · 이 기기에만 저장됨", 온라인 복귀 → `PUT` 발생 → "저장됨"; (e) `PUT` 401 → 설정의 "로컬 전용" 안내와 "다시 연결". `a11y.spec.ts`에 대화상자 열린 상태 추가.
  11. **단위 테스트**(Vitest): 요약 우선순위 표 전수, `SyncBadge` 문구 표 전수, `execute` 래퍼가 성공·비재생일 때만 `notifyCommitted`, pending-delete 저장·재시도·성공 코드 분류.
