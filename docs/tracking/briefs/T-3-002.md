# T-3-002: 결산 뒤 이적시장 생성기·재계약 사전 협상 — `market.ts`(사유 판정·후보 구단·제안 수·종류·안전 잔류·유효기간)·step 7 RENEWAL 제안과 미응답 만료·룰셋 `transferRules`·시장 골든 3종 (domain + content 룰셋)

## 목표

D-43·D-44의 **시장 생성**을 순수 함수로 만든다. 끝나면 (1) 결산 시점 상태에서 시장을 열 사유(`EXPIRED`·`INTEREST`·없음)를 rng 없이 판정하고, (2) 사유가 있으면 `pending = { kind: 'OFFERS', offers, market }`를 결정론적으로 생성하며(후보 구단·제안 수·종류·조건·유효기간·안전 잔류 제안), (3) 계약 마지막 시즌의 step 7 CONTRACT 슬롯이 현 구단 RENEWAL 제안 1건을 열고 응답이 없으면 ADVANCE가 만료 처리하며, (4) 룰셋 `transferRules`가 스키마·데이터에 있고, (5) 제안 비교용 시장 골든 3종이 있다. **결산 → 시장 개방 배선과 명령(ACCEPT/REJECT/NEGOTIATE/LOAN_RETURN)은 T-3-003**이 한다 — 이 PR만 머지된 상태에서 어떤 커리어도 막히지 않아야 한다(생성기는 export만, step 7 제안은 미응답 만료로 자동 통과).

## 생성 규칙(D-43·D-44를 순수 함수로)

새 파일 `packages/domain/src/market.ts`. 모든 값 정수(D-36), rng는 인자로 받은 결정 스트림(`state.rngState`)만 쓰고 소비 순서를 파일 상단 주석에 고정한다(D-9 관례).

### 1. 사유 판정 `judgeMarketReason(state, ruleset): 'EXPIRED' | 'INTEREST' | null` — rng 없음

결산 직전 상태(`state.season !== null`, step 12, `SETTLE_SEASON` 처리 중)를 입력으로 받는다. T-3-003이 `settleSeason` 안에서 호출한다.
- `contract === null`이면 `null`(첫 계약 경로는 Phase 1 그대로).
- `computeContractSeasonsRemaining(contract, timeline) === 0`이면 `'EXPIRED'`(마지막 시즌의 결산 — 시장은 반드시 열린다).
- 아니면 `잔류_선언` 태그가 있으면 `null`.
- 아니면 다음 하나라도 참이면 `'INTEREST'`: `career.tags`에 `이적_희망` / `season.squadRole === 'STARTER'`이고 시즌 평균 평점(`playerStats`의 평점 합 ÷ 평점 경기 수, tenths, 경기 0이면 0) `≥ transferRules.interest.minRatingTenths` / 시장가치 지수(`computeMarketValueIndex(buildMarketValueInput(state, ruleset), ruleset.marketValueRules)`) `≥ transferRules.interest.minIndexCenti`.
- 그 외 `null`. 임대 계약(`contract.kind === 'LOAN'`)의 결산은 `LOAN_RETURN` 경로(T-3-003)이므로 이 함수는 `null`을 돌려주고, 호출자가 먼저 임대를 가른다.

### 2. 시장 생성 `generateMarket({ state, ruleset, reason, revision, rng }): { pending: Extract<Pending, { kind: 'OFFERS' }>; rngState }`

- `market = { openedAtRevision: revision, seasonIndex: state.seasonHistory.length (+1은 하지 않는다 — T-3-001 정의 그대로 "시장이 열린 시점의 seasonHistory.length"), reason, safeOfferId }`.
- **후보 구단**: `ruleset.teams`에서 현 구단 제외, `leagueTier === 'YOUTH'` 제외, `transferRules.demandBands`에서 시장가치 지수 centi가 속한 첫 밴드의 `tiers`에 있는 팀만, `compareCodePoints(id)` 오름차순. 후보가 0이면 밴드를 한 단계씩 넓혀(다음 밴드의 tiers를 합집합) 최소 1팀을 확보한다 — 룰셋 데이터로 도달 가능한 분기만 남긴다(테스트는 실제 1.0.0 룰셋으로).
- **제안 수** = `clamp(1 + interest + agent, 1, 4)`, `interest = 이적_희망 태그 ? 2 : (reason === 'INTEREST' ? 1 : 0)`, `agent = 에이전트_계약 태그 ? 1 : 0`. 후보가 모자라면 후보 수.
- **팀 추첨**: `generateOffers`와 같은 방식(`rollInt(rng, 남은 후보 수)` → 뽑힌 팀 제거).
- **종류**: `reason === 'EXPIRED'`면 전부 `FREE_AGENT`. 아니면 제안마다 `rollInt(rng, 100)`을 `transferRules.kindWeightsByRole[season.squadRole]`의 `TRANSFER` 가중과 비교(`< TRANSFER`면 TRANSFER, 아니면 LOAN). LOAN은 `loan = { parentTeamId: 현 구단, seasons: 1, wageShareBp: transferRules.loan.wageShareBp, buyOptionMinor: rollInt(rng, 10000) < loan.buyOptionChanceBp ? 이적료 : null }`, `lengthSeasons = 1`. TRANSFER는 `transferFeeMinor = transferRules.feeByIndexBand`에서 지수 밴드의 `feeMinor`.
- **조건**(제안마다 rng 순서: 팀 → 종류 → (LOAN이면 바이아웃) → 기간 → 역할 → 등번호 → 적합도): `lengthSeasons`는 `rollRange(offerRules.lengthSeasons)`(LOAN 제외), `rolePromise`는 `offerRules.rolePromiseByTier[tier]`에서 `rollInt`, `appearancePromise.minutesShareBp = contractRules.promiseMinutesShareBp[rolePromise]`, `positionPlan = profile.primaryPosition`, `shirtNumber`·`tacticalFitEstimate`는 `offerRules` 범위 `rollRange`, `wageMinorPerWeek`·`signingBonusMinor`는 `contractRules.wageBands/signingBonus[team.wageBandId][ovr band]`(`offers.ts`의 `findOvrBand`·`lookupBandAmount`를 export해 재사용), `fromTeamId = null`, `leagueTier = team.leagueTier`, `validUntilRevision = revision + transferRules.offerValidityRevisions`, `negotiable`: TRANSFER·FREE_AGENT `{ wage: true, role: true, length: true }`, LOAN `{ wage: false, role: true, length: false }`, `negotiationState: 'OPEN'`, `negotiatedAsk: null`.
- **경쟁자 요약** `competitorSummary = { rank, ovrGap }`: 결정 스트림을 쓰지 않고 파생 시드 `seedRng(\`market:${state.id}:${revision}:${team.id}\`)`로 T-2-002의 경쟁자 생성기를 그 팀·`positionPlan` 기준으로 한 번 돌려, `rank` = 선수의 예상 선발 순위(1 = 1순위), `ovrGap` = `baseOvr − 같은 포지션 최상위 경쟁자 OVR`(음수 가능). 생성기 시그니처가 팀 밖에서 쓰기 어렵게 되어 있으면 최소 리팩터(순수 함수 추출)만 하고 기존 골든이 불변임을 확인한다.
- **안전 잔류 제안**(항상 index 0, id `OFR-${revision}-0`, `market.safeOfferId`): `kind: 'RENEWAL'`, `teamId/teamName = 현 구단`, `fromTeamId = 현 구단`, `validUntilRevision: null`, `negotiable` 전부 false, `competitorSummary: null`, `transferFeeMinor: null`, `loan: null`. 조건은 계약이 남았으면(`reason === 'INTEREST'`) 현 계약 그대로(`lengthSeasons = 잔여 시즌`, 급여·역할·등번호·`appearancePromise`·`positionPlan` = 현 계약, `signingBonusMinor = 0`) — "현 계약 유지" 0비용 항목; 만료면(`reason === 'EXPIRED'`) 현 구단 1시즌(`transferRules.safeRenewal.lengthSeasons`), 급여 = `wageBands[현 구단 band][ovr band] × safeRenewal.wageBp / 10000`(정수 내림), 보너스 0, `rolePromise` = 현 `squadRole`에서 한 단계 아래(STARTER→ROTATION→BENCH→RESERVE, RESERVE는 그대로), 등번호 = 현 계약. D-44의 "tier 3 최저 조건" 대안은 쓰지 않는다(팀 변경 없는 잔류만 — 이 브리프의 결정, PR 본문에 적는다).
- 나머지 제안 id는 `OFR-${revision}-${1..}`. 제안 배열 순서 = 안전 잔류, 추첨 순.

### 3. step 7 재계약 사전 협상(D-43 (a))

- `buildRenewalOffer(state, ruleset, revision): Offer` — rng 없음. 현 구단 RENEWAL: `lengthSeasons = transferRules.renewal.lengthSeasons`, `wageMinorPerWeek = wageBands[현 구단][ovr band] × renewal.wageBpByRole[season.squadRole] / 10000`(내림), `signingBonusMinor = signingBonus[현 구단][ovr band] / 2`(내림), `rolePromise = season.squadRole`, `appearancePromise` 그에 맞게, `positionPlan = 현 계약`, `shirtNumber = 현 계약`, `validUntilRevision = revision + transferRules.offerValidityRevisions`, `negotiable = { wage: true, role: false, length: true }`, `tacticalFitEstimate = context.tacticalFit`, `competitorSummary: null`.
- `season.ts` `selectOpenSlot` CONTRACT 분기: `contract.kind !== 'LOAN'`이고 **진행 중 시즌이 계약 마지막 시즌**(`computeContractSeasonsRemaining(...) === 0`, T-3-001 `contract.isLastSeason`과 같은 의미)이면 `offers: [buildRenewalOffer(...)]`, 아니면 지금처럼 `offers: []`(자동 통과). D-43 (b) 루머 이벤트는 클라이언트가 RUMOUR 후보를 슬롯에 공급해야 하므로 T-3-005·T-3-006 몫 — 여기서는 만들지 않는다.
- **미응답 만료(이 PR의 임시 규칙, T-3-003이 "응답 필수"로 바꾼다)**: `isAutoPassablePending`은 CONTRACT pending을 `offers.length === 0`일 때만 통과시키는데(T-3-001), 이 PR에서는 `offers.length > 0`도 통과시키되 `advance`가 통과 시 제안마다 타임라인 `OFFER_EXPIRED`(refId = offerId, 현재 step)를 남긴다. 이 규칙이 왜 임시인지 코드 주석에 T-3-003을 가리켜 적는다.

### 4. 결산 뒤 시장 개방 함수(배선은 T-3-003)

`openMarketAfterSettlement(settledState, ruleset, revision): { state; opened: boolean }` — `judgeMarketReason`이 `null`이 아니면 `generateMarket`으로 `pending`을 채우고 `rngState`를 갱신한 상태를 돌려준다(타임라인 항목은 넣지 않는다 — 시장 개방은 `pending`으로 충분). **`settleSeason`에서 호출하지 않는다**(T-3-003이 배선하며 그때 e2e·골든이 바뀐다). 결산 직전 상태를 입력으로 받는 `judgeMarketReason`과 결산 뒤 상태를 받는 이 함수의 경계(어느 쪽이 `season`을 갖는지)를 타입으로 분명히 한다.

## 테스트와 인수 조건
