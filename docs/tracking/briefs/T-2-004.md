# T-2-004: 핵심 경기 챕터 — 후보 선택·판단 resolver·`RESOLVE_CHAPTER`·콘텐츠 팩 `chapters` 스키마 + 3종

## 목표

`ADVANCE`가 step의 경기를 돌린 직후 그 step에 핵심 경기 조건(데뷔전·더비·결정전 등)이 맞으면 CHAPTER 결정을 연다.
사용자는 판단 1~3개를 옵션 2~3개 중에서 고르고, 판단 하나가 roll 1회를 소비해 결과가 확정된다.
결과는 그 경기의 기록(평점·태그)·폼·감독 신뢰·팬·태그에만 작용한다(Base OVR·attributes 불변).
FAST 모드는 MAJOR 챕터만 연다. 열리지 않은 챕터는 일반 경기로 남고 roll을 소비하지 않는다.

    payload: {
      chapterId: string;
      definitionVersion: number;
      decisionId: string;
      optionId: string;

`RESOLVE_CHAPTER`는 판단 하나를 닫는다. `decisionsTotal`보다 적게 확정됐으면 pending을 유지한 채 `nextAction: 'DECISION'`(같은 챕터의 다음 판단), 마지막 판단이면 `pending: null`·`nextAction: 'ADVANCE'`·`season.chapters`에 `ChapterRecord` 추가·`resolvedChapterIds`에 기록. 결과 객체는 `RESOLVE_EVENT`처럼 `roll`·`outcomeId`·`appliedEffects`를 돌려준다.

`ChapterTrigger`(domain `types.ts`에 두고 content 스키마가 같은 모양을 검증):

```ts
type ChapterTrigger =
  | { kind: 'DEBUT' }                                   // 커리어 첫 출전(minutes > 0)이 이 step의 경기에 있다
  | { kind: 'DERBY' }                                   // 상대가 리그 라이벌(아래 룰셋 `rivalOpponentIndex`)
  | { kind: 'CUP_FINAL' }                               // kind CUP, round FINAL, 출전(minutes > 0)
  | { kind: 'DECIDER'; maxRankGap: number }             // 리그 마지막 step(캘린더 LEAGUE phase 최종 step)이고 |position − 승격/강등 경계| ≤ maxRankGap
  | { kind: 'TAG'; tag: string };                       // state.tags에 tag가 있다(Phase 3+ 용, 이번엔 스키마만)
```

## 챕터 선택 규칙(D-28·RULE-TIME-003/004)

1. **훅 위치**: `walkToNextDecision`이 step의 경기를 `playStepMatches`로 돌린 **직후**, `selectOpenSlot` 전에 `selectChapter(...)`를 부른다. 입력은 그 step의 `MatchRecord[]`, `payload.chapterCandidates`, `season`(competitions·steps·index), `state`(tags·모드), 리그 정의. 출력은 `{ chapterId, version, importance, matchId } | null`. **roll 없음.**
2. 후보 필터: (a) step에 `CHAPTER` 슬롯이 있고 `skippedByBudget`가 아니다, (b) 슬롯에 `importance`가 있으면 후보 `importance`와 같아야 한다(없으면 둘 다 허용), (c) FAST 모드는 MAJOR만, (d) trigger가 그 step의 경기 중 하나에 맞는다(맞은 경기가 `matchId`; 한 step에 경기가 둘이면 order 오름차순 첫 일치), (e) `resolvedChapterIds`에 `${chapterId}@${seasonIndex}`가 없고, 같은 챕터가 `season.chapters`에 없다.
3. 여러 후보가 남으면 MAJOR 우선, 같은 중요도면 `weight` 내림차순, 같으면 `chapterId` 코드포인트 순. 한 step에 챕터는 최대 1개.
4. 시즌당 챕터 수 상한은 `buildSeasonSteps`가 이미 잘랐다(RULE-TIME-004 챕터 4). 여기서 다시 세지 않는다.
5. 챕터가 열리면 `pending`은 위 CHAPTER 분기, `MatchRecord.chapterId`를 세우고 `decisionsOpened`는 1이다. 이벤트 슬롯은 같은 step에서 열리지 않는다(슬롯 우선순위 EVENT > CHAPTER는 유지하되, 이 캘린더는 한 step에 슬롯이 하나다 — `selectOpenSlot`의 CHAPTER 분기는 `selectChapter` 결과가 null이면 `opened:false`로 넘어가게 바꾼다).
6. 열리지 않은 CHAPTER 슬롯은 일반 경기로 지나간다(이미 계산됨). 기존 placeholder pending `{ kind:'CHAPTER', step }`는 사라진다 — 골든이 그 pending으로 멈춰 있으면 재생 결과가 바뀌므로 아래 golden 절차를 따른다.

## 판단 resolver 규칙

1. 검증 순서: status ACTIVE → pending CHAPTER → `chapterId`/`definitionVersion` 일치 → `decisionId`가 이미 `resolved`에 없음 → `outcomes` 가중치 합이 1 이상 2^32 이하 정수(`resolveEvent`와 같은 검사). 실패는 `fail('VALIDATION_FAILED', …, { reason })`으로, throw 금지. reason 값: `NO_PENDING_CHAPTER`, `PENDING_CHAPTER_MISMATCH`, `DECISION_ALREADY_RESOLVED`.
2. roll은 **판단당 1회** `rollInt(state.rngState, weightSum)` — `resolveEvent`와 같은 누적 가중치 선택. `matchRngState`는 쓰지 않는다(경기 결과는 이미 확정).
3. 적용 순서: `applyEffects(state, chosen.effects, { step })` → tags add/remove → `season.matches[matchId].ratingTenths`에 `chosen.ratingDeltaTenths`를 더하고 `clamp(40, 100)`(평점이 `null`이면 더하지 않는다) → `season.lastRatingTenths`도 그 경기가 시즌 마지막 계산 경기이면 같이 갱신 → `playerStats.ratingSumTenths` 재계산(누적을 새로 합산하지 말고 `delta`만 더한다) → `pending.resolved` 추가 → timeline `CHAPTER_RESOLVED`.
4. 마지막 판단이면 `ChapterRecord`를 `season.chapters`에 넣고 `resolvedChapterIds`에 `${chapterId}@${season.index}` 추가(정렬 유지: `sortUniqueTags`와 같은 코드포인트 정렬). `SquadStatus`는 다시 계산하지 않는다(다음 경기에서 T-2-003 규칙이 처리).
5. 재생: 같은 명령 로그를 다시 돌리면 roll도 같은 순서로 소비된다. 확정된 판단은 `resolved`에 있으므로 같은 `decisionId`를 다시 보내면 `DECISION_ALREADY_RESOLVED`로 거부 — roll을 두 번 소비하지 않는다.
6. 허용 Effect: kind `CURRENT`(form·morale·fitness), `RELATION`(managerTrust·fans·captain·rival), `DEFERRED`. `CONTEXT`·`PERMANENT`는 content 스키마에서 거부한다(챕터는 Base OVR·Fit을 바꾸지 않는다). 단일 outcome 상한은 balance-targets 표(CURRENT ±12, RELATION ±12, 중대 사건 ±25/±20)를 스키마 `superRefine`으로 강제하고, `ratingDeltaTenths`는 −15~+15.

## T-2-003 산출물(PR #39)과의 접점

- `walkToNextDecision(steps, startStepIndex, mode, eligibleEvents, rngState, revision, roleContext, playStepMatches)`가 경기를 돌린 뒤 `selectOpenSlot`을 부른다. 챕터 훅은 이 둘 사이에 들어간다. `PlayStepMatches`는 `(stepIndex) => { results: StepMatchResult[] }`만 돌려주므로, 훅이 `MatchRecord`를 보려면 `createStepMatchWiring`(simulate.ts)이 클로저에 쌓는 `matches` 배열을 훅에도 넘기거나 `PlayStepMatches` 반환에 `records: MatchRecord[]`를 추가한다 — 후자로 한다.
- `MatchRecord.chapterId`는 PR #39가 `null` 고정으로 넣어 두었다. `ratingTenths` 정수 ×10, `clamp(40,100)`. `StepMatchResult.ratingTenths`는 갱신하지 않는다(요약은 경기 시점 값).
- `season.matchRngState`(경기 전용)와 `state.rngState`(결정 전용)가 분리돼 있다(D-37). 챕터 roll은 `state.rngState`.
- `FootballSeason` 필드 추가는 `packages/contracts/src/career-state.ts` `FootballSeasonSchema`·`PendingSchema`·`CommandSchema`(ADVANCE payload optional 필드, RESOLVE_CHAPTER)를 같은 PR에서 함께 고친다(strict 스키마라 필드가 빠지면 API가 거부한다). `KNOWN_GOLDEN_FILES`(contracts `career-state.test.ts`)에 새 골든을 추가한다.

## golden·fixture 절차

- 기존 골든(career-01·02-season·03-underdog·04-gk)은 `chapterCandidates`를 보내지 않으므로 챕터가 열리지 않아야 하고 **stateHash가 바뀌지 않아야 한다**. 단, placeholder CHAPTER pending에서 멈춘 골든이 있으면(있는지 먼저 `grep -l '"kind": "CHAPTER"' packages/fixtures/data/*.json`) 그 골든은 해당 step을 지나가게 되므로 재생성하고 PR 본문에 전후 hash 표와 사유를 적는다.

## 제약

- `Date`·`Math.random` 금지, 정렬은 안정 키, 반올림은 함수마다 한 번. 저장되는 모든 수는 정수(D-36).
- Base OVR·`attributes`·`truePotential`·`context.*` 불변. 챕터는 `CURRENT`·`RELATION`·`DEFERRED`만.
- 문구·주석 한국어. 커밋 `T-2-004: …`, 브랜치 `T-2-004-…`.
- 서브에이전트를 띄우지 않는다 — 리뷰용이든 조사용이든 전부(gstack `/review`·`/codex`·adversarial·`/simplify`·병렬 fork·Agent/Explore 조사 에이전트 금지). 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드).
- e2e 전에 `lsof -nP -iTCP:5174 -sTCP:LISTEN`이 비어 있어야 한다. 비어 있지 않으면 `until ! lsof -nP -iTCP:5174 -sTCP:LISTEN >/dev/null; do sleep 10; done` 뒤 실행.
- PR 직전 `git fetch origin && git merge origin/main`. `pnpm-lock.yaml` 충돌은 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile` 뒤 전체 체인 재실행.
- 명세를 고치지 않는다. D-28·D-38과 충돌하면 그 항목만 PR 본문에 적고 나머지를 끝낸다. `apps/web`은 건드리지 않는다(T-2-008).
