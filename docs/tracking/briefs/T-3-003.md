# T-3-003: 이적시장 명령 처리기(NEGOTIATE·ACCEPT_OFFER v2·REJECT_OFFER·LOAN_RETURN)·결산 배선·임대·약속 위반·Phase 3 태그 평가기 (domain + 룰셋 필드 1개 + web 최소 배선)

## 목표

T-3-002(PR #50)가 만든 시장 생성기를 실제 커리어 흐름에 붙인다. 끝나면 (1) 결산 뒤 시장이 열리고(`openMarketAfterSettlement` 배선), (2) step 7 재계약 제안·시장 제안에 `NEGOTIATE`(roll 1)·`ACCEPT_OFFER`(kind별 원자 전환, D-45)·`REJECT_OFFER`로 응답할 수 있으며(자동 만료 임시 규칙 제거 → 응답 필수), (3) 임대 계약과 `LOAN_RETURN`(D-46), (4) 약속 위반 → `promiseBreaches`·태그·감독 신뢰(D-47), (5) Phase 3 태그 평가기 5종(D-48), (6) 골든 `career-10-transfer`·`career-11-loan`(3시즌)이 있다. 웹은 기존 SCR-009를 재사용하는 라우팅만 붙인다(정식 화면은 T-3-005).

## 1. 공통 전처리 — 만료 정리(rng 없음)

`NEGOTIATE`·`ACCEPT_OFFER`·`REJECT_OFFER`가 `pending.kind === 'OFFERS' | 'CONTRACT'`를 다룰 때 먼저 `expireOffers(pending.offers, nextRevision)`을 돌려 만료분을 제거하고 제안마다 `OFFER_EXPIRED`를 남긴다(안전 잔류는 `validUntilRevision === null`이라 남는다). 대상 offerId가 만료분이면 `VALIDATION_FAILED { reason: 'OFFER_EXPIRED' }`(revision은 오르지 않는다 — fail 경로). `ADVANCE`·`START_SEASON`은 시장 pending이면 `VALIDATION_FAILED { reason: 'MARKET_OPEN' }`(응답 필수).

## 2. `NEGOTIATE { offerId, ask }` — roll 정확히 1회

- 전제: `canNegotiate(offer)`이고 `offer.negotiable[ask]`가 true, `negotiatedAsk === null`(제안당 1회). 안전 잔류·`ROLE` ask인데 `rolePromise === 'STARTER'`면 `VALIDATION_FAILED { reason: 'NOT_NEGOTIABLE' }`.
- 성공 확률(bp) = `transferRules.negotiation.successBp[offer.kind][ask] + transferRules.negotiation.reputationAdjustBpPerPoint × (team.reputation − 3)`, clamp 0..10000(팀은 `ruleset.teams`에서 `offer.teamId`). D-44의 "시장가치 대비 급여 위치 보정"은 룰셋에 상수가 없어 **이 작업에서 하지 않는다**(PR 본문에 명시, T-3-005 전 밸런스 항목).
- `rollInt(rng, 10000) < successBp`면 `COUNTERED`: WAGE → `wageMinorPerWeek = floor(wage × counter.wageBp / 10000)`, LENGTH → `lengthSeasons + counter.lengthDelta`(상한 `offerRules.lengthSeasons.max`), ROLE → 한 단계 위(RESERVE→BENCH→ROTATION→STARTER)와 `appearancePromise.minutesShareBp = promiseMinutesShareBp[새 역할]`. `negotiationState: 'COUNTERED'`, `negotiatedAsk: ask`. 실패면 `WITHDRAWN`: 그 제안을 목록에서 제거(다른 제안·안전 잔류 유지). 둘 다 타임라인 `NEGOTIATED`. pending은 유지(같은 kind), nextAction `'DECISION'`. `rngState` 갱신.

## 3. `REJECT_OFFER { offerId | null }` — rng 없음

- `offerId`: 그 제안 제거 + `OFFER_REJECTED`. 안전 잔류(`market.safeOfferId`)는 개별 거절 불가(`VALIDATION_FAILED { reason: 'SAFE_OFFER' }`). 남은 제안이 안전 잔류뿐이어도 pending 유지(사용자가 잔류를 확정해야 닫힌다).
- `null`(전부 거절 → 잔류): `OFFERS`면 4절의 안전 잔류 수락과 같은 결과 + `OFFER_REJECTED(ALL)`. `CONTRACT`(step 7 RENEWAL)면 제안 제거·pending null·`OFFER_REJECTED(ALL)`·nextAction `'ADVANCE'`(시즌 계속, 결산 뒤 만료 시장이 열린다).

## 4. `ACCEPT_OFFER { offerId }` v2 — rng 없음, kind별 원자 전환(D-45)

`pending.kind`가 `'OFFERS'` 또는 `'CONTRACT'`(offers ≥ 1)일 때 받는다. Phase 1 첫 계약(`market.reason === 'FIRST_CONTRACT'`)은 지금 코드 경로 그대로(회귀 금지). 공통: `이적_희망`·`잔류_선언` 태그 제거, pending null.

- **잔류(현 계약 유지)**: `market.reason === 'INTEREST'`이고 `offer.id === market.safeOfferId` → 계약·팀·context·관계 불변, 타임라인 `OFFER_REJECTED(ALL)`, nextAction `'ADVANCE'`.
- **RENEWAL**(step 7 사전 협상, EXPIRED 안전 잔류, 협상된 RENEWAL): 새 `Contract`(id `CTR-${nextRevision}`, kind PERMANENT, `signedAtRevision = nextRevision`, `signedSeasonIndex = season ? season.index + 1 : seasonHistory.length + 1`, `promiseBreaches 0`, 제안 조건 그대로). 팀·context·관계·clubHistory 항목은 건드리지 않고 현재 열린 stint의 `contractId`만 새 id로 바꾼다(`endReason 'RENEWED'`는 쓰지 않는다 — 예약 유지). 타임라인 `CONTRACT_RENEWED`. nextAction: step 7이면 `'ADVANCE'`, 결산 뒤면 `'ADVANCE'`(다음 시즌 준비 = START_SEASON; 현행 결산 뒤와 같은 화면 흐름).
- **TRANSFER · FREE_AGENT**: 현재 stint 마감(`toSeasonIndex = seasonHistory.length`, `endReason` TRANSFER→`'TRANSFERRED'`, FREE_AGENT→`'EXPIRED'`) → 새 Contract(PERMANENT, `signedSeasonIndex = seasonHistory.length + 1`) → 새 stint(`fromSeasonIndex = signedSeasonIndex`) → `stage`(tier YOUTH면 YOUTH, 아니면 PRO) → `context`: `tacticalFit ← offer.tacticalFitEstimate`, `squadStatus ← contractRules.squadStatusByRole[rolePromise]`, `positionProficiency`는 위 규칙 → 관계: `managerTrust ← transferRules.relationshipCarry.newManagerTrustBase`, `captain ← 0`, `rival ← 0`, `fans ← clamp(floor(fans × fansCarryBp / 10000) + (라이벌 직행 ? rivalMoveFansDelta : 0) + (약속 위반 이적 ? promiseBreachMoveFansDelta : 0), 0, 100)`, `agent` 유지. "라이벌 직행" = `transferRules.rivalPairs`에 (이전 팀, 새 팀) 쌍이 있거나 태그 `잔류_선언`을 가진 채 이적. "약속 위반 이적" = 이전 `contract.promiseBreaches ≥ 1`. 라이벌 직행이면 태그 `배신_이적` 추가. 타임라인 TRANSFER→`TRANSFERRED`, FREE_AGENT→`CONTRACT_SIGNED`. nextAction `'ADVANCE'`.
- **LOAN**: `parentContract ← { ...현재 계약, suspended: true }`, `contract ← 새 Contract(kind 'LOAN', loan: offer.loan, lengthSeasons 1, teamId 임대 구단, signedSeasonIndex = seasonHistory.length + 1)`. 현재 stint 마감(`endReason 'LOANED'`), 새 stint(kind LOAN). context·관계 전환은 TRANSFER와 같되 팬 급락·`배신_이적`은 적용하지 않는다(임대는 배신이 아니다). 타임라인 `LOANED`. nextAction `'ADVANCE'`.
- 완료 조건 3(중복 명령): 기존 멱등 규칙(같은 commandId 재생·revision 충돌)에 기대고, 새 테스트로 "같은 ACCEPT_OFFER 두 번 → 두 번째는 revision 충돌 실패, 계약 1개"를 단언.

## 5. 결산 배선(`settleSeason`)과 step 7 응답 필수

- `settleSeason` 끝(태그 부여 뒤)에 순서대로: (a) **D-47** `result.promiseFulfilment.fulfilled === false`면 `contract.promiseBreaches += 1`, 태그 `약속_위반` 추가, `relationships.managerTrust += transferRules.relationshipCarry.managerTrustPromiseBreach`(clamp 0..100; `SeasonResult.stateDeltas.managerTrust.after`에는 반영하지 않는다 — 결산 결과는 시즌 성적, 이 하락은 결산 뒤 사건). 지켜졌으면 `약속_위반` 제거. (b) `contract.kind === 'LOAN'`이면 6절 LOAN_RETURN 분기. (c) 아니면 `openMarketAfterSettlement(state, ruleset, nextRevision)` — 열리면 `pending = OFFERS`, nextAction `'DECISION'`; 안 열리면 지금과 같다(pending null, nextAction 그대로).
- `judgeMarketReason`은 T-3-002 수정판(season null이면 `seasonHistory` 마지막 결과 폴백)을 그대로 쓴다 — 바꾸지 않는다.
- `season.ts` `isAutoPassablePending`: CONTRACT는 다시 `offers.length === 0`일 때만 통과. `simulate.ts` ADVANCE의 임시 `OFFER_EXPIRED` 자동 만료 블록 제거. `nextActionForPending`: CONTRACT는 `offers.length > 0`이면 `'DECISION'`, 아니면 `'ADVANCE'`.

## 6. 임대 결산과 `LOAN_RETURN { decision }`(D-46) — rng 없음

- 임대 시즌 결산 뒤: `parentRemaining = computeContractSeasonsRemaining(parent.lengthSeasons, parent.signedAtRevision, timeline)`(임대 시즌의 SEASON_STARTED가 원소속 잔여를 소비한다). 출전 비율 `shareBp = floor(result.selectionSummary.minutes × 10000 / possibleMinutes)`(possibleMinutes 0이면 0).
  - `parentRemaining === 0`: 복귀 대신 FA(D-46) — 원소속 계약을 `contract`로 복원(`suspended: false`, `parentContract null`, stint 마감 `RETURNED` + 원소속 stint 재개설)한 뒤 곧바로 `generateMarket({ reason: 'EXPIRED' })`로 `OFFERS` pending(안전 잔류 = 원소속 구단). 타임라인 `LOAN_RETURNED(RETURN)`.
  - 아니면 `pending = { kind: 'LOAN_RETURN', options: ['RETURN', ...(loan.buyOptionMinor !== null && shareBp >= transferRules.loan.buyMinShareBp ? ['PERMANENT'] : [])], buyOptionMinor }`, nextAction `'DECISION'`.
- `LOAN_RETURN { decision: 'RETURN' }`: 원소속 계약 복원(위와 같음), 관계는 임대 구단 값을 버리고 `managerTrust ← newManagerTrustBase`, `captain/rival ← 0`, `fans ← floor(fans × fansCarryBp / 10000)`, context는 원소속 계약의 `rolePromise`·`positionPlan`으로 재설정(`tacticalFit`은 원소속 stint 마감 전 값이 없으므로 `offerRules.tacticalFitEstimate.min`), 타임라인 `LOAN_RETURNED(RETURN)`, nextAction `'ADVANCE'`.
- `LOAN_RETURN { decision: 'PERMANENT' }`(options에 있을 때만): 임대 구단과 PERMANENT 계약 — `lengthSeasons = transferRules.renewal.lengthSeasons`, 급여·계약금은 `contractRules` 밴드 조회(T-3-002 `findOvrBand`·`lookupBandAmount`), `rolePromise = result.selectionSummary.squadRoleAtEnd`, `transferFeeMinor = buyOptionMinor`(표시용). `parentContract null`, 원소속 stint는 이미 `LOANED`로 닫혀 있으므로 그대로, 임대 stint 마감(`endReason 'TRANSFERRED'`) + 새 PERMANENT stint. 관계·context는 유지(같은 구단). 타임라인 `LOAN_RETURNED(PERMANENT)` + `TRANSFERRED`. nextAction `'ADVANCE'`.
