# T-4-001: 부상·관계·평판 타입 슬라이스 — `health`(InjuryEpisode)·`relationshipLog`/`memoryTags`·`season.manager`·`reputation`·Effect kind `HEALTH`·`RESOLVE_EVENT`의 INJURY/NATIONAL_TEAM 처리·DSL `health.*`/`season.manager.*`/`reputation.*`·트랙 B 룰셋 스키마·확장 훅 골격 (domain + contracts + content 스키마 + ADR-010 표)

## 목표

Phase 4(부상·관계·평판, 트랙 B)의 **타입 슬라이스**. T-3-001(PR #48)이 pending 형태·타임라인 kind·DSL 경로를 예약해 두었으므로, 이 작업은 그 예약에 **값을 채울 자리**(상태 필드·룰셋 섹션·Effect kind·명령 처리·훅 호출 지점)를 한 번에 만든다. 부상 발생 roll(T-4-002)·감독 교체·관계 로그·평판 갱신(T-4-003)·대표팀 자격 판정(T-4-004)은 만들지 않는다 — 대신 그 세 작업이 `simulate.ts`를 다시 만지지 않도록 **훅 호출 지점을 미리 박아 둔다**. 끝나면 (1) `CareerState.health`·`relationshipLog`·`memoryTags`·`reputation`, `FootballSeason.manager`·`injuryCount`가 기본값으로 존재하고, (2) `RESOLVE_EVENT`가 `INJURY`·`NATIONAL_TEAM` pending을 닫으며, (3) `HEALTH` Effect와 `RELATION`의 평판 타깃이 스키마·적용기·ADR-010 표에 같이 들어가고, (4) 트랙 B 룰셋 5개 섹션이 스키마·데이터에 있고, (5) `injury.ts`·`relationships.ts`의 항등 훅이 경기 뒤·결산 시 호출된다. 골든 9종은 hash·신규 필드만 바뀌고 `rngState.draws`는 그대로다.

## 데이터 계약(D-49·D-50·D-51을 domain 타입으로)

모든 값은 정수(D-36), 새 필드는 전부 기본값이 있는 additive 필드, `schemaVersion` 1 유지.

### CareerState

- `health: { episodes: InjuryEpisode[] }` — 기본 `{ episodes: [] }`.
  - `InjuryEpisode = { id: string; severity: 'MINOR' | 'MODERATE' | 'MAJOR'; bodyPart: 'KNEE' | 'ANKLE' | 'HAMSTRING' | 'SHOULDER' | 'HEAD'; occurredAt: { seasonIndex: number; step: number; matchId: string }; diagnosisRange: { minMatches: number; maxMatches: number }; rehab: 'EARLY' | 'STANDARD' | 'CONSERVATIVE' | null; recurrenceRiskBp: number; status: 'ACTIVE' | 'REHAB' | 'RECOVERED' | 'RECURRED'; permanentDelta: Array<{ key: AttributeKey; delta: number }> | null }`.
  - id 형식 `INJ-${seasonIndex}-${step}-${n}`(생성기는 T-4-002). "활성 에피소드" = `status`가 `ACTIVE` 또는 `REHAB`인 것 중 배열 마지막 항목.
- `relationshipLog: RelationshipLogEntry[]` — 기본 `[]`. `RelationshipLogEntry = { target: RelationTarget; delta: number; sourceId: string; reasonTag: string | null; seasonIndex: number; step: number }`, `RelationTarget = 'managerTrust' | 'captain' | 'rival' | 'fans' | 'agent'`. 최대 길이는 룰셋 `relationshipRules.logMax`(40) — **추가 로직(applyEffects에서 기록)은 T-4-003**, 여기서는 타입·스키마·기본값·자르기 순수 함수 `appendRelationshipLog(log, entry, max)`만.
- `memoryTags: Record<RelationTarget, string[]>` — 기본 5축 전부 `[]`, 축당 최대 `relationshipRules.memoryTagsMax`(3). 갱신 로직은 T-4-003.
- `reputation: { popularityCenti: number; mediaCenti: number }` — 0~10000, `CREATE_CAREER`에서 룰셋 `reputationRules.initialPopularityCenti`·`initialMediaCenti`(둘 다 5000)로 채운다. `buildMarketValueInput`이 5000 고정 대신 `state.reputation.popularityCenti`를 읽는다(기본값이 5000이므로 지수 결과 불변 — 테스트로 고정).

### FootballSeason

- `manager: SeasonManager | null` — `SeasonManager = { id: string; name: string; preferredArchetypeIds: string[]; tenureSeasons: number; trustBase: number }`.
  - `START_SEASON`이 **rng 없이** 기본 감독을 만든다(`manager.ts` `buildDefaultManager`): `id = \`${teamId}-mgr-1\``, `name = managerRules.names[코드포인트 합(teamId) % names.length]`, `preferredArchetypeIds = tacticalStyles[team.tacticalStyleId].preferredArchetypeIds[profile.primaryPosition]`(없으면 `[]`), `tenureSeasons = seasonHistory 끝에서부터 같은 teamId가 연속된 개수 + 1`(감독 교체가 모델링되기 전이므로 "같은 팀 = 같은 감독"), `trustBase = managerRules.trustBase`. 교체 판정·새 감독 생성·`managerTrust ← trustBase` 재평가는 T-4-003.
- `injuryCount: number` — 이 시즌에 만든 INJURY pending 수(RULE-TIME-004 상한 2), 기본 0. 증가는 T-4-002.

### Effect

- `EffectKind` += `'HEALTH'`. 타깃은 `'availability.matchesRemaining'`·`'health.recurrenceRiskBp'` 둘뿐. 제약: `stackingRule: 'SUM'`, `appliesAt: IMMEDIATE`, `expiresAt: null`만 허용(아니면 `RejectedEffect` reason `HEALTH_RULE`). `activeEffects`에 저장하지 않는다(적용 즉시 소멸). 적용:
  - `availability.matchesRemaining`: `state.season.availability`가 `{ kind: 'INJURY' }`일 때만 `matchesRemaining += delta`(clamp 적용), 아니면 reject reason `NO_ACTIVE_INJURY`.
  - `health.recurrenceRiskBp`: 활성 에피소드가 있을 때만 그 항목의 `recurrenceRiskBp += delta`(clamp), 없으면 reject reason `NO_ACTIVE_EPISODE`.
  - `applyEffects`가 지금은 `attributes/state/context/relationships` 네 bag만 복제·기록하므로 HEALTH는 별도 경로로 `season`·`health`를 갱신한다. `ApplyEffectsResult`의 형태를 바꾸지 말고 `applied`/`rejected`에 같은 방식으로 기록한다.
- `RELATION` 타깃 += `'popularity'`·`'media'` → `state.reputation.popularityCenti`·`mediaCenti`에 SUM(clamp 0~10000). `bagForKind('RELATION')`가 두 bag(relationships·reputation)을 다루게 되므로 타깃 이름으로 분기한다. `resolveDeferredKind`는 `reputation.` 접두를 `RELATION`으로 푼다.
- content `schema/effect.ts`: `EFFECT_KINDS` += `HEALTH`, `HEALTH_TARGETS` 상수, `RELATION_TARGETS` += `popularity`·`media`, `validateEffectTarget`에 HEALTH 분기와 위 제약. Base OVR 직접 변경 금지 검사는 그대로.
- **ADR-010 결정 1 표를 같은 커밋에서 갱신한다**(D-53 규칙): `RELATION` 행에 `reputation.popularityCenti / mediaCenti`(타깃 이름 `popularity`·`media`, Phase 4 미디어·SNS 이벤트·결산)를 더하고, 새 행 `HEALTH | availability.matchesRemaining / health.recurrenceRiskBp | Phase 4 부상 재활·재발(T-4-002)만, SUM·IMMEDIATE·만료 없음`을 추가한다. 이 파일 외 명세·ADR은 고치지 않는다.

### 명령·pending

- `RESOLVE_EVENT`(`resolveEvent`)는 `pending.kind`가 `EVENT` | `INJURY` | `NATIONAL_TEAM`일 때 받는다(`eventId`·`version` 일치 검사는 셋 다 같음). outcome roll·Effect 적용·`resolvedEventIds`·`EVENT_RESOLVED` 타임라인은 EVENT와 동일. 추가로:
  - INJURY: contracts `ResolveEventPayloadSchema`에 선택 필드 `rehabPlan?: 'EARLY' | 'STANDARD' | 'CONSERVATIVE'`를 더하고, pending이 INJURY인데 없으면 `VALIDATION_FAILED` reason `REHAB_PLAN_REQUIRED`. 있으면 `pending.episodeId`의 에피소드를 `status: 'REHAB'`, `rehab: plan`으로 바꾸고 `injury.ts` `applyRehabPlan(episode, plan, injuryRules)`(진단 범위를 `injuryRules.rehab[plan].returnShiftMatches`만큼 이동(min 1 이상), `recurrenceRiskBp += recurrenceAddBp`, clamp 0~10000)를 적용한 뒤 타임라인 `REHAB_CHOSEN`(refId = episodeId). 에피소드가 없으면 `VALIDATION_FAILED` reason `EPISODE_NOT_FOUND`. `availability`와의 동기화(확정 복귀 경기 수)는 T-4-002.
  - NATIONAL_TEAM: 선택 필드 `callUp?: 'ACCEPT' | 'DECLINE' | 'CONDITIONAL'`, 없으면 reason `CALL_UP_REQUIRED`. `ACCEPT`·`CONDITIONAL`은 타임라인 `NATIONAL_TEAM_CALLED`, `DECLINE`은 `NATIONAL_TEAM_DECLINED`(refId = eventId). 체력·관계·태그·챕터 예약은 T-4-004(이벤트 Effect로 표현되는 부분은 이미 outcome 적용으로 처리됨).
  - EVENT pending에 `rehabPlan`/`callUp`이 오면 무시하지 말고 `VALIDATION_FAILED` reason `PAYLOAD_KIND_MISMATCH`.
- `nextActionForPending`: `INJURY`·`NATIONAL_TEAM` → `'DECISION'`. `season.ts` `isAutoPassablePending`: `INJURY`·`NATIONAL_TEAM` → `false`(그 두 줄만 고친다 — CONTRACT 분기는 T-3-002 몫). 생성기가 아직 없으므로 골든에 영향 없음.
- 이벤트 정의(content `schema/event.ts`): `ChoiceSchema`에 선택 필드 `rehabPlan?`·`callUp?`(위 enum). superRefine: `presentation === 'INJURY'`면 모든 choice에 `rehabPlan` 필수, `presentation === 'NATIONAL_TEAM'`이면 모든 choice에 `callUp` 필수, 그 외 presentation(또는 없음)에서는 두 필드 금지. 클라이언트가 선택한 choice의 이 값을 payload로 넘기는 것은 T-4-005.

### 조건 DSL(T-3-001 예약 경로에 값 공급)

`runtime/condition-context.ts`에서 NOT_MODELED였던 경로를 실제 값으로 바꾼다. 스키마 경로 목록은 이미 있으므로 `condition.ts`는 (필요하면) 주석만.

| 경로 | 값 |
|---|---|
| `health.activeSeverity` | 활성 에피소드 severity, 없으면 `''` |
| `health.recurrenceRiskBp` | 활성 에피소드 `recurrenceRiskBp`, 없으면 0 |
| `health.majorInjuries` | `episodes`에서 severity `MAJOR` 개수 |
| `health.injuryEpisode`(Phase 1 경로) | 활성 에피소드 있으면 1, 없으면 0 |
| `health.recurrenceRisk`(Phase 1 경로) | `floor(recurrenceRiskBp / 100)` |
| `reputation.popularityCenti` | `state.reputation.popularityCenti`(기본 5000 — 골든 fixture의 조건 평가 결과가 바뀌지 않는지 확인) |
| `season.manager.id` / `season.manager.tenureSeasons` | `season.manager` 값, 시즌 밖·null이면 `''`/0 |
| `season.stats.recentFormAvg` | 그대로 NOT_MODELED(T-4-003) |

`reputation.popularityCenti`가 0→5000으로 바뀌므로 현재 팩(0.1.0) 이벤트 중 이 경로를 쓰는 정의가 있는지 먼저 확인한다(없어야 정상; 있으면 PR 본문에 적는다).
