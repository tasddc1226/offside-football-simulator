# T-2-006: 시즌 계약·동기화·크기·성능 — contracts 스키마 정합 검사, Snapshot 크기 측정, API-CAR-003 시즌 회귀, Worker 계산 시간

## 목표

Phase 2 Wave 2의 계약·플랫폼 작업. 도메인이 T-2-001~003에서 넓힌 `CareerState`(시즌·경쟁자·선발·경기 기록)가 **contracts 스키마·서버 동기화·리플레이 검증·로컬 저장·Web Worker**를 그대로 통과하는지 확인하고, 빠진 곳을 메우며, 앞으로 도메인이 필드를 더할 때(T-2-004·005) 계약이 자동으로 뒤따르도록 검사를 심는다. 도메인 규칙은 만들지 않는다.

## 참조 명세

- 요구사항 ID: API-CAR-002·003, API-VER-001, CMD-SIM-001~003(+CMD-SIM-004 `RESOLVE_ROLE`, D-34), 05 "저장" checkpoint 종류(STEP_BOUNDARY 포함), 08 "같은 fixture의 state hash가 브라우저 Web Worker·Node·Miniflare에서 같다", 11 "한 세션 이탈 후 복귀 10초 이내", D-33(Snapshot 크기), D-24·D-25.
- 읽는 순서: `docs/tracking/phase-2-plan.md`(T-2-006 행, D-24·D-25·D-33·D-34·D-35) → `docs/development/07-api-contract.md` API-CAR-003·API-VER-001 → `docs/development/05-save-and-versioning.md` → `docs/development/08-testing-strategy.md` 결정론 절 → T-2-001·T-2-002 PR 본문(새 명령·필드·golden 목록).
- 선행: T-2-002 머지. `origin/main`에서 시작한다. 동시 진행: T-2-003(domain·content)이 같은 시기에 `packages/domain`·`packages/content`와 contracts의 시즌 스키마 필드를 **추가**한다. 이 작업은 `packages/domain`·`packages/content`·`apps/web/src`를 만지지 않는다. contracts에서 T-2-003이 추가할 필드(`MatchRecord`·`SeasonPlayerStats`·`availability`)는 만들지 않고, 아래 "정합 검사"가 그 필드가 들어올 때 자동으로 잡도록 한다.

## 작업 내용

### 1. contracts 정합 검사(스키마가 도메인을 뒤따르게)

- `packages/contracts/src/career-state.test.ts`에 **golden 순회 테스트**: `packages/fixtures/src/*/` 아래 모든 `*.golden.json`/fixture의 최종 `state`를 `CareerStateSchema`(strict)로 파싱한다. 도메인이 필드를 더했는데 contracts가 모르면 실패한다. 파싱 결과를 `canonical`로 다시 직렬화해 `stateHash`가 golden과 같은지도 검사한다(스키마의 default·transform이 상태를 바꾸지 않음).
- `START_SEASON`·`SETTLE_SEASON`·`RESOLVE_ROLE`·`ADVANCE` payload 스키마와 `Pending`(`ROLE_PROPOSAL` 포함)·`FootballSeason`·`SeasonSummary`·`CheckpointType`·`TimelineEntry.kind`가 domain 타입과 1:1인지 `expectTypeOf`로 고정한다(이미 있는 방식이 있으면 그 방식).
- `COMMAND_TYPES`에 `RESOLVE_ROLE`이 있고 api `commands` 검증이 받아들이는지 테스트.

### 2. Snapshot 크기 측정(D-33)

- 테스트로 각 golden의 최종 상태 canonical JSON 바이트 수와 `PUT /careers/{id}` 본문 전체 바이트 수(Snapshot + 시즌 한 개 분량의 명령 로그)를 계산해 PR 본문 표에 적는다. 기준: `SNAPSHOT_STATE_RECOMMENDED_BYTES`(256 KB)·`REQUEST_BODY_MAX_BYTES`(1 MB).
- 시즌 상태가 권장치의 절반(128 KB)을 넘으면 **구현하지 말고** PR 본문에 압축 설계(결산 시 `matches`를 `seasonHistory` 요약으로 접는 방식, T-2-005에 넘길 항목)를 적는다. 넘지 않으면 "현 구조 유지"로 적는다. 검사 테스트는 권장치를 상한으로 고정한다(넘으면 실패).

### 3. API-CAR-003·API-VER-001 시즌 회귀(apps/api)

- `apps/api/src/test/cross-runtime-hash.test.ts`가 `packages/fixtures`의 golden을 **전부 순회**하도록 바꾼다(지금 목록이 고정이면). Miniflare에서 career-02(FAST·CHAPTER)·career-03을 리플레이해 `stateHash`가 golden과 같다.
- `apply-sync`·`verify-snapshot` 통합 테스트: career-02의 명령 로그를 (a) 한 번에 PUT, (b) step 경계 checkpoint마다 나눠서 PUT(`baseRevision`·`If-Match` 연쇄), (c) 중간 Snapshot 유실 뒤 같은 `Idempotency-Key` 재시도 — 세 경로의 최종 `verificationStatus`·hash가 같다. 명령 로그 길이가 늘어난 시즌에서 `REQUEST_BODY_MAX_BYTES` 안에 드는지 확인.
- `db:check`·마이그레이션 변경은 없어야 한다. 필요해지면 멈추고 PR 본문에 적는다.

### 4. engine-client·로컬 저장·Web Worker

- `packages/engine-client/src/sync/golden.test.ts`가 golden 전부를 순회하고, `replay`·`fork`·`import`가 시즌 명령(`START_SEASON`·`RESOLVE_ROLE`·`ADVANCE`·`SETTLE_SEASON`)을 포함한 로그로 같은 hash를 내는지 검사한다.
- 로컬 저장소 계약 테스트(`testing/local-store-contract.ts`)에 `STEP_BOUNDARY`·`SEASON_START`·`SEASON_SETTLED` checkpoint Snapshot이 저장·복원되는 항목을 더한다(05 "checkpoint 종류").
- **Worker 계산 시간**: `apps/web/e2e/hash-probe.spec.ts`(브라우저 Web Worker)에 career-02 FAST 시즌 전체 리플레이를 추가해 hash 일치와 걸린 시간(ms)을 기록한다. 상한은 5,000 ms(넘으면 실패), 목표는 PR 본문에 실제 값과 함께 적는다. Node(Vitest)에서 같은 리플레이의 시간도 표로 적는다(T-2-003 PR 본문의 domain 계산 시간과 나란히).
- 앱 화면은 만들지 않는다(T-2-007~009). `apps/web/src`는 금지, `apps/web/e2e`는 `hash-probe.spec.ts`와 그 헬퍼만.

- 만질 경로: `packages/contracts/src/**`(스키마·테스트), `apps/api/src/**`(테스트 위주, 동기화 로직은 회귀가 드러낸 결함만), `packages/engine-client/src/**`(테스트·로컬 저장 계약·필요한 최소 수정), `apps/web/e2e/hash-probe.spec.ts`(+헬퍼), `packages/fixtures/src/**`(읽기만 — golden 수정 금지).

## 제약

- 문구·주석 한국어. 커밋 `T-2-006: …`, 브랜치 `T-2-006-…`.
- 서브에이전트 리뷰 금지(gstack `/review`·`/codex`·adversarial·`/simplify`·병렬 fork). 예외는 Orca PR 게이트용 `/review:pr` 1회(로컬 모드).
- PR 직전 `git fetch origin && git merge origin/main`. T-2-003이 먼저 머지되면 그 golden(career-04)도 자동으로 순회되어야 한다. `pnpm-lock.yaml` 충돌은 `git checkout origin/main -- pnpm-lock.yaml && pnpm install --no-frozen-lockfile` 뒤 전체 체인 재실행.
- 명세를 고치지 않는다. 충돌 지점은 PR 본문에.
