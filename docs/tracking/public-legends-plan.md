# T-11-231: 명예의 전당 공개 페이지 기획

작성일: 2026-10-13 · 상태: 1단계 구현(시즌 결산 페이지는 2단계) · 관련: T-11-061(웹 광고), T-11-027(웹 광고 도입 기획)

> 1단계 구현 메모: 허브 · 순위 8종 · 포지션 4종 · 선수 페이지와 `/about/`, 꼬리글 · 가이드 링크, 사이트맵을 냈다. 새 API는 없다(기존 `GET /v1/hof` · `GET /v1/hof/:id`만 읽는다). 한국어만 그리고, 색인 대상 ID는 엣지에 하루 둔다(`worker.ts` `legendsIndex`).

## 1. 왜 하는가

2026-10-13 06:47 KST, AdSense가 `offside-lab.com`을 **"가치가 별로 없는 콘텐츠"**(Low value content) 정책 위반으로 거절했다. 사이트 소유권 확인과 ads.txt는 이미 승인됐으니 기술 설정 문제는 아니다.

크롤러(`Mediapartners-Google` UA)가 읽는 글은 다음뿐이다.

| 페이지                     | 읽히는 글                  |
| -------------------------- | -------------------------- |
| `/`                        | 약 1,000자 (게임 소개)     |
| `/guide/`                  | 약 7,700자                 |
| `/faq/`                    | 약 6,100자                 |
| `/fairness/`               | 약 1,700자                 |
| `/news/*` 47개             | 업데이트 소식(짧은 글)     |
| 그 밖의 경로(`/about/` 등) | 앱 셸 "불러오는 중"뿐, 404 |

게임 본체(커리어 · 명예의 전당 · 기록실 · 이적시장)는 전부 자바스크립트로 그려져서 크롤러에게는 빈 화면이다. 그런데 이 사이트에는 다른 곳에 없는 데이터가 있다. **공개 명예의 전당 71,907명**(2026-10-13)이고, 선수마다 시즌별 기록 · 트로피 · 수상 · 발롱도르 순위 · 스토리 기록(`LegendSnapshot`)이 있다. 이 데이터를 서버에서 그린 HTML 페이지로 내보내 **사이트만의 콘텐츠**로 만드는 게 이 작업이다.

목표:

1. AdSense 재심사를 통과한다(주목표).
2. "축구 커리어 시뮬레이션"과 선수 기록 검색으로 들어오는 자연 유입을 만든다(부목표).
3. 서버(D1 · Workers) 부담을 늘리지 않는다(CLAUDE.md "백엔드 보호" 규칙).

## 2. 가장 큰 위험: 자동 생성 대량 페이지

선수 7만 명을 똑같은 틀로 모두 색인하면, Google 스팸 정책의 **대규모 콘텐츠 악용**(scaled content abuse)이나 빈약한 콘텐츠로 판정될 수 있다. 그러면 이번 거절 사유가 오히려 강해진다. 그래서 **색인할 페이지를 골라서** 연다.

- 색인(`index, follow` + 사이트맵): 허브 · 순위 · 포지션 · 시즌 페이지, 그리고 아래 조건을 채운 선수 페이지만
- 나머지 선수 페이지: 열어 두되 `noindex, follow`, 사이트맵에서 뺀다(링크 공유와 탐색에는 쓰인다)

**선수 페이지 색인 조건(추천 기본값):** 아래 셋을 모두 채운다.

- 공개 이름이 있다. 익명 선수는 색인하지 않는다.
- 시즌별 상세 기록(`hasDetail`)이 있다.
- 다음 중 하나에 든다.
  - 레전드 점수 전체 상위 1,000
  - 포지션(FW · MF · DF · GK)별 상위 100
  - 서비스 시즌별 상위 100
  - 영구결번 보유

상위 1,000명 표본(2026-10-13)은 이름 공개 958명, 상세 기록 1,000명이다. 포지션은 FW 630 · MF 349 · DF 18 · GK 3이다. 전체 상위만 고르면 FW에 쏠리므로 포지션별 상위를 함께 둔다. 색인 페이지는 약 1,500~2,000개로 예상하며, 실제 수는 구현 때 운영 D1에서 센다.

## 3. 페이지 구성

경로는 `/legends/` 아래에 둔다. 기존 공유 링크 `/career/<id>`는 지금처럼 앱 셸 + 미리보기 메타(`noindex`)로 둔다.

| 경로                          | 내용                                                                                                                                                                                      | 색인       |
| ----------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------- |
| `/legends/`                   | 명예의 전당 소개(오르는 조건, 레전드 점수 · 등급을 매기는 방법), 전체 인원 · 시즌별 인원, 레전드 점수 상위 50, 순위 · 포지션 · 시즌 페이지로 가는 길                                      | 예         |
| `/legends/rank/<sort>/`       | 순위 유형별 상위 100: 레전드 점수 · 골 · 도움 · 공격포인트 · 출전 · 트로피 · 발롱도르 · 은퇴 가치. 유형마다 무엇을 세는지와 최고 기록 한두 줄                                             | 예         |
| `/legends/pos/<FW·MF·DF·GK>/` | 포지션별 상위 100, 그 포지션 은퇴 선수의 평균 최고 OVR · 평균 은퇴 나이 · 대표 세부 포지션 분포(집계 문장)                                                                                | 예         |
| `/legends/season/<n>/`        | 서비스 시즌 결산: 은퇴 인원, 상위 선수, 서버 최초 기록, 영구결번, 오프사이드 컵 결과(있으면). 시즌이 끝난 뒤에는 바뀌지 않는다                                                            | 예         |
| `/legends/p/<careerId>/`      | 선수 한 명: 프로필(포지션 · 국적 · 등번호 · 최고 OVR · 잠재력 · 은퇴 나이 · 마지막 구단), 시즌별 기록 표, 트로피 · 수상 · 발롱도르 · 대표팀, 스토리 기록, 칭호, 영구결번, "게임에서 보기" | 조건부(§2) |
| `/about/`                     | 운영자 · 게임 소개 · 연락처(`contact@offside-lab.com`) · 개인정보처리방침 · 약관 링크. 지금은 404라서 AdSense가 보는 신뢰 신호가 빈다                                                     | 예         |

- 모든 페이지에 메인 · 가이드 · FAQ · 명예의 전당으로 가는 공통 머리글과 꼬리글을 둔다.
- 메인(`/`) 정적 본문과 가이드의 "은퇴 · 명예의 전당" 절에서 `/legends/`로 링크한다.
- 선수 이름은 이미 공개 정책(`NAME_POLICY`: 선수 이름 공개가 켜져 있으면 명예의 전당에 공개)대로 보인다. 익명 선수는 "익명 선수"로 표시한다.
- 구단주 닉네임 · 프로필 ID는 싣지 않는다.
- 숨김(`careers.hidden`) 선수는 목록에서 빼고, 선수 페이지는 404로 둔다.

## 4. 구현 방식

`/news/`와 같은 방식이다. 웹 워커(`apps/web/src/worker.ts`)가 셸 HTML에 서버 데이터로 본문을 그려 넣는다(`public-news.ts`와 같은 구조).

- **셸:** `seo.mjs` `closeBundle`이 `legends-shell.html`을 만든다(`news-shell.html`과 같은 방식, 앱 번들 없이 정적 본문만).
- **데이터:** 이미 있는 공개 API를 쓴다.
  - 목록: `GET /v1/hof`(sort · pos · season · page, 엣지 캐시 60초)
  - 선수: `GET /v1/hof/:id`(스냅샷 포함, 엣지 캐시 300초)
  - 영구결번: `GET /v1/retired-numbers`
  - 서버 최초 기록: `GET /v1/firsts`
  - 새로 만들 것은 시즌 결산 집계 하나다(§3 `season`, 시즌별 인원 · 포지션 평균). 공개 · 엣지 캐시 · 인덱스 규칙을 따르고, 끝난 시즌은 길게 캐시한다.
- **HTML 캐시:** 워커가 그린 HTML을 `caches.default`에 둔다.
  - 목록 · 허브: 1시간
  - 선수: 1일
  - 끝난 시즌: 7일

  크롤러가 7만 페이지를 돌아도 같은 페이지는 API를 하루 한 번만 부른다.

- **사이트맵:** `newsSitemap`처럼 워커가 `sitemap.xml`에 색인 대상만 덧붙인다. 페이지가 많으므로 사이트맵 색인 파일(`/sitemap-legends.xml`)로 나눈다. `lastmod`는 은퇴 시각과 시즌 마감 시각을 쓴다.
- **색인 판정:** 선수 페이지의 색인 여부는 상세 응답에 붙은 순위 정보로 정한다. 상위 목록에 든 ID 집합을 워커가 사이트맵을 만들 때 함께 계산해 캐시에 두고, 선수 페이지는 그 집합으로 `X-Robots-Tag`를 정한다. API에 새 필드가 꼭 필요하면 `rank` 계열로만 더한다.
- **문구:** 페이지 문구는 `packages/app-core/src/i18n`에 ko · en · ja를 둔다. 첫 단계는 한국어 페이지만 색인하고, en · ja는 `?lang=`으로 열되 `noindex`로 둔다. 다국어 색인(`hreflang`)은 반응을 본 뒤 2단계에서 정한다.
- **광고:** 이 단계에서는 광고 칸을 넣지 않는다. 승인 뒤 T-11-061 웹 광고 칸 규칙(맨 아래, 비개인화)을 정적 페이지에도 적용한다.

## 5. 단계

| 단계 | 내용                                                                                                    | 기준                                                                               |
| ---- | ------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| 1    | `/legends/` 허브 · 순위 · 포지션 · 선수 페이지, `/about/`, 메인 · 가이드 링크, 사이트맵, 워커 HTML 캐시 | e2e: 셸 없이 본문이 HTML에 있음, 색인 · noindex 헤더, 반복 요청 시 API 재호출 없음 |
| 2    | 시즌 결산 페이지와 집계 API, 소식 게시판에 시즌 결산 · 데이터 분석 글을 정기적으로(시즌마다 1~2편) 올림 | 시즌 1 마감 직후 첫 결산                                                           |
| 3    | Search Console에서 색인 상태를 2~4주 지켜본 뒤 AdSense 재심사 요청. 승인되면 정적 페이지에 광고 칸      | 색인된 `/legends/` 페이지가 수백 개 이상                                           |

재심사는 1단계 배포 직후가 아니라 **색인이 쌓인 뒤**에 요청한다. 같은 사유로 다시 거절되면 다음 심사까지 더 오래 기다려야 할 수 있기 때문이다.

## 6. 검증

- 단위: 선수 페이지 렌더(익명 · 숨김 · 상세 없음 · 옛 기록 필드 없음), 색인 판정, 사이트맵 크기 상한
- e2e: `/legends/` · 순위 · 선수 페이지를 자바스크립트 없이 읽어 본문이 있는지, 같은 페이지 두 번째 요청에서 API를 다시 부르지 않는지
- API: 새 시즌 집계 공개 조회가 쿠키가 있어도 `sessions` · `profiles`를 조회하지 않는지(`hof.test.ts`와 같은 방식)
- 배포 후: `Mediapartners-Google` · `Googlebot` UA로 읽히는 글자 수를 표 1과 같은 방법으로 다시 잰다.
