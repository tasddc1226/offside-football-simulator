## 1. 목표와 다섯 작업의 관계

매출을 늘릴 후보는 기존 패스의 구매 전환, 신규 구매자의 첫 결제, 멤버십의 반복 결제, 기존 구매자의 스카우트 재구매, 일본 유입의 결제 전환이다. 모두 검증 전 가설이며 매출 증가를 보장하지 않는다.

## 2. 현재 구조에서 재사용할 것과 빈틈

- 패스의 `passRewardBetween`·`passTierOf`와 `passClaimable`을 재사용한다. 패스 없이도 진행도가 쌓이고 중간 구매 시 시즌 처음부터 인정된다. 현재 앱은 `Track`의 전체 단계표 다음에 구매 버튼을 둔다. 전체 보상 합계를 현재 받을 수 있는 보상으로 표시하면 안 된다.
- 멤버십은 월 한국 기준가 4,900원, 광고 제거·출석 보상 2배·출석 시 매일 강화권 1장·뱃지를 제공한다. 매일 자동 지급이나 모든 플랫폼에서 같은 광고 경험을 보장한다고 쓰지 않는다.
- 앱 멤버십은 스토어 자동 갱신 구독이다. **웹 Xsolla 멤버십은 자동 갱신 없는 30일 이용권**이며, 웹에서도 패스를 구매할 수 있다. 웹을 앱 전용 상품 안내로 되돌리거나 두 결제 형태의 갱신 문구를 합치지 않는다.
- 일반 아이템 상품 계약은 `{ item, qty }` 단일 종류다. 스타터팩의 혼합 지급은 SKU 하나 추가로 끝나지 않는다. 거래 검증·모든 아이템 지급·환불·운영 집계를 함께 확장해야 한다.
- Android 멤버십 코드는 현재 `subscriptionOffers[0]`을 고른다. 할인 오퍼의 대상·기본 요금제·가격 단계·토큰 선택을 보강하기 전에는 콘솔에서 할인만 켜지 않는다.
- 기존 `commerce_stage`는 `boost|scout`, 진입점 `shop|player_tab` 중심의 동의 기반 퍼널이다. 패스·멤버십·스타터팩을 이미 측정한다고 간주하지 않는다. `grant_ack`는 일부 복구 거래를 제외하는 클라이언트 관측값이며 서버 전체 매출과 다르다.

## 3. 공통 구매 경험

### 3.1 노출과 우선순위

1. 구매·지급 대기 또는 오류 복구가 있으면 **복구 안내가 판매 안내보다 먼저**다. 기존 구매자가 다시 결제해 해결하도록 유도하지 않는다.
2. 사용자가 직접 연 상점·상품 화면은 언제든 이용할 수 있다. 자동으로 띄우는 결제창이나 연속 팝업은 추가하지 않는다.
3. 게임 결과 뒤의 선제 판매 안내는 인라인 카드 하나만 쓴다. 패스의 새 단계 안내 → 스타터팩 → 멤버십 순으로 고른다. 스카우트 비교는 사용자가 상점을 연 경우에만 나온다.
4. 선제 안내는 프로필·캠페인 기준 7일에 한 번, 한 이용 세션에 최대 한 번이다. 세션은 30분 이상 비활동 뒤 새로 시작한다. 닫으면 해당 캠페인을 7일 숨기며, 관련 상품 구매·구독 활성화 시 바로 제거한다. 직접 방문에는 이 빈도 제한을 적용하지 않는다.
5. 빈도 기억은 게임 세이브와 분리한 버전 있는 설정으로 둔다. 기기 간 완전한 빈도 일치는 보장하지 않는다. 계정 전환·로그아웃 시 이전 계정의 상품·보유량·가격·안내 상태를 보여 주지 않는다.
6. 로그인 전에는 기존 플레이를 계속 제공한다. 자격을 확인할 수 없으면 할인·미결제 전용·수령 가능 수량을 추정하지 않는다. 구매를 선택한 뒤 기존 로그인 경로를 쓰고 현재 프로필로 자격을 다시 확인한다.
7. Game Center·Play Games 연결, ATT 허용, 이용 분석 동의는 구매·할인·보상 자격 조건이 아니다.

기존 게임센터 연결·로그인·공지·동의 안내와 같은 장면에서 경쟁하면 판매 안내를 미룬다. 첫 은퇴 결과를 판매 안내로 가리거나 기존 권한 요청 순서를 바꾸지 않는다.

### 3.3 모바일 화면 방향

기존 축구 기록·보상 카드의 `PitchCard`, `Txt`, `Btn`, `PopSheet`와 공통 디자인 토큰을 쓴다. 새 브랜드·폰트·애니메이션 체계를 만들지 않는다. 라이트 팔레트 기준은 `bg #e9eee8`, `surface #ffffff`, `ink #14201a`, `muted #5c6b62`, `pitch #1c4a35`, `pitchAccent #f0b437`이며 실제 코드는 토큰을 참조한다. 다크 모드는 기존 대응 토큰을 쓴다.

- 상품별 핵심은 실제 받을 보상·실제 결제 가격·적용 기간이다. 본문은 왼쪽 정렬, 금액과 수량은 항목별로 정렬한다. 결제 화면마다 채운 주요 버튼은 하나다.
- 기존 시트 안의 상단 구매 버튼을 기본으로 한다. 하단 고정 버튼을 별도로 넣으려면 안전 영역·닫기·탭바·스크롤 끝의 가림 검증을 통과해야 한다.
- iOS 44pt·Android 48dp 이상 터치 영역, 본문 대비 4.5:1, 큰 글자·스크린리더·움직임 줄이기를 확인한다. 잘린 가격·조건은 터치로도 전체 내용을 확인할 수 있어야 한다.
- 웹 320/390px, 앱 작은/큰 휴대폰·iPad와 가로 화면에서 가격·갱신 조건·닫기가 읽혀야 한다. 설계 문서의 도식은 실기기 검증 증거가 아니다.

## 4. 작업 1: 시즌 패스 구매 전환

### 대상과 제안

판매 가능한 현재 시즌, 패스 미보유, 서버 진행도 확인 완료, 유효한 현지 가격이 있는 구단주에게 제안한다. 이번 시즌 패스를 가진 구단주에게는 구매 대신 수령 상태를 보여 준다. 다음 시즌 선구매·과거 시즌 미수령 보상을 이번 시즌 구매 혜택에 섞지 않는다.

```text
시즌 2 패스                         닫기
현재 진행: 유효 은퇴 12명 · 8단계
지금 구매하면 받을 보상
스카우트권 5장 / 강화권 23장 / 리롤권 33장 / 이름 변경권 1장
[스토어 가격으로 시즌 패스 구매]
이번 시즌 진행도가 반영돼요. 자동 갱신은 없어요.
[전체 단계와 앞으로 받을 보상 보기]
```

위 수량은 기준 코드의 12명·1~8단계 합계 예시다. 하드코딩하지 않고 서버의 현재 시즌·단계와 공통 보상 규칙으로 계산한다. 미보유자는 열린 모든 단계, 보유자는 아직 받지 않은 열린 단계만 합친다. 아이템이 0인 줄은 생략한다. 시즌 일정은 서버가 확정한다.

### 흐름과 범위

- 기존 패스 진입 시 상단에 수령 가능 합계·가격·구매 버튼을 먼저 둔다. 긴 단계표는 펼침으로 제공하되, 보유자의 수령과 과거 시즌 내역에 계속 접근할 수 있게 한다.
- 현재 시즌 5·9·15·25명 기준을 처음 넘은 유효 은퇴 업로드가 서버에서 확인되면, 빈도 제한 안에서 패스 안내 후보가 된다. 여러 기준을 한 번에 넘으면 가장 높은 하나만 쓴다. 기본 은퇴 결과·저장·공유·새 커리어 동작은 유지한다.
- 안내를 만들기 위해 모든 은퇴마다 패스 API를 호출하지 않는다. 로컬에 확정된 최신 진행도·패스 상태가 있을 때만 카드를 만들고, 패스 창을 연 시점에 한 번 확인한다. 최신 상태가 없으면 구체적인 보상 숫자 안내를 생략한다.
- 구매 후 자동 보상 지급으로 바꾸지 않는다. 기존 서버 거래 확인 뒤 ‘열린 보상 받기’를 제공하고 기존 수령 CAS·재시도 키를 재사용한다.
- 시즌 전환으로 결제 시점과 확정 시즌이 달라지면 서버가 실제 연 시즌을 표시한다. ‘지금 수령’ 제안은 구매 직전에 다시 계산한다. 구매 중인 거래에 다른 시즌 상품 결제를 겹치지 않는다.

### 완료 조건

- 진행도 0/12/25/50, 일부 수령, 현재 보유·다음 시즌 보유·과거 시즌 미수령을 구분한다.
- 현재 미보유·12명 예시에서 합계가 규칙과 일치하고, 미래 14단계 총합을 즉시 보상으로 표시하지 않는다.
- 오래된 서버 응답·세션 변경·시즌 마감·상품 조회 실패에 잘못된 구매 버튼이나 수령 보장 문구가 없다.
- 웹은 기존 Xsolla 구매·귀환·상태 갱신을 보존하고, 앱은 해당 스토어 결제만 사용한다.
- 주 지표는 대상 프로필의 패스 첫 구매율과 D7 전체 결제 매출/대상 프로필이다. 패스 매출 상승과 일반 묶음 매출 감소를 함께 본다.

| 지급 후보        | 스카우트권 2장·잠재력 강화권 5장·리롤권 5장                                        |
| 포함하지 않는 것 | 광고 제거·멤버십·패스·확률 상승·기간 제한 아이템                                   |
| 다른 국가 가격   | 스토어별 승인 가격을 그대로 표시. 한국 금액의 앱 자체 환산 금지                    |
| 웹               | 초기 판매 제외. 기존 웹 상품은 유지하고, 웹 결제 이력도 앱 판매 자격 판단에는 포함 |

구성·기준가는 기획 후보다. 기존 묶음·패스 즉시 보상 대비 대체 구매와 공급량 영향을 검토한 뒤 확정한다. 실제 비교할 동일 구성이 없으면 ‘정가 대비 할인’·‘몇 배 가치’ 문구를 쓰지 않는다.

### 자격과 노출

- 서버에 유효한 35세 이상 선수 은퇴가 1건 이상 있고, 현재 로그인 프로필에 실결제 이력이 없는 경우다. 체험·샌드박스·취소·승인되지 않은 보류 거래는 첫 결제로 세지 않는다.
- 최초 실결제 성공 이력은 일반 아이템·광고 제거·패스·앱 구독·웹 결제를 포함한다. **한 번 실결제 후 환불한 프로필도 미결제자로 되돌리지 않는다.** 현재 활성 구독이 없다는 이유로 첫 구매 자격을 주지 않는다.
- 스토어 계정과 게임 프로필의 결합 이력을 확인한다. 기존 구매를 복원 중이거나 귀속을 확인할 수 없으면 자격은 `unknown`이며 판매하지 않는다. 기기 저장값만으로 미결제를 판정하지 않는다.
- 첫 유효 은퇴 뒤 기본 결과를 확인한 후 인라인 카드로 제안하고, 닫은 뒤에는 기존 상점의 해당 상품 자리에서만 다시 열 수 있다. 사용 기한·가짜 카운트다운은 두지 않는다.
- 여기서 1회는 현재 프로필의 정상 구매 경로 기준이다. 한 사람의 여러 계정·서로 다른 프로필까지 완전히 식별한다고 약속하지 않는다. 로그인 시 프로필이 바뀌면 자격을 새로 확인한다.

### 결제·지급·환불 설계 요구

1. 서버에 `eligible|ineligible|unknown|purchase_pending|owned` 자격 계약을 둔다. 자격 조회와 결제 직전 확인을 분리하고, 프로필·상품 버전의 유일 제약으로 동시 시작을 제한한다. 보류 거래가 남았다고 다른 기기에서 새 결제를 시작하지 않는다.
2. 거래 검증은 기존 스토어 경로를 재사용한다. 가격·수량·자격은 클라이언트가 보낸 값을 신뢰하지 않는다. 혼합 구성의 버전을 거래 원장에 고정하고 원장·자격 소진·세 아이템 지급을 원자적으로 처리한다.
3. 같은 스토어 거래 재전송은 같은 결과이며 추가 지급하지 않는다. 오래된 앱에는 혼합 SKU를 판매 목록으로 반환하지 않는다. 기존 단일 상품 API의 응답·지급·환불 계약은 보존한다.
4. 결제 대기·앱 종료·타임아웃 뒤 복구할 수 있어야 한다. 서버 지급을 확인하기 전 스토어 거래를 소비 완료하지 않는다. 결제 전에 만든 예약이 만료돼도 이미 승인된 거래의 지급 권리는 사라지지 않는다.
5. 스토어가 서로 다른 실제 유료 거래를 예외적으로 중복 승인한 경우 ‘이미 구매’로 돈만 받고 끝내지 않는다. 각 승인 거래에 약속한 묶음을 한 번씩 지급하고 중복 구매로 별도 기록해 지원·환불 대상으로 분리한다. 이 예외는 재구매 버튼이나 자격을 다시 열지 않는다.
6. 환불은 거래별 구성·실제 회수량을 남기고 현재 가진 만큼만 아이템별로 회수한다. 이미 소비한 아이템 때문에 다른 상품의 미지급 보상을 빚으로 잡지 않는다. 환불 선행·재통지·부분 처리 실패에도 중복 회수하지 않는다.
7. 자격 조회는 프로필 인덱스·첫 성공 이력으로 제한한다. 구매 화면마다 전체 원장을 훑지 않는다. 새 테이블·인덱스와 이전 거래 집계가 필요하면 확장→전환 순서 및 별도 배포 계획을 쓴다.

### 출시와 완료 조건

- SKU는 App Store Connect와 Play에 각각 등록·승인한다. 콘솔 등록만으로 판매를 열지 않고 서버·지원 앱·가격 조회·신규/기존 구매자 테스트를 모두 확인한다.
- 재설치·다른 기기·다른 플랫폼·계정 전환·환불 이력·보류·동시 구매·복구·중복 통지·테스트 거래를 검증한다. 구버전의 기존 구매도 통과해야 한다.
- 스토어가 상품을 반환하고 서버가 해당 버전을 지원하는 클라이언트에만 판매 허용한다. JS 변경은 호환 runtime의 OTA 검증 후 판단하고, Billing SDK 등 네이티브 변경 시 새 빌드가 필요하다.
- 주 지표는 대상 프로필의 D7 첫 결제율과 **D30 전체 결제 매출/대상 프로필**이다. 스타터팩 매출만 늘고 기존 상품·패스 매출이 줄면 성공으로 보지 않는다.

## 6. 작업 3: 멤버십 가치 전달

### 3A. 기존 기본가의 가입 안내

- 광고 시청을 선택하는 화면에서 사용자가 원할 때 멤버십 비교를 펼친다. 광고를 누른 뒤 다른 판매 화면으로 가로채지 않는다. 광고 로딩 실패·결제 실패를 멤버십 판매 조건으로 쓰지 않는다.
- ‘광고 없이 보상 받기’·‘출석 보상 2배’·‘출석하면 매일 강화권 1장’을 가입 버튼 근처에 둔다. 매일 강화권은 출석 조건을 같은 자리에서 설명한다.
- 이미 멤버십 활성·유예 혜택 중이면 판매 안내를 숨긴다. 평생 광고 제거 보유자에게는 광고 제거를 새 가치로 강조하지 않고 출석·강화권 혜택을 우선한다. 같은 광고 제거를 두 번 사야 한다고 안내하지 않는다.
- 앱은 실제 월 가격·자동 갱신·관리/해지·복원을 표시한다. 웹은 기존 30일 이용권·갱신 없음·기존 기간 뒤 연장 계약을 유지한다. 앱에서 웹 결제로 이동시키는 경로를 추가하지 않는다.
- 가입을 닫거나 취소하면 원래 보상 선택으로 돌아간다. 가입이 확인되면 현재 보상 요청을 기존 권한 경로로 한 번만 처리한다. 광고 시청 콜백과 가입 성공이 겹쳐도 보상을 두 번 주지 않는다.

### 3B. 첫 달 할인은 별도 실험

제안은 **첫 1개월 2,900원 → 이후 월 4,900원 자동 갱신**이다(한국 후보가, 스토어 가격 우선). 무료 체험·연간 요금제·기존 구독자 가격 변경은 이번 초안에 포함하지 않는다. 3A의 효과와 섞지 않고 나중에 비교한다.

- iOS는 신규 구독 대상의 introductory offer를 사용한다. 구독 그룹 자격을 StoreKit에서 확인한다. 기존·이전 구독자용 promotional offer와 섞지 않는다.
- Android는 기존 월 base plan에 신규 구독 대상 오퍼를 구성하고, 명시한 base plan/offer와 실제 사용자 자격에 맞춰 선택한다. `subscriptionOffers[0]` 또는 가장 낮은 가격만으로 선택하지 않는다.
- 할인 기간·첫 결제 금액·다음 정상가·갱신 주기·자동 갱신 여부를 스토어의 가격 단계로 표시한다. 자격·가격 단계를 확인 못 하면 실제 정상가만 보여 주거나 판매를 닫는다. 화면의 할인과 요청에 쓰는 offer token이 일치해야 한다.
- 콘솔 설정·클라이언트 오퍼 선택·스토어 검증·약관/해지 안내가 모두 준비된 플랫폼에서만 연다. 지원하지 않는 앱 버전에는 할인 약속을 노출하지 않는다.

### 완료 조건과 판단

- 비구독·평생 광고 제거·활성 구독·갱신 취소 후 유효 기간·유예·만료·웹 이용권 상태를 구분한다. 복원과 계정 전환 시 안내가 바로 고쳐진다.
- 3A는 가입 전환과 D7 합산 수익을 본다. 3B는 D7 가입률만으로 승리 판정하지 않고 **첫 정상가 갱신을 포함한 D35 수익·갱신·취소·환불**을 본다.
- 광고 수입 감소와 기존 광고 제거·강화권 팩 구매 감소를 함께 계산한다. 구독 이익이 광고 손실을 만회했다고 확인되기 전에는 확대하지 않는다.

## 7. 작업 4: 스카우트 묶음 선택과 재구매

- 기존 `scout_1`, `scout_5`, `scout_50`을 유지한다. 상점을 연 구단주에게 보유량, 수량, 전체 결제 금액, 같은 통화의 장당 단가를 한 번에 비교하도록 한다.
- 큰 묶음을 미리 선택하거나 바로 결제하지 않는다. 상품 선택 뒤 해당 묶음과 실제 총액을 확인하고 스토어 결제를 연다. 작은 묶음·구단 자금 구매·확률/천장 안내를 계속 찾을 수 있어야 한다.
- ‘장당 가격이 가장 낮아요’는 현재 조회된 같은 국가·통화·세금 표시 기준의 숫자 가격으로 실제 비교가 가능한 경우에만 표시한다. ‘인기’·‘추천’·‘할인’은 측정 또는 비교 근거 없이 붙이지 않는다.
- 현지화된 가격 문자열을 잘라 숫자로 바꾸지 않는다. SDK의 숫자 가격·통화 코드·소수 자릿수를 쓰고, JPY는 실제 통화 자릿수에 맞춘다. 가격 정보가 부족하면 장당 가격과 절약률을 숨기고 총액만 보인다.
- 재구매 안내는 이미 상점을 열었고 스카우트를 사용한 기존 구매자에게만 시험한다. 게임 실패·확률 실패 직후 자동 결제 팝업이나 확정 획득 문구를 추가하지 않는다. 남은 천장 수와 구매 수량을 합쳐도 보장 조건을 과장하지 않는다.
- 웹은 기존 Xsolla 확인 단계·현지 통화 안내를 보존한다. 웹이 한국 기준가만 제공하는 상태에서는 엔화 단가·앱 스토어와의 가격 우위를 만들지 않는다.
- 주 지표는 상점 방문 대상의 D7 **전체 매출/대상 프로필**, 주문당 결제 금액, 구매자 수, 재구매율이다. 큰 묶음 주문만 늘고 구매자 수·재방문이 줄면 보류한다.

## 8. 작업 5: 일본 첫 결제 전환

### 대상·언어·상품

- 판매 국가 판단은 구매한 storefront/결제 국가를 쓴다. UI 언어 `ja`, 기기 국가, IP를 일본 구매자로 대체하지 않는다. 광고·게임 지표와 국가를 연결할 수 없으면 결합 분석을 하지 않는다.
- 일본어 이용자는 국가와 관계없이 자연스러운 일본어 안내를 받는다. 일본 storefront 대상 실험의 분모와 일본어 QA 대상은 별개다.
- 1~4번의 일본어는 같은 구현 PR에 포함한다. 아이템 이름·현재 받을 보상·구매 복원·자동 갱신·출석 조건·지원 문의를 원어민 검토 대상으로 둔다.
- 스타터팩은 2번과 같은 구성을 쓰고 일본 승인 가격을 후보표로 검토한다. 한국 가격의 즉석 엔화 환산, 일본만 더 좋은 확률·보상을 주는 변경은 하지 않는다. 콘솔 확인 전 엔화 판매가를 문서나 앱에서 확정하지 않는다.

### 유입 경로와 스토어 소재

1. 먼저 기존 유입에서 상품 노출→구매→첫 플레이 복귀의 일본어 흐름을 확인한다. 일본 Android 실기기에서 가격과 구매·지급·복구를 검증한다. iOS 결과와 합쳐 성과를 만들지 않는다.
2. 다음으로 일본 스토어의 첫 스크린샷·짧은 설명에서 ‘선수 육성→은퇴 선수로 구단 운영’을 보여 주는 소재 한 가지를 비교한다. 현재 공개 빌드에서 가능한 기능만 쓰고, 심사 중 기능은 출시된 것으로 표시하지 않는다.
3. 스토어 전환율은 상세 페이지 방문자 대비 최초 다운로드로 본다. 리뷰 평균은 건수와 함께 보며 소수 리뷰의 상승·하락을 실험 승패로 쓰지 않는다.
4. 유료 유입은 결제·광고·D7 재방문을 관측할 수 있고 해당 버전의 ANR/크래시 악화가 없을 때 후속 소규모 실험으로 한다. 매체·크리에이티브 하나씩 분리하고 예산은 실행안에서 따로 정한다. 이 PR은 광고를 집행하지 않는다.
5. 첫 상품 실험과 스토어 소재·가격·광고 유입을 같은 주에 모두 바꾸지 않는다. 먼저 구매 동선, 다음 소재, 마지막 유입 확대로 원인을 구분한다.

### 완료 조건

- 일본어·엔화·큰 글자·통화 표시·스토어 지역 불일치·다른 지역의 일본어 이용자·로그인 전 복귀·취소/보류/환불을 검증한다.
- 스토어 소재에 개인정보·사용자 원본 선수 이름·승인 전 가격·획득 확률 과장이 없다.
- 일본 Android와 iOS의 첫 결제율·D7 재방문·D30 수익을 따로 본다. 광고비가 있으면 비용을 뺀 기여액까지 확인하고, 국가별 광고 수입을 나눌 수 없으면 일본 수익성 개선은 ‘확인 불가’로 남긴다.

새 계측은 후보 계약이다. 기존 수집 여부를 먼저 확인하고 필요한 최소 범위만 구현한다. 취소한 일일 GA4 보고나 주기적 수집 자동화를 재생성하지 않는다. 구매 처리에 필요한 거래 원장과 선택적 이용 분석을 구분하고, 분석 동의가 없어도 결제·지급·복원은 동작한다.

### 배정과 관측

- 실험 단위는 현재 서버 프로필이다. 실험 ID와 프로필로 고정 배정하며 재접속·플랫폼 이동 때 다시 뽑지 않는다. 기존 은퇴 화면 실험과 ID·키·군을 공유하지 않는다.
- 처음 자격을 충족해 배정된 시점을 `t0`로 두고 전체 배정 대상(ITT)을 분모로 쓴다. 보이는 카드를 누른 사람만 분모로 삼지 않는다. 동의한 표본만 분석할 수 있으면 결과도 그 표본의 결과라고 명시한다.
- 제안 퍼널은 `eligible → offer_view → detail_open → checkout_request → pending/cancel/error → server_grant`다. 실제 기존 이벤트명과 매핑을 먼저 정의하고 기존 enum을 몰래 재해석하지 않는다. 새로운 성공은 서버가 확인한 신규 실거래로 센다.
- 후보 필드는 실험 ID·군·상품 키/버전·진입점·플랫폼·빌드/runtime·UI 언어·스토어 국가·가격 단계·결과 분류다. 분석 이벤트에 영수증·토큰·선수 이름·이메일·원문 프로필 ID를 보내지 않는다. 가입/로그인 식별자를 임의의 분석 키로 새로 전송하지 않는다.
- 구매·환불과 실험군 결합이 필요하면 서버 내부에서 목적·보존 범위·접근 권한을 정해 구현한다. 원장 자체를 GA4로 복제하지 않는다. 계정/동의 변경 시 미전송 분석과 이전 계정 귀속 상태를 폐기한다.

### 지표와 채택 기준 제안

- 공통 사업 지표: 같은 통화·세금/수수료/환불 기준으로 맞춘 **전체 결제 기여액 + 광고 수입 - 추가 유입비**를 대상 프로필 또는 관측 가능한 동일 코호트로 나눈다. 자료가 없으면 gross 판매액을 별도 보조 지표로만 쓴다. 정산되지 않은 추정치는 그렇게 표기한다.
- 각 작업의 지정 지표와 함께 구매자 수·환불률·지급 실패·D7 재방문·크래시/ANR을 본다. 주문 건수를 고유 구매자 수로 부르지 않는다.
- 초기 채택 목표 후보는 대상 프로필당 D7 전체 결제 매출 **상대 +10%**다. 효과 보장이 아니라 검정 설계를 위한 최소 관심 효과다. 최초 구매율은 실제 기준율, 매출은 비구매자의 0을 포함한 프로필별 평균·분산으로 필요 표본을 계산한다. 큰 구매가 드문 분포의 추정 방식과 극단값 처리도 사전에 고정하며 구매율용 표본식을 매출에 그대로 쓰지 않는다. 유의수준 5%·검정력 80%를 설계 기준으로 하고, 3B는 정상가 갱신을 포함한 D35로 판정한다.
- 배정은 내부 QA 후 전체 대상의 10%만 참여(대조 5%·실험 5%)하여 지급/표시 안전성 확인, 이후 대조 50%·실험 50%로 고정하는 제안이다. 이전 참여자의 군은 유지한다. 가격·보상·노출 변경은 서로 다른 실험 ID를 쓴다.
- 최소 14일 모집 후 마지막 대상의 D7이 성숙할 때 비교한다. 2번의 D30·3B의 D35 판단은 해당 기간이 끝나야 한다. 작은 표본이면 기간을 늘리고, 7일 비교만으로 유의한 승리나 갱신 개선을 선언하지 않는다.
- 확대 기준: 필요한 표본과 관측 기간 충족, 사전 정의한 주 지표의 증가 근거, 환불률 +1%p 미만·D7 재방문 -2%p 미만이라는 제안 경계, 지급·안정성 악화 없음. 환불·안정성 분모가 작거나 결합 수익이 관측 불가하면 보류/추가 관측한다. 경계 수치는 실행 전 베이스라인 검토로 확정한다.
- 잘못 청구·오지급·혜택 누락·다른 계정 노출이 재현되면 신규 판매/노출을 즉시 중지한다. 노출을 끄더라도 승인 거래의 지급·복원·환불 처리는 계속한다. 수익만 보고 반복 확인하며 실험을 조기 종료하지 않는다.

## 11. 구현 경계와 실행 백로그

### 공통 검증과 배포

- 네 언어 사전·가이드/FAQ·카피 검토를 같은 구현 PR에 포함한다. 상품 구성/지급량 변경은 공급량·대체 구매 영향과 필요한 밸런스 검증을 기록하고, 게임 결과·규칙 변화가 있으면 프로젝트 밸런스 이력 규칙을 따른다.
- 서버: 권한·실결제 검증·멱등성·원자 지급·계정 귀속·캐시·중복 환불/콜백·지원하지 않는 SKU를 검증한다. 트랜잭션 성공 전후 실패 주입으로 부분 지급이 없는지 확인한다.
- 클라이언트: 오프라인·상점 장애·보류·취소·재설치·계정 전환·지급 재확인·기존 세이브 복구를 확인한다. 파괴적인 저장 형식 변경은 범위 밖이며 필요해지면 마이그레이션을 별도 설계한다.
- 화면: 좁은 웹 화면과 iOS/Android 실기기에서 큰 글자·다크 모드·스크린리더·안전 영역·가격/갱신 조건을 확인한다. 시뮬레이터·mock E2E·Hermes 번들만으로 실제 결제·광고·스토어 오퍼가 검증됐다고 보고하지 않는다.
- 검증 범위는 [CI 테스트 정책](../operations/ci-test-policy.md)을 따른다. 웹 변경은 푸시 전 빌드·번들 검사, E2E는 푸시 후 PR 검사에서 한 번. 새 노출·가격/상품 안내·기능에는 네 언어 릴리즈 노트를 추가한다.
- 코드 머지, 서버 배포, OTA 게시, 스토어 상품 승인, 앱 공개 출시, 실기기 검증, 실험 활성화를 각각 기록한다. 네이티브 의존성이 바뀌면 새 runtime 빌드를 만들고 구 runtime의 구매·복구 경로를 유지한다.
- 코드/상품 준비 후 실험은 플랫폼·버전별 기본 OFF에서 시작한다. 롤백 시 신규 노출과 신규 결제만 멈추고 기존 거래/패스 수령·구독 검증·환불은 계속한다. 이미 산 상품의 가격·구성 버전은 바꾸지 않는다.
