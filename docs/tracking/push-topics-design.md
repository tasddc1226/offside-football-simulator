# 받고 싶은 알림 고르기 설계 (알림 주제 나누기 · 권한 요청 전 선택 · 알림함 묶음 보기)

작성: 2026-11-10. 상태: 구현함(커밋 전), 실기기 화면 확인 전. 작업 ID는 PR을 열 때 잡는다.

사용자가 정한 것: 유저가 받고 싶은 알림을 나눠서 고르게 한다, 11장의 추천안대로 진행한다, 알림함에서도 종류별로 볼 수 있게 한다.

## 1. 왜 하는가

2026-11-10 16:00 KST 운영 집계(읽기 전용)다.

| 항목                                | 값                                                               |
| ----------------------------------- | ---------------------------------------------------------------- |
| 푸시를 받을 수 있는 계정            | 4,103 (iOS 4,025 · 안드로이드 78)                                |
| 유효한 앱 세션 계정 대비            | 약 24% (17,380 중)                                               |
| 종류별 설정을 한 번이라도 바꾼 계정 | 166                                                              |
| 끈 수                               | 공지 116 · 업데이트 89 · 친구 76 · 팀 73 · 이적시장 68 · 독려 18 |

- iOS 숫자는 동의 수가 아니다. iOS는 창을 띄우지 않는 조용한 알림(provisional)으로 자동 등록한다. 정식 허용이 몇 명인지는 서버에 남지 않아 모른다.
- 지금 구분은 굵다. "팀" 하나에 랭크 경기 결과 · 컵 · 리그 · 보상이 다 들어 있고, "독려" 하나에 출석 알림과 복귀 권유가 같이 있다.

목표는 받겠다고 고른 알림만 보내서 정식 허용을 늘리고 끄는 사람을 줄이는 것이다.

## 2. 구현 전 확인 결과 (2026-11-10)

| ----------- | ------------------------ | ------------------------------- |

| 친구 화면   | 45 → 2 → 2               | 10 → 0 → 1                      |
| 컵 접수     | 6 → 1 → 5                | 2 → 0 → 2                       |

"받기"를 누른 뒤 OS 결과: iOS 허용 119 · 차단 36 · 거절 1 · 등록 실패 3, 안드로이드 허용 27 · 거절 15. 같은 기간 조용한 알림 자동 등록은 iOS 1,281명이다.

- **안드로이드가 78계정뿐인 것은 버그가 아니다.** 같은 기간 안드로이드 활성 사용자가 587명이고, 권유는 397명에게 보였다. 권유는 정상으로 뜬다. 수가 적은 것은 모수가 작고 받기를 누르는 비율이 낮아서다.
- **막히는 곳은 "받기"를 누르기 전이다.** 홈 카드는 본 사람의 5~8%만 누른다. 구단 만들기 확인 창은 91%가 "나중에"를 고른다. 판매 등록 직후만 31%로 높다. 알림이 바로 쓸모 있는 순간일수록 누른다.
- 누른 뒤에도 iOS의 23%, 안드로이드의 36%가 OS 창에서 거절한다.

### 2-2. iOS 조용한 알림에서 정식 허용으로

실기기 시험은 하지 않았다. 코드와 운영 수치로 확인했다.

- Expo는 provisional을 "아직 묻지 않음"으로 돌려준다(`ExpoNotificationsPermissionsRequester.swift`). 그래서 앱은 조용한 알림 상태에서도 권유를 띄우고, "받기"를 누르면 정식 권한을 요청한다(T-11-586에서 이미 이렇게 만들었다).
- 조용한 알림 사용자가 대부분인 iOS에서 받기 158건 중 허용 119 · 차단 36이고 "거절(다시 물을 수 있음)"은 1건이다. OS 창이 뜨지 않았다면 대부분이 "거절"로 남았을 것이다. 창은 뜬다.

**정정:** 이 문서의 첫 판은 "조용한 알림 사용자는 권유를 못 받는다"고 썼다. 틀렸다. 조용한 알림은 `pushState.enabled`를 켜지 않아 권유가 그대로 뜬다. 권유 조건은 고치지 않았다.

## 4. 서버

### 4-1. 알림에 주제를 적는다

`notifications.topic`(text, null 허용). 알림을 만드는 9곳 모두에서 주제를 적는다. `source_key` 앞머리로 추론하지 않는다. 주제가 없는 옛 행은 지금처럼 `kind`로 거른다.

### 4-2. 설정 저장: 주제 값이 없으면 옛 설정을 따른다

`push_preferences`에 `topic_match` · `topic_cup` · `topic_league` · `topic_friend` · `topic_reward` · `topic_attendance` · `topic_comeback`(null 허용 · 기본 null). 공지 · 업데이트 · 이적시장은 주제가 하나뿐이라 기존 열을 쓴다.

```
보낼지 = COALESCE(주제 열, 그 알림 종류의 옛 설정 열, 1)
```

- 기존 계정을 옮겨 적지 않는다. "팀"을 꺼 둔 계정은 경기 · 컵 · 리그가 꺼진 채로 유지된다.
- 옛 앱이 옛 키(`team` · `social` · `nudge`)를 바꾸면 그 아래 주제 값을 null로 되돌린다.
- 보상 알림은 종류가 팀 · 친구 둘 다다. 주제를 고르지 않은 계정은 그 알림의 종류 설정을 따른다.
- 판정 SQL은 `push/prefs.ts` 한 곳에 있다. 적재할 때와 보내기 직전에 같은 조건으로 본다.

### 4-3. 설정 API

- `GET · PUT /v1/push/preferences?v=2`: 주제 10개의 실제 적용 값을 돌려준다. `v`가 없으면 지금 응답 그대로다(`?nudge=1` 포함).
- `PUT`은 옛 키와 주제 키를 함께 받는다. 주제 키는 한 요청에 여러 개를 실을 수 있다.

### 4-4. OS 권한 상태

기기 등록 요청의 `permission`(`authorized` · `provisional`, 선택 항목)을 `push_devices.permission`에 남긴다. 옛 앱은 null이다. 이 값으로 정식 허용 계정 수를 센다. 앱은 권한 상태가 바뀌면 다시 등록한다.

### 4-5. 알림함 묶음 보기

`GET /v1/notifications?group=game|market|social|news|nudge`. 없으면 전체다.

| 묶음   | 조건                                                             |
| ------ | ---------------------------------------------------------------- |
| game   | 주제가 match · cup · league, 또는 주제 없는 옛 행 중 종류가 team |
| market | 종류가 market                                                    |
| social | 주제가 friend · reward, 또는 주제 없는 옛 행 중 종류가 social    |
| news   | 종류가 news                                                      |
| nudge  | 종류가 return                                                    |

- 옛 행을 주제로 채워 넣지 않는다(운영 테이블 전체 쓰기를 피한다). 그래서 배포 전에 받은 보상 알림은 "경기 · 대회"에 보인다. 알림은 90일 뒤 사라지므로 그 뒤에는 맞는다.
- 한 사람의 알림 안에서만 거르므로 `notifications_profile_created_idx` 범위 안이다. 새 인덱스는 없다.
- 안 읽은 수는 묶음과 상관없이 전체다(앱 아이콘 숫자와 맞춘다).
- 응답 모양은 그대로다. 옛 앱은 `group`을 보내지 않는다.

### 4-6. 마이그레이션

`0163_push_topics.sql`: null 허용 열 9개 추가. 기존 행을 다시 쓰지 않는다.

## 5. 앱

### 5-1. 권한 요청 전 선택 창

권유에서 "받기"를 누르면 OS 창보다 먼저 받고 싶은 알림을 고르는 창이 뜬다(`components/PushPicker`).

- 묶음 5개를 고른다. 처음 값은 경기 · 대회, 이적시장, 친구 · 보상, 게임 소식이 켬이고 **출석 · 복귀 알림만 끔**이다.
- 권유가 뜬 자리의 묶음을 맨 위에 올린다(판매 등록 → 이적시장, 구단 · 리그 · 컵 · 은퇴 → 경기 · 대회, 친구 화면 → 친구 · 보상).
- "알림 받기"를 누르면 OS 권한을 묻고, 켜지면 고른 값을 요청 하나로 저장한다. OS에서 거절하면 기기에만 두었다가 나중에 설정에서 켤 때 저장한다.
- 하나도 고르지 않으면 "알림 받기"를 누를 수 없다.
- 판매 등록 · 구단 만들기 · 리그 신청 · 컵 접수 뒤의 확인 창은 이 선택 창으로 바뀐다(그 자리의 제목 · 설명이 위에 나온다). 창을 닫으면 "나중에"다.
- 홈 · 친구 · 은퇴 카드에서 창을 닫으면 아무 일도 없다(카드가 남는다).
- 권유 자리와 간격 규칙(곳마다 한 번 · 3일 간격 · 홈 7일 보류)은 그대로다.

### 5-2. 설정 화면

토글 6개가 묶음 제목 아래 주제 10개로 바뀐다. iOS에서 조용한 알림 상태면 전체 토글 아래에 "지금은 알림 센터에만 조용히 쌓여요. 켜면 소리와 배너로 받아요." 한 줄이 나온다.

### 5-3. 알림함

전체 · 읽지 않음 탭 아래에 묶음 칩이 생긴다: 모든 종류 · 경기 · 대회 · 이적시장 · 친구 · 보상 · 게임 소식 · 출석 · 복귀. 읽지 않음과 함께 쓸 수 있다. 칩을 바꿀 때만 다시 불러온다.

### 5-4. 웹

푸시와 알림함은 앱 전용이라 웹 화면은 바뀌지 않는다. 공개 가이드의 출석 알림 문장만 네 언어로 고쳤다("알림을 켠" → "출석 알림을 켠").

## 6. 기존 사용자에게 바뀌는 것

- 이미 알림을 받고 있는 사람의 설정 값은 그대로다.
- 새로 "받기"를 누르는 사람은 선택 창을 거치고, 출석 · 복귀 알림은 직접 켜야 받는다. 조용한 알림으로 받던 iOS 사용자가 정식 허용으로 넘어올 때도 같다.
- 리텐션 홀드아웃은 2026-11-11 00:00 KST에 끝난다. 복귀 푸시 효과가 크게 나오면 선택 창의 처음 값을 켬으로 바꾼다.

## 7. 측정

| 볼 것                        | 어디서                                               |
| ---------------------------- | ---------------------------------------------------- |
| 정식 허용 계정 수 (플랫폼별) | `push_devices.permission`                            |
| 권유 → 받기 → 고름 → OS 허용 | GA4 `push_optin_view` · `accept` · `pick` · `result` |
| 묶음별 선택 비율             | `push_optin_pick`의 `groups`(예: `game,market`)      |
| 주제별 끔 수                 | `push_preferences`                                   |

- `groups`는 GA4 맞춤 측정기준으로 등록해야 보고서에서 나눠 볼 수 있다(등록 전 수치는 소급되지 않는다).
- 기준선은 2-1의 표다. 선택 창이 한 단계를 더하므로, "받기 → OS 허용" 비율이 지금(iOS 75%, 안드로이드 64%)보다 떨어지는지 먼저 본다.

## 8. 검증

- 서버: 주제 상속, 옛 키가 주제 값을 되돌림, 주제가 옛 설정보다 먼저, 보내기 직전 재확인, 알림함 묶음, 권한 상태 저장(`routes/notifications.test.ts`).
- 앱: 선택 창 흐름 · 분석 이벤트 · 거절 때 기기에만 보관(`pushAsk.test.mjs`), 주제 설정 저장소(`pushPreferences.test.mjs`), 권한 상태 전송(`push.test.mjs`), 묶음 규칙(`pushTopics.test.ts`).
- **남은 것:** 시뮬레이터 · 실기기에서 선택 창, 설정 화면, 알림함 칩의 실제 모양과 OS 창 순서를 확인하지 않았다.
- 되돌리기: 서버 판정을 종류 설정만 보게 되돌리면 지금 동작이다. 열은 남겨 둔다.

## 9. 배포 순서

서버가 먼저 나가야 한다. 앱이 먼저 나가면 `?v=2` 응답이 옛 모양이라 앱이 옛 설정을 주제로 펴서 읽고, 주제 저장은 서버가 나올 때까지 실패한다. 운영 배포는 API와 OTA를 한 번에 내므로 따로 맞출 일은 없다. 새 네이티브 의존성이 없어 OTA로 나간다.
