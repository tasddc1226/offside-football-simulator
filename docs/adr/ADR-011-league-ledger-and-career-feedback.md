# ADR-011. 소속 리그 결과 원장과 커리어 피드백의 분리

- 상태: Superseded by ADR-013 (2026-09-24). 제안 (2026-09-14). 구현 전 계약 검토 대상이며 기존 운영/저장 규칙은 변경하지 않는다.
- 관련: [PRD](../archive/offside/product/career-world-prd.md), [작업 계획](../archive/offside/development/20-career-world-plan.md), [ADR-003](ADR-003-simulation-location.md), [ADR-004](ADR-004-content-format.md), [시간 모델](../archive/offside/development/11-time-model-and-pacing.md), [WORLD STAGE](../archive/offside/development/15-world-stage-expansion.md)
- 조사 기준: main `cb6d2995c127a225a0cb926830ed47d808424ddd`

## 맥락

현재 `computeLeaguePosition`은 다른 팀 경기를 계산하지 않고 기대승점으로 내 팀 순위를 근사한다(`packages/domain/src/season-stats.ts:173–208`). 타팀 승무패·득실·승점 표를 이 숫자에 맞춰 생성하면 서로 맞붙은 결과와 표가 모순될 수 있다. `CompetitionRecord`는 내 팀의 대회 기록이지 리그 전체 원장이 아니다.

동시에 원작 관찰에서 선택의 후속 결과와 시간·평가·은퇴 연출의 가치가 확인됐다. 이를 게임 결과를 바꾸는 규칙과 화면 표현으로 분리해야 재시도·동기화·리플레이가 유지된다. 기존 FAST 정책에서 일반 선택 이벤트는 자동 노출되지 않으므로 콘텐츠 저작만으로 새 경험이 생기지 않는다.

## 제안 결정

### 1. 한 커리어의 소속 리그만 가벼운 경기 원장으로 계산한다

전 세계 모든 리그나 NPC 선수단을 시뮬레이션하지 않는다. 신규 지원 버전에서 현재 선수의 소속 리그 한 시즌을 대상으로 고정 참가팀 목록, 홈/원정 대진, 최소 스코어 결과를 만든다. 타팀전은 선수별 출전·능력치·부상을 계산하지 않는 별도 순수 스코어 함수다.

원장은 커리어별 독립 세계다. 서로 다른 커리어가 같은 구단·연도를 표시해도 하나의 공유 순위표를 보장하지 않는다. 파생 seed의 career scope는 재생 가능한 입력 seed/버전으로 정의하고 기기 ID·현재 시각·새로 발급한 DB ID에 의존하지 않는다. 같은 입력의 재생과 fork가 요구하는 기존 결정론을 유지한다.

이는 WORLD STAGE의 전 세계 전체 경기 시뮬레이션 회피 원칙을 유지하면서, **표로 공개하는 소속 리그 안에서는 팀 간 결과가 일치해야 한다**는 범위를 구체화한 제안이다. 기존 `Team`을 `Club`로 개명하거나 해외·등록 정책을 먼저 구현하지 않는다.

참가팀은 기존 명명 팀과 부족 인원을 채우는 결정론적 가상 팀으로 시즌 시작에 고정한다. 표시 이름·전력 생성 규칙은 새 ruleset/content 계약에 넣고 ID를 안정화한다. 표의 가상 팀을 자동으로 계약/이적 가능한 팀으로 취급하지 않는다.

참가팀 수는 정확히 `league.teamCount`다. 팀 ID 정렬을 기준으로 홈/원정 2회전 대진을 만들고 홀수 팀 수에는 BYE를 둔다. BYE는 팀·경기·승점으로 저장하지 않는다. 정책은 입력 배열의 순서와 무관해야 한다. 사용자 표시 이름 override는 seed나 전력에 섞지 않고, 과거 표의 팀명은 당시 표시 snapshot 또는 고정 팩 참조로 보존한다.

### 2. 대진·내 경기·라운드 완료는 하나의 결과를 공유한다

- 신규 버전의 전체 홈/원정 대진에서 내 팀 일정을 투영한다. 기존 독립적인 내 일정과 타팀 일정을 각각 생성해 나중에 맞추지 않는다.
- 내 팀 경기는 기존 `playMatch` 경로의 확정 결과가 정본이다. 같은 경기의 리그 원장 결과를 다시 뽑지 않는다. 타팀전만 새 경량 함수가 계산한다.
- 12-step을 12경기로 해석하지 않는다. 리그 라운드를 기존 경기 구간 step 3~11에 결정론적으로 배치하고, 한 step에 여러 라운드를 허용한다.
- `playStepMatches`에서 내 경기 결과를 만든 직후 해당 라운드의 나머지 결과를 합쳐 whole round를 원자 반영하고, 그 뒤에만 부상/이벤트 pending을 외부에 노출한다. 내 팀이 BYE인 라운드도 같은 step에서 타팀전을 확정한다. `fixtureId`/완료 라운드 집합으로 중복을 막으며 `currentStep`만으로 재진입을 판단하지 않는다.
- 컵·대표팀 경기는 리그 원장에 넣지 않는다. 내 팀 `CompetitionRecord`의 승무패·득실·position은 같은 원장의 투영과 일치해야 한다.
- 경기별 고유 키는 최소 `career scope + season index + leagueId + round + homeTeamId + awayTeamId` 의미를 구분한다. 재개/이적/왕복 대진이 충돌하지 않아야 한다.

부상·징계·대표팀·복무로 선수가 결장해도 팀 경기는 계속 진행한다. 내 팀 경기의 기존 OUT/선수 통계 처리와 팀 스코어를 유지한다. 실제 경기 계산 없이 시즌을 건너뛰는 별도 경로가 발견되면 WP-01에서 지원/제외를 명시하고, 그 경로를 0경기 꼴찌로 표시하지 않는다. 이적·임대의 소속 변경은 현재 시즌 경계 계약을 유지하고 다음 시즌에 새 로스터를 만든다.

### 3. 타팀 난수와 정렬은 독립적·결정론적으로 유지한다

타팀 결과는 커리어 seed에서 분리한 리그 namespace와 fixture 키로 파생한다. 전역 main RNG나 내 경기 `matchRngState`를 UI 조회 또는 타팀 경기 수만큼 소모하지 않는다. 기존 `matchRngState` 분리 패턴을 참고하되 새 API 이름/직렬화 계약은 WP-01에서 확정한다.

타팀 스코어 확률·전력 보정 계수는 새 ruleset에 둔다. UI나 소스에 숨은 별도 밸런스 상수를 추가하지 않는다. 내 경기 `playMatch` 자체의 고정 draw 계약은 유지하고, 새 일정으로 상대와 호출 순서가 바뀌는 영향은 신규 버전의 변화로 검증한다.

같은 버전의 같은 명령 로그는 같은 결과를 만든다. 새 버전의 내 일정·순위 분포는 달라질 수 있으므로 구버전과 새 버전의 결과 동등성을 요구하지 않는다. 대신 구버전 경로·아티팩트·golden은 불변이다.

MVP 순위 규칙은 승점(3/1/0) → 득실차 → 다득점 → 안정 팀 ID 오름차순으로 제안한다. 승점과 동률 규칙은 버전 규칙으로 명시하고 런타임 locale 정렬이나 UI 임의 정렬을 사용하지 않는다. 승자승·플레이오프는 별도 대회 형식 없이 끼워 넣지 않는다.

### 4. 진행 중 최소 원장, 결산 후 불변 요약을 저장한다

다음은 **신규 설계 개념이며 현재 존재하는 API/타입이 아니다**.

| 개념 | 저장/조회 책임 |
|---|---|
| LeagueSeasonLedger | 현재 시즌에만 존재하는 optional 필드. 참가팀/일정 정책 버전·확정 fixture의 최소 스코어·진행 경계 |
| StandingRow | 원장에서 순수하게 계산하는 표시 모델: teamId, P/W/D/L/GF/GA/GD/PTS/rank. 진행 중 중복 정본으로 저장하지 않음 |
| FinalLeagueTable | 결산 시 고정한 리그/시즌/참가팀 식별과 최종 행을 SeasonResult에 한 번 저장. SeasonSummary.result와 Archive는 이를 참조/보존하며 Summary 바깥에 같은 배열을 중복 저장하지 않음 |
| CareerFeedback | 실제 요청·효과·결과의 source ID와 단계. 선택과 연출을 게임 효과로 중복 반영하지 않음 |

진행 중 타팀 결과는 fixture ID와 스코어처럼 최소한만 저장한다. 대진은 고정 정책으로 재구성할 수 있지만 현재 시즌 내 경기의 상세 기록은 기존 정본을 유지한다. 결산 후 타팀 경기별 로그를 매 시즌 누적하지 않고 최종 표만 보존한다. 이 절약으로 서버 실제 body 제한을 만족하는지는 반드시 실측한다.

`hashSeasonResult` 전에 최종 표와 실제 효과를 확정한다. 이후 새 시즌·이적·새 사건이 과거 결과를 재작성하지 않는다. strict Zod 계약, snapshot, import/export, fork/replay, 서버 검증을 도메인과 함께 갱신한다. 구버전 저장의 새 optional 필드는 absent 그대로 유지하며 가짜 0점 표나 새 필드 기본값을 넣지 않는다.

기능을 지원하는 활성 리그 시즌에서 원장이 없거나 충돌하면 데이터 불일치로 처리하고 기존 복구 경로를 제공한다. UI가 표를 합성하거나 이미 진행한 경기를 조용히 재추첨하지 않는다. 시즌 시작 전·명시적으로 미지원인 상태·구버전의 absent와 손상을 구별한다. 과거 타팀 경기별 상세 조회는 최종 표만 저장하는 MVP의 비범위다.

### 5. 순위는 맥락이며 실제 승강격과는 분리한다

MVP는 표·우승·순위 구간·결산을 연결한다. 기존 소속 변경·계약 체계에 승강격을 암묵적으로 추가하지 않는다. 승격권/강등권을 표시할 때 실제 리그 이동이 아님을 설명한다. 실제 참가팀 교체·타 리그 이동·대륙 자격은 새로운 세계 상태 계약 이후다.

순위가 실제 원장 기반으로 바뀌면 `DECIDER` 챕터, 우승 판정, Legacy 입력도 영향을 받는다. UI만 바꾸는 릴리스로 취급하지 않고 새 버전의 분포·기록을 검증한다. 같은 저장에서 일부 소비자는 근사 순위, 다른 소비자는 실제 표를 읽게 두지 않는다.

### 6. 사건과 애니메이션을 서로 다른 계층에 둔다

사건은 `조건 → 선택 → 실제 효과 → 후속 결과`의 저장 가능한 근거를 갖는다. 기존 면담·이적·부상·대표팀·은퇴 명령을 우선 사용하고 새로운 상태/명령이 필요한 경우에만 공유 계약을 확장한다. 신규 FAST 노출 경로는 일반 EVENT를 추가하면 자동으로 열린다고 가정하지 않는다. 기존 필수 상태 처리 우선순위와 결정 예산 안에서 별도 게이트를 설계한다.

모션은 이미 확정한 결과의 표현이다. 실제 처리 상태가 없는 서버 협상·심사 단계를 사실처럼 꾸미지 않는다. 필요한 경우 `결과 확인` 연출임을 분명히 한다. DOM/접근성에는 최종값을 먼저 두며 애니메이션 tick을 저장·난수·hash·명령과 연결하지 않는다.

기존 DSN-MOT-001을 따른다: 화면/모달 시간 토큰, 카운트업 최대 800ms와 건너뛰기, OS/앱 모션 감소 시 즉시 결과. 여러 시즌 회고는 전체 건너뛰기·최종 기록 바로 보기·재열람이 가능해야 하며, 효과 종료 이벤트가 오지 않아도 최종 상태에 접근할 수 있어야 한다.

## 대안과 선택 이유

| 대안 | 장점 | 채택하지 않는 이유 |
|---|---|---|
| 기존 순위를 기준으로 타팀 표를 장식적으로 생성 | UI 작업이 빠름 | 대진·승패·승점·득실 보존 관계를 증명할 수 없음 |
| 모든 리그와 NPC 선수의 전체 경기 엔진 실행 | 세계를 넓게 표현 | 현재 요구보다 큰 성능·저장·밸런스 비용 |
| 조회할 때 매번 타팀 결과 생성, 아무 결과도 저장하지 않음 | 저장량 작음 | 정책/호출 경계 실수로 과거 결과·진행 경계가 달라질 위험; 최소 확정 원장 선호 |
| 서버가 리그 진행을 계산 | 공통 세계 구현에 유리 | 단일 커리어·오프라인 목표와 ADR-003에 불필요한 네트워크 의존 |
| 애니메이션 종료 시 효과 적용 | 화면 구현이 단순해 보임 | 탭 종료·감소 설정·재시도에 따라 결과가 달라짐 |

## 영향·비용·전환

영향은 domain 일정/경기 결선/집계/결산, contracts, content 버전, engine-client 저장·리플레이, web 표·결과에 걸친다. UI에는 게임 계산을 넣지 않는다. 새 public HTTP endpoint나 D1 리그 테이블은 기본적으로 필요하지 않으며 기존 checkpoint 경로를 쓴다.

정확한 새 ruleset/content 버전 번호는 착수 시 registry 충돌 확인 후 배정한다. 현재 1.6.0/0.6.1을 덮어쓰지 않는다. 새 팩의 호환 목록·체크섬·loader·retirement registry·실제 CREATE 경로를 함께 검증한다. 배포와 서비스 시즌 활성화는 분리하고, rollback 시에도 생성된 커리어의 해당 버전 실행 아티팩트를 남긴다.

## 결정 확정 전 게이트

WP-01에서 참가팀 최대 수·불완전 라운드/휴식 복무 처리·최소 저장 형식·동률 규칙을 실행 가능한 계약으로 확정한다. 한 시즌 및 20시즌의 Snapshot/실제 PUT body 크기, Worker 실행 시간, 구버전 리플레이를 확인하지 않고 데이터 모델을 확정하지 않는다. 기존 정책의 수치 예산을 넘으면 먼저 원장 형식과 저장 범위를 줄이고 임의로 서버 제한을 올리지 않는다.

현재 크기 기준은 `packages/contracts/src/headers.ts:19–23`의 state 권장 **262,144 bytes**, request body hard cap **1,048,576 bytes**다. `packages/contracts/src/snapshot-size.test.ts`와 `apps/api/src/middleware/bodyGuard.ts` 경로를 따라 UTF-8 직렬화된 state와 commands 포함 전체 PUT을 따로 측정한다. 이 계획의 인수 기준은 최대 지원 팀 수×20시즌에서 state 256KiB 이하, 전체 PUT 1MiB 이하이며 API가 허용한다는 이유로 state 권장치를 초과 통과시키지 않는다.

이 ADR이 채택될 때에만 신규 버전의 근사 순위 정책(D-35)을 대체하도록 개발 명세와 결정 로그를 함께 갱신한다. 구버전 정책은 계속 남는다.
