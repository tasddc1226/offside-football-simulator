# ADR-015. 슬랙 에이전트 팀: 개발 · 기획 · 운영 · 마케팅

- 상태: 확정 (2026-10-15, T-11-273). 미결 항목은 단계별 도입 중에 정한다. 5~7단계(주장 · 위험도별 자동 시작 · 사건 대응)는 2026-10-17 개정(T-11-325)
- 관련: [ADR-007](ADR-007-hosting-and-infra.md)(Cloudflare 인프라), [CLAUDE.md](../../CLAUDE.md)의 개발·운영 규칙, [CI 테스트 정책](../operations/ci-test-policy.md)

## 배경

OFFSIDE는 1인 운영이다. 지금 운영 슬랙(Offside-Lab, 무료 플랜)에는 알림 채널 다섯 개가 있고, API와 GitHub Actions가 채널마다 웹훅으로 한 방향 알림만 보낸다.

| 채널                          | 보내는 곳              | 내용                                                   |
| ----------------------------- | ---------------------- | ------------------------------------------------------ |
| `#offside-purchases` (비공개) | API `iap/alerts.ts`    | 실결제 · 환불                                          |
| `#offside-alerts`             | `slack-operations.yml` | 운영 점검(D1 용량 · 매일 작업 지연 등)                 |
| `#offside-daily`              | `slack-operations.yml` | 아침 리포트                                            |
| `#offside-feedback`           | `slack-feedback.yml`   | 커뮤니티 글 · 릴리즈노트 댓글 피드백 후보(원문 링크만) |
| `#offside-releases`           | `slack-releases.yml`   | 운영 배포 결과                                         |

알림을 읽고, 재현하고, 이슈로 만들고, 고치고, 공지 · 광고 문구를 쓰는 일은 모두 사람이 한다. 이 ADR은 역할별 에이전트 네 개가 같은 슬랙에서 서로 일을 넘기며 이 일을 맡고, 사람은 승인과 방향만 정하는 구조를 정한다.

## 결정 요약

1. **역할 네 개, 슬랙 앱 네 개.** 개발(`@dev`) · 기획(`@plan`) · 운영(`@ops`) · 마케팅(`@mkt`)을 각각 따로 만든 슬랙 앱(봇)으로 둔다. 이름 · 아이콘 · 권한이 역할마다 다르다.
2. **모델은 일마다 정해 명시한다(2026-10-16 T-11-289에서 "전부 Opus 5.5"를 바꿨다).** 유저 반응 분류 · 경보 첫 정리는 Claude Haiku 5.5(`claude-haiku-5-5`), 아침 주기 작업 보고는 Claude Sonnet 5.5(`claude-sonnet-5-5`), 운영자 지시 · 넘겨받은 일 · 코드 작업은 Claude Opus 5.5(`claude-opus-5-5`)다. 기본값 · 상속에 맡기지 않고 모든 호출 · 하위 에이전트에 모델 ID를 명시한다. 응답의 모델이 다르면 그 작업을 실패로 끝낸다.
3. **Claude API 키로 돌린다.** Claude Console 조직의 `offside-agents` 워크스페이스에 크레딧을 충전하고, 역할마다 키를 하나씩 발급한다(키 4개). claude.ai 구독(Pro · Max)은 쓰지 않는다. Agent SDK로 만든 에이전트에 구독 로그인을 쓰는 것은 Anthropic 정책상 허용되지 않는다([Agent SDK 개요](https://code.claude.com/docs/en/agent-sdk/overview), [법률 · 준수](https://code.claude.com/docs/en/legal-and-compliance)).
4. **Cloudflare에서 돌린다.** 슬랙 이벤트를 받는 Worker, 스레드마다 상태를 지키는 Durable Object, 에이전트를 실행하는 Sandbox 컨테이너로 나눈다. 운영 API(`offside-api`)와 운영 D1에는 붙이지 않는다.
5. **되돌리기 어렵거나 밖으로 나가는 일은 사람이 승인한다.** 머지, 운영 배포, 운영 DB 쓰기, 게임 안 공지 · 댓글, 광고 · 스토어 · 드림보트 게시, 돈이 드는 설정 변경이 여기에 든다. 승인은 슬랙 버튼이고 운영자 본인만 누를 수 있다.
6. **슬랙은 대화 창구이고 기억은 우리 저장소에 둔다.** 무료 플랜은 90일이 지난 메시지가 보이지 않고 1년이 지나면 지워진다. 작업 상태 · 결정 · 산출물은 Durable Object 저장소와 R2 · GitHub에 남긴다.
7. **단계적으로 연다.** 읽기만 하는 운영 에이전트부터 열고, 권한이 큰 개발 에이전트는 마지막에 연다.

## 도구와 권한

원칙은 **읽기는 넓게, 쓰기는 승인 뒤 GitHub Actions로만**이다. 에이전트가 프롬프트 주입에 속거나 토큰이 새어도 운영을 직접 바꿀 수 없게, 쓰기 권한은 에이전트가 아니라 기존 워크플로(`deploy-production.yml` 등)가 갖는다.

## 채널과 소통 규칙

- **채널을 새로 만든다.** `#agent-desk`(사람이 일을 맡기고 에이전트끼리 넘기는 곳)와 `#agent-approvals`(승인 버튼만 모이는 곳)를 만든다. 기존 알림 채널 다섯 개는 그대로 두고, `@ops` · `@plan`이 읽는다.
- **작업 하나는 스레드 하나다.** 스레드 첫 메시지에 작업 카드(목표, 담당 역할, 상태, 연결된 이슈 · PR)를 두고 상태가 바뀌면 그 카드를 고친다.
- **넘기기는 정해진 형식으로만 한다.** `→ @plan: <요청>` 꼴로 다음 역할을 멘션하고, 넘길 때 필요한 근거(링크 · 수치)를 붙인다. 형식 밖의 봇 메시지에는 다른 봇이 반응하지 않는다.
- **무한 대화를 막는다.**
  - 같은 스레드에서 봇끼리 주고받는 횟수는 6번까지다. 넘으면 멈추고 사람을 부른다.
  - 봇은 자기 메시지에 반응하지 않는다.
  - 같은 이벤트는 한 번만 처리한다(슬랙 `event_id`로 중복 제거).
- **사람 지시가 우선한다.** 운영자의 메시지가 스레드에 오면 진행 중인 단계를 멈추고 그 지시를 먼저 읽는다.

## 승인 단계

다음 작업은 에이전트가 `#agent-approvals`에 요청 카드(무엇을, 왜, 되돌리는 방법, 예상 비용)를 올리고 운영자가 **승인**을 눌러야 실행된다. Worker가 버튼을 누른 사람의 슬랙 사용자 ID를 확인하고, 운영자가 아니면 거절한다.

- main 머지(PR squash)
- 운영 배포(`deploy-production.yml`), 마이그레이션
- 운영 D1 · R2 쓰기, 운영 도구의 밸런스 · 공지 변경
- 게임 안 공지 · 업데이트 게시판 글, 사용자 댓글 답글
- 드림보트 · 스토어 · 광고 게시, 광고 예산 변경
- 비용이 드는 설정 변경(Cloudflare · Console 한도 포함)

승인 기록(누가, 언제, 무엇을)은 R2에 남긴다. 승인 없이 위 작업을 하는 도구는 에이전트에게 주지 않는다. 승인은 도구 권한 쪽에서 막고, 프롬프트에만 기대지 않는다.

## 인프라

```
슬랙 이벤트 · 버튼 ──▶ Worker `offside-agents` (서명 확인, 3초 안에 응답, 중복 제거)
                          │ Queue
                          ▼
                 Durable Object `AgentThread` (스레드 하나 = 객체 하나, 순서대로 처리, 상태 · 비용 기록)
                          │
                          ▼
                 Sandbox 컨테이너 (Agent SDK + 역할 도구, 작업이 없으면 잠듦)
                          │
                          ▼
              슬랙 chat.postMessage(역할 봇 토큰) · GitHub · 읽기 전용 운영 조회
```

- **별도 Worker.** `apps/agents`를 새 앱으로 두고 `offside-api`와 배포를 나눈다. 운영 API 장애 · 배포가 에이전트에 번지지 않고, 그 반대도 같다.
- **Durable Object.** 스레드마다 작업 카드, 대화 요약, 쓴 토큰 · 비용, 승인 대기를 저장한다. 운영 D1은 용량 한도(10GB)에 가까워 쓰지 않는다.
- **Sandbox 컨테이너.** Agent SDK는 셸 · 파일 시스템이 필요해 Worker에서 바로 돌릴 수 없다. 컨테이너를 쓰고, 작업이 없으면 잠들게 해 비용을 줄인다. 개발 에이전트만 저장소를 체크아웃하고, 다른 역할은 저장소를 읽기 전용으로 받는다.
- **운영 데이터 읽기.** `@ops`는 D1 읽기 전용 토큰으로 조회한다. 쿼리마다 행 상한을 두고, 운영 D1 읽기 비용 규칙(필요한 만큼, 인덱스와 함께)을 지킨다.
- **1단계 결정(2026-10-15, T-11-277).** 읽기만 하는 역할(`@ops` · `@plan` · `@mkt`)은 셸이 필요 없어 Sandbox 없이 Durable Object 안에서 Messages API 도구 루프로 돌린다. Queue도 두지 않고 Worker가 스레드 객체에 바로 넘긴다(객체가 알람으로 하나씩 처리). Sandbox · Agent SDK는 저장소를 고치는 `@dev`(3단계)에서 다시 확인한다.
- **실제 구성(1단계).** 코드는 `apps/agents`, 역할 설명은 `apps/agents/roles/<역할>.md`. 슬랙 주소는 `https://agents.offside-lab.com/slack/<역할>/events`. 운영 D1은 바인딩하지 않고 D1 **읽기** 권한만 있는 API 토큰으로 조회한다(쓰기 쿼리는 Cloudflare가 거절하는 것을 확인했다). 같은 경보의 6시간 재안내는 24시간 안에 다시 정리하지 않는다.
- **Cloudflare MCP(1단계).** `@ops`는 Cloudflare 공식 MCP(`https://mcp.cloudflare.com/mcp`)로 Workers 로그 · 실행 기록 · 분석을 읽는다. 토큰은 읽기 권한만 준다(계정: Workers 스크립트 · Workers Observability · Account Analytics · D1 · 계정 설정, 영역 `offside-lab.com`: Analytics, 사용자: 세부 정보 · 멤버십). Worker가 직접 MCP 서버와 연결해 그 도구를 Claude에 넘긴다. Claude API MCP 커넥터는 이 서버와 연결에 실패했고, 직접 연결하면 토큰이 Claude API 요청에 실리지 않는 장점도 있다.
- **2단계 결정(2026-10-15, T-11-277).** `@plan`의 첫 일은 유저 반응 살피기다. 게임 댓글은 D1 읽기 토큰으로, 라운지 채팅(채팅방 Durable Object에만 7일 보관)은 `offside-api`에 더한 내부 읽기 주소로 읽는다. 이 주소는 토큰이 맞을 때만 열리고(아니면 404) 가린 줄 · 운영자 줄을 빼고 작성자 가명 · 본문만 준다. 채팅방 객체에 에이전트 Worker를 바로 묶지 않은 것은 가리기 · 정지 같은 쓰기 메서드까지 열리기 때문이다. 넘기기는 줄 머리 `→ @역할:` 형식으로 Worker 안에서 하고, 스레드마다 6번까지다. GitHub 이슈 만들기는 쓰기 토큰이 필요해 아직 하지 않고 "작업 후보"로 적는다. 디시 마이너 갤러리는 웹훅 · RSS가 없어 공개 목록 · 글 · 댓글을 매시간 상한(글 8개)을 두고 읽는다. Cloudflare Worker에서 읽으면 빈 응답이 잦아(T-11-280) GitHub Actions 러너가 읽어 Worker에 넣는다. `@ops`는 매일 아침 주기 작업 보고(GitHub 예약 워크플로 · Worker cron의 결과와 예정)를 올린다.

- **3단계 결정(2026-10-15, T-11-285).** `@dev`는 Sandbox 대신 GitHub Actions(`agent-dev.yml`)에서 고친다. 공개 저장소라 러너 시간이 들지 않고, "쓰기는 Actions로만" 원칙과 맞는다. Worker의 `@dev`는 운영자가 직접 맡긴 일(멘션 · 답글)에만 `start_work`로 작업을 띄우고, 넘겨받은 일로는 띄우지 않는다(유저 글이 섞일 수 있다). `work` 잡의 Claude Code(Opus 5.5, 작업당 $5 · 80턴)는 읽기 토큰만 갖고 커밋까지만 한다. `publish` 잡은 main에 있는 고정 스크립트(`.github/scripts/agent-dev-publish.mjs`)로 그 커밋을 main 위에 얹고, `.github/` · 비밀 파일을 건드리면 거절한 뒤 GitHub App(`offside-dev-agent`, contents · pull_requests · actions 쓰기, checks 읽기, workflows 없음) 토큰으로 `agent-dev/<run>` 브랜치 · PR을 연다. PR CI는 비밀값을 쓰지 않는다. CI가 끝나면 `agent-dev-ci.yml`이 Worker에 알리고, 통과면 `#agent-approvals`에 승인 카드가 온다. 버튼은 운영자만 누를 수 있고, 머지 직전에 PR 열림 · 승인한 커밋 · 검사 통과 · main 최신을 다시 확인한다(main이 앞서면 브랜치를 맞추고 새 카드를 기다린다). main은 저장소 규칙(PR 필수 · 강제 push · 삭제 금지, 관리자만 예외)으로 보호한다. e2e는 PR CI에 맡긴다(미결 3). 승인 기록은 지금은 Durable Object에 두고 R2 이관은 미결로 둔다.
- **4단계 결정(2026-10-16, T-11-296).** `@mkt`는 운영 배포가 `mode=deploy`로 성공했을 때(`agent-release.yml`이 `workflow_run`으로 받아 Worker에 알린다, 운영 배포 워크플로는 바꾸지 않는다) 드림보트 업데이트 요약 초안만 쓴다(Sonnet 5.5). 자료는 드림보트 마지막 게시 시각 뒤 main 커밋과 그 커밋이 더한 게임 안 릴리즈 노트다. 게임 안 공지는 PR의 `.release-notes`가 배포 때 게시하므로 따로 초안을 쓰지 않는다. 요약 형식(1~3줄 · 줄 60자 · 내부 표기 없음)은 Worker가 다시 검사하고, 드림보트 보내기는 `#agent-approvals` 승인 버튼(운영자만)으로만 한다. 드림보트 주소는 Worker 비밀값 `DREAMBOAT_URL`이다.
- **넘기기 왕복(2026-10-16, T-11-298 → 2026-10-17 T-11-325에서 폐기).** 처음엔 넘겨받은 일의 결과를 넘긴 역할에게 한 번 돌려줬으나, 같은 결론을 한 번 더 정리하는 호출만 늘어 없앴다. 넘겨받은 역할이 결론과 운영자 할 일을 직접 쓰고, 이어서 맡길 일이 있을 때만 넘기기 줄을 쓴다(반복 상한 6번). 답의 역할 키는 슬랙에 올릴 때 진짜 봇 멘션으로 바꾸고, 넘기기는 바꾸기 전 답으로 고른다. 넘기기 규칙은 네 역할 공통 `roles/team.md`다.

- **답 규칙 · 출시 상태 · 스레드를 넘는 기억(2026-10-17, T-11-332).** 답이 길고 추정이 섞여 운영자가 다시 묻는 일이 잦아, 네 역할 공통 "답 규칙"(`roles/team.md`)을 두었다. 첫 줄에 결론, 정해진 형식이 없으면 5줄 안, 확인한 사실만 근거와 함께 쓰고 모르면 "확인 못 함"으로 쓴다. 과정 · 인사 · 맺음말 · 동료 답 되풀이는 쓰지 않는다. 긴 조사 뒤에도 지키도록 운영자 지시 · 넘기기 · 경보 요청 끝에 같은 규칙을 한 줄 다시 붙인다. 말투는 첫 문장 어미에만 입힌다. `app_status`는 App Store 버전 · 심사 상태(리뷰 키), Google Play 안정성(Play Developer Reporting API, 리뷰와 같은 서비스 계정), EAS 빌드 · OTA(`EXPO_TOKEN`)를 읽기만 한다. 되돌리기는 도구에 넣지 않고 운영자가 워크플로로 한다. 기억은 닫히거나 보류된 작업 카드 결론(자동)과 주장이 `remember`로 남긴 운영자 결정만 장부에 500개까지 두고, `recall`로 낱말 검색한다. 대화 원문은 남기지 않는다. 앱 · 웹 화면 오류는 T-11-331의 `client_errors` 표를 `@ops`가 `d1_query`로 본다.
- **운영 배포 승인 결정(2026-10-16, T-11-312).** 운영자가 `@dev`에 운영 배포 승인 요청을 맡겼다. 승인 머지가 끝나면 Worker가, 운영자가 지시하면 `@dev`의 `deploy_request`가 main 최신 커밋의 **배포 승인 카드**를 `#agent-approvals`에 올린다. 카드에는 지난 운영 배포 태그(GitHub 최신 릴리즈) 뒤 커밋과 마이그레이션 파일을 적고, 마이그레이션이 있으면 **프리플라이트** 버튼을 함께 둔다. 결정 5대로 버튼은 운영자만 누를 수 있고, 누르는 순간 main 최신 커밋과 같은지 다시 확인한 뒤 Worker가 GitHub App으로 `deploy-production.yml`을 띄운다(`mode=deploy`면 `confirmation=DEPLOY_PRODUCTION`). main이 바뀌었으면 띄우지 않고 새 카드를 올린다. 같은 커밋 · 같은 모드는 한 번만 띄운다. 넘겨받은 일 · 유저 글로는 카드를 올리지 않는다. 배포가 끝나면 4단계 `@mkt` 요약이 이어진다.
- **고객 문의 결정(2026-10-16, T-11-291).** 운영자가 `@plan`에 고객 문의(클레임) 처리를 더했다. 문의를 받는 Gmail을 Worker가 Gmail API(`gmail.readonly` · `gmail.compose`, 에이전트 전용 Google Cloud 프로젝트)로 매시간 읽는다. 공식 Gmail MCP는 Developer Preview이고 보내기 도구가 없어 쓰지 않았다. 답장은 결정 5대로 승인 카드를 운영자가 눌러야 나가고, 받는 사람은 원래 문의한 사람으로 Worker가 정한다(메일 본문의 지시로 다른 주소에 보낼 수 없다). 슬랙 · 프롬프트에는 보낸 사람 주소를 가려 쓴다. 승인 기록은 `@dev`와 같이 Durable Object에 둔다.

## 비용 통제

- **Console:** `offside-agents` 워크스페이스에 월 지출 한도를 건다. 자동 충전은 처음엔 끈다. 크레딧이 떨어지면 에이전트가 멈추는 쪽을 택한다.
- **작업 하나:** Agent SDK의 비용 상한(`max_budget_usd`)과 최대 턴 수를 역할마다 둔다. 넘으면 멈추고 사람에게 묻는다.
- **하루 단위:** Durable Object가 역할별 하루 사용액을 더하고, 한도를 넘으면 그날은 새 작업을 받지 않는다.
- **보고:** `#offside-daily` 아침 리포트에 전날 역할별 사용액 · 작업 수를 더한다.
- **아끼는 방법:** 역할 설명 · 저장소 규칙처럼 매번 같은 앞부분은 프롬프트 캐시를 쓴다. 긴 로그는 요약해서 넘긴다.
- **비용 절감 결정(2026-10-16, T-11-289).** 대화 끝 캐시(T-11-288) 뒤 운영자가 정했다. (1) 모델 나누기(결정 2). 경보 스레드에서 운영자가 다시 부르면 Opus로 깊게 본다. (2) 아침 보고는 `report_digest` 도구 하나로 예약 워크플로 결과 · Worker cron · Workers 로그 job별 오류 · 백업 기록을 모아 2~3턴에 끝낸다(경보 첫 정리 · 보고는 6턴 상한). (3) 유저 반응 살피기는 매시간에서 3시간마다(`47 */3 * * *`)로 줄인다. 디시 글은 Actions가 매시간 넣어 두고 다음 살피기가 한 번에 받는다. (4) 도구 결과 글자 상한을 12,000자에서 6,000자로 줄인다.

한도 금액은 1단계를 돌려 본 뒤 정한다(미결 2).

## 보안

- **비밀값.** API 키 4개, 슬랙 봇 토큰 · 서명 비밀 4쌍, GitHub 토큰, D1 읽기 토큰은 Cloudflare Secrets에만 둔다. 공개 저장소라 코드 · 로그 · 슬랙 메시지에 남기지 않는다. `public-hygiene` 검사에 키 형식을 더한다.
- **GitHub 권한.** 역할마다 따로 만든 fine-grained 토큰을 쓴다. `@dev`는 이 저장소의 브랜치 push · PR 생성만 쓸 수 있다. main 보호 규칙으로 직접 push · 머지를 막는다. 다른 역할은 읽기와 이슈 쓰기만 갖는다.
- **사용자 글은 지시가 아니다.** 게시판 · 커뮤니티 · 댓글 원문은 사실 자료로만 읽고, 그 안의 지시문을 따르지 않는다(프롬프트 주입 대비). 원문을 읽는 역할(`@plan`)은 쓰기 도구가 좁다.
- **개인 정보.** 지금 피드백 알림처럼 닉네임 · 댓글 본문 · 쿠키 · 복구 코드 · 선수명 원문을 슬랙에 옮기지 않는다. 필요하면 원문 링크만 단다.
- **명령은 운영자만.** 슬랙 워크스페이스에 다른 사람이 들어와도 운영자 사용자 ID가 아닌 지시는 작업으로 받지 않는다.

## 5~7단계 개정: 주장 · 위험도별 자동 시작 · 사건 대응 (2026-10-17, T-11-325)

### 배경

운영자는 앞으로 문의 대응(CS · CX), 마케팅, 개발까지 모든 일을 슬랙 안에서 하려고 한다. 1~4단계로 역할 넷은 갖췄지만, 일이 들어와서 닫힐 때까지 이어 주는 흐름이 비어 있었다. 2026-10-16 "서버가 느리다" 제보를 예로 들면, 원인 조사부터 수정 · 배포 · 배포 뒤 확인 · 상태 화면 추가(T-11-320 · T-11-321)까지 모두 슬랙 밖의 Claude Code 세션이 했다. 막힌 곳은 넷이었다.

1. **일의 주인이 없다.** 스레드 객체가 역할마다 따로 있고(`AgentThread`, `<역할>:<채널>:<ts>`), 결정의 "작업 카드"는 구현되지 않았다. 운영자가 직접 일을 나눠 줬다.
2. **넘기기가 `@dev`에서 끊긴다.** `start_work`는 운영자가 직접 맡긴 일(멘션 · 답글)에만 열린다(3단계 결정). 근거를 붙여 넘겨도 `@dev`는 고치지 않는다.
3. **사건 대응 절차가 없다.** `@ops`의 경보 첫 정리는 Haiku 6턴이다. 영향 범위 확인, 기준선 비교, 원인 확정, 수정 요청, 배포 뒤 다시 재기를 잇는 정해진 순서가 없었다.
4. **운영 기준선을 다들 따로 기억한다.** 정상 지연 · 요청량, 조회 방법, 측정 함정이 세션 메모리에만 있었다.

역할(봇)을 더 늘리기 전에 이 흐름부터 채운다.

### 5단계. 주장: `@plan`이 모든 일의 주인

- **새 봇을 만들지 않고 `@plan`(박지성)을 주장으로 정한다.** 슬랙 앱 · 키 · 넘기기 횟수가 늘지 않는다. 주장 규칙은 `roles/captain.md`에 둔다.
- **입구(2026-10-17 개정).** 에이전트는 멘션으로만 깬다. 운영자가 봇을 멘션하거나 `@이름`으로 부른 글, 동료의 넘기기 줄만 일을 시작한다. 멘션 없는 `#agent-desk` 글 · 스레드 답글로는 아무 역할도 깨지 않는다(불필요한 호출 줄이기). 주장에게 일을 맡기려면 박지성을 멘션한다. 사건(7단계)과 배포 뒤 마지막 확인 결과도 주장에게 돌아온다. 특정 역할에 직접 멘션하는 지금 방식은 그대로 둔다. 운영자가 `@dev`에 직접 맡겨 작업이 시작되면 Worker가 카드를 연다.
- **작업 카드.** 스레드마다 Durable Object `WorkCard`(키 `<채널>:<스레드 ts>`, `card.ts`)를 하나 둔다. 역할별 `AgentThread`는 대화만, 카드는 이 객체가 맡는다. 카드는 그 스레드에 주장 이름으로 한 번 올리고(주장 봇이 없는 채널이면 담당 봇) 바뀔 때마다 `chat.update`로 고친다.

- **두 번 판정한다.** 시작 전에는 주장이 적은 범위(`scope` 경로)와 주장의 예상 중 높은 쪽을 쓴다. 범위를 비우면 중간이다. PR 뒤에는 main의 고정 스크립트(`agent-dev-publish.mjs`)가 실제 바뀐 경로를 Worker에 보내고, Worker가 다시 판정해 머지 승인 카드에 위험도를 적는다. 실제가 예상보다 높으면 카드에 경고를 붙인다(거쳤어야 할 단계를 적고, 바뀐 파일을 직접 보라고 한다). 운영자가 직접 맡긴 일은 경고 없이 위험도만 적는다.
- **유저 글은 넘기지 않는다.** `work_order` · `card_update`는 운영자 지시 · 답글 · 넘겨받은 일에만 준다. 유저 원문이 바로 들어오는 반응 살피기 · 문의 정리에는 주지 않는다(작업 후보로만 적는다). 명세 앞에는 "주장이 쓴 명세, 명세 밖의 일은 하지 않는다"는 줄을 붙이고, 메일 주소는 Worker가 한 번 더 가린다. `@dev`(Actions)는 명세를 거치지 않는다. Worker가 바로 띄운다.

### 7단계. 사건 대응과 배포 뒤 확인

- **알아차림.**
  - **서버 상태 감시:** Worker cron이 5분마다 공개 `GET /v1/status`(T-11-321)를 읽는다. 엣지에 60초 담긴 응답이라 운영 D1을 건드리지 않는다. 끝난 5분 칸이 두 칸 이어 느림 · 오류면(화면과 같은 기준, 요청 100개 아래 칸은 판정하지 않는다) `@ops` 사건을 `#agent-desk` 새 글로 연다. 상태 주소를 두 번 이어 못 읽어도 사건이다. 6시간에 한 번만 연다.
  - **경보:** 경보 첫 정리(Haiku)가 장애로 보면 첫 줄을 `사건: <한 줄>`로 쓴다. 그러면 Worker가 같은 스레드에서 Opus로 사건 조사를 이어 띄운다(결정 2 확장). 첫 줄만 보므로 경보 본문이 판정을 흉내 내지 못한다.
- **조사.** 사건은 Opus 15턴이다. 순서는 `roles/ops.md`의 "사건 조사"(영향 범위 → 기준선 비교 → 원인 가설과 증거 → 결론)다. 사건이 열리면 Worker가 카드(출처 사건, 담당 `@ops`, 조사)를 연다. 고쳐야 하면 `@ops`가 `→ @plan:`으로 넘기고, 주장이 위험도 표대로 `work_order`를 낸다.
- **배포 뒤 확인.** 운영 배포가 성공하면(`agent-release.yml`이 이미 Worker에 알린다) 상태가 배포인 카드를 본다. 사건 카드면 확인 중으로 바꾸고 `WorkCard` 알람으로 30 · 60분 뒤 `@ops` 확인(Sonnet 10턴)을 띄운다. `@ops`는 조사 때 본 지표를 같은 방법으로 다시 재서 전후 표를 단다. 60분 확인이 끝나면 Worker가 결과를 주장에게 넘긴다. 좋아졌으면 주장이 닫고, 그대로거나 나빠졌으면 되돌리기 · 추가 수정 명세를 내거나 운영자에게 묻는다. 되돌리기도 머지 · 배포는 승인을 받는다. 사건이 아닌 카드는 배포로 닫는다.
- **운영 기준선 지식 파일.** `apps/agents/knowledge/ops-baseline.md`에 정상 범위(하루 요청량 · 경로별 지연 · D1 지표), 상태 판정 기준, 조회 방법, 측정 함정을 적고 `@ops` · 주장의 시스템 프롬프트에 넣는다. 사건이 닫히면 주장이 바뀐 기준선 · 새 함정을 명세로 낸다. 에이전트 프롬프트가 되는 파일이라 위험도 중간(시작 카드)이다. 공개 저장소라 비밀값 · 운영 사용자 ID · 개인 정보는 넣지 않는다.

## 검토한 대안

- **Claude Tag(슬랙 안 공식 Claude).** Team · Enterprise 전용이고 봇 이름이 하나라 역할을 나눌 수 없다.

- **이 맥에서 돌리기.** 맥이 잠들면 멈춘다. 셀프호스트 러너 때 같은 문제를 겪었다.
- **봇 하나에 역할 전환.** 앱 수(무료 플랜은 앱 · 워크플로 합쳐 10개)는 아끼지만, 권한을 역할마다 나눌 수 없다. 지금 앱 3개 + 4개 = 7개라 한도 안이다.
