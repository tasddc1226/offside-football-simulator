# Working agreement

- Mobile first (2026-10-03): 모든 UI 작업은 모바일 최적화를 우선한다. 좁은 화면의 가독성, 터치 배치·조작, 하단 메뉴와 저장 버튼의 가림, 가로 넘침을 실제 로컬 모바일 화면에서 확인한다. 편집 중에는 타입·린트와 화면 확인만 하고, 검증 범위는 `docs/operations/ci-test-policy.md`를 따른다(웹을 바꿨으면 푸시 전에 빌드·번들 검사, e2e는 푸시 뒤 PR 검사에서 한 번).
- Implementation is done directly by the Claude Code main session (2026-09-24; supersedes the "delegate to Sonnet 5" rule). Subagents are used only for independent, parallelizable work (copy writing, test backfill, unrelated features) and must implement directly without re-delegating.
- The main session reviews, verifies, merges and deploys its own changes.
- Protect the backend (2026-09-25): request data only when it is actually needed. Load on open, never refetch the same data on every screen entry, and avoid N+1 and polling. Web GETs go through `cachedGet`. Public reads never look up the session (`resolveSession` only where required). Shared public GETs use `edgeCached` with a `purgeEdge` on every write that changes them. New sort/filter queries ship with an index. See "백엔드 보호 · 요청 최소화 규칙" in `CLAUDE.md`.
- User-facing copy (2026-10-02): follow `docs/tracking/copy-style.md` (canonical). Ending labels are save keys; never rename them without a migration.
- Localization gate (2026-10-05, Japanese since 2026-10-07): every user-facing string lives in `ko` + `en` + `ja` dictionaries (`packages/app-core/src/i18n`, `packages/game/src/i18n`, server copy in `apps/api/src/i18n`); write the English and Japanese in the same PR. `pnpm lint:i18n` fails when hardcoded Korean grows past `tooling/i18n-baseline.json`; lower the baseline with `--update` when you remove Korean. See "다국어 규칙" in `CLAUDE.md` and `docs/operations/i18n.md`.
- Release notes (2026-10-03): user-visible changes include a reviewed `.release-notes/*.json` entry in the same PR. Follow `.release-notes/README.md`; use a new stable ID and state web/app availability truthfully. Production deploy publishes only unseen entries and preserves manually written notes. CI `Release notes guard` fails when user-facing sources change without a new entry; opt out with a PR body line `release-notes: none` or the `no-release-note` label. Whether a change needs a note follows "노트를 쓸지 고르는 기준" in `.release-notes/README.md`: write one when users get new behavior or information; skip it (with a one-line reason) for visual polish, refactors, admin/agent tooling, one-off ops pushes, tests, CI and docs.
- Balance patch history (2026-10-17, T-11-333): a change that alters career outcomes, odds, or score formulas without a server balance version must add `"balance"` to its release-note entry — `true` for copy only, or `{ "changes": [{ "key", "from", "to" }] }` when a balance-spec default changes. Publishing records it in `balance_patches` so it appears in the public `GET /v1/balance/history` (Odds guide → Odds and fairness). Prefer a server balance version for tunable values; those are recorded automatically. Adding `balance` to an already-published entry does nothing. See `.release-notes/README.md`.
- Preserve immutable old saves: any change to the save format must ship the matching migration code in `packages/game/src` so existing `localStorage` saves keep loading. Preserve unrelated user work.
